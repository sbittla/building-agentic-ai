# Chapter 7: Real APIs

Most useful agents talk to services on the internet, and those services fail in ways local files never do. In this chapter you'll wrap a free weather API as agent tools and build a trip-packing agent on top of it. You'll add retries with backoff, clear failure messages, caching and a call budget: the patterns every production agent needs for external calls.

**What you'll build:** a trip-packing agent over a live weather API, with caching, retries and tools that run in parallel.

**You are here:** Tools and APIs in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Wrap a real HTTP API as agent tools.
- Handle timeouts, rate limits and server errors with retries and backoff.
- Return failures to the model as data it can explain or work around.
- Let the agent resolve ambiguous inputs by asking the user.
- Add caching and measure its effect on latency and API calls.

This chapter uses Open-Meteo, which is free for non-commercial use and needs no API key. You'll use two of its endpoints (URLs that each answer one kind of request):

- **Geocoding**: city name → candidate places with latitude and longitude.
- **Forecast**: latitude and longitude → daily temperatures and rain probability.

## 7.3 What can go wrong with an API call

| Failure | Example | Retry? | What the model should get |
| --- | --- | --- | --- |
| Timeout | Server slow or network down | Yes, with backoff | "Service unavailable after 3 tries" |
| 429 Too Many Requests | Rate limit hit | Yes, after waiting | Same, if retries run out |
| 5xx server error | Provider outage | Yes | Same |
| 4xx client error | Bad parameters | **No**; retrying won't help | The error, so it can fix the call |
| Empty result | Misspelled city | No | "No place called X. Check spelling." |
| Ambiguous result | Five places called Portland | No | All candidates, so it can ask |

`_get_json` implements this table. It retries timeouts, 429s and 5xx errors, fails fast on other 4xx errors and raises a clear message when it runs out of tries. `run_tool` turns that message into an `ERROR:` string for the model. Two details make the retries polite:

- **`Retry-After` first.** A 429 or 503 often says how long to wait (`Retry-After: 20`). The server knows best, so `_wait_before_retry` uses that value when it's there.
- **Backoff with jitter** otherwise. *Backoff* means waiting longer after each failure: about 0.5 s, then 1 s, then 2 s. *Jitter* randomly stretches or shrinks each wait by up to 50%. Without it, a hundred clients that failed together retry together, and the outage repeats. There's no wait after the final attempt, since no retry follows.

## 7.4 Ambiguity: ask the user

`geocode("Portland")` returns Portland, Oregon **and** Portland, Maine, among others. Because the tool returns all candidates and its description says "If more than one plausible match exists, ask the user", the agent asks instead of guessing. This is the same principle as Chapter 5: **tools expose ambiguity; the model resolves it with the user.**

## 7.5 Caching

Weather forecasts don't change every second. `_get_json` caches (stores and reuses) each response for 10 minutes, keyed by URL and parameters. Caching matters because agents often repeat calls: the same city is geocoded twice in one conversation, or a multi-city trip checks the same place again.

The cache is **bounded** (500 entries, oldest dropped first), because an agent can ask about thousands of places. It also uses a **lock**, so only one thread changes it at a time, because exercise 7.5 runs tools in parallel threads.

Caching gives you three wins:

- **Lower latency**: a cache hit is microseconds instead of hundreds of milliseconds.
- **Fewer API calls**: you stay under rate limits and pay less.
- **Stable answers**: repeated questions get consistent data.

The `stats` dictionary counts real HTTP calls and cache hits, so you can measure the effect (exercise 7.6).

## 7.6 Budgets for external calls

A confused agent can call an API dozens of times. Protect external services with a per-run budget:

```
MAX_HTTP_CALLS = 20

def run_tool(name, args):
    if stats["http_calls"] >= MAX_HTTP_CALLS:
        return "ERROR: API budget for this run is used up. Answer with what you have."
    ...
```

The error message tells the model what to do next: answer with what it has. Without that guidance, a budget only produces a confused final answer.

:::note The support agent so far
The support agent reaches its first outside service: the carrier's tracking API. Each call gets a timeout, retries with backoff for timeouts and 5xx errors, a clear message the agent can pass on when the carrier is down ("tracking is unavailable right now; your parcel shipped on 3 October") and a cache, so ten questions about the same parcel cost one call.
:::

## Architect's Takeaway

External APIs fail as a matter of course: give every call a timeout, a retry limit and a failure message the model can act on.

## Common mistakes

- **No timeout.** A hung request freezes the whole agent. Always pass `timeout=`.
- **Retrying 4xx errors.** A bad request stays bad; retrying wastes time and quota.
- **Retrying without backoff.** Hammering a struggling service makes the outage worse.
- **Returning the whole API response.** Pick the fields the model needs.
- **Guessing between ambiguous matches** instead of asking.

## Summary

- Wrap external APIs in tools with timeouts, retries with backoff, and clear failure messages.
- Retry timeouts, 429 and 5xx; fail fast on other 4xx.
- Return all candidates for ambiguous inputs and let the model ask the user.
- Cache responses that don't change quickly; measure hits and calls.
- Budget external calls per run, and tell the model what to do when the budget runs out.
