# Chapter 7: Real APIs

Most agents hit the same wall when they move from demo to pilot. The demo's tools were functions that always answered; the pilot's tools were services that sometimes don't. Ask an agent what to pack for Portland and, before the model sees a single temperature, the weather service can time out, tell you to slow down, or reveal that "Portland" is five places. None of that is the model's fault, and all of it is your code's job.

**What you'll build:** a trip-packing agent over a live weather API, with caching, retries and tools that run in parallel.

**You are here:** Tools and APIs in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), section 0.4 (web APIs and HTTP).

## Learning objectives

By the end of this chapter you can:

- Wrap a real HTTP API as agent tools.
- Handle timeouts, rate limits and server errors with retries and backoff.
- Return failures to the model as data it can explain or work around.
- Have the agent ask the user about ambiguous inputs.
- Add caching and measure its effect.

**In the real world.** The official MCP quickstart builds a weather server too: weather is the simplest real API with network failures, ambiguous places and rate limits all in one. In Chapter 12 you'll turn this chapter's code into an MCP server.

- **Forecast**: latitude and longitude → daily temperatures and rain probability.

## 7.3 What can go wrong with an API call

Table: API failures and how to handle them {#t:api-failures}
| Failure | Example | Retry? | What the model should get |
| --- | --- | --- | --- |
| Timeout | Server slow or network down | Yes, with backoff | "Service unavailable after 3 tries" |
| 429 Too Many Requests | Rate limit hit | Yes, after waiting | Same, if retries run out |
| 5xx server error | Provider outage | Yes | Same |
| 4xx client error | Bad parameters | **No**; retrying won't help | The error, so it can fix the call |
| Empty result | Misspelled city | No | "No place called X. Check spelling." |
| Ambiguous result | Five places called Portland | No | All candidates, so it can ask |

`_get_json` implements {{t:api-failures}}: it retries timeouts, 429s and 5xx errors, fails fast on other 4xx errors and raises a clear message when it runs out of tries, which `run_tool` hands to the model as an `ERROR:` string.

The retries are also polite. A 429 or 503 often says how long to wait (`Retry-After: 20`), and `_wait_before_retry` uses that value when it's there. Otherwise it backs off, waiting longer after each failure: about 0.5 s, then 1 s, then 2 s. Each wait gets *jitter*, a random stretch or shrink of up to 50%, because a hundred clients that failed together and retry together just repeat the outage.

But every row of {{t:api-failures}} assumes the call only *reads*. A tool that changes something is different, and its worst failure is the timeout: the request may have succeeded on the other side after your client gave up. Retry it blindly and you charge the card twice.

:::warn Tool contract for mutations
Before you give an agent a tool that changes anything outside your process, write down each of these and test it:
- **Idempotency key or strategy.** How a repeat is recognized: a key the caller sends (`job_id:step`, an order id), a unique constraint, or a natural key ("set status to shipped" is already idempotent).
- **Failure semantics.** What each failure means outside. A timeout means *unknown*, not *failed*.
- **Safe-retry classification.** Which failures you retry as they are, which need a status check first, and which go to a person.
- **Timeout behavior.** How long the tool waits, and how you learn afterwards what happened: a status query by the same key, or a reconciliation job.
:::

Table: Retry semantics for common mutating tools {#t:mutation-contracts}
| Tool | Idempotency | After a timeout |
| --- | --- | --- |
| Payment or refund | Provider idempotency key per payment intent | Retry with the same key; the provider returns the first result |
| Support ticket | Unique client-generated request id | Look the id up before creating another |
| Reservation (room, table, seat) | Hold with an id, then confirm | Query the hold; confirm it or let it expire, never book again blind |
| Provisioning (account, VM, repository) | Deterministic name, create-if-absent | Re-run: it finds what it made |
| Database write | Insert-or-update (upsert) on a natural or request key, in a transaction | Retry; the key makes the second write a no-op |

Every row follows one pattern: give the action an identity, and after a timeout ask before you act again. Chapter 5's to-do tools were the small version, Chapter 19 makes it the rule for every step of a long-running job (section 19.5), and the launch checklist in section 30.7 asks for this contract for every tool that changes something.

## 7.4 Ambiguity: ask the user

`geocode("Portland")` returns Portland, Oregon **and** Portland, Maine, among others. The tool returns every candidate, and its description says "If more than one plausible match exists, ask the user", so the agent asks. You saw the same idea in Chapter 5: **tools show the ambiguity, and the model resolves it with the user.**

## 7.5 Caching

Forecasts don't change every second, and agents repeat themselves: the same city gets geocoded twice in one conversation. So `_get_json` caches (stores and reuses) each response for 10 minutes, keyed by URL and parameters. A hit takes microseconds instead of hundreds of milliseconds, saves rate limit and gives repeated questions the same data.

The cache is **bounded** (500 entries, oldest dropped first), because an agent can ask about thousands of places, and it has a **lock**, because exercise 7.5 runs tools in parallel threads. The `stats` dictionary counts real HTTP calls and cache hits, so you can measure the effect (exercise 7.6).

## 7.6 Budgets for external calls

A confused agent can call an API dozens of times in one run. Cap it:

```
MAX_HTTP_CALLS = 20

def run_tool(name, args):
    if stats["http_calls"] >= MAX_HTTP_CALLS:
        return "ERROR: API budget for this run is used up. Answer with what you have."
    ...
```

The message tells the model what to do next, so it wraps up with what it has; a bare refusal tends to produce a confused final answer.

:::note The support agent so far
The support agent calls its first outside service, the carrier's tracking API, with a timeout, retries with backoff, a message it can pass on when the carrier is down ("tracking is unavailable right now; your parcel shipped on October 3") and a cache, so ten questions about one parcel cost one call.
:::

:::note In the field
Halfway through a pilot, the customer's carrier API starts rate-limiting you, and nobody told you the limit. Ask for it in writing during discovery and put it in the integration contract of section 31.4. Then show the customer the cache-hit rate: it's often the cheapest way to stay under their limit.
:::

## Common mistakes

- No timeout. A hung request freezes the agent. Always pass `timeout=`.
- Retrying 4xx errors. A bad request stays bad.
- Retrying without backoff. Hammering a struggling service prolongs the outage.
- Returning the whole API response. Pick the fields the model needs.
- Guessing between ambiguous matches instead of asking.

## Key takeaways

**Architect's takeaway:** External APIs fail routinely, so give every call a timeout, a retry limit and a failure message the model can act on.

- Retry timeouts, 429 and 5xx with backoff; fail fast on other 4xx.
- A timeout on a tool that changes things means *unknown*: retry only with an idempotency key.
- Return all candidates for ambiguous inputs and let the model ask the user.
- Cache what changes slowly, and measure hits and calls.
- Budget external calls per run, and tell the model what to do when it runs out.
