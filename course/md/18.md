# Chapter 18: Agentic RAG and Knowledge Systems

Here's a question a colleague might put to your team's notes: "What caused the Kafka lag incident, and how many orders were cancelled in total?" It reads like one question, but it's two, and they live in different places. The cause is in an incident report; the count is in the shop database, where no search over your notes will ever find it. Even the first half is harder than it looks. Search for `ERR-4471` by meaning and the top hit may be about `ERR-4417`; search for "temperature units" by keyword and you miss the note that says "prefers Celsius". So you'll build the retrieval machinery carefully first, and only then hand an agent the job of deciding where to look.

**What you'll build:** a knowledge agent that plans what to look up, searches several sources, knows when it has enough evidence and checks its citations before answering.

**You are here:** Context and Memory (knowledge) in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 6 (agentic search and citations), Chapter 16 (context), the measurement interlude.

## Learning objectives

By the end of this chapter you can:

- Split documents into chunks that keep their source and line numbers.
- Explain embeddings, and choose between local, hosted and offline embedders.
- Build vector and keyword (BM25) indexes and combine them with rank fusion.
- Give an agent retrieval as a tool with citations, and measure it with recall@k and MRR.
- Let an agent plan its information needs and choose a source for each.
- Check whether the evidence is sufficient, and search again or abstain when it isn't.
- Verify an answer's citations and numbers against the evidence in code.

**In the real world.** Chapter 6 compared agentic search with RAG (retrieval-augmented generation: fetching relevant passages and adding them to the prompt before the model answers). Deep-research features in today's assistants go further: they plan several searches, search again where the evidence is thin and cite every claim. Anthropic's documentation points to Voyage AI for embeddings, while small local models such as model2vec are free and run on a laptop CPU.

## 18.3 Embeddings

An **embedding** is a list of numbers (a vector) that represents a text's meaning. Texts with similar meanings get vectors that point in similar directions, so "temperature units" sits near "prefers Celsius" though they share no words. Similarity is the **cosine** of the angle between two vectors. Because the vectors are normalized to length 1, that's a plain dot product (`self.vectors @ q`).

Table: Embedders in the kit
| Embedder | Semantic? | Cost | Needs |
| --- | --- | --- | --- |
| `LocalEmbedder` (model2vec, potion-base-8M) | Yes, good | Free | A one-time ~30 MB download |
| `VoyageEmbedder` (voyage-4-lite) | Yes, best | Paid per token | `VOYAGE_API_KEY` |
| `HashingEmbedder` | No: similar *words* only | Free | Nothing |

`get_embedder()` picks Voyage if you have a key, the local model otherwise, and hashing if the local model can't be downloaded. To choose explicitly, set `EMBEDDER=local`, `voyage` or `hashing` in `.env`.

:::warn Queries and documents must use the same embedder
Vectors from different models can't be compared. The index file records which embedder built it; rebuild the index whenever you switch.
:::

## 18.4 Keyword search and hybrid ranking

Embeddings are weak at exact identifiers: to them, `ERR-4471` and `ERR-4417` look almost identical. **BM25**, the classic keyword ranking behind most search engines, scores documents by how often the query words appear, giving more weight to rare words. `Index.search(mode="hybrid")` runs both searches and merges the rankings with **reciprocal rank fusion**: each chunk scores `1/(60 + rank)` in each list, the scores are added, and a chunk that ranks well in either list rises to the top:

## 18.5 Retrieval as a tool

`search_knowledge` returns the top passages, each prefixed with its `(file:line)`. As a tool, it gives you RAG's retrieval quality plus the agent's ability to search again with different words, or give up honestly, when results look wrong. The system prompt requires citations. ## 18.6 Measuring retrieval

Before tuning prompts, check that the right passages are found at all. Teams can spend days rewording a system prompt to fix answers whose source passage was never retrieved; no wording can help that. `evaluate` runs 12 questions with a known source file and reports two numbers per mode:

- **Recall@k**: the fraction of relevant documents found in the top k results. Each of these questions has exactly one right file, so here it's simply how often that file makes the top k (also called hit rate@k).
- **MRR** (mean reciprocal rank): the average of 1 / (position of the first correct result). Finding it first scores 1; finding it second scores 0.5.

In the kit's small corpus, questions share many words with their answers, so keyword search does well. Differences appear with **paraphrased** questions (exercise 18.5), the kind real users ask. Mind the sample size, too: with 12 questions, one question moves recall by 8 points, so small differences between modes are noise. Real retrieval evals use 100 or more questions, ideally from real user queries. And retrieval is only half the job: exercise 18.6 also checks the **answers**.

## 18.7 Going further

Once the basics work, these techniques are worth knowing:

- **Reranking.** Retrieve generously (say the top 30 by hybrid search), then let a **reranker** model score each candidate against the question and keep the best five. Rerankers read question and passage together, which makes them more accurate than embeddings but too slow for a whole collection.
- **Contextual retrieval.** A chunk like "Fix: rolled back, then added 6 partitions" means little on its own. Before embedding, prepend a sentence of context generated from the whole document ("From the June 2 Kafka lag incident report:"). Anthropic's published results show this substantially reduces failed retrievals, especially combined with BM25 and reranking.
- **Access control.** This index mixes work and personal notes, so ask the right question and the home router page comes back. In a real system, store who may see each chunk and **filter results by the asking user's permissions before the model sees them**. A prompt that says "don't reveal personal notes" is not a control.

## 18.8 From RAG to agentic retrieval

Classic RAG retrieves once, then answers. That works when one search finds everything. The Kafka question from the start of the chapter needs a passage from the team notes *and* a number from the shop database, so an **agentic knowledge system** replaces the pipeline with a loop the agent drives:

Figure: Agentic retrieval: the agent decides when it has enough
Alt: From a goal, the agent decides what is needed and where, then searches. Without enough evidence it searches again. With enough, it answers with citations; if the claims are verified it delivers, and if not it revises or abstains.

The agent decides what to retrieve, where from, whether the result is trustworthy and sufficient, and whether to search again. Your code keeps the loop bounded (at most two rounds here) and checks the final answer. Chapter 22 makes that split its central principle: the model proposes, code decides.

After each round of searches, a second structured call judges the evidence *before* anything is written:

@@code ch18_agentic.py::assess

The verdict says whether the evidence answers the whole question and, if not, which searches would fill the gap. The loop runs those and assesses again, up to `max_rounds`. When the budget runs out and the evidence still falls short, **answer what's supported and say plainly what isn't**: an honest "the notes don't say when ZooKeeper will be removed" beats a confident guess.

Evidence also has a trust level: a reviewed runbook and an unvetted web page shouldn't count the same. When sources conflict, prefer the more authoritative and more recent (section 16.4), and say so when it matters.

## 18.11 Verifying the answer

The model writes the answer from the evidence alone, citing the origin after every fact. Then code checks it:

The checks are simple, and they catch most unsupported answers. Every factual sentence must have a citation. Every citation must point at evidence that was actually retrieved, not a plausible file name the model invented. And every number in a sentence must appear in the evidence it cites, because numbers are where invented details do the most damage and they're easy to check exactly.

`answer` returns the problems alongside the text, so your application can revise, warn or abstain. Run it with `./course.sh python ch18_agentic.py`. These checks are deterministic, fast and free, so they run on every answer; a model-graded judge (Chapter 27) can check subtler things, such as whether a cited passage really supports the claim, on a sample.

## Common mistakes

- Chunks without sources, so answers can't be cited or checked.
- Mixing embedders between indexing and querying.
- Vector-only search for content full of codes, names and ids.
- Tuning the prompt before measuring retrieval: no prompt fixes a passage that wasn't retrieved.
- One index for everyone, so users retrieve documents they shouldn't see.
- No sufficiency check, so the agent answers from thin evidence instead of searching again or abstaining.
- Trusting citations without checking that the source was actually retrieved.

## Key takeaways

**Architect's takeaway:** An agent can't cite what it never retrieved, so measure retrieval first and check every citation in code.

- Embeddings capture meaning, BM25 captures exact words, and hybrid ranking gets both.
- Retrieval works best as a tool the agent can call repeatedly.
- Measure retrieval with recall@k and MRR before tuning anything else.
- Agentic retrieval plans its needs, picks a source for each and searches again when evidence is thin.
- Verify answers in code: citations must point at retrieved evidence, and numbers must appear in it.
