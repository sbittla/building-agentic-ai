# Chapter 8: Self-Correction: A Text-to-SQL Agent

Databases are blunt, and that makes them a good teacher. Misspell a table and SQLite answers at once with `no such table: custmers`: exact, immediate and impossible to misread. Hand that error back to the model and it checks the schema and tries again. Self-correction, which sounds like an advanced feature, turns out to be mostly a good error message and the loop you already have.

**What you'll build:** a SQL analyst that recovers from its own errors, stays read-only and is measured against verified answers.

**You are here:** Tools, with feedback from Evaluation in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 2 (tools), Chapter 4 (agent loop).

## Learning objectives

By the end of this chapter you can:

- Build an agent that turns questions into SQL and answers with real numbers.
- Enforce safety in the database layer, not the prompt.
- Feed error messages back so the agent fixes its own mistakes.
- Evaluate answers against known-correct results.

**In the real world.** Uber's QueryGPT turns questions into SQL for a platform that runs roughly 1.2 million interactive queries a month. One agent finds the business domain, one picks tables (and asks the user to confirm them) and one drops irrelevant columns to save tokens. In its limited release, 78% of users said it saved them time.

## 8.3 Safety in layers

The agent writes SQL you've never seen, so protect the data in layers, strongest first:

Table: Layers of database safety, strongest first
| Layer | How | Can the model get around it? |
| --- | --- | --- |
| Read-only connection | `mode=ro` in the connection URI | No; the database refuses writes |
| Read-only database user | Grant only SELECT (in Postgres or MySQL) | No |
| Statement check | Allow only `SELECT` or `WITH` at the start | Sometimes; `WITH x AS (...) DELETE ...` starts with WITH |
| Prompt instruction | "Never modify data" | Yes; a prompt is a request |

Try `run_query("WITH x AS (SELECT 1) DELETE FROM orders")`. The statement check lets it through because it starts with `WITH`, but the read-only connection blocks it with "attempt to write a readonly database". The connection is the real guard; the other layers are extras.

:::warn Prompts are not security
A clever input or a plain model mistake can override anything a prompt says. Enforce limits in code and in permissions.
:::

## 8.4 Error-driven self-correction

Models often write wrong SQL: a misspelled table, a column that doesn't exist, a `GROUP BY` mistake. A smarter prompt won't stop that. A **feedback loop** will:

1. The model writes SQL.
2. `run_query` fails and returns the **exact** database error plus a hint: "ERROR: no such table: custmers. Check table/column names with get_schema and retry."
3. The model reads the error, fixes the SQL and tries again.

You don't change the Chapter 4 loop at all. The more specific the error, the faster the fix; a bare "query failed" gives the model nothing to work with.

## 8.5 Keeping results small

`run_query` returns at most 50 rows and says when it has cut the result. Without the cap, `SELECT * FROM orders` would put 400 rows into the history, and every later step would pay for them (section 4.6). The truncation message suggests the fix: "add LIMIT or aggregate".

## 8.6 Checking answers

A confident, nicely formatted answer can still be wrong: a bad join, cancelled orders counted, the wrong date range. So the system prompt asks for the final SQL, which a person can review.

It also defines "revenue". Left undefined, the term can drift between runs: one might sum prices, the next multiply by quantity, a third drop cancelled orders. Real companies keep such definitions in a *semantic layer* or *data catalog*. And you test against **gold answers**, questions whose correct results you've computed yourself (exercise 8.7). The measurement interlude that follows this chapter shows how many runs that comparison needs before you can trust it.

## Common mistakes

- A writable connection "because the prompt says read-only."
- Vague error messages that give the model nothing to fix.
- Unlimited result sets that flood the context window.
- Undefined business terms such as "revenue" or "active customer".
- Trusting the answer without looking at the SQL.

## Before you move on

- **You should understand:** why the read-only connection is the guard and the `SELECT`/`WITH` check only an extra, and how exact errors let the model repair its SQL.
- **You should be able to build:** `get_schema` and `run_query` over a `mode=ro` connection, with a deadline, a 50-row cap and a defined "revenue".
- **Prove it:** exercise 8.3 matches your own query (Customer 13, 19,238).
- **Break it on purpose:** in a copy of `ch08_sql_tools.py`, drop `?mode=ro`, then run `run_query("WITH x AS (SELECT 1) DELETE FROM orders")` and count the orders. The tool reports an error, yet the rows are gone; `./course.sh data db` restores them.
- **Defend this decision:** why read-only belongs to the connection, not the prompt.

## Key takeaways

**Architect's takeaway:** Each retry after an error is another model call, so measure how often the agent self-corrects and what that adds in latency and tokens.

- A text-to-SQL agent needs only `get_schema` and `run_query`.
- Exact error messages turn failures into self-correction.
- Cap result sizes and say when you truncate.
- Evaluate against known answers; confidence proves nothing.
