# Chapter 8: Self-Correction: A Text-to-SQL Agent

Agents make mistakes, and the useful ones notice and fix them. In this chapter you'll build an agent that answers plain-English questions about a shop database by writing and running SQL. You'll make it safe with a read-only connection, then let database errors steer it toward correct queries. Finally you'll check its answers against results you know are right.

**What you'll build:** a SQL analyst that recovers from its own errors, stays read-only and is measured against verified answers.

**You are here:** Tools, with feedback from Evaluation in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Build an agent that turns questions into SQL and answers with real numbers.
- Enforce safety in the database layer, not the prompt.
- Use error messages as feedback so the agent fixes its own mistakes.
- Evaluate answers against known-correct results.

## Real-world connection

Uber's QueryGPT turns natural-language questions into SQL for its data platform, which handles roughly 1.2 million interactive queries a month. It splits the work among several agents: one finds the business domain, one picks tables (and asks the user to confirm them) and one removes irrelevant columns to save tokens. In its limited release, 78% of users said it saved them time compared with writing the query from scratch. This chapter builds the core of that system on a small database.

## 8.3 Safety in layers

The agent writes SQL you have never seen, so protect the data in layers. From strongest to weakest:

| Layer | How | Can the model get around it? |
| --- | --- | --- |
| Read-only connection | `mode=ro` in the connection URI | No; the database refuses writes |
| Read-only database user | Grant only SELECT (in Postgres or MySQL) | No |
| Statement check | Allow only `SELECT` or `WITH` at the start | Sometimes; `WITH x AS (...) DELETE ...` starts with WITH |
| Prompt instruction | "Never modify data" | Yes; prompts are requests, not guarantees |

Try `run_query("WITH x AS (SELECT 1) DELETE FROM orders")`. The statement check lets it through because it starts with `WITH`, but the read-only connection blocks it with "attempt to write a readonly database". The connection is the real guard; the other layers are extras.

:::warn Prompts are not security
Never rely on the system prompt to prevent harm. A clever input or a model mistake can override anything written in a prompt. Enforce limits in code and in permissions.
:::

## 8.4 Error-driven self-correction

Models often write wrong SQL: a misspelled table, a column that doesn't exist, a `GROUP BY` mistake. The fix isn't a smarter prompt. It's a **feedback loop**:

1. The model writes SQL.
2. `run_query` fails and returns the **exact** database error plus a hint: "ERROR: no such table: custmers. Check table/column names with get_schema and retry."
3. The model reads the error, fixes the SQL and tries again.

The agent loop from Chapter 4 already supports this; all you add is a good error message. The more specific the error, the faster the fix. A bare "query failed" gives the model nothing to work with.

## 8.5 Keeping results small

`run_query` returns at most 50 rows and tells the model when it has truncated the result. Without this cap, `SELECT * FROM orders` would put 400 rows into the history, and every later step would pay for them (section 4.6). The truncation message suggests the fix: "add LIMIT or aggregate".

## 8.6 Checking answers

A confident, nicely formatted answer can still be wrong: a bad join, cancelled orders counted, the wrong date range. Three checks help:

- **Show the SQL.** The system prompt asks for the final query so a human can review it.
- **Define business terms.** The system prompt defines "revenue". In real systems these definitions live in a *semantic layer* or *data catalog*, a shared place where a company records what its business terms mean.
- **Evaluate against gold answers.** Write questions whose correct results you've computed yourself, and compare (exercise 8.7). The interlude that follows this chapter shows how many runs that comparison needs before you can trust it.

## Architect's Takeaway

Self-correction is expensive: measure latency and token costs before mandating it.

## Common mistakes

- **A writable connection** "because the prompt says read-only."
- **Vague error messages** that give the model nothing to fix.
- **Unlimited result sets** that flood the context window.
- **Undefined business terms**, so "revenue" or "active customer" means something different on each run.
- **Trusting the answer without looking at the SQL.**

## Summary

- A text-to-SQL agent needs only `get_schema` and `run_query`; the model does the rest.
- Enforce read-only access at the connection or user level, not in the prompt.
- Exact error messages turn failures into self-correction.
- Cap result sizes and tell the model when you truncate.
- Evaluate against known answers, because a confident answer can still be wrong.

Your SQL agent reads data but never changes it. Before Chapter 9 gives an agent actions that change things, a short interlude turns this chapter's gold answers into a measurement you can trust: every case run several times, with a margin of error.

:::ex Simple | 8.3 | Top customers
Ask for the top five customers by revenue. Check the answer by running this query yourself: `SELECT c.name, SUM(oi.quantity * p.price) AS revenue FROM customers c JOIN orders o ON o.customer_id = c.id JOIN order_items oi ON oi.order_id = o.id JOIN products p ON p.id = oi.product_id WHERE o.status != 'cancelled' GROUP BY c.id ORDER BY revenue DESC LIMIT 5`.
**Done when:** The agent's numbers match your query (the top customer is Customer 13 with 19,238).
:::

:::ex Simple | 8.4 | Watch it self-correct

**Done when:** The trace shows a failing query, the error and a corrected query.
:::

:::ex Medium | 8.5 | Retry budget and log
Limit the agent to three failed queries per question. Log every query to `query_log.jsonl`, with whether it succeeded and any error.
**Done when:** The log shows at least one self-correction, and the budget message appears when you force repeated failures.
:::

:::ex Medium | 8.6 | Confirm the tables
Add a `propose_tables(question)` step like QueryGPT's table agent: before querying, the agent lists the tables it plans to use and asks the user to confirm.
**Done when:** The user can reject a table and the agent adapts its query.
:::

:::ex Complex | 8.7 | An evaluation harness
Write 15 questions with gold-answer SQL you've verified by hand. Build a harness that runs the agent on each question, runs the gold SQL and compares the result values (ignoring column names and row order). Report accuracy, then improve the system prompt or tools and report again.
**Hint:** Ask the agent to end its answer with the final SQL in a code block, then run that SQL yourself for comparison.
**Done when:** You have before and after accuracy, and a list of the failure types you found.
:::
