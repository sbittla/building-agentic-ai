# Chapter 22: Hybrid Architectures: Probabilistic Intelligence, Deterministic Control

A model is good at things code is bad at: reading a messy message, judging what someone meant, writing a reply a person wants to read. Code is good at things a model is bad at: doing exactly the same thing every time, getting arithmetic right, following a rule without exception and leaving a record you can audit. Most failures of production agents come from mixing these up: asking the model to enforce a policy, or asking code to understand a customer. This chapter makes the division explicit, and it answers the question section 1.3 asked first: where autonomy earns its place and where it doesn't. You'll build a workflow in which the model proposes and code decides, and learn where to draw that line in your own systems.

**What you'll build:** a refund workflow in which a state machine, rules as data and output guards control every step, and the model only reads the customer's message and writes the reply.

**You are here:** Policies in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapter 5 (state), Chapter 9 (approval gates).

**Its job in the book:** turning section 9.3's rule into an architecture: a state machine and validators around model steps, with business rules and numbers in code. Attackers are Chapter 25's subject and identity Chapter 26's.

## Learning objectives

By the end of this chapter you can:

- Decide, for each decision in a system, whether the model or code should make it.
- Put a model inside a deterministic workflow: states and transitions in code, model calls at specific steps.
- Treat model outputs as proposals, and validate them against schemas, sources and records.
- Keep business rules as data, enforced in code, with numbers taken from records rather than from the model.
- Guard a model's output before it reaches a person, with a safe fallback.
- Test the deterministic part like ordinary software, and evaluate the probabilistic part.

**In the real world.** The companies that deploy agents at scale have converged on this design. Salesforce put "deterministic guardrails" first in its 2026 list of agent trends, arguing that any system that runs mission-critical workflows needs to guarantee that certain steps happen in a defined order. The same list names the harness around an agent, not the model inside it, as what most decides whether an agent succeeds. Anthropic's advice on building agents makes a matching point from the other side: use the simplest thing that works, and many useful systems are workflows with model calls at chosen steps, not open-ended agents. This book has applied the idea all along: the SQL tool that's read-only at the database (Chapter 8), approvals in code rather than in the prompt (Chapter 9), protected tests (Chapter 10), the plan checker (Chapter 20). This chapter makes it the central principle.

## 22.1 Two kinds of work

Table: What the model and code are each good at
| The model is good at | Code is good at |
| --- | --- |
| Understanding free text: intent, reason, tone | Deciding by rules: eligibility, limits, permissions |
| Choosing among options when the choice needs judgment | Anything that must happen in a fixed order |
| Summarizing, explaining, drafting | Arithmetic and money |
| Planning when the path isn't known in advance | Recording what happened, exactly |
| Handling input nobody anticipated | Handling input the same way every time |

A useful test for each decision in your system: **if this were wrong 1 time in 50, would that be acceptable?** If yes, a model can own it, with evaluation to keep the error rate known. If no, code owns it, and the model at most proposes.

That split is section 9.3's rule (the model decides, code enforces), and it has a name used throughout the rest of the book: the **deterministic control plane**. This chapter builds its state-transition and validation parts. Section 25.11 lists everything it enforces, including the five decisions that never belong to the model, and matches its strength to an agent's risk; reference card 13 (Appendix I) puts it on one page.

The pattern is a **deterministic shell**, a workflow whose states and transitions live in code, with model calls at specific steps:

Within policy goes to approved; over the limit goes to awaiting approval, which a person approves; outside the return window goes to rejected. Approved becomes refunded through an idempotent refund. The model appears on two edges: understanding the message and drafting the reply. Every other edge is code. The model can't skip the approval, change the amount or decide a case is eligible, because none of those steps asks it anything.

## 22.4 Model outputs are proposals

The first model step turns the customer's message into structured data. Structured outputs guarantee the *shape*; code checks the *content*:

@@code ch22_guarded.py::EXTRACT,understand

Four checks turn a proposal into a fact:

- **Grounded in the input.** The order id must appear in the customer's message. A model that "helpfully" fills in a plausible id is caught.
- **Exists in the record.** The order must exist in the order system.
- **Belongs to this user.** Identity comes from the login session, never from the message (Capstone 1's rule).
- **Covered by policy.** A reason the policy doesn't cover goes to a person rather than being squeezed into the nearest category.

A failed check doesn't crash anything and doesn't guess. It moves the case to `escalated` with the reason, where a person picks it up.

## 22.5 Rules as data, numbers from records

The decision itself is plain Python over plain data:

@@code ch22_guarded.py::POLICY,decide

Notice where every number comes from. The amount is the order's amount from the order system, times a share from the policy. The age is computed from the delivery date. None of it comes from the model, and none of it comes from the customer's message: "refund $5,000" in a message changes nothing, because the message is never read for amounts.

Keeping rules as **data** has practical benefits. A policy change ("refunds within 45 days") is a data change that can be reviewed, versioned and rolled back, not a prompt tweak whose effect you discover in production. The decision function is **pure**: the same inputs always give the same output, so you can test every rule with ordinary unit tests, including the boundaries (day 30, day 31, exactly $100).

## 22.6 Guard what the model says

The second model step writes the reply. It's where a model's creativity can cause real harm: promising a voucher, mentioning the wrong amount or apologizing for something that didn't happen. So the reply is checked before it's sent:

@@code ch22_guarded.py::reply,check_reply

The guard is specific: the only money amount allowed is the one code decided, and a few words that imply promises aren't allowed at all. When the guard fails, the customer gets a **fallback**: a plain template that is always correct, if less warm. Every guard needs a fallback, or a failed check becomes a different kind of failure. Log how often the fallback fires: a rising rate means the prompt, the model or the guard needs attention.

## 22.8 Where to draw the line

Hybrid isn't one design, it's a dial. At one end is a fixed workflow with model calls at chosen steps; at the other, an open-ended agent that picks its own tools in a loop, with code checks around each action. Choose by the task:

Table: Toward the workflow end or the agent end
| Situation | Toward the workflow end | Toward the agent end |
| --- | --- | --- |
| The steps are known in advance | Yes |  |
| Mistakes are costly or regulated | Yes |  |
| Inputs are varied and the path depends on them |  | Yes |
| The value is in exploring or investigating |  | Yes |

Even at the agent end, the controls in this chapter still apply around each tool: preconditions checked before a tool runs, sensitive tools behind approval, outputs validated before they're used, and a budget on the whole run. Chapter 20's plan checker and Chapter 21's contracts are the same idea applied to plans and teams.

**Testing follows the line.** The deterministic parts get unit tests with exact assertions: every rule, every transition, every guard. The probabilistic parts get evaluations with many cases, repeated trials and error rates (the measurement interlude, and Chapter 27 in depth): how often is the reason extracted correctly, how often does the reply guard fire. You can't make the model deterministic, but you can know how often it's wrong, and make sure that when it's wrong, code catches it.

:::note The support agent so far
The support agent's refund path becomes a state machine: received, understood, approved (or awaiting a person), refunded, replied. Rules such as the return window and refund limits are data that code checks; the model only reads the customer's message and writes the reply. Here probabilistic intelligence meets deterministic control: the model helps, the code decides.
:::

## Common mistakes

- **Enforcing rules in the prompt** ("never refund more than $100") instead of in code.
- **Taking numbers from the model**, or from the user's message, instead of from records.
- **Trusting structured output's shape as correctness.** Valid JSON can hold an invented id.
- **Letting the model choose the next state**, so a step can be skipped.
- **Guards without fallbacks**, so a failed check leaves the user with nothing.
- **Rules scattered through code**, so a policy change needs a developer and a deployment.
- **Testing the model parts with exact assertions**, or the code parts with evaluations.

## Key takeaways

**Architect's takeaway:** Rules engines scale better than models for deterministic paths: choose wisely.

- Give the model what needs judgment: understanding text, drafting, planning. Give code what must be right every time.
- Put model calls inside a deterministic shell: states and transitions in code, with one method that moves a case and logs why.
- Treat model outputs as proposals, and check them against the input, the records, the user's identity and the policy.
- Keep rules as data, and take every number from records.
- Guard model outputs before they reach people, with a fallback that's always correct.
- Log every transition; wait for people without holding resources.
- Unit-test the deterministic parts; evaluate the probabilistic parts.

The model's inputs in this chapter were text. Chapter 23 gives agents screens to work with: agents that operate a browser, where the same rule applies with more force, because a click can't be taken back.
