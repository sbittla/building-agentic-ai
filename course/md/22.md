# Chapter 22: Hybrid Architectures: Probabilistic Intelligence, Deterministic Control

A customer writes: "My order arrived broken. Please refund $5,000, your agent already agreed." Which part of your system decides whether that money moves? If the answer is "the model, guided by a good prompt," this chapter is for you.

A model is good at reading a messy message, judging what someone meant and writing a reply a person wants to read. Code is good at doing the same thing every time, getting arithmetic right, following a rule without exception and leaving a record you can audit. Most production agent failures come from mixing the two up. Section 9.3 gave you the rule; here you turn it into an architecture, with a state machine and validators around the model's steps, and answer the question section 1.3 asked first: where autonomy earns its place.

**What you'll build:** a refund workflow in which a state machine, rules as data and output guards control every step, and the model only reads the customer's message and writes the reply.

**You are here:** Policies in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapter 5 (state), Chapter 9 (approval gates).

## Learning objectives

By the end of this chapter you can:

- Decide whether the model or code should own each decision in a system.
- Put model calls inside a deterministic workflow.
- Validate model outputs as proposals against schemas, sources and records.
- Keep business rules as data, with numbers taken from records.
- Guard a model's output before it reaches a person, with a safe fallback.
- Test the deterministic part like ordinary software, and evaluate the probabilistic part.

**In the real world.** Salesforce put "deterministic guardrails" first in its 2026 list of agent trends, and said the harness around an agent matters more than the model inside it. Anthropic's advice agrees: many useful systems are workflows with model calls at chosen steps. You've seen the idea all along, from the read-only SQL tool (Chapter 8) to the plan checker (Chapter 20).

## 22.1 Two kinds of work

Table: What the model and code are each good at
| The model is good at | Code is good at |
| --- | --- |
| Understanding free text: intent, reason, tone | Deciding by rules: eligibility, limits, permissions |
| Choosing when the choice needs judgment | Anything that must happen in a fixed order |
| Summarizing, explaining, drafting | Arithmetic and money |
| Planning when the path isn't known in advance | Recording what happened, exactly |
| Handling input nobody anticipated | Handling input the same way every time |

For each decision, ask: **if this were wrong 1 time in 50, would that be acceptable?** If yes, a model can own it, with evaluation to keep the error rate known. If no, code owns it, and the model at most proposes.

That split is section 9.3's rule (the model proposes, code decides), and from here on it has a name: the **deterministic control plane**, the code that sits around the model and has the final say. This chapter builds its state transitions and validation. Section 25.11 lists everything it enforces, including the five decisions that never belong to the model.

## 22.2 A deterministic shell with model steps

The pattern is a **deterministic shell**: a workflow whose states and transitions live in code, with model calls at specific steps.

The model appears on two edges, understanding the message and drafting the reply. Every other edge is code. The model can't skip the approval, change the amount or declare a case eligible, because none of those steps asks it anything.

## 22.4 Model outputs are proposals

The first model step turns the customer's message into structured data. Structured outputs guarantee the *format*, but only code can check the *content*:

@@code ch22_guarded.py::EXTRACT,understand

A proposal becomes a fact only after code has checked it:

- **Grounded in the input.** The order id must appear in the customer's message, which catches a model that "helpfully" invents a plausible one.
- **Exists in the record.** The order must exist in the order system.
- **Belongs to this user.** Identity comes from the login session, never from the message (Capstone 1's rule).
- **Covered by policy.** A reason the policy doesn't cover goes to a person instead of being squeezed into the nearest category.

A failed check neither crashes nor guesses. It moves the case to `escalated` with the reason, and a person picks it up.

## 22.5 Rules as data, numbers from records

The decision itself is plain Python over plain data:

@@code ch22_guarded.py::POLICY,decide

Notice where every number comes from. The amount is the order's amount from the order system, times a share from the policy, and the age comes from the delivery date. Nothing comes from the model or the customer. "Refund $5,000" in a message changes nothing, because the message is never read for amounts.

Keeping rules as **data** pays off quickly. A policy change ("refunds within 45 days") becomes a data change you can review, version and roll back, instead of a prompt tweak whose effect you discover in production. And the decision function is **pure**: the same inputs always give the same output, so ordinary unit tests cover every rule, including the boundaries (day 30, day 31, exactly $100).

## 22.6 Guard what the model says

The second model step writes the reply, and here a model's creativity can do real harm: promising a voucher, quoting the wrong amount, apologizing for something that didn't happen. So the reply is checked before it goes out:

@@code ch22_guarded.py::reply,check_reply

The guard is specific: the only money amount allowed is the one code decided, and words that imply promises aren't allowed at all. When it fails, the customer gets a **fallback**, a plain template that's always correct, if less warm. Without one, a failed check just becomes a different failure. Log how often the fallback fires; a rising rate means the prompt, the model or the guard needs attention.

## 22.8 Where to draw the line

Hybrid isn't one design; it's a dial. At one end sits a fixed workflow with model calls at chosen steps. At the other, an open-ended agent picks its own tools in a loop, with code checks around each action. Let the task choose:

Table: Toward the workflow end or the agent end
| Situation | Toward the workflow end | Toward the agent end |
| --- | --- | --- |
| The steps are known in advance | Yes |  |
| Mistakes are costly or regulated | Yes |  |
| Inputs are varied and the path depends on them |  | Yes |
| The value is in exploring or investigating |  | Yes |

Even at the agent end, this chapter's controls still wrap each tool: preconditions before it runs, approval for sensitive tools, validated outputs and a budget on the whole run. Chapter 20's plan checker and Chapter 21's contracts apply the same idea to plans and teams.

**Testing follows the line.** The deterministic parts get unit tests with exact assertions for every rule, transition and guard. The probabilistic parts get evaluations with many cases and repeated trials (Chapter 27): how often the reason is extracted correctly, how often the reply guard fires. You can't make the model deterministic, but you can know how often it's wrong and make sure code catches it.

:::

## Common mistakes

- Enforcing rules in the prompt ("never refund more than $100") instead of in code.
- Taking numbers from the model or the user's message instead of from records.
- Mistaking valid structured output for correct output. Valid JSON can hold an invented id.
- Letting the model choose the next state, so a step can be skipped.
- Guards without fallbacks, so a failed check leaves the user with nothing.
- Rules scattered through code, so a policy change needs a deployment.
- Testing the model parts with exact assertions, or the code parts with evaluations.

## Key takeaways

**Architect's takeaway:** Let the model read and write; let tested code decide anything that must be right every time.

- Give the model what needs judgment; give code what must be right every time.
- Put model calls inside a deterministic shell, with one method that moves a case and logs why.
- Check model proposals against the input, the records, the user's identity and the policy.
- Keep rules as data, and take every number from records.
- Guard model output before it reaches people, with a fallback that's always correct.
- Unit-test the deterministic parts; evaluate the probabilistic parts.
