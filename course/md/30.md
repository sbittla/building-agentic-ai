# Chapter 30: Deploying Agents: From One Service to an Agent Platform

An agent that runs only in your terminal helps only you. In this chapter you'll put an agent behind a web API that other apps and people can call safely, with authentication, rate limits, private sessions, budgets and streamed progress. You'll serve an MCP server remotely with token-based authorization and work through a checklist for going live. Then you'll step back to the view of an architect: what an organization needs when many teams ship agents, and one reference architecture that places everything this book built.

**What you'll build:** an agent API with keys, rate limits, private sessions and streaming, a remote MCP server with OAuth, a production image you can deploy and a map of the shared platform and reference architecture your agents fit into.

**You are here:** User / API, and every layer at once in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Put an agent behind a web API with authentication, rate limits and per-caller sessions.
- Stream an agent's progress to clients as it works.
- Enforce per-request budgets and fail cleanly when the model service fails.
- Serve an MCP server remotely over HTTP, protected by a token.
- Deploy the service to a cloud host as a secure container, test it from the outside and know what to check before going live.
- Name the shared services of an agent platform, say what to standardize first and keep tenants isolated.
- Place every part of an agent system in one end-to-end reference architecture.

## Real-world connection

So far every agent has run in your terminal. Real users reach agents through an app, a chat window or another service, which means an HTTP API. The concerns change: who is calling, how often, whose conversation this is, what a request may cost and what happens when the model provider has a bad minute. The same applies to MCP: GitHub and many other vendors offer remote MCP servers that any authorized client can reach over HTTPS.

## 30.1 The architecture

Here is the production deployment you'll build in this chapter. Callers reach one container over HTTPS. Inside it, the agent API checks the key, applies the caller's rate limit and loads the caller's session, then hands the request to the agent loop with its budgets. The loop calls the model provider, the remote MCP server and the session database. The platform supplies secrets when the container starts, and logs and traces flow out to a collector.

On your laptop the session database is a SQLite file and the "collector" is your terminal. Section 30.6 shows what changes in the cloud.

## 30.2 The agent API

@@code ch30_service.py::api_key,rate_limit,session_lock,run,chat,chat_stream

Run it with `./course.sh serve-api` and open `http://localhost:8080/docs` for interactive documentation. The important parts:

- **Fail closed.** The service **refuses to start** without `AGENT_API_KEYS` (the `lifespan` check). A service with a built-in default key is protected by a password anyone can read in a book. `./course.sh setup` puts a long random key in your `.env`.
- **Authentication.** Every request needs `Authorization: Bearer <key>`. Keys are compared with `hmac.compare_digest`, which takes the same time wherever the strings differ, so attackers can't guess keys by timing the responses. The service then works with a **key id** (a SHA-256 fingerprint of the key). The session table and the logs store only the key id, never the key itself.
- **Rate limiting.** Each key has its own **token bucket**, an allowance of `AGENT_RATE_PER_MINUTE` requests that refills continuously. Over the limit, the API returns **429** with a `Retry-After` header, the signal Chapter 7's tools respect. The buckets live in this one process; with several server processes you'd keep them in a shared store such as Redis.
- **Sessions.** Each conversation is stored in SQLite under a session id, together with the key id that created it. Another caller who guesses the id gets a **404**, so conversations are private per caller. A session handles **one request at a time**, and a second concurrent request gets **409**. Otherwise both would load the same history and one turn would be silently lost. History is **bounded** (`AGENT_MAX_HISTORY`) and cut only before a plain user message, as in Chapter 16.
- **Budgets.** Every request has a step cap (`AGENT_MAX_STEPS`) and a token budget (`AGENT_MAX_TOKENS`), using the `should_stop` hook from Chapter 4.
- **Failures.** If the model call fails, the caller gets a clean **502** with a generic message, and the log records the error type. Stack traces and internal details never reach the caller.
- **Logs.** One JSON line per request with a request id, key id, session, latency and token counts: the trace fields from Chapter 28. Message text and keys are never logged.

## 30.3 Streaming progress

An agent can take many seconds to answer. `/v1/chat/stream` responds immediately and sends **Server-Sent Events** (SSE), a standard way for a server to push a stream of messages over one HTTP response, as the agent works: a `tool` event for each tool call, then an `answer` event. The agent runs in a background thread and passes events to the response through a queue. Two details matter in production. First, a **keep-alive** comment every 15 seconds stops proxies from closing a quiet connection. Second, when the client **disconnects**, the response's `finally` sets a `cancelled` flag that `should_stop` checks, so the agent stops at its next step instead of spending tokens on an answer nobody will read. Clients read the stream line by line, as `chat_stream` in `ch30_client.py` does:

## 30.4 A remote MCP server

@@code ch30_remote_mcp.py::StaticTokenVerifier,require,build_server

A remote MCP server is a web service that many clients reach over the network, so it needs real authorization. The MCP specification uses **OAuth 2.1**, the standard protocol for granting apps limited access with tokens. In OAuth terms, your server is a **resource server**: it doesn't issue tokens or handle sign-in. It only checks tokens issued by an **authorization server**, your identity provider (Okta, Entra ID, Auth0, Keycloak and so on). The MCP SDK implements the protocol side for you:

- A request without a valid token gets **401**, with a `WWW-Authenticate` header pointing to `/.well-known/oauth-protected-resource/mcp`. That **protected-resource metadata** (RFC 9728) tells an MCP client which authorization server to send the user to and which scopes exist, so clients like Claude can sign the user in by themselves.
- `verify_token` decides whether a token is valid and what it may do. Here it looks tokens up in your `.env` (`MCP_TOKEN` may read and write, `MCP_READONLY_TOKEN` may only read). In production it would verify a signed JWT (JSON Web Token, a signed token format) from your identity provider, or call the provider's introspection endpoint.
- `validate_token_resource=True` rejects tokens issued **for a different server** (the token's audience). Without it, a token a user gave to some other MCP server could be replayed here.
- **Scopes per tool**: `add_task` calls `require("todo:write")`, so the read-only token can list tasks but not add them. Least privilege applies to tools, not only to servers.
- **Client registration**: MCP clients now identify themselves with a **Client ID Metadata Document**, a small JSON file at a URL they control, instead of registering dynamically with each authorization server. Your resource server doesn't change, but your identity provider must support it.
- **Host checking** (`transport_security`) refuses requests whose `Host` header isn't one you listed (421). This blocks DNS-rebinding attacks, in which a web page in your browser tricks it into sending requests to a server on your machine.

Run it with `./course.sh serve-mcp` and connect with `./course.sh python ch30_client.py mcp`. Clients send the token with `create_mcp_http_client(headers=...)`, as `remote_tools` does in the client file.

:::warn Never pass the user's token through
If your MCP server calls another API on the user's behalf, don't forward the token it received: it was issued for *your* server. Get a separate token for the downstream API (for example with OAuth token exchange). The MCP specification forbids token passthrough for this reason. Always use HTTPS outside your own machine.
:::

Every managed container platform follows the same five steps, so learn them once: build an image, run it locally the way the cloud will, give the platform your secrets, deploy with limits and test the public URL from the outside.

**3. Test it from the outside.** A **smoke test** is a short set of checks you run after every deployment, before users arrive: does it answer, does it refuse strangers, does a real question work? This one exits with an error if anything fails, so a CI pipeline can stop a bad release:

@@code ch30_smoke_test.py::smoke

**4. Deploy to a managed host.** Google Cloud Run, AWS App Runner, Azure Container Apps, Fly.io and Render all run a container image for you, give it an HTTPS address and restart it when the health check fails. The details differ, but you always do the same things:

| Step | Why |
| --- | --- |
| Push the image to the platform's registry | The platform runs exactly the image you tested |
| Store `ANTHROPIC_API_KEY` and `AGENT_API_KEYS` in the platform's secret manager | Secrets never sit in the image, the code or a shell history |
| Set a **maximum instance count** and a request timeout | A traffic spike or a looping agent can't run up an unlimited bill |
| Use the HTTPS address the platform gives you | Keys travel encrypted; never serve plain HTTP |
| Turn on log collection and a budget alert | Logs go to stdout; the platform keeps and searches them |

Exercise 30.7 walks through Cloud Run as one example. The solution script shows every command. If you'd rather not host the agent loop at all, Claude Managed Agents (section 24.8) runs it, with its sandbox, on Anthropic's infrastructure; you'd then deploy only the thin service in front of it.

**5. Smoke-test the real URL**, then read the first few log lines. Only then send users.

:::warn SQLite lives inside one container
`sessions.db` is a file inside the container. Cloud platforms start extra copies under load and replace containers freely, and each copy has its own file, which disappears with it. For a demo, limit the service to **one instance** and accept that sessions reset on restart. For real users, replace the SQLite session store with a managed database (PostgreSQL, for example) that every instance shares. The same goes for the rate-limit counters, which live in memory.
:::

## 30.7 Launch checklist

This list gathers the whole book into the checks to make before real users touch your agent. Each line points to where the book covers it.

**Security and trust**

- [ ] Every endpoint except health checks needs an API key or user sign-in, and the service refuses to start without its keys (section 30.2).
- [ ] The agent has its own identity and short-lived, scoped tokens; tools check ownership and limits (Chapter 26).
- [ ] Every write tool needs approval or is covered by a reviewed policy; risky actions use step-up tokens (Chapters 9, 14 and 26).
- [ ] Outbound requests go only to allowed sites; canaries and a leak scan guard the tools; rendered output is sanitized (Chapter 25).
- [ ] Generated code runs in an isolated sandbox with no secrets (Chapter 10).
- [ ] Injection red-team tests pass with a model that obeys the attacker (exercise 25.6).
- [ ] Remote MCP servers verify token audience and scopes; HTTPS everywhere (section 30.4).
- [ ] Sessions are private to their owner; keys are stored and logged only as fingerprints.

**Quality**

- [ ] The evaluation suite grades outcome, process and cost, and gates every change in CI (Chapter 27).
- [ ] Continuous evaluation samples production runs and watches for drift (section 27.8).
- [ ] There's a clear path to a human when the agent can't help.

**Reliability**

- [ ] Timeouts, retries with limits and a clean error response when the model API fails (Chapters 4 and 19).
- [ ] Long-running work is checkpointed and resumable, with idempotent side effects (Chapter 19).
- [ ] A health endpoint, and a smoke test that passes against the real URL (section 30.6).
- [ ] A maximum instance count and a request timeout.

**Cost and performance**

- [ ] Iteration caps, per-request budgets and per-user daily budgets are enforced in code (Chapter 29).
- [ ] Prompt caching is on, and simple steps use a smaller model where the eval suite shows no quality loss (Chapters 16 and 20).
- [ ] Offline work (evals, bulk grading, reports) uses the Message Batches API at half price.
- [ ] Load-tested open-loop at expected peak; p95 latency, error rate and capacity against rate limits are known (Chapter 29).
- [ ] Cost per successful task is known, and alerts fire on unusual spend.

**Operations**

- [ ] Traces for every request (OpenTelemetry), with secrets and personal data removed (Chapter 28).
- [ ] Failure classes and SLO alerts for success rate, p95 latency, cost per success and tool errors (Chapter 28).
- [ ] Model name and prompt versions are pinned and logged with each trace.
- [ ] A kill switch disables the agent, a single tool or an agent identity at once (section 26.7).

## 30.8 From one agent to an agent platform

Everything so far ships one agent. Organizations rarely stop at one. Once a support team, a finance team and an engineering team each ship an agent, each team rebuilds the same pieces: keys for the model provider, a way to sign agents in, a gateway for tools, an eval suite, traces and a budget alarm. That is waste, and it is risk: five teams means five ways to store a secret and five audit trails that don't join up. The answer most organizations reach is a **platform team** that runs the shared services and offers **paved roads**, the supported, documented way to do each job, so a product team can ship an agent by writing its prompts, tools and evals, not its infrastructure.

This section is for the staff engineer, architect, engineering manager or CTO who has to plan that platform. You've already built a small version of every piece.

| Platform component | What it does | Where you built a small version |
| --- | --- | --- |
| Model gateway | One front door to model providers: holds the keys, routes by task, enforces budgets and falls back when a provider fails | Routing and fallback (Chapter 20), budgets and concurrency caps (Chapter 29) |
| Agent runtime | Runs the loop and keeps long jobs alive across crashes | The loop (Chapter 4), durable jobs (Chapter 19), runtimes (Chapter 24) |
| MCP gateway | One front door to tools: authorizes every call, filters tool lists, logs every argument | Chapter 15 |
| Identity | Gives every agent its own identity and short-lived, scoped tokens on behalf of a user | Chapter 26 |
| Secrets | Stores keys outside code and images and hands them over at run time | Chapter 0 and section 30.6 |
| Policy engine | Decides what an agent may do, as reviewed rules rather than prompt text | Chapters 9, 14 and 22 |
| Evaluation service | Runs suites on every change and samples production runs | Chapter 27 |
| Observability | Collects traces, failure classes and SLOs across all agents | Chapter 28 |
| Memory service | Stores long-term memories with owners, scopes and forgetting | Chapter 17 |
| Vector and search infrastructure | Indexes documents for hybrid retrieval | Chapter 18 |
| Workflow engine | Runs deterministic steps, checkpoints and retries around model steps | Chapters 19 and 22 |
| Human approval service | Routes risky actions to the right person and records the decision | Chapter 9, step-up tokens in Chapter 26 |
| Cost controls | Per-request, per-user and per-team budgets, with alerts | Chapter 29 |
| Tenant isolation | Keeps each customer's or team's data, sessions and spend apart | Memory scopes (Chapter 17), sessions and keys (section 30.2) |
| Audit trail | An append-only record of who did what, as which agent, for whom | Chapters 9, 14, 26 and 28 |

The picture groups those components into a few shared services. Product teams build agents on top; the platform reaches models, tools and data, and people on their behalf.

@@image d-7c2fe2dcea53.png

**Tenant isolation.** A platform serves many tenants: customers, business units or teams. Sharing compute is fine. Some things must never be shared:

- **Memory.** One tenant's memories must never be recalled for another. Every memory carries an owner and a scope, and recall filters on them before ranking, as in section 17.7.
- **Sessions.** A session belongs to the key or user that created it, and anyone else gets a 404, as in section 30.2.
- **Caches with private scope.** A cached tool list or result that depends on who asked is `private`, never served to another user (section 15.3). The same rule applies to any response cache you add.
- **Tokens.** Each agent gets its own short-lived token for each user it acts for, and a gateway never passes one caller's token to a server behind it (Chapter 26 and section 15.5).

Give each tenant its own keys, rate limits and budgets, so one tenant's traffic spike or looping agent can't exhaust another's allowance, and put the tenant id on every trace (section 28.1) so you can answer "which customers were affected?"

**Build, buy or run managed.** For each component you can build it, buy a product or use a managed service from a cloud or model provider. The trade-offs are the ones section 24.5 used for the agent runtime: control and portability against the time and people it takes to run the thing yourself. Buy or rent what isn't your advantage, build what is and keep the interfaces your own (OpenTelemetry for traces, MCP for tools, your own eval cases) so you can swap a component later without rewriting every agent.

Here's the decision matrix for five high-impact components. For each, ask: *Can we maintain this for 3+ years without the core team becoming on-call for it?* If no, buy.

| Component | Build | Buy (Managed) |
| --- | --- | --- |
| **Agent Orchestration** | Pros: Full control, minimal overhead; Cons: Distribute traces, queues, retries yourself | Pros: Built-in traces, multi-tenant isolation, SLA; Cons: Vendor lock-in, less control. **Recommendation: Buy for >5 agents, build for <3** |
| **Memory & State** | Pros: Custom schema, embedded access; Cons: Replication, expiration, access control | Pros: Multi-tenant, expiration rules, built-in backups; Cons: API latency. **Recommendation: Buy for high-traffic, build for privacy-critical** |
| **Vector Database (RAG)** | Pros: Own the data; Cons: Operational burden (updates, versioning, rebalancing) | Pros: Managed updates, SIMD search, pricing per query; Cons: Retention limits. **Recommendation: Buy for <1M docs, build only if docs change constantly and you need exact version control** |
| **Observability / APM** | Pros: Custom dashboards, no PII; Cons: Sampling, aggregation, debugging at scale is hard | Pros: OpenTelemetry integration, built-in SLO alerts, dashboards; Cons: Costs scale with volume. **Recommendation: Buy from day 1 (avoid cost after 1M requests)** |
| **Evals / Testing** | Pros: Domain-specific assertions; Cons: Labeling, test data maintenance, regression detection | Pros: Pre-built frameworks, benchmark suites, LLM-as-judge; Cons: Tuning, token costs. **Recommendation: Build core logic, buy benchmarking layer** |

**What to standardize first.** You can't build everything at once. This order puts the risky, hard-to-change parts first:

1. **Identity and secrets.** Every agent gets an identity, and no key lives in code. Retrofitting identity after 20 agents ship is painful.
2. **Gateways.** A model gateway and an MCP gateway give you one place to enforce keys, budgets, allow-lists and logging.
3. **Tracing and cost attribution.** Every call carries agent, user, tenant and team, so you can see what fails and who pays.
4. **Evaluation gates.** No agent change ships without passing its suite in CI.
5. **Shared memory and retrieval.** Worth sharing once the first four are in place and teams keep building the same index.

## Architect's Takeaway

Production systems need strong isolation: one tenant's mistakes shouldn't break others.

## Common mistakes

- **No authentication** "because it's internal".
- **One global rate limit** instead of per caller, so one client or one looping agent can starve everyone.
- **Session ids as the only protection** for conversations.
- **Returning stack traces** or logging prompts and keys. Secrets don't belong in images or logs either; scan both before shipping.
- **Long requests with no feedback**, so users retry and double the load.
- **No kill switch.** On-call engineers need to turn an agent off in seconds, without a code push.
- **No smoke test from the outside.** Test the public URL with wrong keys, load and unhappy paths, not only the happy one.
- **Every team building its own gateway, identity and eval stack**, so no one can answer what all the agents cost or did.
- **Sharing a cache, memory store, database table or token across tenants** because it was simpler.
- **Building shared memory first** and identity, gateways and tracing last.

## Summary

- An agent service needs auth, per-caller rate limits, private sessions, budgets and clean errors.
- Stream progress with Server-Sent Events so long runs feel responsive.
- Remote MCP servers run over Streamable HTTP (MCP's HTTP transport) and must be authenticated.
- Configuration and secrets come from the environment; logs record ids and numbers, not content.
- Deploy a small, non-root image with secrets given at run time, limits on instances and cost and a smoke test against the public HTTPS URL.
- When many teams ship agents, a platform team provides shared gateways, identity, policy, memory, workflow, evaluation, observability and cost controls as paved roads. Standardize identity and secrets first.
- Memory, sessions, private caches and tokens are never shared between tenants; each tenant gets its own keys and budgets.
- The reference architecture (user or API, runtime, model, MCP, APIs and A2A, environment, with evaluation and observability across all layers) places every agent you build.

That completes Part 9 and the chapters. The capstone projects come next: larger builds where you combine tools, memory, retrieval, evaluation and deployment into complete agents of your own design.

- [ ] Run an evaluation suite with repeated trials in CI, and calibrate a model judge against human labels.
- [ ] Trace every model call and tool call, and find the slow or failing step from the traces.
- [ ] Load-test an agent with correct latency measurement and report cost per request.
