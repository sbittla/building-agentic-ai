# Chapter 30: Deploying Agents: From One Service to an Agent Platform

An agent that runs only in your terminal helps only you. In this chapter you'll put an agent behind a web API that other apps and people can call safely, with authentication, rate limits, private sessions, budgets and streamed progress. You'll serve an MCP server remotely with token-based authorization and work through a checklist for going live. Then you'll take MCP to company scale, with long-running tools, a gateway in front of every server, registries and company-wide sign-on, and step back to the view of an architect: what an organization needs when many teams ship agents, and one reference architecture that places everything this book built.

**What you'll build:** an agent API with keys, rate limits, private sessions and streaming, a remote MCP server protected by a token, a production image you can deploy, a report server whose tools start work and return at once on Chapter 19's durable runner, a gateway that hides, authorizes, rate-limits and audits every call to the servers behind it, and a map of the shared platform and reference architecture your agents fit into.

**You are here:** User / API, and every layer at once in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

## Real-world connection

So far every agent has run in your terminal. Real users reach agents through an app, a chat window or another service, which means an HTTP API. The concerns change: who is calling, how often, whose conversation this is, what a request may cost and what happens when the model provider has a bad minute. The same applies to MCP: GitHub and many other vendors offer remote MCP servers that any authorized client can reach over HTTPS.

## 30.1 The architecture

Here is the production deployment you'll build in this chapter. Callers reach one container over HTTPS. Inside it, the agent API checks the key, applies the caller's rate limit and loads the caller's session, then hands the request to the agent loop with its budgets. The loop calls the model provider, the remote MCP server and the session database. The platform supplies secrets when the container starts, and logs and traces flow out to a collector.

## 30.2 The agent API

@@code ch30_service.py::api_key,rate_limit,session_lock,run,chat,chat_stream

Run it with `./course.sh serve-api` and open `http://localhost:8080/docs` for interactive documentation. The important parts:

- **Fail closed.** The service **refuses to start** without `AGENT_API_KEYS` (the `lifespan` check). A service with a built-in default key is protected by a password anyone can read in a book. `./course.sh setup` puts a long random key in your `.env`.
- **Authentication.** Every request needs `Authorization: Bearer <key>`. Keys are compared with `hmac.compare_digest`, which takes the same time wherever the strings differ, so attackers can't guess keys by timing the responses. The service then works with a **key id** (a SHA-256 fingerprint of the key). The session table and the logs store only the key id, never the key itself.
- **Rate limiting.** Each key has its own **token bucket**, an allowance of `AGENT_RATE_PER_MINUTE` requests that refills continuously. Over the limit, the API returns **429** with a `Retry-After` header, the signal Chapter 7's tools respect. The buckets live in this one process; with several server processes you'd keep them in a shared store such as Redis.
- **Sessions.** Each conversation is stored in SQLite under a session id, together with the key id that created it. Another caller who guesses the id gets a **404**, so conversations are private per caller. A session handles **one request at a time**, and a second concurrent request gets **409**. Otherwise both would load the same history and one turn would be silently lost. History is **bounded** (`AGENT_MAX_HISTORY`) and cut only before a plain user message, as in Chapter 16.
- **Budgets.** Every request has a step cap (`AGENT_MAX_STEPS`) and a token budget (`AGENT_MAX_TOKENS`), using the `should_stop` hook from Chapter 4.
- **Failures.** If the model call fails, the caller gets a clean **502** with a generic message, and the log records the error type. Stack traces and internal details never reach the caller.
- **Logs.** One JSON line per request with a request id, key id, session, latency and token counts: the trace fields from Chapter 28. Message text and keys are never logged.

## 30.3 Streaming progress

An agent can take many seconds to answer. `/v1/chat/stream` responds immediately and sends **Server-Sent Events** (SSE), a standard way for a server to push a stream of messages over one HTTP response, as the agent works: a `tool` event for each tool call, then an `answer` event. The agent runs in a background thread and passes events to the response through a queue. Two details matter in production. First, a **keep-alive** comment every 15 seconds stops proxies from closing a quiet connection. Second, when the client **disconnects**, the response's `finally` sets a `cancelled` flag that `should_stop` checks, so the agent stops at its next step instead of spending tokens on an answer nobody will read. Clients read the stream line by line, as `chat_stream` in `ch30_client.py` does:

## 30.4 A remote MCP server

@@code ch30_remote_mcp.py::StaticTokenVerifier,require,build_server

A remote MCP server is a web service that many clients reach over the network, so it needs real authorization. The MCP specification uses **OAuth 2.1**, the standard protocol for granting apps limited access with tokens. In OAuth terms, your server is a **resource server**: it doesn't issue tokens or handle sign-in. It only checks tokens issued by an **authorization server**, your identity provider (Okta, Entra ID, Auth0, Keycloak and so on). The MCP SDK implements the protocol side for you:

- A request without a valid token gets **401**, with a `WWW-Authenticate` header pointing to `/.well-known/oauth-protected-resource/mcp`. That **protected-resource metadata** (RFC 9728) tells an MCP client which authorization server to send the user to and which scopes exist, so clients like Claude can sign the user in by themselves.
- `verify_token` decides whether a token is valid and what it may do. Here it looks tokens up in your `.env` (`MCP_TOKEN` may read and write, `MCP_READONLY_TOKEN` may only read). In production it would verify a signed JWT (JSON Web Token, a signed token format) from your identity provider, or call the provider's introspection endpoint.
- `validate_token_resource=True` rejects tokens issued **for a different server** (the token's audience). Without it, a token a user gave to some other MCP server could be replayed here.
- **Scopes per tool**: `add_task` calls `require("todo:write")`, so the read-only token can list tasks but not add them. Least privilege applies to tools, not only to servers.
- **Client registration**: MCP clients now identify themselves with a **Client ID Metadata Document**, a small JSON file at a URL they control, instead of registering dynamically with each authorization server. Your resource server doesn't change, but your identity provider must support it.
- **Host checking** (`transport_security`) refuses requests whose `Host` header isn't one you listed (421). This blocks DNS-rebinding attacks, in which a web page in your browser tricks it into sending requests to a server on your machine.

Run it with `./course.sh serve-mcp` and connect with `./course.sh python ch30_client.py mcp`. Clients send the token with `create_mcp_http_client(headers=...)`, as `remote_tools` does in the client file.

:::warn Never pass the user's token through
If your MCP server calls another API on the user's behalf, don't forward the token it received: it was issued for *your* server. Get a separate token for the downstream API (for example with OAuth token exchange). The MCP specification forbids token passthrough for this reason. Always use HTTPS outside your own machine.
:::

| Step | Why |
| --- | --- |

**5. Smoke-test the real URL**, then read the first few log lines. Only then send users.

:::warn SQLite lives inside one container
`sessions.db` is a file inside the container. Cloud platforms start extra copies under load and replace containers freely, and each copy has its own file, which disappears with it. For a demo, limit the service to **one instance** and accept that sessions reset on restart. For real users, replace the SQLite session store with a managed database (PostgreSQL, for example) that every instance shares. The same goes for the rate-limit counters, which live in memory.
:::

## 30.7 Launch checklist

This list gathers the whole book into the checks to make before real users touch your agent. Each line points to where the book covers it.

**Security and trust**

- [ ] Every endpoint except health checks needs an API key or user sign-in, and the service refuses to start without its keys (section 30.2).
- [ ] The agent has its own identity and short-lived, scoped tokens; tools check ownership and limits (Chapter 26).
- [ ] Every write tool needs approval or is covered by a reviewed policy; risky actions use step-up tokens (Chapters 9, 14 and 26).
- [ ] Outbound requests go only to allowed sites; canaries and a leak scan guard the tools; rendered output is sanitized (Chapter 25).
- [ ] Generated code runs in an isolated sandbox with no secrets (Chapter 10).
- [ ] Injection red-team tests pass with a model that obeys the attacker (exercise 25.6).
- [ ] Remote MCP servers verify token audience and scopes; HTTPS everywhere (section 30.4).
- [ ] Sessions are private to their owner; keys are stored and logged only as fingerprints.

**Quality**

- [ ] The evaluation suite grades outcome, process and cost, and gates every change in CI (Chapter 27).
- [ ] Continuous evaluation samples production runs and watches for drift (section 27.8).
- [ ] There's a clear path to a human when the agent can't help.

**Reliability**

- [ ] Timeouts, retries with limits and a clean error response when the model API fails (Chapters 4 and 19).
- [ ] Long-running work is checkpointed and resumable, with idempotent side effects (Chapter 19).
- [ ] A health endpoint, and a smoke test that passes against the real URL (section 30.6).
- [ ] A maximum instance count and a request timeout.

**Cost and performance**

- [ ] Iteration caps, per-request budgets and per-user daily budgets are enforced in code (Chapter 29).
- [ ] Prompt caching is on, and simple steps use a smaller model where the eval suite shows no quality loss (Chapters 16 and 20).
- [ ] Offline work (evals, bulk grading, reports) uses the Message Batches API at half price.
- [ ] Load-tested open-loop at expected peak; p95 latency, error rate and capacity against rate limits are known (Chapter 29).
- [ ] Cost per successful task is known, and alerts fire on unusual spend.

**Operations**

- [ ] Traces for every request (OpenTelemetry), with secrets and personal data removed (Chapter 28).
- [ ] Failure classes and SLO alerts for success rate, p95 latency, cost per success and tool errors (Chapter 28).
- [ ] Model name and prompt versions are pinned and logged with each trace.
- [ ] A kill switch disables the agent, a single tool or an agent identity at once (section 26.7).

## 30.8 Long-running tools: start, then check

Section 30.4 put one MCP server on the network. A company runs dozens of them, for hundreds of agents and people, and Chapter 15's protocol changes are only the start. Sections 30.8 to 30.11 build the pieces most teams add next: a job pattern for slow tools, a gateway in front of every server, a policy for choosing servers from registries, and sign-on run by the company's identity provider. Each one leans on something from Parts 7 to 9: durable jobs (Chapter 19), agent identity (Chapter 26) and tracing (Chapter 28).

A tool call should answer in seconds. Clients, proxies and load balancers close connections that stay silent for too long, and a model waiting on a five-minute call holds everything up. Work that takes minutes (building a report, exporting data, running a deployment) needs a different shape: **start the work, return a handle at once, let the caller check on it**.

@@code ch30_jobs_server.py::start_report,job_status

The pattern has four parts:

1. **`start_report` returns immediately** with a job id and a suggested polling interval. The work runs in the background on Chapter 19's durable runner, so each step is checkpointed in SQLite.
2. **`job_status` reports progress**, and the result once the job has finished.
3. **A `request_id` makes starting safe to retry.** If the call times out and the agent tries again, it gets the same job instead of a second report. This is Chapter 19's idempotency key, applied to a tool.
4. **Nothing is lost in a restart.** When the server starts (`python ch30_jobs_server.py stdio`), `resume_unfinished` claims jobs a previous process left behind; finished steps aren't repeated.

Run `./course.sh python ch30_jobs_server.py` to start a report for March 2026 and poll it to completion.

The status names aren't arbitrary. They're the ones MCP's **Tasks extension** (`io.modelcontextprotocol/tasks`) uses to make this pattern part of the protocol:

Table: This chapter's job tools compared with the Tasks extension
|  | This chapter's tools | Tasks extension |
| --- | --- | --- |
| Starting | A `start_…` tool returns a job id | Any `tools/call` may return a task (`resultType: "task"`) with a `taskId` |
| Checking | A `job_status` tool | `tasks/get` |
| Asking for input | `input_required` with a note for a person | `input_required` with requests the client answers through `tasks/update` |
| Stopping | Your own tool | `tasks/cancel` (cooperative: the server may still finish) |
| Statuses | `working`, `completed`, `input_required`, `cancelled` | the same, plus `failed` |

With the extension, the *server* decides per call whether to answer directly or return a task, and the client handles whichever arrives, so a host can show progress for any slow tool without the model polling. Clients and SDKs are adding support through 2026. Until yours has it, the tools above work with every client, and moving to the extension later changes the wrapper, not your durable runner.

:::tip Who polls?
If the model polls, every check costs a model call. Let the host or the harness poll where you can, and give the model a tool that waits (exercise 30.10) or tell it roughly when to check back.
:::

## 30.9 Gateways: one front door

Once a company has many servers, it stops letting every agent connect to each of them. It puts a **gateway** in front: agents connect to the gateway only, and the gateway connects to the servers.

@@code ch30_gateway.py::POLICY,Gateway.call_tool,Gateway._check

- **Deny by default.** Only the tools in `POLICY` exist behind the gateway. When a server adds a `delete_everything` tool, no agent sees it until someone adds it to the list.
- **Every call is authorized with Chapter 26's tokens.** A token names the agent, the user it acts for, the gateway as its audience and its scopes. The planner can add tasks but can't query sales; the analyst can query sales but can't add tasks.
- **Rate limits per agent** stop one runaway loop from overloading a server that others depend on.
- **One audit trail** records every call, allowed or refused, with the agent and the user, and with the arguments redacted as in section 28.3. That's where Chapter 28's traces start.

## 30.10 Registries and the supply chain

How do you find servers, and how do you know a server is what it claims to be? The **MCP Registry** (`registry.modelcontextprotocol.io`) is the official catalogue of public servers. It stores metadata, not code: a server's name, where to get its package (npm, PyPI, a Docker image) or its URL, and how to run it. Names follow a reverse-DNS pattern, such as `io.github.someone/weather`, and only the owner of that GitHub account or domain can publish under that name. That proves who published a server. It doesn't prove the code is safe; scanning is left to the package registries and to the marketplaces built on top of the registry. The registry is still in preview, so expect changes.

Companies usually run their own **private registry** too, with the same API, listing only the servers they've reviewed. Hosts point to it instead of the public one.

A sensible supply-chain policy, building on Chapter 14's server review:

- **Pin versions.** Install `server@1.4.2`, not "latest", and review the changes before you upgrade.
- **Watch the tool definitions.** A server can change a tool's description after you approved it, and a description is text the model reads, which makes it a way to inject instructions. A gateway can store a hash of each approved definition and refuse tools whose definition changed until someone reviews them.
- **Run third-party servers with the fewest rights** they need: their own container, a read-only token, no access to other secrets (Chapter 13's minimal environment).
- **Keep the gateway's allow-list** as the final word, whatever a registry says.

## 30.11 Authorization for companies {api}

Section 30.4 protected a remote server with a token. In a company those tokens come from OAuth, and the 2026-07-28 revision tightened that flow and added a company-wide option:

- **Issuer validation.** A client must now check that the authorization response came from the server it expected (the `iss` parameter from RFC 9207) before redeeming the code. This closes the "mix-up" attack, in which a malicious authorization server tricks a client into sending it a code meant for a different one.
- **Client ID Metadata Documents.** A client identifies itself with a URL pointing to a small JSON document that describes it. The old approach, Dynamic Client Registration, is deprecated: every client used to register itself with every server, which left servers with thousands of unverified registrations.
- **Enterprise-Managed Authorization**, an extension. Instead of every employee approving every server, the company's identity provider (Okta, Microsoft Entra ID and similar) decides. The client, signed in with the employee's company account, asks the identity provider for a signed grant for a particular server; the identity provider checks company policy (group, role, device); the server's authorization server exchanges that grant for an access token. Access is granted, and revoked, in one place.

Notice that all of this identifies the *user and the client application*. Which *agent* is acting, the question at the heart of Chapter 26, is still open. MCP's August 2026 roadmap makes **agent identity** one of its priorities, based on workload identity federation (the way cloud workloads prove who they are without stored secrets) and proof-of-possession tokens (DPoP), which are useless to anyone who steals them without the matching private key. Until that lands, use the pattern from Chapter 26 and section 30.9's gateway: the gateway verifies an agent token and records agent and user on every call.

## 30.12 From one agent to an agent platform

Everything so far ships one agent. Organizations rarely stop at one. Once a support team, a finance team and an engineering team each ship an agent, each team rebuilds the same pieces: keys for the model provider, a way to sign agents in, a gateway for tools, an eval suite, traces and a budget alarm. That is waste, and it is risk: five teams means five ways to store a secret and five audit trails that don't join up. The answer most organizations reach is a **platform team** that runs the shared services and offers **paved roads**, the supported, documented way to do each job, so a product team can ship an agent by writing its prompts, tools and evals, not its infrastructure.

This section is for the staff engineer, architect, engineering manager or CTO who has to plan that platform. You've already built a small version of every piece.

**Tenant isolation.** A platform serves many tenants: customers, business units or teams. Sharing compute is fine. Some things must never be shared:

- **Memory.** One tenant's memories must never be recalled for another. Every memory carries an owner and a scope, and recall filters on them before ranking, as in section 17.7.
- **Sessions.** A session belongs to the key or user that created it, and anyone else gets a 404, as in section 30.2.
- **Caches with private scope.** A cached tool list or result that depends on who asked is `private`, never served to another user (section 15.3). The same rule applies to any response cache you add.
- **Tokens.** Each agent gets its own short-lived token for each user it acts for, and a gateway never passes one caller's token to a server behind it (Chapter 26 and section 30.9).

Give each tenant its own keys, rate limits and budgets, so one tenant's traffic spike or looping agent can't exhaust another's allowance, and put the tenant id on every trace (section 28.1) so you can answer "which customers were affected?"

**Build, buy or run managed.** For each component you can build it, buy a product or use a managed service from a cloud or model provider. The trade-offs are the ones section 24.5 used for the agent runtime: control and portability against the time and people it takes to run the thing yourself. Buy or rent what isn't your advantage, build what is and keep the interfaces your own (OpenTelemetry for traces, MCP for tools, your own eval cases) so you can swap a component later without rewriting every agent.

Here's how that plays out for five components that most platforms need early. For each one, ask: *can we keep this running for three years without the core team becoming its on-call?* If not, buy or rent it. The conditions below are starting points for your own decision record (Appendix K), not thresholds that hold everywhere.

Table: Build or buy, for five platform components
| Component | Build it when | Buy or rent it when | Keep your own, either way |
| --- | --- | --- | --- |
| **Agent runtime and orchestration** | You have a few agents and the loop, retries and traces from this book are enough | Many teams ship agents and need queues, retries, isolation and support you'd otherwise build | The tool interfaces and the policy layer (sections 14.5 and 30.9) |
| **Memory and state** | The data is sensitive and the rules (section 17.10) are specific to you | You need replication, backups and expiry at high volume | The write gate, provenance and deletion rules |
| **Retrieval index** | The collection is small or changes constantly (section 6.6) | The collection is large and you'd rather not run index rebuilds | The evaluation set that measures retrieval (section 18.6) |
| **Observability** | Rarely: tracing at scale is hard to run well | Almost always; send OpenTelemetry so you can switch vendors (section 28.1) | The span names and attributes, and the SLO definitions |
| **Evaluation** | The checks and cases, which only you can write (Chapter 27) | The runner, dashboards and judge tooling around them | The suite itself and the release gate |

**What to standardize first.** You can't build everything at once. This order puts the risky, hard-to-change parts first:

1. **Identity and secrets.** Every agent gets an identity, and no key lives in code. Retrofitting identity after 20 agents ship is painful.
2. **Gateways.** A model gateway and an MCP gateway give you one place to enforce keys, budgets, allow-lists and logging.
3. **Tracing and cost attribution.** Every call carries agent, user, tenant and team, so you can see what fails and who pays.
4. **Evaluation gates.** No agent change ships without passing its suite in CI.
5. **Shared memory and retrieval.** Worth sharing once the first four are in place and teams keep building the same index.

**Governance.** When dozens of agents ship, someone must be able to answer four questions at any time: which agents exist, who owns each one, what each can touch, and who decided it could go live. The answers belong to the platform, not to each team's memory:

- **An agent inventory.** One record per agent: owner, kind (section 1.9), model, tools and scopes, the data it reads and writes, its risk tier and its current version. The identity registry from Chapter 26 is the natural home, because an agent without an identity can't call anything.
- **Launch review by risk tier.** A read-only helper for employees needs its eval suite and a named owner. An agent that acts on customers' money or data also needs a threat model and red-team results (Chapter 25), approval policies (Chapter 9), a scorecard (section 27.6) and a security sign-off. Write the tiers down so a team knows the bar before it builds.
- **Data retention and privacy.** Decide how long traces, memories and audit logs are kept, who may read them, and how a customer's request to delete their data reaches every store an agent wrote to (sections 17.6 and 28.3).
- **Regulation.** Laws are starting to apply to agents. The EU AI Act sorts AI systems into risk tiers: a few practices are banned, uses such as hiring, credit or education are high-risk and need risk management, logging, documentation and human oversight, and since August 2026 anyone talking to a chatbot must be told it's an AI. Map each agent in the inventory to the rules that apply where it runs, and check with your legal team; this book isn't legal advice.
- **Incident response.** Define severity levels, who may flip an agent's kill switch (section 26.7), and a rule that every incident ends with a postmortem and a new evaluation case (section 27.8).

## 30.13 The agent lifecycle in production

Section 1.10 named the stages of the agent engineering lifecycle. You've now built a piece of each, and {{t:lifecycle-now}} says where:

Table: The lifecycle stages you've now built {#t:lifecycle-now}
| Stage | What you have now |
| --- | --- |
| Decide and design | The questions of sections 1.3 and 1.9, decision records (Appendix K), the reference architecture (section 30.15) |
| Build | The loop, tools, MCP servers, context, memory, durable jobs, plans, teams and controls (Chapters 2–24) |
| Secure | A threat model (section 25.2), regression scenarios (section 25.10), a risk tier (section 25.11), identities and tokens (Chapter 26) |
| Evaluate | Case files, trials and intervals, trajectory checks and a scorecard (the measurement interlude, Chapter 27) |
| Optimize | Context engineering (Chapter 16), model routing (Chapter 20), cost and capacity models and the economics of section 29.9 |
| Deploy | A CI gate (section 27.7), a launch checklist (section 30.7) and a container you can deploy (section 30.6) |
| Operate | Traces, failure classes, SLOs and alerts (Chapter 28), budgets and capacity (Chapter 29) |
| Improve | Production samples graded and turned into new cases (section 27.8), and the improvement loop that takes a fix from those cases to production (section 30.14) |

Four parts of the lifecycle only matter once an agent has real users. They're short, but skipping any of them is how good agents cause bad incidents.

**Deploy gradually.** A new version (a new prompt, a new tool, a new model) shouldn't reach every user at once:

1. **Shadow.** Run the new version on a copy of real traffic without showing its answers or taking its actions. Grade both versions' answers with your checks and compare (the same `compare` idea as the measurement interlude, on real questions).
2. **Canary.** Send a small share of traffic, say 1% and then 10%, to the new version. Watch its SLOs and failure classes next to the old version's.
3. **Roll back without a deploy.** Keep the old version running and switch traffic back with configuration, not a code change. If the canary burns its error budget (section 28.10), roll back automatically.

Actions make shadowing harder: a shadow can't issue real refunds. Shadow the *decision* instead: record what the new version would have done, and compare it with what the current version did.

**Version the whole agent.** An agent's behavior comes from many parts, and any of them can change it. One release is the bundle: the model id, the system prompt, the tool definitions and MCP server versions, skills, policies and the eval suite that approved it. Give the bundle a version, put it on every trace (section 28.1) so an incident points to a release, and pin the model to a dated id rather than an alias that moves.

**Plan for the model to change.** Providers retire models on a published schedule, and a new model can be cheaper or better on average while worse for *your* agent. When a new model arrives: run your suite and scorecard on it, recalibrate any model judge against your human labels (section 27.2), compare cost per successful task (section 29.2), since a new tokenizer or more thinking changes the bill, then shadow and canary it like any other release. Subscribe to deprecation notices so a retirement date never arrives as a surprise.

**Retire it cleanly.** Agents get replaced, merged or switched off, and an agent that's half-retired still holds credentials:

- Tell its users, and send them somewhere else.
- Switch it off with the kill switch (section 26.7), then remove its routes from the gateways (section 30.9) and its entry from the inventory (section 30.12).
- Revoke its identity and every token derived from it (section 26.7).
- Apply the retention policy to its memories and sessions: delete what it shouldn't keep, export what it must (Chapter 17).
- Keep the audit log for as long as the policy says; it may be the record of what the agent did for whom.
- Cancel its scheduled jobs and leases (Chapter 19), and delete its secrets.

## 30.14 The agent improvement loop

You now have every piece needed to make an agent better on purpose: traces and failure classes (Chapter 28), suites, trials and a regression gate (the measurement interlude and Chapter 27), latency and cost you can measure (Chapter 29), and gradual release (section 30.13). Used one at a time, they're tools. Joined, they're the **agent improvement loop**: the routine that turns what went wrong in production into a release that's proven better before every user gets it. It's the heart of AgentOps.

```mermaid

flowchart TB
  A[Production traces and grades] --> B[Mine failures into eval cases]
  B --> D[Baseline: current release on the grown suite]
  D --> E[One change: prompt, skill, tool or model]
  E --> F[Offline evaluation]
  F -->|pass| G[Shadow]
  G -->|pass| H[Canary]
  H -->|pass| I[Promote]
  F -->|fail| X[Reject]

  H -->|fail| R[Roll back]
  X -.->|try another change| E
  I --> A
  R --> A
```

Figure: The agent improvement loop {#f:improvement-loop}
Alt: Production traces and grades feed failure mining, which produces new deduplicated, labeled eval cases. The current release is measured on the grown suite as the baseline, then a change to the prompt, a skill, a tool or the model makes a candidate. The candidate passes three gates in turn: offline evaluation, shadow and canary. Failing offline or in shadow rejects it, and a dotted arrow leads back to trying another change; failing the canary rolls it back. Promote and roll back both lead back to production traces.

Each stage takes something from the one before and hands something on, and every gate is decided by code against a threshold written down in advance:

Table: The stages of the improvement loop {#t:improvement-stages}
| Stage | Consumes | Produces | Who decides |
| --- | --- | --- | --- |
| Mine failures | Production traces and their grades (section 27.8) | Failed runs, each with its taxonomy classes (section 28.8) | `classify_detailed`: a failed grade or any class counts |
| Build cases | Failed runs, with a reviewer's label | New eval cases, deduplicated, each with its class and source trace | A person writes the expected answer; code removes duplicates |
| Baseline | The grown suite and the current release | Pass rates per case, with intervals | Nobody: it's the yardstick |
| Change | A failure class and its mitigation (section 28.8) | A candidate release with a new bundle version (section 30.13) | The engineer |
| Offline evaluation | Both versions on the suite, three trials per case | Pass rates, the gate's z, broken old cases, the mined-case pass rate | `gate` must not block, no old case may break, 90% of mined-case runs must pass |
| Shadow | Mirrored real requests | Paired grades for both versions; users see only the current one | `gate` must not block, and the candidate may be worse on at most 2% |
| Canary | 10% of real traffic | Each version's SLOs and error-budget burn (section 28.10) | Any missed SLO or a burn rate over 1 rolls back; fewer than 30 runs holds |
| Promote or roll back | Every stage's result | A decision record with the evidence; the new cases stay in the suite | Code, applying thresholds people agreed on in review |

**Mining failures.** The loop starts from runs that production already graded, the sample section 27.8 sends through checks, the judge and human review:

- **No new classifier.** Chapter 28's `classify_detailed` names the classes. A run that failed its grade but matches none is labeled `unclassified`, which tells you the taxonomy needs a new class (step 8 of section 28.12).
- **A trace says what happened, not what should have.** The expected answer comes from a reviewer. A failure without a label waits for review instead of becoming a case with a guessed answer, because a wrong expected answer teaches the gate to block the fix.
- **One problem, one case.** In the demo, 44 failed runs are three distinct problems. Without deduplication, the most frequent failure would fill the suite and outweigh everything else. `normalize` merges questions that differ only in case, spacing and punctuation; paraphrases need embedding similarity (section 18.3) and a person to confirm the group.
- **Each case remembers where it came from.** Its id starts with the failure class and its `source` is the trace id, so you can count cases per class and jump from a case back to the run that produced it.

An old case that passed every trial and now fails is a regression however good the average looks, and a change made to fix the mined cases has to fix them.

- **Shadow never shows its answers.** Users get the current version's answer; `shown` records exactly what they got, and the candidate's answer is graded and dropped. For an agent that acts, shadow the decision instead (section 30.13). The demo grades with the reviewer's label; on live traffic you'd use section 27.8's checks and calibrated judge, because nobody has written the expected answer yet.
- **The canary is production evaluation on a slice.** A stable hash sends 10% of requests to the candidate (in production, hash the user or the tenant, so one person doesn't bounce between versions). `measure_slos` from section 28.10 measures each side from its traces, and the burn rate is how fast that side spends its error budget: 1 means failing exactly as often as the objective allows, and 3.3 means failing 3.3 times as often (section 28.11). Release 1.5 is promoted. Release 1.6 gives the same right answers, so it passes offline evaluation and shadow, and the canary rolls it back: its answers take over nine seconds, against an 8-second p95 objective. Notice the current version's own burn rate of 3.3. That's why the loop ran: 1.4 was spending its error budget more than three times too fast. The demo also writes `release_decisions.json`, one record per candidate with the decision, the reasons, the thresholds it was held to and each stage's numbers, without raw traces or answers. Store it with the bundle version, so an incident can be traced to the release and to the evidence that let it out.

**How a failure stops coming back.** The three mined cases join the suite whatever the decision, because a rejected release doesn't make the failure less real. On the next turn, 1.5 is the baseline and passes them in every trial. Any later release that makes up the revenue figure again breaks an old case, and `max_broken` rejects it offline, before a single user sees it. That's how one bad answer in production becomes a test that runs on every release from then on.

**Who decides.** Every gate is a line of code and a number in `GATES`. People still make the decisions that need judgment: they write the labels, and they set the thresholds in review ahead of time, the way they set SLOs (section 28.10). Code applies them the same way every time, and the decision record shows which numbers it used. Overriding a gate means changing a threshold, in review, where everyone can see it.

This is an educational loop with fake agents that answer the same way every time. A production version mirrors traffic at the gateway (section 30.9), groups paraphrased failures with embeddings and a review queue, raises the canary in steps (1%, 10%, 50%) over hours with burn-rate alerts on two windows (section 28.11), rolls back by switching traffic in configuration, and compares cost per successful task, not only cost per task (section 29.2). Exercise 30.12 moves the latency check forward into shadow, so a slow release never reaches a user at all.

## Architect's Takeaway

Production systems need strong isolation: one tenant's mistakes shouldn't break others.

## Common mistakes

- **No authentication** "because it's internal".
- **One global rate limit** instead of per caller, so one client or one looping agent can starve everyone.
- **Session ids as the only protection** for conversations.
- **Returning stack traces** or logging prompts and keys. Secrets don't belong in images or logs either; scan both before shipping.
- **Long requests with no feedback**, so users retry and double the load.
- **No kill switch.** On-call engineers need to turn an agent off in seconds, without a code push.
- **No smoke test from the outside.** Test the public URL with wrong keys, load and unhappy paths, not only the happy one.
- **Every team building its own gateway, identity and eval stack**, so no one can answer what all the agents cost or did.
- **Sharing a cache, memory store, database table or token across tenants** because it was simpler.
- **Tools that block for minutes** instead of starting a job and returning, or jobs started without an idempotency key, so a retried call does the work twice.
- **Letting the model poll in a tight loop**, paying for every check.
- **Trusting a gateway header without checking the body**, or passing an agent's token straight through to the servers behind the gateway.
- **Showing every tool to every agent** when search and a scoped allow-list would do.
- **Treating a registry listing as a security review.** It proves who published a server, not that it's safe.
- **Building shared memory first** and identity, gateways and tracing last.
- **Fixing a production failure without adding its case**, so the next release brings it back, or promoting a change because it looked better instead of because gates with written thresholds passed.

## Summary

- An agent service needs auth, per-caller rate limits, private sessions, budgets and clean errors.
- Stream progress with Server-Sent Events so long runs feel responsive.
- Remote MCP servers run over Streamable HTTP (MCP's HTTP transport) and must be authenticated.
- Configuration and secrets come from the environment; logs record ids and numbers, not content.
- Deploy a small, non-root image with secrets given at run time, limits on instances and cost and a smoke test against the public HTTPS URL.
- Long-running tools return a job handle at once, run durably and are safe to retry; MCP's Tasks extension standardizes the same shape.
- A gateway gives one place to allow-list tools, check agent tokens, rate-limit, cache and audit, and can offer tools through search.
- Registries verify publishers, not code: pin versions, watch tool definitions and keep your own allow-list. Company sign-on is moving to issuer validation, client metadata documents and enterprise-managed authorization.
- When many teams ship agents, a platform team provides shared gateways, identity, policy, memory, workflow, evaluation, observability and cost controls as paved roads. Standardize identity and secrets first.
- Memory, sessions, private caches and tokens are never shared between tenants; each tenant gets its own keys and budgets.
- Govern agents with an inventory, launch reviews by risk tier, retention rules, a map to regulation and an incident process.
- Release gradually (shadow, canary, rollback), version the whole agent, plan for model retirements and retire agents cleanly.
- The improvement loop mines production failures into deduplicated, labeled cases, then gates a change offline, in shadow and in a canary with code and thresholds, and records the evidence. Every failure it finds stays in the suite, so it can't come back unnoticed.
- The reference architecture (user or API, runtime, model, MCP, APIs and A2A, environment, with evaluation and observability across all layers) places every agent you build.

That completes Part 9 and the chapters. The capstone projects come next: larger builds where you combine tools, memory, retrieval, evaluation and deployment into complete agents of your own design.
