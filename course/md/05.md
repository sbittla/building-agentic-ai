# Chapter 5: State and Short-Term Memory

So far your agents forget everything the moment the program exits. In this chapter you'll give an agent state that outlives a session: a to-do list stored in a file, which the model reads and changes only through tools. Along the way you'll learn to make tools safe to call twice and to have the agent ask a question when a request is ambiguous.

**What you'll build:** a to-do agent whose state survives restarts, with tools that are safe to retry.

**You are here:** Memory  — Intermediate(state) in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Explain the difference between conversation history and persistent state.
- Build tools that read and write state stored outside the model.
- Design tools that are safe to call twice (idempotent).
- Make an agent ask a clarifying question instead of guessing.

## 5.1 Two kinds of memory

|  | Conversation history | Persistent state |
| --- | --- | --- |
| Where it lives | The `messages` list in your program | A file, database or service |
| Lifetime | One session; gone when the program exits | Until you delete it |
| Who changes it | Appended every turn | Only tools, when the model calls them |
| Size limit | The model's context window | Your disk |
| Example | "Earlier you said your name is Srini" | The tasks in `tasks.json` |

The model itself remembers nothing. Everything it "knows" about the past is either resent in the history or fetched by a tool. The history is the agent's **short-term memory**: what happened in this session. The task list is **state**: the facts the agent works on, kept outside the model. In this chapter the source of truth is a file, and the model touches it only through tools. Long-term memory about the user (preferences, past decisions, lessons learned) is a harder problem with its own rules, and gets its own chapter: Chapter 17.

## 5.2 The to-do tools

@@code ch05_todo_tools.py::_load,_save,add_task,complete_task,find_tasks,today

Walk through the design:

- **`_save` writes to a temporary file, then renames it.** The rename happens in one step, so a crash mid-write never leaves you with half a JSON file.
- **Tasks have numeric IDs.** Titles can repeat or be vague ("the milk thing"), but IDs are exact. `complete_task` takes an ID, and the model uses `find_tasks` to turn words into IDs.
- **The `today` tool.** "What's due this week?" needs today's date, and the model has no clock.

## 5.3 Idempotent tools

A tool is **idempotent** if calling it twice has the same effect as calling it once. Agents retry and models sometimes repeat a call, so make tools that change state idempotent where you can:

- `add_task` checks for an open task with the same title and returns "Already exists" instead of adding a duplicate.
- `complete_task` on a finished task returns "already done" instead of an error.

For every tool that changes something, ask: "What happens if the agent calls this twice?"

## 5.4 Ambiguity: ask, don't guess

"Complete the milk task" is clear when there's one milk task. With "Buy milk" and "Buy oat milk", the agent must not guess. Two things make it ask:

1. `find_tasks` returns **all** matches, so the model can see there's more than one.
2. The `complete_task` description says: "If several tasks could match the user's words, ask the user which one first."

A clarifying question is a normal final answer. The loop ends, the user replies and the next `run_agent` call continues with the history. You need no special code.

:::tip Put behavior rules where the model looks
Rules about a tool belong in the tool's description. Rules about the whole agent belong in the system prompt. The model reads both on every call.
:::

## 5.5 Choosing a storage backend

| Backend | Good for | Watch out for |
| --- | --- | --- |
| JSON file | Learning; single user; under a few thousand records | Two processes writing at once can lose data |
| SQLite | Single machine; queries; up to millions of rows | Locking under heavy concurrent writes |
| Postgres or a hosted DB | Many users, many agents, production | Needs setup, credentials and migrations |
| MCP Memory server | Sharing memory across different agent apps | Another process to run and secure |

Start with JSON. Move to SQLite when you need queries or safety under concurrency, meaning several processes writing at once (exercise 5.7).

## 5.6 What the agent should (and shouldn't) remember

Long-term memory is powerful but risky. Chapter 17 builds it properly, with kinds, owners, expiry and defenses against planted memories. Until then, before you store something, ask:

- **Is it durable?** A task, yes. "The user is in a meeting right now", no.
- **Is it the user's to share?** Don't store secrets, passwords or other people's private details.
- **Can the user see and delete it?** Good memory systems are inspectable, like a JSON file you can open.

:::note The support agent so far
The support agent gets state. Open cases and their notes live in storage outside the model, changed only through tools that are safe to call twice, so a restart or a retried call never loses or duplicates a case. When a customer's request is ambiguous ("cancel my order" with three open orders), the agent asks instead of guessing.
:::

## Architect's Takeaway

Episode boundaries drive memory costs: choose them by session, not by time.

## Common mistakes

- **Letting the model "remember" tasks in history only.** They vanish on restart.
- **Completing tasks by title.** "Complete milk" hits the wrong task. Use IDs.
- **Non-atomic writes** that corrupt the file on a crash.
- **Tools that fail on repeats** instead of being idempotent.
- **Guessing on ambiguity** instead of asking the user.

## Summary

- History lasts one session. Persistent state lives outside the model and is changed only by tools.
- Use exact identifiers (IDs) for anything a tool changes, and give the model a way to look them up.
- Make state-changing tools idempotent, because agents repeat calls.
- When a request is ambiguous, the right answer is a question.
- Choose storage by scale and concurrency: JSON, then SQLite, then a database.

:::

:::ex Medium | 5.6 | Clarify, don't guess
Add "Buy milk" and "Buy oat milk", then say "complete the milk task". Make sure the agent asks which one. Reply "the oat one" and check that it completes the right task.
**Done when:** A transcript shows the question, your answer and the correct completion.
:::

:::ex Complex | 5.7 | Move to SQLite
Replace the JSON store with SQLite behind the same tool functions, so the model sees no difference. Write a one-time migration from `tasks.json`, add unit tests for every tool, and run two agent processes at once to show that SQLite handles concurrent writes where JSON loses data.
**Hint:** Use `sqlite3` with a `UNIQUE` index on lowercase title for open tasks.
**Done when:** Tests pass, migration works, and you have a demo of the concurrency difference.
:::
