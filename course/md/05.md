# Chapter 5: State and Short-Term Memory

Tell your Chapter 4 agent to add "renew passport" to your list. Restart the program and ask what's on the list. It has never heard of your passport. Nothing broke: the list only ever lived in `messages`, and `messages` died with the process. An agent you can rely on tomorrow needs somewhere to keep things that isn't the conversation.

**What you'll build:** a to-do agent whose state survives restarts, with tools that are safe to retry.

**You are here:** Memory (state) in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop).

## Learning objectives

By the end of this chapter you can:

- Tell conversation history from persistent state.
- Build tools that read and write state stored outside the model.
- Design tools that are safe to call twice (idempotent).
- Make an agent ask instead of guessing.

**In the real world.** Coding agents keep a running task list outside the model, and the reference MCP **Memory** server gives any agent a persistent knowledge graph (facts and the links between them). In Chapter 13 you'll turn this chapter's to-do tools into an MCP server.

## 5.1 Two kinds of memory

Table: Conversation history and persistent state
|  | Conversation history | Persistent state |
| --- | --- | --- |
| Where it lives | The `messages` list in your program | A file, database or service |
| Lifetime | One session; gone when the program exits | Until you delete it |
| Size limit | The model's context window | Your disk |
| Example | "Earlier you said your name is Srini" | The tasks in `tasks.json` |

The model remembers nothing. Everything it "knows" about the past is resent in the history or fetched by a tool. The history is the agent's **short-term memory** (Chapter 17 calls it *working memory*). The task list is **state**: the facts the agent works on, kept outside the model. Long-term memory about the user is a harder problem, and it gets Chapter 17 to itself.

Some choices in this file are worth a second look. `_save` writes to a temporary file and then renames it. The rename happens in one step, so a crash mid-write never leaves half a JSON file. ## 5.3 Idempotent tools

A tool is **idempotent** if calling it twice has the same effect as calling it once. If that sounds like a big word for a small idea, it is, but the idea matters: agents retry and models repeat calls, so make state-changing tools idempotent where you can. `add_task` returns "Already exists" when an open task has the same title, and `complete_task` on a finished task returns "already done" instead of an error. For every tool that changes something, ask what happens if the agent calls it twice.

## 5.4 Ambiguity: ask, don't guess

"Complete the milk task" is clear until "Buy oat milk" sits next to "Buy milk". Then the agent must not guess. It asks when it can see the ambiguity and knows what to do about it:

1. `find_tasks` returns **all** matches, so the model sees there's more than one.
2. The `complete_task` description says: "If several tasks could match the user's words, ask the user which one first."

A clarifying question is just a final answer. The loop ends, the user replies, and the next `run_agent` call picks up from the history. You write no special code.

:::tip Put behavior rules where the model looks
Rules about a tool go in its description; rules for the whole agent go in the system prompt. The model reads both on every call.
:::

## 5.5 Choosing a storage backend

Table: Storage backends for agent state
| Backend | Good for | Watch out for |
| --- | --- | --- |
| JSON file | Learning; single user; under a few thousand records | Two processes writing at once can lose data |
| SQLite | Single machine; queries; up to millions of rows | Locking under heavy concurrent writes |
| Postgres or a hosted DB | Many users, many agents, production | Needs setup, credentials and migrations |
| MCP Memory server | Sharing memory across agent apps | Another process to run and secure |

Start with JSON. Move to SQLite when you need queries or when several processes write at once (exercise 5.7).

## 5.6 What the agent should (and shouldn't) remember

Chapter 17 builds long-term memory properly. Until then, ask yourself before you store anything:

- **Is it durable?** A task, yes. "The user is in a meeting right now", no.
- **Is it the user's to share?** Don't store passwords or other people's private details.
- **Can the user see and delete it?** A JSON file you can open passes this test.

:::note The support agent so far
The support agent gets state. Open cases live outside the model, changed only by tools that are safe to call twice, so a restart or retry never loses or duplicates a case. Faced with "cancel my order" and three open orders, it asks which one.
:::

## Common mistakes

- Keeping tasks only in the history. They vanish on restart.
- Completing tasks by title. "Complete milk" hits the wrong task. Use IDs.
- Non-atomic writes that corrupt the file on a crash.
- Tools that fail on a repeat call.
- Guessing when the request is ambiguous.

## Key takeaways

**Architect's takeaway:** Decide what lives in the history and what lives in state before you write a tool. Only state survives a restart, and only tools should change it.

- History lasts one session; state lives outside the model and only tools change it.
- Change things by exact ID, and give the model a tool to look IDs up.
- Make state-changing tools idempotent, because agents repeat calls.
- When a request is ambiguous, the right answer is a question.
- Grow storage with scale: JSON, then SQLite, then a database.
