# Chapter 2: Tool Calling (Function Calling)

What is 17.5% of 84,213? A model will answer at once, with total confidence, and whether the digits are right is partly luck. The fix is to let the model hand the arithmetic to your code. It looks like a small trick, but it's the first step from chatbot to agent, and every chapter after this one stands on it.

**What you'll build:** a calculator agent that calls a safe tool you wrote, handles errors and explains its answer.

**You are here:** Tools in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 1 (agent basics).

## Learning objectives

By the end of this chapter you can:

- Describe a tool to a model with a name, a description and a JSON Schema.
- Follow the `tool_use` → `tool_result` round-trip in code.
- Write a tool that is safe to expose to a model.
- Return tool errors the model can recover from.

**In the real world.** Finance, invoicing and analytics assistants never trust the model's arithmetic. They hand calculations to code, just as this chapter's calculator agent does, and the same split sits behind support bots that look up orders and coding agents that run tests.

## 2.1 What a tool is

A **tool** is an ordinary function in your program plus a description the model can read:

- **name**: how the model refers to the tool (`calculate`).
- **description**: plain English explaining when and how to use the tool. It matters most, because it's all the model knows about the tool.
- **input_schema**: a JSON Schema (a standard format for describing the structure of JSON data) for the arguments, so the model knows what to send.

The model never sees your Python code. It decides from the description alone whether to call the tool. The MCP tools of Chapter 12 use the same three parts.

Your second tool evaluates arithmetic. The tempting version is `eval(expression)`. **Never do this.** The expression comes from the model, and the model's input can come from users or documents. `eval("__import__('os').system('rm -rf ~')")` is valid Python.

:::warn Tools are an attack surface
Anything a tool can do, an attacker who controls the model's input can try to make it do. Design for the worst input, not the expected one.
:::

## 2.4 The round-trip, step by step

Look at `ask` in the file above. One tool call takes two model calls:

1. **You send** the question and the `TOOLS` list.
2. **The model replies** with `stop_reason == "tool_use"` and a block like `{"type": "tool_use", "id": "toolu_01…", "name": "calculate", "input": {"expression": "0.175 * 84213"}}`.
3. **Your code runs** `calculate("0.175 * 84213")` and gets `"14737.275"`.
4. **You send back** the whole conversation: the question, the model's `tool_use` message and a new user message holding a `tool_result` block with the same `tool_use_id`.
5. **The model replies** with a text answer that uses the result.

The `tool_use_id` links each result to its request. Ask for three tools at once and you return three results, each with its own ID.

If two model calls and a hand-built conversation feel like a lot of ceremony for one multiplication, they are, for now. Chapter 4 wraps this round-trip in a loop you write once and never think about again.

:::tip Why the result goes in a "user" message
To the model, everything that isn't the model is the "user" side of the conversation, including your tool results. So they're sent with `role: "user"`.
:::

:::tip The same concept on other platforms
OpenAI and Google call tool calling *function calling*, and open-source servers such as Ollama and vLLM offer it through OpenAI-compatible APIs; the kit's local-model adapter translates between the two formats for you. The loop is the same everywhere: describe tools, let the model ask, run the tool in your code, send back the result. Appendix J maps every concept in the book to other providers.
:::

## 2.5 Writing descriptions that work

Compare two descriptions for the same tool:

Table: A weak and a strong tool description
| Weak | Strong |
| --- | --- |
| "Calculator." | "Evaluate an arithmetic expression exactly. Use this for ANY arithmetic, including percentages (write 17.5% of X as `0.175*X`). Supports `+ - * / ** %` and parentheses." |

The strong version tells the model **when** to use the tool ("ANY arithmetic"), **how** to format the input (percentages as decimals) and **what** is supported. Good descriptions are the cheapest way to improve an agent. Start with what the tool does, in one sentence. Say when to use it and, if needed, when not to. Give an example input in the parameter description, and use `enum` when only certain values are valid. Chapter 3 shows you how to measure the effect.

## 2.6 Errors are data

Tools fail: bad input, division by zero, a timeout. If your tool raises, your program crashes and the model never learns what went wrong. So catch the error and send it back as the tool result with `is_error: true`:

```
try:
    output = calculate(**block.input)
    is_error = False
except Exception as exc:
    output = f"ERROR: {type(exc).__name__}: {exc}"
    is_error = True
results.append({"type": "tool_result", "tool_use_id": block.id,
                 "content": output, "is_error": is_error})
```

Now the model sees `ERROR: ZeroDivisionError: division by zero` and can explain it or try a different expression. You'll use this pattern in every chapter from here on.

## Common mistakes

- Using `eval`, or any tool that runs arbitrary code, without a sandbox (an isolated environment that limits what code can touch).
- Vague descriptions, so the model does math in its head.
- A mismatched or missing `tool_use_id`. The API rejects the request.
- Returning non-string results. Convert to text or JSON first.
- Letting exceptions escape. One bad input crashes the whole agent.

## Key takeaways

**Architect's takeaway:** A tool is a contract with the model. A clear description gets it used correctly, and strict input checks keep it safe when it is misused.

- A tool is a function plus a name, a description and a JSON Schema.
- The model asks with a `tool_use` block; your code runs it and replies with a `tool_result` carrying the matching ID.
- The description is the model's only guide, so write it carefully.
- Treat every tool input as untrusted; never `eval` it.
- Return errors as data with `is_error: true` so the model can recover.
