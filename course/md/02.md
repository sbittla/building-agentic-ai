# Chapter 2: Tool Calling (Function Calling)

A model on its own can only produce text: it can't check today's date or do exact arithmetic. Tools fix that, and they're what turns a chatbot into an agent. In this chapter you'll build two tools, a date lookup and a safe calculator, and wire each one into the round-trip where the model asks for a tool and your code runs it. You'll also learn to write descriptions the model follows and to return errors it can recover from.

**What you'll build:** a calculator agent that calls a safe tool you wrote, handles errors and explains its answer.

**You are here:** Tools in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Describe a tool to a model with a name, a description and a JSON Schema.
- Follow the full `tool_use` → `tool_result` round-trip in code.
- Write a tool that is safe to expose to a model.
- Return tool errors in a way the model can recover from.

## Real-world connection

Finance, invoicing and analytics assistants never trust the model's arithmetic. They hand calculations to code, the same way this chapter's calculator agent does. "The model decides, code computes" is behind every production agent, from support bots that look up orders to coding agents that run tests.

## 2.1 What a tool is

A **tool** is an ordinary function in your program plus a description the model can read. The description has three parts:

- **name**: how the model refers to the tool (`calculate`).
- **description**: plain English explaining when and how to use the tool. This is the most important part, because it's all the model knows about the tool.
- **input_schema**: a JSON Schema (a standard format for describing the shape of JSON data) that describes the arguments, so the model knows what to send.

The model never sees your Python code. It sees only the description and decides from that alone whether to call the tool. The same three parts reappear in Chapter 12, when you publish tools as an MCP server: MCP uses the same name, description and JSON Schema, so nothing you learn here is wasted.

## 2.4 The round-trip, step by step

Look at the `ask` function in the file above. One tool call takes two model calls:

1. **You send** the question plus the `TOOLS` list.
2. **The model replies** with `stop_reason == "tool_use"` and a content block like `{"type": "tool_use", "id": "toolu_01…", "name": "calculate", "input": {"expression": "0.175 * 84213"}}`.
3. **Your code runs** `calculate("0.175 * 84213")` and gets `"14737.275"`.
4. **You send back** the whole conversation: the original question, the model's `tool_use` message and a new user message containing a `tool_result` block with the same `tool_use_id`.
5. **The model replies** with a normal text answer that uses the result.

The `tool_use_id` links each result to the request it answers. If the model asks for three tools at once, you return three results, each with its own ID.

:::tip Why the result goes in a "user" message
From the model's point of view, everything that isn't the model is the "user" side of the conversation, including your tool results. That's why tool results are sent with `role: "user"`.
:::

:::tip The same concept on other platforms
Tool calling is a concept, not a Claude feature. OpenAI and Google call it *function calling*, and open-source servers such as Ollama and vLLM offer it through OpenAI-compatible APIs; the kit's local-model adapter translates between the two shapes for you. The loop is the same everywhere: describe tools, let the model ask, run the tool in your code, send back the result. Appendix J maps this and every other concept in the book to other providers.
:::

## 2.5 Writing descriptions that work

Compare two descriptions for the same tool:

Table: A weak and a strong tool description
| Weak | Strong |
| --- | --- |
| "Calculator." | "Evaluate an arithmetic expression exactly. Use this for ANY arithmetic, including percentages (write 17.5% of X as `0.175*X`). Supports `+ - * / ** %` and parentheses." |

The strong version tells the model **when** to use the tool ("ANY arithmetic"), **how** to shape the input (percentages as decimals) and **what** is supported. Good descriptions are the cheapest way to improve an agent, and you'll measure their effect in Chapter 3.

Guidelines:

- Start with what the tool does, in one sentence.
- Say when to use it and, if needed, when **not** to.
- Give an example input in the parameter description.
- Use `enum` in the schema when only certain values are valid.

## 2.6 Errors are data

Tools fail: bad input, division by zero, a network timeout. If your tool raises an exception, your program crashes and the model never learns what went wrong. Instead, catch the error and send it back as the tool result, with `is_error: true`:

```
try:
    output = calculate(**block.input)
    is_error = False
except Exception as exc:
    output = f"ERROR: {type(exc).__name__}: {exc}"
    is_error = True
results.append({"type": "tool_result", "tool_use_id": block.id,
                 "content": output, "is_error": is_error})
```

Now the model sees `ERROR: ZeroDivisionError: division by zero` and can explain it to the user or try a different expression. Turning exceptions into messages makes agents robust, and you'll use this pattern in every chapter from here on.

## Architect's Takeaway

Tools are contracts with models: clear input specs prevent injection attacks.

## Common mistakes

- **Using `eval`**, or any tool that runs arbitrary code, without a sandbox (an isolated environment that limits what the code can touch).
- **Vague descriptions**, so the model does math in its head instead of calling the tool.
- **A mismatched or missing `tool_use_id`.** The API rejects the request.
- **Returning non-string results.** Convert them to text or JSON first.
- **Letting exceptions escape.** One bad input crashes the whole agent.

## Summary

- A tool is a function plus a name, a description and a JSON Schema.
- The model asks for a tool with a `tool_use` block. Your code runs it and replies with a `tool_result` that has the matching ID.
- The description is the model's only guide, so write it carefully.
- Treat every tool input as untrusted; never `eval` it.
- Return errors as data with `is_error: true` so the model can recover.

You now know how to build a tool, but not yet whether the model uses it well. Chapter 3 shows you how to measure that, so you can tell whether a change to a description or prompt actually helps.
