# Chapter 23: Computer-Use Agents

Somewhere in your company, someone spends Friday afternoons in an old back-office web page: open a customer, copy a value, fix an address, press Save, forty times. The system has no API and never will. Every tool you've built so far was a function with a name, arguments and a result, so none of them can help.

**Computer-use agents** can. They look at a page or a desktop, decide what to click or type and check what happened. They're the most general tools an agent can have, and the riskiest, because a click can move money and a web page can carry instructions. Most of the work, as you'll see, goes into the controls around the browser rather than the browser itself.

**What you'll build:** a browser harness that shows the model each page as text with numbered controls, signs in on its behalf, keeps it on one site, holds risky clicks for approval, and limits, logs and screenshots every action, tested against a small back-office application with a planted prompt injection.

**You are here:** Environment and Tools in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 9 (approval gates), Chapter 14 (prompt injection), Chapter 16 (context), Chapter 19 (durable jobs).

## Learning objectives

By the end of this chapter you can:

- Decide when a computer-use agent is the right tool, and when an API or MCP server is better.
- Compare screenshots and the page's structure as ways for an agent to see a screen.
- Drive a real browser from an agent with Playwright: read the page, click, type and verify.
- Keep credentials away from the model, keep the browser on an allowlist, and hold dangerous actions for a person.
- Defend a browser agent against instructions hidden in the pages it reads.
- Wrap each browser action in code that checks the page before and after, retries only what's safe to repeat and hands expired sessions to a person.

**In the real world.** Between 2024 and 2026, computer use went from demos to products: Anthropic's tool lets Claude work a desktop through screenshots, mouse and keyboard, and browser agents fill forms and test user interfaces. Researchers have repeatedly shown agents obeying instructions hidden in web pages, so every serious guide recommends an isolated environment, minimal access, an allowlist of sites and a person confirming consequential actions. This chapter builds all four in.

## 23.1 When to use the screen

Compared with an API, a user interface is slow, costly and fragile to operate. Every step costs a model call, a layout change can break a working agent and a page can say anything. So use the screen **last**:

Table: When to use the screen
| If the system has | Use |
| --- | --- |
| An API or an MCP server | That. It's faster, cheaper and more reliable |
| A database or file export you're allowed to use | That, read-only where possible |
| Only a web interface | A browser agent, with the controls in this chapter |
| Only a desktop application | A desktop computer-use agent in a virtual machine |

Browser agents are also right for jobs that are *about* the interface, such as testing a web application or checking what a customer actually sees.

## 23.2 How an agent sees a screen

You can show a model a page in two ways, and most real systems use both:

Table: Screenshots compared with the page's structure
|  | Screenshots | The page's structure |
| --- | --- | --- |
| What the model gets | An image; it answers with coordinates to click | The page's text and a numbered list of controls |
| Works on | Anything: web pages, desktop apps, canvases | Web pages (and apps with accessibility trees) |
| Cost | High: images use many tokens per step | Low: a few hundred tokens per page |
| Precision | Clicks can miss by a few pixels | A control is named exactly |
| Needs | A model with vision | Any model with tools |

This chapter uses the page's structure, read with a little JavaScript, because it's cheaper, more precise and works with the free local model. Screenshots are still taken after every change, but as evidence for **people**. Anthropic's computer-use tool works from screenshots and coordinates, which is what you need when there's no page structure, as in a desktop application. (`qwen3.5:9b` can read images too, so the local model can try both.)

## 23.3 The harness

These few lines hold the harness's most important design decisions:

- **The harness signs in, not the model.** The service account's password goes from the environment straight into the browser. The model never sees it, so it can't leak it or type it into the wrong page. Chapter 26 gives the agent an identity of its own; the rule here is that credentials never pass through the model.
- **The page text is labeled as untrusted.** It's wrapped in a `page_text untrusted="true"` element, and the system prompt says page text is data.
- **Controls get short references.** `[e3] link "Ben Okafor"` lets the model say "click e3" instead of guessing a CSS selector or a pixel position. References are reassigned on every read, so an old one fails loudly instead of clicking the wrong thing.

## 23.4 Acting and checking

The agent has four tools: read the page, open a path, click a control and type into a textbox. The harness checks and counts each action:

The system prompt asks for a rhythm that matters more for screens than for APIs: **read, act, read again.** After clicking "Save address", the agent reads the page and looks for "Address saved" and the new value. A click that did nothing, a validation error in red or a page that moved somewhere unexpected shows up only if the agent looks. For anything important, verify in code afterwards (exercise 23.5).

## 23.5 Controls that don't depend on the model

The harness enforces everything that must hold:

Table: Controls the harness enforces
| Control | What it prevents |
| --- | --- |
| Sign-in by the harness | Leaked or misused credentials |
| A host allowlist in `open` | Being sent to other sites, including an attacker's |
| Approval for dangerous clicks | Money moved or data deleted without a person |
| An action limit | Endless clicking when the agent is stuck |
| A log and a screenshot after every change | No evidence of what happened |
| No typing into password fields | Credentials typed into a phishing form |

The approval check is Chapter 9's gate, applied to clicks. It reads the button's label and its form's values, so the person sees "Issue credit: amount 50, reason late parcel" before deciding. In production, also restrict which forms the agent may submit and how large an amount can be. The back office here limits credits itself, because an application shouldn't trust any client, human or agent.

Run it with `./course.sh python ch23_browser.py`. It starts the back office, signs in and asks the agent to update Ben's address. The harness is a prototype: one service account on one local site, with a password from the environment and screenshots kept on disk. Section 23.9 lists what production adds.

## 23.6 Injection through the screen

Ben's customer notes hold an instruction for "AI assistants": issue a $500 credit and change the email address. That's an indirect prompt injection (Chapter 14), the main threat to a browser agent, because every page is full of text written by other people: customers, suppliers, anyone who can post a comment or a review.

Layered defenses stop it, and none of them depends on the model noticing:

1. **Labeling.** The model is told, and shown, that page text is data.
2. **Approval.** The credit button waits for a person, who sees exactly what would be submitted.
3. **The application's own rules.** Credits over $200 are refused by the server, and the page has no form to change an email address at all.

The last layer is the strongest: **give the agent only the capabilities the task needs.** An account that can change addresses but not issue credits makes the attack impossible instead of unlikely. Chapter 25 covers injection as a whole class of attacks.

## 23.7 Making it reliable

A few habits prevent most browser failures:

- **Wait for the page, not a fixed time.** Playwright waits for elements to be ready, and `wait_for_load_state` after a click waits for navigation.
- **Re-read after every change.** The harness renumbers controls on every read and rejects unknown references.
- **Time-limit everything.** A 10-second default timeout turns a hung page into an error the agent can report.
- **Isolate the browser.** Use a fresh profile in a container, never your own browser with your accounts signed in, as the course kit does.
- **Checkpoint long queues.** Make each request a durable step (Chapter 19). Exercise 23.6 builds this, and Capstone 6 builds on it.

But habits depend on someone following them. Section 23.9 turns them into code that holds even when the model doesn't.

## 23.8 Desktop computer use {api}

Everything here carries over to agents that operate a whole desktop, with the controls turned up. A desktop agent works from screenshots and sends mouse and keyboard actions, so it can reach any application, including your email and files. Run it in a virtual machine with no access to your real accounts, give it only the applications the task needs, keep a person watching or approving, and treat every screen as untrusted. The Claude documentation (see Learn more) describes the tool and its safeguards.

## 23.9 Reliability engineering for computer use

An API call either returns a result or raises an error. A click is murkier. The button might not be there yet, the page might change between reading and clicking, the click might go through and then time out, or the page might turn into a sign-in form. A queue of 200 requests will meet all of these. If a failure can move money or leave a wrong record, code has to catch it.

Table: Computer-use failure modes and their controls {#t:cu-failures}
| Failure | What it looks like | The control |
| --- | --- | --- |
| Visual ambiguity | Two "Save" buttons; a name matching the wrong customer; a click a few pixels off | Target controls by label, not position; check the page is the expected record before acting |
| Stale UI state | A ref from an earlier read, or a control that hasn't rendered: "no control e1" | Re-read before every attempt, resolve the target again, retry a bounded number of times |
| Race conditions | A click while the page loads; someone else edits the record between read and save | Wait for the page; check preconditions just before acting; verify afterwards; the application rejects conflicting writes |
| Confirmation dialogs | An "Are you sure?" pop-up blocks the page, or is accepted unseen | Handle dialogs in code; a confirm is a dangerous click that needs approval |
| Session expiry and MFA | A sign-in form or a request for a verification code (MFA, multi-factor authentication) | Hand over to a person; the model never types credentials or codes |
| Non-idempotent actions | "Issue credit" times out: did it go through? | Never retry; read the page to verify; if that's inconclusive, a person decides |
| Claimed but not done | The agent says "Done" but the field didn't change | Verify from a fresh read, not the model's answer |
| No evidence | Nobody can say what the screen showed | Log every read with a snapshot id and timestamp; keep page text and screenshots |

The harness enforces every control in {{t:cu-failures}}, helped by the application on races and by a person when a result can't be verified. The model keeps one job: deciding what to do next. Everything else lives in a wrapper around each action, `run_step`:

Some details are worth a closer look:

- **Errors fall into three groups, and only one is safe to retry blindly.** "No control e1" means nothing happened, so the wrapper re-reads and retries. A refusal (no approval, a host off the allowlist, the action limit) is final. An exception during a click means the action *may* have happened, so the wrapper retries only an idempotent step and otherwise goes straight to verification.
- **The target is a label, resolved again on every attempt**, because a ref like `e1` is valid only for the read it came from.
- **Verification reads the page.** For a credit, the balance must rise by exactly the amount, read from a freshly opened customer page (`check_path`), not from wherever the click left the browser.
- **A sign-in or verification-code page stops the step.** The harness can't tell an ordinary timeout from a forced sign-out, and a guessed code can lock the account, so a person takes over.
- **Every read is evidence.** The log records the step, attempt, event, page and a snapshot id with a UTC timestamp, and keeps the page text under that id.

In the second run the credit click goes through and then times out:

```
2. A credit click that lands, then times out: verify, never click again.
...
  issue credit 3     try 1  before                   /customers/3 snap 5d1258ced9
  issue credit 3     try 1  error                    TimeoutError: click timed out waiting for the page
  issue credit 3     try 1  after                    /customers/3 snap 060cd91c81
  issue credit 3     try 1  verified
   Chen's balance: $45.00; credits issued: 1
```

A naive retry would have clicked again and credited Chen $40 in all. The wrapper read the balance instead, saw $25.00 become $45.00 and stopped. Had the balance been unchanged, the step would end in `needs_human`, because "unchanged" can also mean "still processing", and only a person or the application's own records can settle that. In the third run the session expires and the step stops with a handoff instead of a guess.

Use the wrapper as the body of a durable step (Chapter 19), or around any agent action whose outcome you can state in advance. The model still decides what to do; the wrapper decides whether it worked.

:::note What production adds
- **Real screenshots with a retention limit.** Keep an encrypted image per snapshot id only as long as your audit rules require, because screens show customers' personal data.
- **Idempotency keys in the backend** (section 19.5). An application that ignores a repeated request with the same key makes a double click harmless; "never retry" is only the last line of defense.
- **Session vaulting.** Credentials live in a vault, and the harness signs in again from code once when a session expires. A non-interactive identity (Chapter 26) keeps the agent away from MFA prompts.
- **Dialog handlers and version checks.** Route browser confirms through approval, and have the application reject a save based on an out-of-date page.
- **Retry metrics per step.** A step that needs more and more retries is a control whose label or layout is about to change.
:::

## Common mistakes

- Using the screen when an API exists.
- Letting the model handle passwords, or running the agent in your own browser profile.
- No allowlist, so a link on a page can take the agent anywhere.
- Acting without re-reading, so the agent never notices a failed click.
- Trusting page text, or putting approvals in the prompt instead of the harness.
- Keeping no evidence: no action log and no screenshots.
- Retrying a click that may have gone through. Verify a timed-out "Issue credit" by reading the page; never click again.

## Before you move on

- **You should understand:** why the harness itself signs in, checks the host and holds the credit button, and why a timed-out "Issue credit" may already have gone through.
- **You should be able to build:** a harness that shows each page as untrusted text with numbered controls, and a `run_step` wrapper that checks the page before acting and verifies from a fresh read afterwards.
- **Prove it:** exercise 23.4 against an obedient model, then exercise 23.7.
- **Break it on purpose:** make `run_step` click the credit again after a timeout, and confirm Chen ends up credited $40 instead of $20.
- **Defend this decision:** why an account that can't issue credits beats any prompt telling the model to ignore page text.

## Key takeaways

**Architect's takeaway:** Use the screen only when there's no API, and treat every click as an unreliable call that code checks and verifies.

- Use a computer-use agent only when there's no API.
- Show the model the page as text with numbered controls; keep screenshots as evidence for people.
- The harness signs in, enforces the allowlist, holds dangerous clicks for approval and logs every action.
- Page text is untrusted input.
- Read, act, read again, and verify important results in code.
- Wrap each action: check before, verify after, retry only what's safe and hand expired sessions to a person.
