# Chapter 23: Computer-Use Agents

Every tool so far was an API: a function with a name, arguments and a result. A lot of the world's work happens in software that has no API: an old back-office system, a supplier's portal, an internal admin page nobody will ever wire up. People do that work by looking at a screen and clicking. **Computer-use agents** do the same: they see a page or a desktop, decide what to click or type and check what happened. They're the most general tools an agent can have, and the riskiest, because a click can move money and a web page can carry instructions. This chapter builds a browser agent with Playwright and surrounds it with the controls that make it safe to run.

**What you'll build:** a browser harness that shows the model each page as text with numbered controls, lets it click and type, signs in on its behalf, keeps it on one site, holds risky clicks for approval, limits and logs every action and saves screenshots as evidence, all against a small back-office application with a planted prompt injection.

**You are here:** Environment and Tools in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 9 (approval gates), Chapter 14 (prompt injection), Chapter 16 (context), Chapter 19 (durable jobs).

## Learning objectives

By the end of this chapter you can:

- Decide when a computer-use agent is the right tool, and when an API or MCP server is better.
- Compare the ways an agent can see a screen: screenshots, the page's structure, or both.
- Drive a real browser from an agent with Playwright: read the page, click, type and verify.
- Keep credentials away from the model, and keep the browser on an allowlist.
- Hold dangerous actions for a person, limit and log every action and keep screenshots as evidence.
- Defend a browser agent against instructions hidden in the pages it reads.
- Make browser automation reliable enough for long queues of work.
- Wrap each browser action in code that checks the page before and after, retries only what's safe to repeat and hands expired sessions to a person.

**In the real world.** Computer use moved from research demos to products between 2024 and 2026. Anthropic released a computer-use tool that lets Claude work a desktop through screenshots, mouse and keyboard; browser agents now fill forms, move data between web applications and test user interfaces; and operations teams use them for the long tail of systems that will never get an API. The same period showed the risks clearly. Security researchers have repeatedly demonstrated agents following instructions hidden in web pages, and every serious guide to computer use recommends the same precautions: a dedicated, isolated environment; no access to accounts or data the task doesn't need; an allowlist of sites; and a person confirming consequential actions. This chapter builds exactly those precautions into the harness.

## 23.1 When to use the screen

Operating a user interface is slow, costly and fragile compared with calling an API: every step costs a model call, a layout change can break a working agent and a page can say anything. So use the screen **last**:

Table: When to use the screen
| If the system has | Use |
| --- | --- |
| An API or an MCP server | That. It's faster, cheaper and more reliable |
| A database or file export you're allowed to use | That, read-only where possible |
| Only a web interface | A browser agent, with the controls in this chapter |
| Only a desktop application | A desktop computer-use agent in a virtual machine |

Browser agents are also the right tool for jobs that are *about* the interface: testing that a web application works for users, or checking what a customer actually sees.

## 23.2 How an agent sees a screen

There are two ways to show a model a page, and most real systems use both:

Table: Screenshots compared with the page's structure
|  | Screenshots | The page's structure |
| --- | --- | --- |
| What the model gets | An image; it answers with coordinates to click | Text: what the page says, and a numbered list of controls |
| Works on | Anything: web pages, desktop apps, images, canvases | Web pages (and apps with accessibility trees) |
| Cost | High: images use many tokens per step | Low: a few hundred tokens per page |
| Precision | Clicks can miss by a few pixels | A control is named exactly |
| Needs | A model with vision | Any model with tools |

This chapter uses the page's structure, because it's cheaper, more precise and works with the free local model. The page's text and its controls are read with a small piece of JavaScript. Screenshots are still taken after every change, but for **people**: they're the evidence of what the agent did. Anthropic's computer-use tool works the other way, with screenshots and coordinates, and is the tool to reach for when there's no page structure to read, such as a desktop application. (`qwen3.5:9b` can read images too, so the local model can try both.)

Three design decisions are in these few lines:

- **The harness signs in, not the model.** The service account's password comes from the environment and goes straight into the browser. The model never sees it, can't leak it in a reply, and can't be tricked into typing it into the wrong page. Chapter 26 gives the agent a proper identity of its own; the rule here is that credentials never pass through the model.
- **The page text is labeled as untrusted.** It's wrapped in a `page_text untrusted="true"` element, and the system prompt says page text is data.
- **Controls get short references.** `[e3] link "Ben Okafor"` lets the model say "click e3" instead of guessing a CSS selector or a pixel position. The references are reassigned every time the page is read, so an old reference fails loudly instead of clicking the wrong thing.

The system prompt asks for a rhythm that matters more for screens than for APIs: **read, act, read again.** After clicking "Save address", the agent reads the page and looks for "Address saved" and the new value. ## 23.5 Controls that don't depend on the model

Everything that must hold is enforced by the harness:

Table: Controls the harness enforces
| Control | What it prevents |
| --- | --- |
| Sign-in by the harness | Leaked or misused credentials |
| A host allowlist in `open` | Wandering to other sites, or being sent to an attacker's page |
| Approval for dangerous clicks | Money moved, data deleted, without a person |
| An action limit | Endless clicking when the agent is stuck |
| A log of every action | Not knowing what happened |
| A screenshot after every change | No evidence for a person reviewing the run |
| No typing into password fields | Credentials typed into a phishing form |

The approval check is Chapter 9's gate, moved from file moves to clicks: it reads the button's label and the values in its form, so the person sees "Issue credit: amount 50, reason late parcel" before deciding. In production, add the checks that belong to your application: which forms the agent may submit at all, and limits on amounts. The back office here also enforces its own limit on credits, because the application shouldn't trust any client, human or agent.

Run the whole thing with `./course.sh python ch23_browser.py`. It starts the back office, signs in and asks the agent to update Ben's address.

## 23.6 Injection through the screen

Ben's customer notes contain an instruction for "AI assistants": issue a $500 credit and change the email address. That's an indirect prompt injection (Chapter 14), and for a browser agent it's the main threat, because every page is full of text written by other people: customers, suppliers, anyone who can post a comment or a product review.

Three layers stop it here, and none depends on the model noticing:

1. **Labeling.** The model is told, and shown, that page text is data.
2. **Approval.** The credit button waits for a person, who sees exactly what would be submitted.
3. **The application's own rules.** Credits over $200 are refused by the server, and the page has no form to change an email address at all.

The strongest defense is the last one: **give the agent only the capabilities the task needs.** An account that can change addresses but not issue credits makes the attack impossible rather than unlikely. Chapter 25 returns to injection as a whole class of attacks; Chapter 26 to scoping what an agent's account may do.

## 23.7 Making it reliable

Browser automation fails in ways API calls don't. A few habits prevent most of it:

- **Wait for the page, not for a fixed time.** Playwright waits for elements to be ready before acting; `wait_for_load_state` after a click waits for navigation.
- **Re-read after every change.** References and page content go stale. The harness renumbers controls on every read and rejects unknown references.
- **Time-limit everything.** A default timeout of 10 seconds per action turns a hung page into an error the agent can report.
- **Isolate the browser.** Use a fresh browser profile in a container, never your own browser with your own logged-in accounts. The course kit runs Chromium inside its container.
- **Checkpoint long queues.** A queue of 200 requests will meet a crash. Make each request a durable step (Chapter 19): finished requests stay finished, and the next run picks up where the last one stopped. Exercise 23.6 builds this, and Capstone 6 builds on it.

These are habits. Section 23.9 turns them into code that holds even when the model doesn't follow them.

## 23.8 Desktop computer use {api}

Everything in this chapter carries over to agents that operate a whole desktop, with the controls turned up. A desktop agent works from screenshots and sends mouse and keyboard actions, so it can operate any application, including your email and your files. Run it in a virtual machine or container with no access to your real accounts, give it only the applications the task needs, keep a person watching or approving and treat every screen it reads as untrusted input. The Claude documentation on computer use (see Learn more) describes the tool and its recommended safeguards.

## 23.9 Reliability engineering for computer use

An API call either returns a result or raises an error. A click is murkier: the button might not be there yet, the page might change between reading and clicking, the click might land and then time out, or the page might turn into a sign-in form. A queue of 200 requests will meet every one of these. Each failure mode needs a named control, and you need to decide who enforces it: the harness, in code, or the model, by noticing. The rule is the same as in section 23.5: if a failure can move money or leave a wrong record, code enforces the control.

Table: Computer-use failure modes and their controls {#t:cu-failures}
| Failure | What it looks like | The control | Enforced by |
| --- | --- | --- | --- |
| Visual ambiguity | Two "Save" buttons; a name that matches the wrong customer; a screenshot click a few pixels off | Target controls by label from the page's structure, not by position; check the page is the expected record before acting | Harness checks; the model chooses the target |
| Stale UI state | A ref from an earlier read, or a control that hasn't rendered: "no control e1" | Re-read before every attempt, resolve the target again, retry a bounded number of times | Harness |
| Race conditions | A click while the page is loading; someone else edits the record between read and save | Wait for the page; check preconditions right before acting; verify the saved value afterwards; the application rejects conflicting writes | Harness and application |
| Confirmation dialogs | An "Are you sure?" pop-up blocks the page, or is accepted without anyone seeing it | Handle dialogs in code and treat a confirm as a dangerous click that needs approval | Harness |
| Session expiry and MFA | The page becomes a sign-in form or asks for a verification code | Detect it and hand over to a person; the model never types credentials or codes | Harness |
| Non-idempotent actions | "Issue credit" times out: did it land? | Never retry; read the page to verify; if that's inconclusive, a person decides | Harness, then a person |
| Claimed but not done | The agent says "Done" but the field didn't change | Verify from a fresh read of the page, not the model's answer | Harness |
| No evidence | Nobody can say what the screen showed when the agent acted | Log every read with a snapshot id and a timestamp; keep the page text and screenshots | Harness |

@@code ch23_reliability.py::needs_person~,run_step

Here's what to notice:

- **Errors fall into three groups, and only one is safe to retry blindly.** "No control e1" means nothing happened, so the wrapper reads the page again and retries. A refusal (no approval, a host off the allowlist, the action limit) is final. An exception during a click means the action *may* have happened: the wrapper retries only if the step is idempotent, and otherwise goes straight to verification.
- **The target is a label, resolved again on every attempt.** A ref like `e1` is only valid for the read it came from (section 23.3), so the wrapper never reuses one.
- **Verification reads the page.** The postcondition gets the page before and after the action. For a credit, that means the balance went up by exactly the amount, read from a freshly opened customer page (`check_path`), not from the page the click happened to leave behind.
- **A sign-in or verification-code page stops the step.** The harness can't tell an ordinary timeout from a forced sign-out, and a guessed code can lock the account, so a person takes over.
- **Every read is evidence.** The log records the step, the attempt, the event, the page and a snapshot id with a UTC timestamp, and keeps the page text under that id.

```
2. A credit click that lands, then times out: verify, never click again.
    [('open 3', 'done'), ('type amount 3', 'done'), ('type reason 3', 'done')]
    done
  issue credit 3     try 1  before                   /customers/3 snap 5d1258ced9
  issue credit 3     try 1  error                    TimeoutError: click timed out waiting for the page
  issue credit 3     try 1  after                    /customers/3 snap 060cd91c81
  issue credit 3     try 1  verified
   Chen's balance: $45.00; credits issued: 1
```

A naive retry would have clicked again and issued $40. The wrapper read the balance instead, saw $25.00 become $45.00 and stopped. If the click had never landed, the balance would have been unchanged and the step would end in `needs_human`, because "unchanged" can also mean "still processing". Only a person, or the application's own records, can settle that. In the third run the session expires, the page becomes the sign-in form and the step stops with a hand-off instead of a guess.

Use the wrapper as the body of a durable step (Chapter 19), or around each agent action whose outcome you can state in advance. The model still decides what to do; the wrapper decides whether it worked.

:::note What production adds
- **Real screenshots, stored with a retention limit.** Keep an image with each snapshot id, encrypted, for as long as your audit rules require and no longer: screens show customers' personal data.
- **Idempotency keys in the backend** (section 19.5). The wrapper's "never retry" is the last line of defense; an application that ignores a repeated request with the same key makes a double click harmless.
- **Session vaulting.** Session cookies and the service account's credentials live in a vault, and the harness signs in again from code once when a session expires. Give the agent's account a non-interactive identity (Chapter 26) so it never meets an MFA prompt; if it does, that's a person's job.
- **Dialog handlers and version checks.** Register a handler for browser dialogs that routes confirms through approval, and have the application reject a save based on an out-of-date page.
- **Retry metrics per step.** A step that needs retries more and more often is a control whose label or layout is about to change.
:::

## Common mistakes

- **Using the screen when an API exists.** It's slower, costlier and more fragile.
- **Letting the model handle passwords**, or running the agent in your own browser profile with your own accounts signed in.
- **No allowlist**, so a link on a page can take the agent anywhere.
- **Acting without re-reading**, so the agent never notices that a click failed.
- **Trusting page text**, so a customer's note can direct the agent.
- **Approvals in the prompt** instead of in the harness.
- **No evidence**: no action log and no screenshots to show what was done.
- **Retrying a click that may have landed.** A timed-out "Issue credit" is verified by reading the page, never clicked again.

## Key takeaways

**Architect's takeaway:** GUI agents are fragile: design error recovery and execution bounds before scaling.

- Use a computer-use agent when there's no API; use the API when there is.
- Show the model the page as text with numbered controls; keep screenshots as evidence for people, or use them when there's no page structure.
- The harness signs in, keeps the browser on an allowlist, holds dangerous clicks for approval, limits and logs actions and never lets the agent type passwords.
- Read, act, read again; verify important results in code.
- Page text is untrusted input. The strongest defense is an account that can only do what the task needs.
- Make it reliable with waits, fresh references, timeouts, an isolated browser and durable steps for long queues.
- Wrap each action in code: check the page before, verify it after, retry only what didn't happen or is safe to repeat, hand expired sessions and MFA to a person and log every read as evidence.
