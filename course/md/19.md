# Chapter 19: Long-Running Agents

Every agent so far has worked in one sitting: a question goes in, a few model calls later an answer comes out. Real work doesn't fit that shape. Onboarding a customer touches four systems and waits for a payment. Writing a report takes dozens of queries across an afternoon. Migrating a codebase takes days. Over hours, processes crash, APIs time out, rate limits bite and people go home, and an agent that starts again from scratch after every failure repeats side effects and pays for the same model calls twice. This chapter turns the agent loop into work that survives all of that. It's also where agent engineering starts to look like distributed-systems engineering.

**What you'll build:** a durable job runner that checkpoints every step, retries safely, recovers from a crash, escalates to a person and undoes finished work when a job is abandoned, and a harness that carries open-ended work across many sessions.

**You are here:** Agent runtime (durable execution) in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapter 5 (state), Chapter 7 (retries and backoff).

## Learning objectives

By the end of this chapter you can:

- Describe the shape of long-running work: goal, plan, execute, checkpoint, recover, continue, verify, deliver.
- Save a job's progress as data, so a crash costs one step, not the whole job.
- Retry transient failures with backoff and a limit, and recognize errors that must not be retried.
- Make side effects safe to repeat with idempotency keys.
- Share work between workers with leases, so a dead worker's job is picked up.
- Escalate to a person, and undo completed steps with compensation.
- Carry open-ended work across sessions with a checklist, progress notes and checks in code.

**In the real world.** Coding agents are the clearest example of the shift. Anthropic's engineering team described how they got Claude to build a complete web application over many sessions, each starting with an empty context. Two things made it work. An **initializer** session first wrote a feature list of more than 200 end-to-end features, all marked failing, plus a progress file and an initial git commit. Every later session then read the progress file and the git log, worked on **one** feature, tested it end to end, and committed. Without that structure, the agent tried to do everything at once or declared victory early. The same ideas, state outside the model, small verified steps and checkpoints, apply to any long job, not only code.

## 19.1 From prompt → answer to goal → deliver

A chat is **prompt → answer**. A long-running agent follows a longer cycle:

@@image d-39f5722abe80.png

Figure: The shape of long-running work
Alt: Goal, plan, then execute a step and checkpoint it. While more steps remain, the next one runs; a failure goes to recover, which retries, resumes or escalates, and returns to the step. When no steps remain, the work is verified and delivered.

Don't confuse this with the async code of Chapter 11. `asyncio.gather` runs several calls at once inside one process; if the process crashes, is redeployed or is stopped for a day while a person approves a step, everything it was doing is gone. Durability is a different property, and this chapter builds it.

Table: Concurrency and durability are different things {#t:async-vs-durable}
| | Async concurrency (`asyncio`) | Durable execution (this chapter) |
| --- | --- | --- |
| Solves | Waiting on several slow calls at once | Work that must survive crashes, deploys and long pauses |
| State lives in | The process's memory | Storage that outlives the process |
| After a crash | Everything in flight is lost | Resume from the last checkpoint |
| Hours or days | No | Yes, with leases and timeouts |
| Human approval pauses | Only while the process stays up | The job waits in storage |
| Repeated side effects | Not handled | Idempotency keys and escalation (section 19.5) |

You often want both: async inside a step to make it fast, and durable steps around it so the job survives.

Two things are new. **Checkpoint** means that after each step, what was done and what it produced are written somewhere that outlives the process. **Recover** means that a failure, whether a timeout, a crash or a step that needs a person, leads back into the cycle instead of ending it. Chapter 20 is about the plan; this chapter is about everything around it.

## 19.2 What breaks when work takes hours

Short runs hide these failures because they're rare per minute. Over hours they become certain:

Table: What breaks when work takes hours, and the mechanism that fixes it
| What happens | Without care | The mechanism | Section |
| --- | --- | --- | --- |
| The process crashes | The job starts over; finished work repeats | Checkpoints | 19.3 |
| An API times out | The whole job fails on one blip | Retries with backoff | 19.4 |
| A step hangs | The job never ends | Timeouts and deadlines | 19.4 |
| A retry repeats a payment or an email | The customer is charged twice | Idempotency keys | 19.5 |
| A worker dies holding a job | The job is stuck forever | Leases | 19.6 |
| A step keeps failing | The agent guesses, or loops | Escalation to a person | 19.7 |
| The job must be abandoned halfway | Half-done state is left behind | Compensation | 19.7 |
| The work doesn't fit one context window | The agent forgets what it did | Progress notes and a checklist | 19.8 |

## 19.3 Checkpoints: a job is data

The core idea is simple: a job is not a running program, it's **rows in a database**. Each step has a status (`pending`, `running`, `done`, `failed`), its arguments and its result:

@@code ch19_durable.py::SCHEMA,create_job

The runner works through the steps in order and saves each result before starting the next:

@@code ch19_durable.py::run_job

Read what happens after a crash. The next call to `run_job` loads the steps, skips everything already `done`, and reuses their saved results, including the text of any model call. That last part matters for agents in a way it doesn't for ordinary jobs: a model call is expensive and **not repeatable**. Ask again and you'll get a different welcome message, so the email sent in step 3 would no longer match what step 2 recorded. The rule is: **checkpoint model outputs like any other result**, and never regenerate what a later step already used.

Arguments can refer to earlier results: `"$2"` means "the result of step 2". Because results come from the checkpoint, a resumed job passes exactly the same values it would have passed without the crash.

Run the demo, crash it and run it again:

```
./course.sh python ch19_durable.py --crash 2   # stops after steps 1 and 2
./course.sh python ch19_durable.py             # resumes at step 3
```

The report shows steps 1 and 2 done once, and `services.json` shows one account and one email.

## 19.4 Retries, timeouts and errors you mustn't retry

Most failures in long jobs are **transient**: a timeout, a rate limit, a service restarting. Waiting and trying again fixes them. Some are **permanent**: invalid input, a request refused by policy, a charge over a limit. Retrying those wastes time and money, and can make things worse. Chapter 7 drew the same line for one HTTP call (retry timeouts, 429 and 5xx; fail fast on other 4xx); a durable job applies it to every step, and remembers the attempts across restarts.

@@code ch19_durable.py::Permanent,_attempt~,_run_step

Four rules are in that code:

- **Retry with backoff.** Wait 1 second, then 2, then 4. Retrying immediately hammers a service that's already struggling.
- **Cap the attempts.** After three tries, a person looks at it (section 19.7). An agent that retries forever is a runaway bill.
- **Classify errors.** Code raises `Permanent` for what retrying can't fix; everything else is treated as transient.
- **Time-limit every step, and the job as a whole.** A step that hangs holds the whole job. The deadline catches jobs that make slow progress forever.

Notice that the step is marked `running` and committed **before** the attempt. If the process dies mid-step, the next run knows the step started and may have had an effect. That's what the next section is about.

:::tip Retries at three levels
The Claude SDK already retries overloaded and rate-limited API calls (Chapter 4 sets `max_retries=3`). The agent loop retries a failed tool when the model reads the error and tries again (Chapter 8). The job runner retries a whole step. Each level handles different failures; don't let them multiply into 3 × 3 × 3 attempts without meaning to.
:::

## 19.5 Idempotency: doing it twice must be safe

An operation is **idempotent** if doing it twice has the same effect as doing it once. Reading is idempotent. Setting a field to a value is idempotent. Sending an email or charging a card is not.

After a crash, the runner can't know whether a `running` step's side effect happened: the email may have gone out a millisecond before the process died. There are only two safe answers:

1. **Make the side effect idempotent with a key.** The runner gives every step a key that never changes, such as `job_id:step`, and passes it on every attempt. The receiving system remembers keys it has seen and ignores repeats. Payment providers such as Stripe accept exactly this kind of *idempotency key*; for your own services, a unique constraint on the key does the job.
2. **If you can't, ask a person.** An unkeyed side effect with an unknown outcome is escalated rather than repeated or skipped.

@@code ch19_durable.py::_record,charge

The demo services de-duplicate by key, so running step 3 twice sends one email. `action(..., effect="unkeyed")` marks steps that can't do this, and `_run_step` escalates them after a crash instead of guessing. Chapter 5's to-do tools made the same point on a small scale: a retried `add_task` mustn't add the task twice. Section 7.3's tool contract for mutations ({{t:mutation-contracts}}) is the checklist to write for each tool before it goes into a job.

## 19.6 Leases and task queues

In production, jobs sit in a queue and several **workers** take them. If a worker dies holding a job, someone must notice. A **lease** handles this: a worker claims a job for a limited time and renews the lease after each step. If the lease runs out, the worker is presumed dead and another worker may take the job:

@@code ch19_durable.py::claim

The claim is a conditional update, so two workers can't take the same free job. Because every step is checkpointed and every side effect is keyed, the new worker simply calls `run_job` and continues where the old one stopped. Leases can't guarantee that only one worker is running at a time (the "dead" worker may only be slow), which is one more reason side effects must be idempotent.

## 19.7 Escalation and compensation

Some failures need a person: a charge over the automatic limit, a step that failed three times, a job past its deadline. The runner doesn't guess. It marks the job `needs_human` with a reason and stops. A person then decides:

@@code ch19_durable.py::resolve~,compensate

- **Retry** after fixing the cause, for example raising the limit.
- **Skip**, giving the result the step would have produced.
- **Abandon**, which runs **compensation**: each finished step's undo action, newest first. An account is deleted, a charge is refunded. This is the *saga* pattern from database research: a long transaction built from steps, each with a compensating step, instead of one lock held for hours.

Some steps can't be undone. An email can't be unsent. `compensate` lists them so a person can follow up, perhaps with a second email. Deciding which steps have an undo, and which need a person, is part of designing the job, not something to discover during an incident.

Waiting is normal in long-running work. A job may sit in `needs_human` for a day. Because it's rows in a database, not a program in memory, waiting costs nothing.

## 19.8 Open-ended work: a harness across sessions

A durable job needs its steps known in advance. Much agent work isn't like that: "write the weekly sales report" or "add these twenty features" needs the agent to decide how, and takes more model calls than fit in one context window. The answer, from the Anthropic example at the start of this chapter, is to keep the state of the work **outside the model**, in files every new session reads:

- A **checklist** written first, before any work, with a check your code can run for each item. Everything starts `failing`.
- A **progress file** in plain words: what each session did and learned.
- **One item per turn**, verified by its check, then saved. An item is `passing` only when the check passes, not when the model says it's done.

@@code ch19_harness.py::REPORT,check~,session

Each session starts with a fresh context. The brief holds the goal, the one item to work on, the last few progress notes, and, on a retry, why the previous attempt failed its check. That's context engineering (Chapter 16) applied across sessions: the progress file is a structured note that replaces a conversation history too long to keep.

Run a session with `./course.sh python ch19_harness.py`, then run it again: the second session reads the notes and continues with the next items. Stop it halfway and nothing is lost except the item in progress.

Three failure modes from the Anthropic write-up are worth designing against explicitly:

Table: Failures of open-ended work and their defenses
| Failure | Defense in the harness |
| --- | --- |
| Declaring victory early | The checklist, written up front, defines done; checks run in code |
| Doing too much at once, leaving a mess | One item per turn, saved before the next |
| Each session re-learning the project | The progress file and the checklist, read at the start |

In a codebase, the checkpoint is a **git commit** per item: it records the work, and a bad change can be reverted to the last good state.

## 19.9 Durable execution in production

The runner in this chapter is small enough to read in one sitting. In production, you'd usually build on a **durable execution** platform, such as Temporal or a cloud provider's workflow service, which offers the same ideas with more guarantees: persistent event histories, timers that survive restarts, leases, retries and signals from people. Whatever you use, check four things:

- **Every model call's output is recorded** and reused on replay, never regenerated.
- **Every side effect is idempotent** or explicitly escalated.
- **Humans are part of the workflow**: a job can wait days for a decision without holding resources.
- **You can see where every job is**: its current step, attempts, errors and history. Chapter 28 connects this to tracing.

Long-running agents also change how you evaluate them. A 3-hour job that fails at hour 2 and resumes correctly is a success; one that finishes fast but double-charges a customer is not. Chapter 27 measures the whole trajectory, not only the final answer.

:::note The support agent so far
The support agent's refunds become durable jobs. A return refund waits days for the parcel to arrive back at the warehouse: the job checkpoints each step, survives restarts, gives the payment call an idempotency key so the customer is never refunded twice, and escalates to a person if the parcel never arrives.
:::

## Common mistakes

- **Keeping the job's state only in memory**, so a crash restarts everything. Design checkpoints from day one.
- **Checkpointing the wrong things.** Save each step's status and result, including model outputs; the goal is to resume the job, not to rebuild it.
- **Regenerating model output on resume**, so later steps no longer match what earlier steps used.
- **Retrying everything**, including errors that retrying can't fix, or retrying forever.
- **Side effects without idempotency keys**, so a retry charges twice or sends two emails.
- **No lease or heartbeat**, so a dead worker's job never finishes, and a job that hangs at hour 11 goes unnoticed.
- **Letting the agent guess after repeated failures** instead of escalating to a person.
- **No plan for undo**, so an abandoned job leaves half-done state behind.
- **Trusting the model's "done"** instead of a check in code.
- **Never cleaning up finished jobs**, so old state piles up. Set an expiry policy.

## Key takeaways

**Architect's takeaway:** Design checkpointing before you need it: agent state must survive restarts.

- Long-running work follows goal, plan, execute, checkpoint, recover, continue, verify, deliver.
- A job is data: each step's status and result are saved before the next step starts, including model outputs.
- Retry transient failures with backoff and a limit; raise permanent errors immediately; time-limit steps and jobs.
- Give every side effect a stable idempotency key, or escalate when its outcome is unknown.
- Leases let another worker finish a dead worker's job.
- Escalate to a person when the runner shouldn't guess, and compensate finished steps, newest first, when a job is abandoned.
- For open-ended work, keep a checklist with checks in code and a progress file, and do one verified item at a time.

The job runner executes a plan it's given. Chapter 20 is about making the plan: how an agent breaks a goal into steps, checks the plan before running it, replans when things change, and picks the right model for each step.
