# Chapter 19: Long-Running Agents

A call that fails once in a thousand is invisible in a chat. Put two hundred of them in a job that runs every night, and on roughly one night in five something breaks partway through. Say it's a redeploy, arriving just as your onboarding agent writes the welcome email, after it has already created the customer's account and charged their card. Run the job again from the top and the customer gets a second account and a second charge, and you pay for every model call twice. If you've worked on distributed systems, much of this chapter will feel familiar. The new part is that one of your workers is a model, and it rarely gives the same answer twice.

**What you'll build:** a durable job runner that checkpoints every step, retries safely, recovers from a crash, escalates to a person and undoes finished work when a job is abandoned, plus a harness that carries open-ended work across sessions.

**You are here:** Agent runtime (durable execution) in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapter 5 (state), Chapter 7 (retries and backoff).

## Learning objectives

By the end of this chapter you can:

- Describe the cycle of long-running work: goal, plan, execute, checkpoint, recover, continue, verify, deliver.
- Save a job's progress as data, so a crash costs one step instead of the whole job.
- Retry transient failures with backoff and a limit, and recognize errors that must not be retried.
- Make side effects safe to repeat with idempotency keys.
- Use leases so another worker picks up a dead worker's job.
- Escalate to a person, and undo completed steps with compensation.
- Carry open-ended work across sessions with a checklist, progress notes and checks in code.

**In the real world.** Anthropic's engineering team got Claude to build a complete web application over many sessions, each starting with an empty context. An **initializer** session first wrote a list of more than 200 end-to-end features, all marked failing, plus a progress file and a first git commit. Every later session read the progress file and git log, built and tested **one** feature, and committed. Without that structure, the agent tried to do everything at once or declared victory early.

## 19.1 From prompt → answer to goal → deliver

A chat is **prompt → answer**. A long-running agent follows a longer cycle:

@@image d-39f5722abe80.png

Figure: The cycle of long-running work
Alt: Goal, plan, then execute a step and checkpoint it. While more steps remain, the next one runs; a failure goes to recover, which retries, resumes or escalates, and returns to the step. When no steps remain, the work is verified and delivered.

Don't confuse this with the async code of Chapter 11. `asyncio.gather` runs several calls at once inside one process; if that process crashes or is redeployed, everything it was doing is gone.

Table: Concurrency and durability are different things {#t:async-vs-durable}
| | Async concurrency (`asyncio`) | Durable execution (this chapter) |
| --- | --- | --- |
| Solves | Waiting on several slow calls at once | Surviving crashes, deploys and long pauses |
| State lives in | The process's memory | Storage that outlives the process |
| After a crash | Everything in flight is lost | Resume from the last checkpoint |
| Waiting for approval | Only while the process stays up | The job waits in storage |

You often want both: async inside a step for speed, durable steps around it for survival.

Two steps in the cycle are new, and they carry the rest of the chapter. **Checkpoint** means each step's outcome is written somewhere that outlives the process. **Recover** means a failure, whether a timeout, a crash or a step that needs a person, leads back into the cycle instead of ending it. Chapter 20 is about the plan; this chapter is about everything around it.

## 19.2 What breaks when work takes hours

Failures that are rare per minute become certain over hours:

Table: What breaks when work takes hours, and the mechanism that fixes it
| What happens | Without care | The mechanism | Section |
| --- | --- | --- | --- |
| The process crashes | Finished work repeats | Checkpoints | 19.3 |
| An API times out | The whole job fails on one blip | Retries with backoff | 19.4 |
| A step hangs | The job never ends | Timeouts and deadlines | 19.4 |
| A retry repeats a payment | The customer is charged twice | Idempotency keys | 19.5 |
| A worker dies holding a job | The job is stuck forever | Leases | 19.6 |
| A step keeps failing | The agent guesses, or loops | Escalation to a person | 19.7 |
| The job must be abandoned halfway | Half-done state is left behind | Compensation | 19.7 |
| The work outgrows one context window | The agent forgets what it did | Progress notes and a checklist | 19.8 |

## 19.3 Checkpoints: a job is data

A job is not a running program; it's **rows in a database**. Each step has a status (`pending`, `running`, `done`, `failed`), its arguments and its result:

@@code ch19_durable.py::SCHEMA,create_job

The runner saves each step's result before starting the next:

@@code ch19_durable.py::run_job

After a crash, the next call to `run_job` loads the steps, skips everything already `done` and reuses their saved results, including the text of any model call. That matters for agents in a way it doesn't for ordinary jobs, because a model call is expensive and **not repeatable**. Ask again and you get a different welcome message, so the email sent in step 3 no longer matches what step 2 recorded. So **checkpoint model outputs like any other result**, and never regenerate what a later step already used.

Arguments can refer to earlier results: `"$2"` means "the result of step 2". Because results come from the checkpoint, a resumed job passes exactly the values it would have passed without the crash.

Run the demo, crash it and run it again:

```
./course.sh python ch19_durable.py --crash 2   # stops after steps 1 and 2
./course.sh python ch19_durable.py             # resumes at step 3
```

Steps 1 and 2 ran once, and `services.json` shows one account and one email.

## 19.4 Retries, timeouts and errors you mustn't retry

Most failures in long jobs are **transient**: a timeout, a rate limit, a service restarting. Waiting and trying again fixes them. Some are **permanent**: invalid input, a request refused by policy, a charge over a limit. Retrying those wastes time and money. Chapter 7 drew this line for one HTTP call (retry timeouts, 429 and 5xx; fail fast on other 4xx); a durable job applies it to every step and remembers the attempts across restarts.

@@code ch19_durable.py::Permanent,_attempt~,_run_step

Retry with **backoff** (1 second, then 2, then 4), because retrying immediately hammers a service that's already struggling. **Cap the attempts**: after three tries a person looks at it (section 19.7), since an agent that retries forever is a runaway bill. **Classify errors**: code raises `Permanent` for what retrying can't fix, and everything else counts as transient. And **time-limit every step and the job as a whole**, so neither a hung step nor slow progress runs forever.

Notice that the step is marked `running` and committed **before** the attempt. If the process dies mid-step, the next run knows the step started and may have had an effect. Which brings us to the hard part.

:::tip Retries at three levels
The Claude SDK retries overloaded and rate-limited API calls (Chapter 4 sets `max_retries=3`). The agent loop retries a failed tool when the model reads the error (Chapter 8). The job runner retries a whole step. Don't let them multiply into 3 × 3 × 3 attempts without meaning to.
:::

## 19.5 Idempotency: doing it twice must be safe

An operation is **idempotent** if doing it twice has the same effect as doing it once. Reading and setting a field are idempotent; sending an email or charging a card is not. After a crash, the runner can't know whether a `running` step's side effect happened: the email may have gone out a millisecond before the process died. There are only two safe answers:

1. **Make the side effect idempotent with a key.** The runner gives every step a key that never changes, such as `job_id:step`, and passes it on every attempt. The receiving system ignores keys it has seen. Payment providers such as Stripe accept exactly this kind of *idempotency key*; for your own services, a unique constraint does the job.
2. **If you can't, ask a person.** An unkeyed side effect with an unknown outcome is escalated, never repeated or skipped.

@@code ch19_durable.py::_record,charge

The demo services de-duplicate by key, so running step 3 twice sends one email. `action(..., effect="unkeyed")` marks steps that can't, and `_run_step` escalates them after a crash instead of guessing. Section 7.3's tool contract for mutations ({{t:mutation-contracts}}) is the checklist to fill in for each tool before it goes into a job.

## 19.6 Leases and task queues

In production, jobs sit in a queue and several **workers** take them. If a worker dies holding a job, someone must notice. With a **lease**, a worker claims a job for a limited time and renews it after each step. If the lease runs out, the worker is presumed dead and another may take the job:

@@code ch19_durable.py::claim

The claim is a conditional update, so two workers can't take the same free job. Because steps are checkpointed and side effects keyed, the new worker just calls `run_job` and continues. Leases can't guarantee that only one worker runs at a time (the "dead" worker may only be slow), which is one more reason side effects must be idempotent.

## 19.7 Escalation and compensation

Some failures need a person: a charge over the automatic limit, a step that failed three times, a job past its deadline. The runner doesn't guess. It marks the job `needs_human` with a reason and stops, and a person decides:

@@code ch19_durable.py::resolve~,compensate

- **Retry** after fixing the cause, for example raising the limit.
- **Skip**, giving the result the step would have produced.
- **Abandon**, which runs **compensation**: each finished step's undo action, newest first. The account is deleted, the charge refunded. This is the *saga* pattern from database research: a long transaction built from steps, each with a compensating step, instead of one lock held for hours.

Some steps can't be undone; an email can't be unsent. `compensate` lists them so a person can follow up. Decide which steps have an undo while you design the job, before an incident forces the question. And don't worry about the wait: a job sitting in `needs_human` for a day is just rows in a database, so it costs nothing.

## 19.8 Open-ended work: a harness across sessions

A durable job needs its steps known in advance. "Write the weekly sales report" or "add these twenty features" needs the agent to decide how, and takes more model calls than fit in one context window. The answer, from the Anthropic example at the start of the chapter, is to keep the state of the work **outside the model**, in files every new session reads:

- A **checklist**, written before any work, with a check your code can run for each item. Everything starts `failing`.
- A **progress file** in plain words: what each session did and learned.
- **One item per turn**, verified by its check, then saved. An item is `passing` only when its check passes, whatever the model says.

@@code ch19_harness.py::REPORT,check~,session

Each session starts with a fresh context. Its brief holds the goal, the one item to work on, the last few progress notes and, on a retry, why the previous attempt failed its check. That's context engineering (Chapter 16) across sessions: the progress file replaces a conversation history too long to keep.

Run `./course.sh python ch19_harness.py`, then run it again: the second session reads the notes and continues with the next items. Stop it halfway and you lose only the item in progress. The harness defends against the failures the Anthropic write-up describes:

Table: Failures of open-ended work and their defenses
| Failure | Defense in the harness |
| --- | --- |
| Declaring victory early | The checklist, written up front, defines done; checks run in code |
| Doing too much at once, leaving a mess | One item per turn, saved before the next |
| Each session re-learning the project | The progress file and the checklist, read at the start |

In a codebase, the checkpoint is a **git commit** per item, so a bad change can be reverted to the last good state.

## 19.9 Durable execution in production

`ch19_durable.py` is a production pattern: its checkpoints, keys, leases and escalations are the real ones, but jobs live in one SQLite file and the demo services are a JSON file. In production you'd usually build on a **durable execution** platform, such as Temporal or a cloud provider's workflow service, which offers the same ideas with more guarantees: persistent event histories, timers that survive restarts, leases, retries and signals from people. Whatever you use, check that:

- every model call's output is recorded and reused on replay, never regenerated;
- every side effect is idempotent or explicitly escalated;
- a job can wait days for a person's decision without holding resources;
- you can see every job's current step, attempts, errors and history (Chapter 28 connects this to tracing).

Long-running agents also change how you evaluate them. A 3-hour job that fails at hour 2 and resumes correctly is a success; one that finishes fast but double-charges a customer is not. Chapter 27 measures the whole trajectory, not only the final answer.

:::note The support agent so far
The support agent's refunds become durable jobs. A return refund waits days for the parcel to reach the warehouse: the job checkpoints each step, survives restarts, gives the payment call an idempotency key so no one is refunded twice, and escalates to a person if the parcel never arrives.
:::

## Common mistakes

- Keeping the job's state only in memory, so a crash restarts everything.
- Regenerating model output on resume, so later steps no longer match what earlier steps used.
- Retrying everything, including permanent errors, or retrying forever.
- Side effects without idempotency keys, so a retry charges twice or sends two emails.
- No lease or heartbeat, so a dead worker's job never finishes.
- Letting the agent guess after repeated failures instead of escalating to a person.
- No plan for undo, so an abandoned job leaves half-done state behind.
- Trusting the model's "done" instead of a check in code.
- Never cleaning up finished jobs, so old state piles up. Set an expiry policy.

## Before you move on

- **You should understand:** why a model call's output is checkpointed and reused on resume instead of regenerated, and why a step found `running` after a crash has an unknown outcome.
- **You should be able to build:** a runner that saves each step's status and result before the next starts, retries transient errors with backoff and a cap, and fails `Permanent` errors at once.
- **Prove it:** exercise 19.3 (one email after the resume), then exercise 19.4.
- **Break it on purpose:** in exercise 19.4, make `LEASE` shorter than one step so a second worker claims a running job, and check that the keys still keep one charge per job.
- **Defend this decision:** why an unkeyed side effect with an unknown outcome goes to a person instead of being retried or skipped.

## Key takeaways

**Architect's takeaway:** Design checkpoints, idempotency keys and undo actions up front; the first crash will test all three.

- A job is data: each step's status and result, model outputs included, are saved before the next step starts.
- Retry transient failures with backoff and a limit; fail permanent errors immediately; time-limit steps and jobs.
- Give every side effect a stable idempotency key.
- Leases let another worker finish a dead worker's job.
- Escalate when the runner shouldn't guess, and compensate finished steps, newest first, when a job is abandoned.
- For open-ended work, keep a checklist with checks in code and a progress file, and do one verified item at a time.
