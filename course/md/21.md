# Chapter 21: Multi-Agent Orchestration

A lead agent asks its analyst for "the Q3 numbers." The analyst sends back three paragraphs with eleven figures in them, and the lead quotes the wrong one in its final report, with complete confidence. Every log line looks healthy, because neither agent did anything wrong on its own. They simply never agreed on what a handoff should look like.

Chapter 11 showed you small teams that lived in one program and trusted each other. Real teams are bigger and messier: two agents do the same work, one confused agent's mistake spreads to the rest, and some members belong to other companies. You'll build what keeps such a team honest, from contracts and hard limits to a protocol for agents you don't run, and a way to tell whether the team is worth what it costs.

**What you'll build:** an orchestrator where a lead delegates to specialists through one tool, with contract-checked results, a shared task board with hard limits, contained failures and remote specialists reached over A2A.

**You are here:** Agent runtime and A2A in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapter 11 (multi-agent systems), Chapter 13 (agents as MCP servers).

## Learning objectives

By the end of this chapter you can:

- Choose a team topology.
- Define contracts for what agents hand each other, and enforce them in code.
- Keep one shared record of the team's work, with limits on depth, tasks and tokens.
- Give each agent a brief instead of the whole conversation.
- Contain one agent's failure, and resolve disagreements with independent verification.
- Publish and call agents with A2A, and choose between MCP and A2A.
- Decide, with measurements, whether a team pays for itself.

**In the real world.** By 2026, multi-agent systems were shipping in research features, coding tools and enterprise platforms where agents from different vendors pass work along. A 2025 study of popular frameworks sorted 14 failure modes into three families: poor system and task design, misalignment between agents, and weak verification. Microsoft's guidance answers with least privilege, audit trails, human approval for high-impact actions and sharing only the context each agent needs.

## 21.1 Topologies

How agents are wired together decides how work and errors flow through them:

Table: Team topologies
| Topology | How it works | Good for | Watch out for |
| --- | --- | --- | --- |
| **Supervisor** | One lead delegates to specialists and combines results | Most tasks; the default | The lead becomes a bottleneck |
| **Hierarchy** | Specialists delegate further to sub-specialists | Large tasks that split into levels | Runaway depth and cost |
| **Pipeline** | Each agent transforms the previous one's output | Fixed sequences: draft, review, format | One bad stage spoils the rest |
| **Shared board** | Agents read and write one shared record of tasks | Many loosely coupled agents | Conflicting writes, stale reads |
| **Network** | Independent agents call each other across companies | Cross-organization work | Trust, identity, versioning |

Chapter 11's patterns (router, handoff, critic, vote) fit inside these. This chapter's code is a supervisor with a limited hierarchy, a shared board and optional network members over A2A. Start with a supervisor, and add the others only when a measurement says you need them.

## 21.2 Contracts between agents

Between agents, a vague handoff is where things first go wrong, as the opening story showed. A **contract** fixes the structure of what agents hand each other:

@@code ch21_orchestrator.py::RESULT,SUBMIT

Every specialist finishes by calling `submit_result`, and the orchestrator validates the arguments against the JSON schema in code, with the `jsonschema` library. An answer without evidence, a confidence that isn't one of the three allowed words, or a 10,000-character essay is rejected with a message the specialist can act on, like a tool error in Chapter 8. The brief going the other way is a contract too. The delegate tool's description tells the lead that specialists can't see its conversation, so every brief has to stand on its own.

## 21.3 A shared board and hard limits

The orchestrator keeps one **board** of tasks: who has each task, who gave it, how deep in the hierarchy it sits and what came back.

@@code ch21_orchestrator.py::Agent,Task,Board.post

The board enforces the limits no prompt can guarantee:

- **Depth.** A specialist may delegate further only while the task is shallower than `max_depth`. Otherwise agents delegate to agents that delegate to agents, and nobody does the work.
- **Task count.** After `max_tasks` the team accepts no new tasks, so two agents asking each other the same question hit this limit instead of your budget.
- **No duplicate work.** An agent that already finished the same brief gets the stored result back.
- **A token budget per agent.** An agent over budget fails its next task, and the lead hears about it.

Only the orchestrator writes the board, so no agent can mark another's task done or rewrite a result. It's Chapter 17's rule for shared memory, applied to shared work.

## 21.4 Briefs, not histories

A specialist gets exactly one thing, the brief. It never sees the lead's conversation, the other specialists' results or the lead's tools:

@@code ch21_orchestrator.py::Team.delegate_tool,Team.run_task

Context isolation (Chapter 16) pays off here. Each specialist's context stays small, so it's cheaper and more focused. A prompt injection that reaches one specialist can't reach the others, because they never see its context. And you can test each specialist alone, like a function. The price is that the lead must write good briefs: the objective, what's out of scope, the form of the answer and the facts the specialist needs, just as Chapter 11's `make_plan` asked.

## 21.5 How teams fail, and containment

Teams of agents fail in ways single agents don't:

Table: How teams of agents fail, and the defense for each
| Failure | Example | Defense |
| --- | --- | --- |
| Vague handoffs | "Get the numbers" comes back as prose | Contracts (section 21.2) |
| Duplicate or conflicting work | Two agents query the same data and disagree | The board; verification (section 21.6) |
| Runaway delegation | Agents keep handing work down or around | Depth and task limits |
| Cascading errors | One wrong result becomes everyone's premise | Evidence in every result |
| Silent failure | A specialist gives up; the lead invents its answer | Failures reported as errors |
| Over-trust | The lead obeys a specialist's text | Results labeled as data |

The orchestrator **contains** failures. When a specialist fails, runs out of budget or ends without a result, the lead's delegate call returns an `ERROR:` result. Nothing raises, and the lead can retry with a better brief, ask another specialist or report that part as unknown:

@@code ch21_orchestrator.py::Team.delegate

Results come back wrapped in a `<result from=... task=...>` label, so the lead reads them as data from a named agent, never as instructions.

## 21.6 Resolving disagreement

When two agents disagree, or when one result matters a lot, don't let the lead pick the answer it likes. Give it a way to check:

- **Independent verification.** A checker agent re-derives the claim with its own tools and query, without seeing how the first agent did it. The demo team uses one for the key number.
- **Evidence over confidence.** When two results conflict, compare their queries and sources. A confidence label costs the agent nothing to write.
- **Code where code can decide.** If the database can compute the number, compute it (Chapter 22). Agents are for judgment, not arithmetic.
- **A person** for disagreements that matter and that evidence can't settle.

Run the demo with `./course.sh python ch21_orchestrator.py`. The board shows the lead's task, then the analyst's and the checker's one level deeper, with each agent's tokens. Compared with the analyst alone, the team costs more, and it's worth it only if the check catches mistakes you care about.

## 21.7 Agents across boundaries: A2A

Section 13.6 published an agent as an MCP tool, which works well when you control both sides. Across companies it strains. The caller must know the tool's name in advance, gets no progress while a long task runs, and has no task it can track, cancel or resume. **A2A (Agent2Agent)** is the open protocol for that case. Google released it in 2025 and handed it to the Linux Foundation that summer, the same umbrella that now hosts MCP, and a stable 1.0 specification followed in early 2026. Microsoft, AWS and Google Cloud support it.

Table: How MCP and A2A divide the work
|  | MCP | A2A |
| --- | --- | --- |
| Connects | An agent to **tools** and data | An agent to **other agents** |
| The other side is | A server with functions you call | An independent agent with its own model, tools and limits |
| You discover it with | `list_tools` after connecting | An **agent card** at `/.well-known/agent-card.json` |
| One exchange is | A tool call and a result | A **task** that moves through states (working, completed, failed) and returns **artifacts** |
| Typical use | Give your agent capabilities | Delegate a whole job to an agent someone else runs |

Most systems need only MCP. Reach for A2A when the agent you want to call belongs to another team or company, runs on a framework you don't control, or works long enough that the caller needs progress updates. Here is the Chapter 8 analyst, published with the official Python SDK, `a2a-sdk`:

@@code ch21_a2a_server.py::CARD,AgentLoopExecutor.execute,RequireToken,build_app~

The **agent card** is the public description: the agent's name, its *skills* with examples, how to reach it and, when you set `A2A_TOKEN`, that callers need a bearer token. The **executor** turns each incoming task into one run of the Chapter 4 `run_agent` loop, reporting *working*, then *completed* with the answer as an artifact, or *failed*. The **server** publishes the card and a JSON-RPC endpoint. Its token check leaves the card public on purpose, because the card is how callers find you.

The client reads the card, sends a message and streams the events back. It can also wrap a remote agent as an ordinary tool, and `Agent(remote_url=...)` in `ch21_orchestrator.py` puts one on the board like any local specialist:

@@code ch21_a2a_client.py::ask_remote_agent,a2a_tool~

Try it in one terminal (the client starts its own copy of the server):

```
./course.sh python ch21_a2a_client.py                # card, then one task
./course.sh python ch21_a2a_client.py --coordinator  # a local agent delegates to it
```

Or run the server alone with `./course.sh serve-a2a`, open `http://localhost:9999/.well-known/agent-card.json` in your browser, and point the client at it from a second terminal with `--url http://agentic-ai-a2a:9999` (the server runs in its own container, and that's the name other containers use to reach it).

Contracts, limits and containment still apply across the boundary, and crossing it adds work of its own. You now have to **authenticate both ways**. Require a token (or OAuth, or mutual TLS) for incoming tasks, and check who you're calling, since a *signed* agent card proves which organization published it. You also have to remember that **a remote agent's answer is untrusted content** from a model you don't control. Mark it as untrusted before it enters your context (exercise 14.5), keep it away from the agent that acts (section 25.5), and never let it trigger an irreversible action without your own approval gate.

## 21.8 MCP or A2A?

Both protocols can put another agent behind a call. Microsoft's guidance compares them like this:

Table: An agent behind MCP or behind A2A
|  | An agent behind MCP | An agent behind A2A |
| --- | --- | --- |
| Best for | One orchestrator that keeps control of reasoning and results | Independent agents, often from other organizations, that report progress |
| Who reasons | The host calls tools and combines outputs | The called agent reasons on its own; its tools are hidden |
| Change | New capabilities usually need the client to learn new tools | Capabilities are discovered from the agent card at run time |

The practical rule: **MCP inside your system, A2A at its boundary.** Expose an agent your team runs as an MCP tool, or call it in code as `ch21_orchestrator.py` does. Save A2A's cards, tasks and progress updates for agents another company runs.

MCP and A2A are two of several ways to connect an agent system's parts. Go down this card and pick the simplest thing that meets each need; Appendix I repeats it as a one-page reference.

## 21.9 When not to build a team

Section 11.5's test still decides: independent parts, parallelism that matters and a measured gain worth the cost. If a fixed workflow (Chapter 1) can do the job, it's cheaper and more predictable than negotiating agents. If every part needs everything, one agent with good context engineering (Chapter 16) beats a team. A common design passes work among five agents when one well-briefed agent would be faster, cheaper and far easier to debug. And "worth the cost" must now include the coordination overhead, which the next section measures.

The support agent becomes a small team. A lead reads the request and delegates to specialists (billing, shipping, returns) through one tool, each with only the tools its job needs. Results come back as checked contracts, and depth, task and budget limits stop the team from running away.
:::

## 21.10 Does the team pay for itself?

A team isn't automatically better than one agent. It's a trade, and you settle it with measurements. The question is whether **the extra capability the team creates exceeds its coordination cost and the extra ways it can fail.**

The capability is higher success on hard tasks and lower latency when parts run at once. The cost is **coordination overhead**, meaning everything the team spends that one agent doesn't. It breaks down into the terms below, and you can measure each one from a trace (Chapter 28) or from per-run stats.

Table: The overhead terms of a team of agents {#t:coordination-overhead}
| Term | What causes it | How to measure it |
| --- | --- | --- |
| Extra model calls | The lead plans and synthesizes; every worker runs its own loop | Model calls per task (`steps` in `run_agent`'s stats), the lead's counted separately |
| Duplicated context | Each worker loads the system prompt and tool definitions again | First-call input tokens, summed over every worker but one |
| Inter-agent messages | Briefs out, results back, checks | Delegations and results per task, on the board (section 21.3) |
| Synchronization | The lead waits for the slowest worker | Slowest worker's latency minus the mean, per task |
| Retries | Contract violations, failed workers, re-delegation | Retries per task |
| Latency | Planning, slowest worker and synthesis run in sequence | p50 and p95 per task, on the same tasks as one agent |
| Failure propagation | More steps that can fail; one bad result misleads the rest | Share of tasks with a failed part; success on known answers |
| Total cost | All of the above, priced | Cost per task and per successful task (section 20.9) |

Put together, the terms make a simple model:

```
team cost     = sum of worker costs + lead planning + lead synthesis
                + duplicated context + messages                 (all priced as tokens)
team latency  = lead planning + max(worker latencies) + synthesis
p(task right) = p(lead steps) x p(step) ^ n                     n worker steps
```

Look at the `max` first. The team is only as fast as its slowest worker, and it adds two model calls to the critical path, so parallel workers save time only when that sum beats one agent doing the parts itself. Then look at the exponent. Suppose each step is right 97% of the time. A lead that plans and synthesizes around three workers has five steps, and gets all of them right 0.97 to the fifth power of the time, or 86%, against 97% for one step. Real steps differ, of course. A narrowly briefed worker may beat one agent juggling everything, and that's the capability you're paying for, so measure it. But the exponent is why a team needs containment. A contained failure is visible and can be retried, and one retry per worker lifts the same team back to 94%. A failure that raises, or that the lead papers over, gets no second chance.

So the team is worth it in two cases. The first is when its **success gain, valued per task, exceeds its extra cost per task**. Written out, (team success − single success) × what one success is worth > team cost per task − single cost per task, and the gain has to be clear of the overlap between the two confidence intervals. The second is when the team meets a **latency or quality requirement** that one agent can't, such as a p95 your SLO (section 28.10) demands.

Divide the extra cost by the success gain and you get the **break-even value**, which is what a right answer must be worth for the team to pay for itself. `ch21_coordination.py` computes the report and the verdict from the per-run stats `run_agent` returns (`steps`, `input_tokens`, `output_tokens`), plus `ok`, latency, cost and the team's coordination terms:

The simulator's latencies and error rates are stated assumptions, so it shows each design's mechanics exactly and says nothing about how good a real model is. A right answer is valued at $0.05.

Table: One agent or a lead with workers, on the simulator {#t:team-economics}
| Questions | Design | Success (95% CI) | Calls | Tokens | p95 s | $ per task | Verdict |
| --- | --- | --- | ---: | ---: | ---: | ---: | --- |
| One-part | One agent | 97% (92–99%) | 3.0 | 1,109 | 4.6 | 0.0031 | **One agent** |
| One-part | Lead with workers | 97% (92–99%) | 5.0 | 1,325 | 7.1 | 0.0041 | |
| Multi-part | One agent | 93% (79–98%) | 3.0 | 1,229 | 5.5 | 0.0038 | **One agent** |
| Multi-part | Lead with workers | 97% (83–99%) | 8.5 | 2,752 | 7.8 | 0.0083 | |
| Multi-part, 3 s tools | One agent | 93% (79–98%) | 3.0 | 1,229 | 17.4 | 0.0038 | |
| Multi-part, 3 s tools | Lead with workers | 97% (83–99%) | 8.5 | 2,752 | 15.7 | 0.0083 | **Team** (SLO 16 s) |
| Multi-part, 3 s tools | One agent, parallel tool calls | 93% (79–98%) | 3.0 | 1,229 | 13.5 | 0.0038 | **One agent** |

On **one-part questions** there's nothing to split, so the team is pure overhead. It gets the same answers with two more calls (both the lead's) at 1.3 times the cost.

On **multi-part questions** the team sends 1,347 more input tokens per task, 225 of them duplicated context, and waits 0.23 seconds for its slowest worker. It costs 2.2 times as much and is slower, because one agent already asks for every part in one turn. The team got one more task of 30 right, but the intervals overlap almost entirely, so that's no evidence of a gain. The break-even value is $0.13 per right answer. The verdict is one agent, or more tasks in the evaluation if you think the gain is real.

With **3-second tools**, only the team meets a 16-second p95 SLO, which is a valid reason to pay 2.2 times as much. But let one agent run its tool calls at the same time (section 29.8 measures this) and it reaches 13.5 seconds at the single agent's price. Always compare the team with the best single agent you can build.

None of this means teams never pay. On broad research, where each worker reads different sources and one context can't hold them all, Anthropic measured a real gain (Chapter 11). But you have to measure the gain on your tasks against every term in the table, and each term has a cheaper fix to try first. Parallel tool calls help with latency, context engineering (Chapter 16) handles big contexts, and a workflow (Chapter 1) suits fixed steps. `failure_propagation` covers the failure side. It shows how many parts are still right when a pipeline breaks partway, when one crash stops the team, and when failures are contained and retried. In production, read these terms from your traces and rerun the comparison whenever a model, prompt or price changes.

## Common mistakes

- Starting with a team when one agent, or a workflow, would do.
- Prose handoffs with no contract, so every agent guesses what the others meant.
- Passing whole conversations between agents instead of briefs.
- No limits on depth, task count or tokens.
- Letting agents write shared state directly, so one confused agent rewrites everyone's picture.
- Raising exceptions from a failed specialist, which takes down the whole team, or hiding the failure so the lead invents an answer.
- Comparing a team with a weak single agent, or on too few tasks, so it "wins" by one task in 30 inside overlapping intervals.

## Key takeaways

**Architect's takeaway:** Start with one agent, put every limit in code, and add agents only when measurements show a gain.

- Start with a supervisor and limited depth; pick other topologies on evidence.
- Contracts define what agents hand each other, and code validates them.
- Only the orchestrator writes the board, and it enforces depth, task, duplicate and budget limits.
- Specialists get briefs instead of histories, and failures come back as error results the lead can handle.
- Settle disagreements with independent verification, evidence, code and people.
- MCP inside your system, A2A at its boundary.
- A team pays for itself only when its measured gain beats its coordination overhead, or it meets a requirement one agent can't.
