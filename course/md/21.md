# Chapter 21: Multi-Agent Orchestration

Chapter 11 built your first teams: a lead with parallel researchers, a router, a pipeline, a writer with a critic. Those teams were small, lived in one program and trusted each other. Real multi-agent systems are bigger and messier. Specialists hand work to other specialists, results come back in shapes nobody agreed on, two agents do the same work, one confused agent's mistake spreads to all the others, and some agents belong to other teams or other companies. This chapter is about the engineering that keeps a team of agents coordinated: contracts, a shared record of the work, limits, isolation, verification and a protocol for agents you don't run yourself.

**What you'll build:** an orchestrator in which a lead delegates to specialists through one tool, with results checked against a contract, a shared task board, depth, task and budget limits, contained failures and remote specialists reached over A2A.

**You are here:** Agent runtime and A2A in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Choose a team topology: supervisor, hierarchy, pipeline, shared board or network.
- Define contracts for what agents hand each other, and enforce them in code.
- Keep one shared record of the team's work, with limits on depth, tasks and tokens.
- Give each agent a brief instead of the whole conversation.
- Recognize how teams of agents fail, and contain one agent's failure.
- Resolve disagreements between agents with independent verification.
- Publish an agent with the A2A protocol, call a remote agent and choose between MCP and A2A.

## Prerequisites

## Real-world connection

Multi-agent systems moved from demos to products in 2025 and 2026: research features with a lead and parallel subagents, coding tools that run several agents on one codebase and enterprise platforms where agents from different vendors hand work to each other. The same period produced sober lessons. Anthropic reported that its multi-agent research system beat a single agent on broad research questions but used many times the tokens (Chapter 11), and a 2025 study of popular multi-agent frameworks grouped 14 failure modes into three families: problems in how the system and its tasks are designed, misalignment between agents and weak verification of results. Microsoft's guidance for multi-agent systems stresses least privilege, auditability, human approval for high-impact actions between agents and limiting the context agents share to what's necessary. Those are the themes of this chapter.

## 21.1 Topologies

How agents are connected decides how work and errors flow:

| Topology | How it works | Good for | Watch out for |
| --- | --- | --- | --- |
| **Supervisor** | One lead delegates to specialists and combines their results | Most tasks; the default | The lead becomes a bottleneck |
| **Hierarchy** | Specialists can delegate further, to their own sub-specialists | Large tasks that split naturally into levels | Runaway depth and cost |
| **Pipeline** | Each agent transforms the previous agent's output | Fixed sequences: draft, review, format | One bad stage spoils the rest |
| **Shared board** | Agents read and write one shared record of tasks and results | Many agents, loosely coupled | Conflicting writes, stale reads |
| **Network** | Independent agents call each other across teams or companies | Cross-organization work | Trust, identity, versioning |

The Chapter 11 patterns (router, handoff, critic, vote) fit inside these. This chapter's code is a supervisor that allows a limited hierarchy, keeps a shared board and can include network members over A2A. Start with a supervisor and add the others only when a measurement says you need them.

## 21.2 Contracts between agents

Inside one agent, the model reads whatever a tool returns. Between agents, a vague handoff is the first family of failures: the lead asks for "the numbers", the specialist returns a paragraph, and the lead guesses which number mattered. A **contract** fixes the shape of what agents hand each other:

@@code ch21_orchestrator.py::RESULT,SUBMIT

Every specialist finishes by calling `submit_result`, and the orchestrator validates the arguments against the JSON schema with the `jsonschema` library **in code**. An answer without evidence, a confidence that isn't one of three words, or a 10,000-character essay is rejected with a message the specialist can act on, like a tool error in Chapter 8. The brief going the other way is a contract too, even though it's prose: the delegate tool's description tells the lead that specialists can't see its conversation, so every brief must stand alone.

## 21.3 A shared board and hard limits

The orchestrator keeps one record of the team's work, a **board** of tasks: who has each task, who gave it, how deep in the hierarchy it is and what came back.

@@code ch21_orchestrator.py::Agent,Task,Board

The board enforces the limits no prompt can guarantee:

- **Depth.** A specialist may delegate further only while the task is shallower than `max_depth`. Without it, agents delegate to agents that delegate to agents, and nobody does the work.
- **Task count.** The team stops accepting new tasks after `max_tasks`. A loop of agents asking each other the same question hits this limit instead of your budget.
- **No duplicate work.** If the same agent already finished the same brief, the stored result is returned instead of running it again.
- **A token budget per agent.** An agent over its budget fails its next task, and the lead hears about it.

Only the orchestrator writes the board. Agents see it through what the orchestrator gives them, so no agent can mark another's task done or rewrite a result. This is Chapter 17's rule for shared memory applied to shared work.

## 21.4 Briefs, not histories

The delegate tool gives a specialist one thing: the brief. Not the lead's conversation, not the other specialists' results, and not the lead's tools:

@@code ch21_orchestrator.py::Team.delegate_tool,Team.run_task

This is context isolation (Chapter 16) as a design rule, and it pays three times. Each specialist's context stays small, so it's cheaper and more focused. A prompt injection that reaches one specialist through a tool result doesn't reach the others, because they never see its context. And each specialist can be tested alone, with a brief and a contract, like a function. The cost is that the lead must write good briefs: the objective, what's out of scope, the form of the answer and any facts the specialist needs. Chapter 11's `make_plan` asked for exactly that.

## 21.5 How teams fail, and containment

Teams of agents fail in ways single agents don't:

| Failure | Example | Defense |
| --- | --- | --- |
| Vague handoffs | "Get the numbers" comes back as prose | Contracts (section 21.2) |
| Duplicate or conflicting work | Two agents query the same data and disagree | The board; independent verification (section 21.6) |
| Runaway delegation | Agents keep handing work down or around | Depth and task limits |
| Cascading errors | One agent's wrong result becomes everyone's premise | Evidence in every result; verification |
| Silent failure | A specialist gives up, and the lead invents its answer | Failures reported as errors |
| Over-trust | The lead treats a specialist's text as instructions | Results labeled as data from another model |

The orchestrator **contains** failures. When a specialist fails, runs out of budget or ends without a result, the lead's delegate call returns an `ERROR:` result that says so. Nothing raises, and the lead can retry with a better brief, ask another specialist or report that part as unknown:

@@code ch21_orchestrator.py::Team.delegate

Results come back wrapped in a `<result from=... task=...>` label, so the lead's model sees them as data from a named agent, not as its own conclusions or as instructions.

## 21.6 Resolving disagreement

When two agents disagree, or when one result matters a lot, don't let the lead pick the answer it likes. Give it a way to **check**:

- **Independent verification.** A checker agent re-derives the claim with its own tools and its own query, without seeing how the first agent did it. The demo team has one, and the lead's instructions say to use it for the key number.
- **Evidence over confidence.** The contract requires evidence. When two results conflict, compare the evidence (the queries, the sources), not the confidence labels.
- **Code where code can decide.** If the disagreement is about a number the database can compute, compute it (Chapter 22). Agents are for judgment, not arithmetic.
- **A person** for disagreements that matter and can't be settled by evidence.

Run the demo with `./course.sh python ch21_orchestrator.py`. The board shows the lead's task, the analyst's task and the checker's task, one level deeper, and the token use of each agent. Compare it with asking the analyst alone: the team costs more, and it's only worth it if the check catches mistakes you care about.

## 21.7 Agents across boundaries: A2A

Everything so far ran inside one program. Section 13.6 published an agent as an MCP tool, which works well inside one team, where you control both sides. Across teams and companies it starts to strain: the caller has to know the tool's name in advance, it gets no progress while a long task runs and a tool call has no notion of a task that can be tracked, cancelled or resumed. **A2A (Agent2Agent)** is the open protocol for that case. Google released it in 2025, it reached a stable 1.0 specification in early 2026, and since August 2026 it has been hosted by the same Linux Foundation body as MCP. Microsoft, AWS and Google Cloud support it in their agent platforms.

The two protocols divide the work:

|  | MCP | A2A |
| --- | --- | --- |
| Connects | An agent to **tools** and data | An agent to **other agents** |
| The other side is | A server with functions you call | An independent agent with its own model, tools and limits |
| You discover it with | `list_tools` after connecting | An **agent card** at `/.well-known/agent-card.json` |
| One exchange is | A tool call and a result | A **task** that moves through states (working, completed, failed) and returns **artifacts** |
| Typical use | Give your agent capabilities | Delegate a whole job to an agent someone else runs |

In short: MCP below, A2A above. Most systems need only MCP. Reach for A2A when an agent you want to call is owned by another team or company, built with a framework you don't control, or runs long enough that the caller needs progress updates.

@@code ch21_a2a_server.py::CARD,AgentLoopExecutor.execute,RequireToken,build_app

It has three parts. The **agent card** is the agent's public description: its name, what it's good at (its *skills*, with examples), how to reach it and, when you set `A2A_TOKEN`, that callers need a bearer token. The **executor** turns each incoming task into one run of the same `run_agent` loop you wrote in Chapter 4, reporting a *working* status first and then either a *completed* task with the answer as an artifact or a *failed* one. The **server** publishes the card and a JSON-RPC endpoint; the token check deliberately leaves the card public, because the card is how callers find you.

The client side discovers the agent from its card, sends a message and reads the stream of events. It also wraps a remote agent as an ordinary tool, so a coordinator can delegate to it without knowing it's an agent, and `Agent(remote_url=...)` in `ch21_orchestrator.py` puts a remote agent on the team's board like any local specialist:

```

./course.sh python ch21_a2a_client.py --coordinator  # a local agent delegates to it
```

Or run the server on its own with `./course.sh serve-a2a`, open `http://localhost:9999/.well-known/agent-card.json` in your browser, and point the client at it from a second terminal with `--url http://agentic-ai-a2a:9999`.

Everything earlier in this chapter still applies across the boundary (contracts, limits, containment), with two additions:

- **Authenticate both ways.** Require a token (or OAuth, or mutual TLS) for tasks, and check who you're calling: an agent card can be *signed*, so a caller can verify it came from the organization it claims.
- **A remote agent's answer is untrusted content.** It comes from a model you don't control, fed by data you can't see. Mark it as untrusted before it enters your context (exercise 14.5), keep it away from the agent that acts (section 25.5), and never let it trigger an irreversible action without your own approval gate.

## 21.8 MCP or A2A?

Both protocols can put another agent behind a call. Microsoft's multi-agent guidance compares them along lines that match this book:

|  | An agent behind MCP | An agent behind A2A |
| --- | --- | --- |
| Best for | A single orchestrator that keeps control of reasoning and results | Independent agents, often from other organizations, that negotiate and report progress |
| Who reasons | The host orchestrates tool calls and combines the outputs | The called agent uses its own reasoning; its tools are hidden from the caller |
| Change | New capabilities usually need the client to learn new tools | Capabilities are described in the agent card and discovered at run time |
| Context | Stays with the host | A context id lets agents keep related tasks together |
| Use it for | Your own agents, APIs and data, where you want control | External agents and cross-organization workflows |

A practical rule: **MCP inside your system, A2A at its boundary.** An agent your team runs is usually best exposed as an MCP tool, or called directly in code as in `ch21_orchestrator.py`. An agent another team or company runs is where A2A's cards, tasks and progress updates earn their complexity.

### The decision card: MCP, A2A, API, workflow or something else?

MCP and A2A are two of several ways to connect the parts of an agent system. When you design one, go down this card and pick the simplest thing that meets each need. Appendix I repeats it as a one-page reference card.

| You need to... | Use | Where in this book |
| --- | --- | --- |
| Connect a model to a tool or to data | A tool; package it as an **MCP** server to share it | Chapters 2, 12 |
| Let independent agents collaborate across a boundary | **A2A** | Section 21.7 |
| Let one service call another, conventionally | A plain **API** | Chapters 7, 30 |
| Run a deterministic business process | A **workflow** or state machine | Chapters 1, 22 |
| Get a person's decision before acting | **Human in the loop**: an approval gate | Chapters 9, 26 |
| Run work that takes hours and must survive crashes | A **durable workflow** | Chapter 19 |
| Search and retrieve knowledge | A **retrieval system** (search, RAG) | Chapters 6, 18 |
| Do something local and simple | A plain **tool** (a function) | Chapter 2 |
| Share one front door for many tools, with policy | An **MCP gateway** | Chapter 15 |

Most real systems combine several rows. The support agent in this book uses tools behind MCP, a workflow for refunds, human approval above a limit, retrieval for policy questions and, if a partner company runs the shipping agent, A2A at that one boundary.

## 21.9 When not to build a team

Multi-agent systems are tempting to over-build. Before adding an agent, check that it earns its place:

- **Does the work split into parts that don't need each other's context?** If every part needs everything, one agent with good context engineering is better.
- **Does parallelism matter?** A team is faster only when subtasks run at the same time.
- **Is the extra cost worth it?** Measure quality, time and tokens against a single agent (exercise 11.6), and report cost per successful task (Chapter 20).
- **Can a workflow do it?** A fixed pipeline of model calls (Chapter 1) is cheaper and more predictable than agents negotiating.

The support agent becomes a small team. A lead agent reads the request and delegates to specialists (billing, shipping, returns) through one tool, each with only the tools its job needs. Results come back as checked contracts, not prose, and depth, task and budget limits stop the team from running away.
:::

## Architect's Takeaway

Wrong routing costs more than wrong execution: invest in routing quality early.

## Common mistakes

- **Starting with a team** when one agent, or a workflow, would do.
- **Prose handoffs** with no contract, so every agent guesses what the others meant.
- **Passing whole conversations** between agents instead of briefs.
- **No limits** on depth, task count or tokens.
- **Letting agents write shared state directly**, so one confused agent rewrites everyone's picture.
- **Raising exceptions** from a failed specialist, so one failure takes down the whole team, or hiding the failure so the lead invents an answer.
- **Treating another agent's answer as trusted**, or as instructions.
- **Using A2A between your own agents** in one program, where a function call or MCP is simpler.

## Summary

- Choose a topology deliberately; a supervisor with limited depth is the usual start.
- Contracts define what agents hand each other, and code validates them.
- A shared board records the team's work; only the orchestrator writes it, and it enforces depth, task, duplicate and budget limits.
- Specialists get briefs, not histories: smaller, safer and testable.
- Contain failures as error results the lead can handle, and label results as data from another agent.
- Resolve disagreements with independent verification, evidence, code and people.
- A2A connects agents across teams and companies through agent cards and tasks; MCP inside your system, A2A at its boundary.

Every rule in this chapter that mattered was enforced by code, not by the prompt: the contract, the limits, the board. Chapter 22 makes that the central design principle: probabilistic intelligence where judgment is needed, deterministic control everywhere else.
