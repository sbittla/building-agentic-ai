# Chapter 24: Skills, Frameworks and Agent Runtimes

You've built every part of an agent by hand: the loop, tool schemas, limits, approval gates, memory, and in this part durable jobs, plans, teams, controls and a browser. In this chapter you'll build agents three more ways, with the Anthropic SDK's tool runner, the Claude Agent SDK and LangChain, see what a fully managed runtime takes off your hands, and package know-how as skills an agent loads when it needs them. By the end you'll be able to read any framework's documentation with confidence and decide which runtime, if any, earns its place.

**What you'll build:** the same agent with the Claude tool runner, the Agent SDK, LangChain and Managed Agents, plus a skill of your own and an evaluation that shows whether it helps.

**You are here:** Agent runtime in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Map every part of your hand-built agent onto a framework's features.
- Use the Anthropic SDK's tool runner to replace your own loop.
- Build an agent with the Claude Agent SDK: custom tools, permissions, turn and budget limits.
- Build a model-agnostic agent with LangChain's `create_agent`.
- Choose between building by hand and using a framework.
- Package know-how as an Agent Skill, and test whether it actually helps.
- Run an agent on Claude Managed Agents.
- Choose a runtime for long-running, multi-agent work.

## Real-world connection

You wrote the loop yourself so you'd understand it. In production, most teams use a framework (a library that supplies the plumbing so you write less of it). The Claude Agent SDK is the same agent runtime that powers Claude Code, packaged for your own agents. LangChain and LangGraph are widely used, model-agnostic alternatives. Because you've built every part by hand, you'll recognize what each feature in their documentation does.

## 24.2 The tool runner: your loop, built in {api}

@@code ch24_tool_runner.py

`@beta_tool` reads the function's type hints and docstring (including the `Args:` section) to build the JSON Schema you wrote by hand in Chapter 2. `tool_runner` calls the model, runs the tools it asks for, sends the results back and repeats, up to `max_iterations`. It's Chapter 4's `run_agent` in one call. Iterating over the runner gives you each model response as it happens, so tracing still works.

## 24.3 The Claude Agent SDK {api}

@@code ch24_agent_sdk.py::approve,OPTIONS,ask

The Agent SDK runs a full agent runtime in a separate process and handles the communication with it for you. Notice four things:

- **In-process tools.** `@tool` functions are served by an MCP server running inside your program (`create_sdk_mcp_server`). Their names become `mcp__shop__run_query`, the same `server__tool` namespacing you built in Chapter 13.
- **Isolation.** `tools=[]` turns off the built-in tools (file editing, shell, web). `strict_mcp_config=True` ignores any MCP servers configured elsewhere on the machine, and `setting_sources=[]` ignores settings files. Without these, an agent can pick up capabilities you never gave it.
- **Permissions.** `allowed_tools` lists tools that are approved automatically. Every other tool call goes to `can_use_tool`, the Chapter 9 approval gate as a callback (a function the SDK calls for you). Here `get_schema` is auto-approved, and `run_query` is allowed only for `SELECT` statements.
- **Limits.** `max_turns` is the iteration cap, and `max_budget_usd` stops the run when it reaches a dollar amount. The final `ResultMessage` reports turns and cost.

:::warn allowed_tools skips your approval callback
A tool listed in `allowed_tools` is approved **before** `can_use_tool` is consulted, so your callback never runs for it. The SDK prints a `CanUseToolShadowedWarning` when this happens. Here the warning is expected for `get_schema`, which is deliberately auto-approved. Put only harmless tools in `allowed_tools`, and route everything else through the callback or a `PreToolUse` hook.
:::

The approval callback needs the prompt as a stream of messages ("streaming input"), which is why `ask` passes `_prompt(question)` rather than a plain string.

## 24.4 LangChain: model-agnostic agents {api}

@@code ch24_langchain.py

`create_agent` turns plain functions into tools (the docstring is the description), runs the loop on LangGraph and returns the full message history. Replace `ChatAnthropic` with another provider's chat model and nothing else changes. That portability is the main reason to choose it, along with its middleware (pluggable steps that run around each model or tool call) for summarization, call limits and human approval.

## 24.5 Build or buy?

| Build by hand when… | Use a framework when… |
| --- | --- |
| You're learning, or the agent is small | The agent needs sessions, compaction, subagents or hooks you'd otherwise write |
| You need full control of every request | You want well-tested plumbing and fewer lines to maintain |
| Dependencies must be minimal | Your team already uses the framework |

Whatever you choose, keep the practices from this book: tool design, approval gates in code, evaluation suites and cost tracking all apply. A framework changes how much code you write, not what good looks like.

## 24.6 Using other model providers {api}

This book uses Claude for every example, but almost nothing in it is specific to one provider. Most models with tool calling (from OpenAI, Google, Mistral or open-weight models you run yourself) follow the same pattern: you send messages and tool definitions, the model asks for a tool, your code runs it and sends back the result.

| Carries over unchanged | Differs between providers |
| --- | --- |
| The agent loop, iteration caps and budgets (Chapter 4) | The message format: how tool calls and results are wrapped |
| Tool design: names, descriptions, JSON Schema, errors as text | The names of stop reasons and of the tool-choice settings |
| Approval gates, sandboxes, policies and the lethal trifecta | Prompt caching, thinking and structured-output options |
| Evaluation suites, judges and load tests | Prices, rate limits and context sizes |
| MCP servers and clients: MCP is vendor-neutral | Which built-in tools the API offers |

Three ways to switch, from least to most work:

1. **Use a framework's model interface.** In `ch24_langchain.py`, replacing `ChatAnthropic` with another provider's chat model is a one-line change (section 24.4).
2. **Keep model calls behind one function.** This book's code already does: every chapter gets its client from `get_client()` in `ch04_agent.py` and reads the reply in one place, `next_action`. Write a small adapter that converts your messages and tools to the other provider's format and its reply back, and the rest of your agent stays the same.
3. **Use an OpenAI-compatible endpoint** if your provider or model server offers one, with a library that speaks that format.

The kit itself shows a fourth way: if a model server speaks the Anthropic Messages API, point the SDK at it with `ANTHROPIC_BASE_URL`, and fill any gaps with a small proxy. That's how the free local model in Appendix H works: Ollama serves `qwen3.5:9b`, and `course/local_adapter.py` turns forced tools and structured outputs into requests a local model understands. Read it after this section: it's the "small adapter" from option 2, built as a service.

Whichever you choose, rerun your evaluation suite (Chapter 27) after switching. Models differ in how eagerly they call tools and how well they follow tool descriptions, and only measurement tells you whether the new model is as good for *your* agent.

## 24.7 Agent Skills: packaging know-how {api}

A **skill** is a folder that teaches an agent how to do one kind of task: a `SKILL.md` file with a name, a one-line description and instructions, plus optional `scripts/`, `references/` and `assets/` folders. It started at Anthropic and is now an open format (agentskills.io) read by Claude Code, the Claude Agent SDK, the Claude API and many other agents, so a skill you write once works in all of them.

The design is **progressive disclosure**, which is context engineering (Chapter 16) as a file format. The agent sees only each skill's description (about 100 tokens) until a task matches it. Then it reads the instructions, and only if those mention a reference file or script does it load that too. A hundred installed skills cost a few thousand tokens, not a few hundred thousand.

:::tip On the free local model
Writing a skill needs no model at all, but running one through the Claude API (`ch24_skills.py`, exercise 24.6) uses Anthropic's code-execution container, so it needs Claude (`PROVIDER=claude`).
:::

This file checks skills against the specification and gives your own Chapter 4 agent the same behavior, with one extra tool:

@@code ch24_skills.py::parse_skill,validate,catalog,read_skill,system_prompt

Rules the validator enforces, straight from the specification: `name` is 1–64 lowercase letters, digits and single hyphens, and matches the folder name; `description` says **what the skill does and when to use it**, in at most 1,024 characters (it's the only part the model sees up front, so write it like a tool description); keep `SKILL.md` under 500 lines and move details into `references/`.

A skill is **procedural memory that people wrote down and reviewed** (Chapter 17): the agent doesn't learn it from a conversation, a person writes it, a teammate reviews it, and version control records every change. That makes skills the safe home for "how we do things here", and it means a skill deserves the same testing as code. The question isn't whether the skill reads well; it's whether the agent does the task better with it than without it. Exercise 24.8 measures exactly that, with checks in code on the agent's output.

:::warn A skill is code you're choosing to trust
A skill can tell an agent to run its scripts. Treat a third-party skill like a third-party MCP server (section 14.3): read it before installing, pin the version and give the agent no more permissions than the skill needs.
:::

## 24.8 Claude Managed Agents: renting the whole runtime {api}

The tool runner and the Agent SDK still run the loop on *your* machine. **Claude Managed Agents** runs it on Anthropic's: you define an agent (model, system prompt, tools, MCP servers, skills), an **environment** (a sandbox with its own file system and network rules) and start **sessions**. The agent works in its sandbox with built-in tools (bash, file reading and editing, search, web fetch), and your code follows a stream of events.

:::tip On the free local model
Claude Managed Agents runs on Anthropic's servers, so this section and its exercise need Claude (`PROVIDER=claude` in `.env`). On the local model the kit stops with a clear message instead. Appendix H lists every exercise that needs Claude.
:::

| You built | In Managed Agents |
| --- | --- |
| The loop and its tools (Chapters 4, 6, 10) | Runs on the server; the built-in toolset is `agent_toolset_20260401` |
| Tools that must stay local (Chapter 8's database) | **Custom tools**: the session pauses, your code runs the tool and sends `user.custom_tool_result` |
| Approval gates (Chapter 9) | **Permission policies** per tool: `always_allow`, `always_ask` (you answer with `user.tool_confirmation`) or `auto` |

| Budgets (Chapters 4 and 10) | A hard **session budget**; the session stops with `budget_reached` |
| Memory (Chapter 16) | **Memory stores** mounted into sessions |
| Multi-agent teams (Chapter 11) | A coordinator agent with a roster of subagents |

Choose it when you want long-running agents with a real sandbox, and you'd rather not operate that sandbox yourself. Keep building by hand when you need to run fully on your own infrastructure, or need control over every request. Managed Agents was a public beta when this book was written, so check the documentation for current names.

## 24.9 Choosing a runtime

Part 7 added requirements that a simple loop doesn't meet: work that survives crashes, plans and model routing, teams of agents, hard controls and sandboxes. A **runtime** is whatever runs your agent and provides those things. You have a spectrum of choices:

| Runtime | Where the loop runs | What you get | What stays your job |
| --- | --- | --- | --- |
| Your own loop (this book) | Your code | Full control, no dependencies | Everything in Chapters 19–23 |
| The tool runner | Your code | The loop, with less code | Durability, teams, controls |
| The Claude Agent SDK | Your machine or container | Sessions, subagents, hooks, permissions, built-in tools | Hosting, durability across machines, evaluation |
| LangGraph and similar | Your code | Graphs of steps, checkpointers, many model providers | Choosing and operating the storage, controls |
| A durable-execution platform with your loop inside | Your workers | Crash-proof steps, retries, timers, waiting for people | The agent logic itself |
| Claude Managed Agents | Anthropic's servers | Sandboxes, sessions, permissions, budgets, memory stores | Your tools that must stay local, evaluation |

Ask the same questions of any option:

- **Where does state live, and does a session survive a crash?** (Chapter 19)
- **How are approvals and hard rules expressed**, and can the model get around them? (Chapters 9 and 22)
- **Can you see every step:** model calls, tool calls, tokens and cost? (Chapter 28)
- **Where does code run, and what can it reach?** (Chapters 10 and 23)
- **What does it cost at your volume**, and what would moving away cost?

There's no single right answer. A common path is to prototype with your own loop, move the agent logic onto the Agent SDK or a framework once the design settles, and put anything long-running inside a durable runner. The practices stay the same whichever you choose.

## 24.10 Where the field is going

A few more developments you'll meet as you keep building. Each reuses what you already know:

- **Computer use** (Chapter 23) and **agent-to-agent protocols** such as A2A (Chapter 21) are now core techniques rather than previews. Claude's API also offers computer use and a hosted browser as ready-made toolsets; the controls from Chapter 23 apply to them unchanged.
- **An advisor for the executor.** A cheaper, faster model does the work and consults a stronger model only for hard decisions. Claude's API offers this as an *advisor tool*; it's the orchestrator-and-workers idea from Chapter 11, inside a single agent.
- **Agents that buy things.** Payment networks and AI companies are building protocols for agents to shop and pay on a user's behalf. Every lesson on approvals, budgets and identity applies, because the mistake now costs real money.

## Architect's Takeaway

A framework packages the loop, not the judgment: keep your controls and evaluations portable, and rerun them whenever you change runtime.

## Common mistakes

- **Treating the framework as magic.** Map each feature to what you built, and read what it sends.
- **Putting risky tools in `allowed_tools`**, which bypasses your approval callback.
- **Forgetting isolation settings** and inheriting tools from the machine's configuration.
- **Skipping limits** (`max_turns`, budgets) because the framework "handles it".
- **Rewriting a working hand-built agent** to use a framework, without a reason.

## Summary

- Frameworks package the loop, tool schemas, limits, approvals and memory you built by hand.
- The tool runner is the lightest step: your Chapter 4 loop in one call.
- The Claude Agent SDK is a full agent runtime; isolate it and gate tools with `can_use_tool`.
- A skill is reviewed procedural memory; test that it improves results, with checks in code.
- Choose a runtime by where state lives, how controls are enforced, what you can observe, where code runs, and cost.
- LangChain's `create_agent` is model-agnostic and extensible with middleware.
- Agent Skills package instructions and files that an agent loads only when a task needs them.
- Claude Managed Agents runs the loop and the sandbox for you; custom tools, permission policies and budgets keep you in control.
- The practices matter more than the framework.
- Almost everything in this book works with other model providers: keep model calls behind one function, and rerun your evaluations when you switch.

Part 7 made agents far more capable: they run for hours, plan, work in teams, operate screens and run on real runtimes. Capability without trust is a liability. Part 8 is about trust: Chapter 25 defends agents against the attacks aimed at them, and Chapter 26 gives every agent an identity and only the permissions its task needs.
