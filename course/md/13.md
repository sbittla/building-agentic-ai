# Chapter 13: Build Your Own MCP Client

What exactly did Claude Desktop do in Chapter 12? Between your question and your weather tool, something started the server, asked it what tools it had, showed them to the model and carried each call back. It's easy to treat that layer as magic. It isn't, and it's less code than you'd guess.

**What you'll build:** your own MCP client and host that connects any number of servers to your agent, and an agent that other agents call as an MCP tool.

**You are here:** MCP and Agent runtime in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapters 5 and 8 (the tools it serves), Chapter 12 (MCP basics), the asynchronous Python interlude.

## Learning objectives

By the end of this chapter you can:

- Connect to MCP servers from Python and list their tools.
- Convert MCP tool definitions into the format your model expects.
- Route each tool call to the right server when several are connected.
- Replace the hard-coded tools in your agent loop with tools discovered at run time.
- Publish an agent as an MCP server, so other agents can delegate to it.
- Let a server ask the user for missing details (elicitation) through your host.

**In the real world.** Every MCP host, from Claude Desktop to IDEs to Copilot's cloud agent, does what you'll build here. Write one and you know how they all work underneath.

## 13.1 What changes in the loop

Compare the Chapter 4 loop with an MCP host:

Table: The Chapter 4 agent compared with an MCP agent
|  | Chapter 4 agent | MCP agent |
| --- | --- | --- |
| Tool list | `TOOLS`, written in your code | Built at start-up from `list_tools()` on each server |
| Running a tool | `run_tool(name, args)` calls a Python function | `client.call_tool(name, args)` sends a JSON-RPC request |
| Adding a tool | Edit code and redeploy | Add a server to a config file |
| Errors | `ERROR:` strings | `result.is_error` plus a message |

The loop itself doesn't change. Only where the tools come from does.

**`MCPHub.__aenter__`** calls `_connect` for each server, which starts it with `stdio_client`, opens a `Client` and lists its tools. One `AsyncExitStack` holds every connection open and closes them all at the end. An optional `"log"` entry sends a server's stderr to a file.

Each tool is renamed `server__tool`, so `add_task` becomes `todo__add_task` and two servers' `search` tools no longer collide. The server name also goes into each description. The prefix is this host's convention: MCP makes tool names unique only within one server, so keeping servers apart is the host's job. Each input schema is already JSON Schema, so it needs no conversion.

**`hub.call`** splits the prefixed name, sends the call to the right client and joins the text blocks of the result. On the wire the error flag is `isError`; the SDK gives it to you as `result.is_error`. **`run_mcp_agent`** is the Chapter 4 loop made async, plus one hook, `before_call`, that Chapter 14 uses for policy.

:::warn This host approves nothing yet
MCP doesn't ask the user before a tool call; Claude Desktop does because its developers built that in. `run_mcp_agent` calls whatever the model picks. That's fine for your to-do and read-only SQL servers, but don't point it at a server that can change anything else until Chapter 14 adds a policy through `before_call`.

## 13.4 Connection lifecycle

Entering `Client(...)` in an `async with` block starts the server process and connects to it; leaving the block shuts it down. Since the 2026-07-28 MCP specification, the protocol is **stateless**. There's no start-up handshake, and every request carries the protocol version and what the client supports. The specification gives clients an optional `server/discover` request for asking a server what *it* supports (section 15.2 shows the raw messages). The SDK sends it for you, and falls back to the old `initialize` handshake when a server was written for an older revision, so your hub works with both. Because every client sits on one `AsyncExitStack`, even a crash or Ctrl+C closes every server cleanly.

:::tip Discovery is dynamic
Tools are listed at connection time. Add a tool to a server, restart the host, and the model sees it with no change to host code.
:::

## 13.5 Reading resources and prompts

Tools are for the model. Resources and prompts are usually for the host or the user:

```
client = hub.clients["shopdb"]
defs = await client.read_resource("shopdb://definitions")
system = "Business definitions:\n" + defs.contents[0].text

prompt = await hub.clients["weather"].get_prompt("packing_advice", {"city": "Pune"})
question = prompt.messages[0].content.text
```

`read_resource` and `get_prompt` send the protocol's `resources/read` and `prompts/get`; when to read a resource is the host's choice. A common pattern is to read important resources at start-up and add them to the system prompt.

## 13.6 Agents as MCP servers

A tool doesn't have to be a small function. Wrap a whole agent in one tool and any MCP host can delegate to it without knowing there's an agent inside. This is how the multi-agent patterns from Chapter 11 cross team lines: the data team publishes its analyst agent, and a coordinator elsewhere uses it as an ordinary tool.

@@code ch13_agent_server.py::mcp,MAX_STEPS,ask_sql_analyst

A few details make it safe to share. The inner agent keeps its own limits. `MAX_STEPS` is fixed inside the server, so no caller can make it loop forever, and it can use only its read-only SQL tools. Failures come back as errors: if the inner agent is cut off or refuses, the tool raises `ToolError` and the caller sees `is_error` (section 2.6). And the coordinator gets a short answer instead of the inner agent's transcript, the same compression that lets the research team scale (section 11.3).

Adding the analyst is one line in `servers.json`; the coordinator then sees `analyst__ask_sql_analyst` among its tools and decides when to delegate. That works inside one team. When the agent belongs to another company, runs for hours or must report progress, the Agent2Agent protocol (A2A) fits better; Chapter 21 publishes this same analyst with A2A.

## Common mistakes

- No namespacing, so same-named tools collide.
- Opening a new connection for every call. Keep clients open for the whole session.
- Ignoring `is_error` and passing failures on as normal results.
- Starting servers with relative paths that break from another folder.
- Blocking the event loop with `input()` or slow code; use `asyncio.to_thread`.

## Before you move on

- **You should understand:** what changes when tools come from servers and what doesn't (the loop), and why keeping servers' tool names apart is the host's job.
- **You should be able to build:** an `MCPHub` that gives each server a minimal environment, holds connections on one `AsyncExitStack`, names tools `server__tool` and passes `is_error` through.
- **Prove it:** exercise 13.3 answers one question with tools from `todo` and `shopdb`; exercise 13.6 survives a killed server.
- **Break it on purpose:** in `_connect`, register each tool as plain `tool.name`, ask what's on your to-do list and read the `unknown server` error that `hub.call` returns.
- **Defend this decision:** why `ch13_agent_server.py` fixes `MAX_STEPS` inside the server instead of letting callers set it.

## Key takeaways

**Architect's takeaway:** Your agent is only as reliable as the servers it calls, so make server failures visible and easy to debug.

- An MCP host lists each server's tools for the model; the loop doesn't change.
- Route each call with `call_tool`, and pass `is_error` through.
- Keep connections open for the session with `AsyncExitStack`.
- Resources hold reference data; prompts are user-selected templates.
- A whole agent can be an MCP tool, with its own limits and honest errors.
