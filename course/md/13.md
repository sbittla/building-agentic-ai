# Chapter 13: Build Your Own MCP Client

In Chapter 12, Claude Desktop was the host that called your server. In this chapter you'll build the host yourself: an agent that connects to several MCP servers, discovers their tools at run time and routes each tool call to the right one. You'll wrap your to-do and SQL tools as two more servers and answer questions that need both.

**What you'll build:** your own MCP client and host that connects any number of servers to your agent, and an agent that other agents call as an MCP tool.

**You are here:** MCP and Agent runtime in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Connect to MCP servers from Python and list their tools.
- Convert MCP tool definitions into the format your model expects.
- Route each tool call to the right server when several are connected.
- Replace the hard-coded tools in your agent loop with tools discovered at run time.
- Publish an agent as an MCP server, so other agents can delegate to it.
- Let a server ask the user for missing details (elicitation) through your host.

## Real-world connection

Every MCP host, from Claude Desktop to IDEs to Copilot's cloud agent, does what you'll build here: start or connect to servers, list their tools, give those tools to the model and route each call back to the server that owns it. Once you've written a host, you understand how every MCP-enabled product works under the hood.

## 13.1 What changes in the loop

Compare the Chapter 4 loop with an MCP host:

Table: The Chapter 4 agent compared with an MCP agent
|  | Chapter 4 agent | MCP agent |
| --- | --- | --- |
| Tool list | `TOOLS`, written in your code | Built at start-up from `list_tools()` on each server |
| Running a tool | `run_tool(name, args)` calls a Python function | `client.call_tool(name, args)` sends a JSON-RPC request |
| Adding a tool | Edit code and redeploy | Add a server to a config file |
| Errors | `ERROR:` strings | `result.is_error` plus a message |

The loop itself doesn't change: call the model, run tools, send results, repeat.

Here are the key parts:

- **`MCPHub.__aenter__`** starts each server with `stdio_client`, opens a `Client` and lists its tools. `AsyncExitStack` keeps all connections open together and closes them all at the end. An optional `"log"` entry in the config sends a server's stderr to a file instead of your terminal.
- **Namespacing.** Tools are renamed `server__tool` (for example `todo__add_task`). Two servers can both have a tool called `search`, and the prefix keeps them apart. The server name is also added to each description, so the model knows where a tool comes from.
- **Schema conversion.** MCP gives each tool an `input_schema`, which is already JSON Schema, so it maps directly onto the model's tool format.
- **`hub.call`** splits the name, sends the call to the right client and joins the text content blocks of the result.
- **`run_mcp_agent`** is the Chapter 4 loop, made async, with one extra hook, `before_call`, that Chapter 14 uses for policy.

Run it with `python ch13_mcp_agent.py servers.json` and ask "What's on my to-do list, and which product category earned the most revenue?" The agent uses tools from two different servers to answer one question.

## 13.4 Connection lifecycle

Entering `Client(...)` in an `async with` block starts the server process and connects to it. Since the 2026-07-28 MCP specification, the protocol is **stateless**: there's no start-up handshake, and every request carries the protocol version and what the client supports. A client can ask a server what *it* supports with a `server/discover` request, and the SDK does this for you. Servers written for older versions of the specification still expect the old `initialize` handshake, and the SDK falls back to it automatically, so your hub works with both. Leaving the block shuts the server down. Because the hub puts every client on one `AsyncExitStack`, a crash or Ctrl+C still closes every server cleanly.

:::tip Discovery is dynamic
Tools are listed at connection time. Add a tool to a server, restart the host and the model sees it, with no change to host code. This is the practical payoff of MCP.
:::

## 13.5 Reading resources and prompts

Tools are for the model. Resources and prompts are usually used by the host or the user:

```
client = hub.clients["shopdb"]
defs = await client.read_resource("shopdb://definitions")
system = "Business definitions:\n" + defs.contents[0].text

prompt = await hub.clients["weather"].get_prompt("packing_advice", {"city": "Pune"})
question = prompt.messages[0].content.text
```

A common pattern is to read important resources at start-up and add them to the system prompt, so the model always has them.

## 13.6 Agents as MCP servers

A tool doesn't have to be a small function. Wrap a whole agent in one tool, and you've published it: any MCP host can now delegate to it without knowing an agent is inside. This is how the multi-agent patterns from Chapter 11 work across teams and products: the data team publishes its analyst agent, the support team publishes its order agent, and a coordinator agent uses both as ordinary MCP tools.

@@code ch13_agent_server.py

Three details make this safe to share:

- **The inner agent keeps its own limits.** `MAX_STEPS` is fixed inside the server, so a caller can't make it loop forever, and the inner agent can use only its own read-only SQL tools.
- **Failures are errors, not answers.** If the inner agent is cut off or refuses, the tool raises `ToolError`, so the caller sees `is_error` and can react (section 2.6).
- **One question per call, one answer back.** The coordinator gets a short answer, not the inner agent's transcript, the same compression that makes the research team scale (section 11.3).

Adding it to your hub is one line in `servers.json`. The coordinator's model then sees `analyst__ask_sql_analyst` next to its other tools and decides when to delegate.

Publishing an agent as an MCP tool works well inside one team, where you control both sides. When the agent belongs to another team or company, runs for a long time, or must report progress, the Agent2Agent protocol (A2A) fits better. Chapter 21 publishes this same analyst with A2A.

## Architect's Takeaway

MCP server quality directly determines agent reliability; prioritize robust debugging.

## Common mistakes

- **No namespacing**, so tools with the same name on two servers collide.
- **Opening and closing a connection for every call.** Keep clients open for the whole session.
- **Ignoring `is_error`** and passing failures to the model as if they were normal results.
- **Starting servers with relative paths** that break when the host runs from another folder.
- **Blocking the event loop** with `input()` or slow code. Use `asyncio.to_thread`.

## Summary

- An MCP host lists tools from each server and gives them to the model; the loop itself doesn't change.
- Namespace tool names by server to avoid collisions and help the model.
- Route each call to its server with `call_tool`, and pass `is_error` through.
- Keep connections open for the session with `AsyncExitStack`.
- Use resources for reference data and prompts for user-selected templates.
- Wrap a whole agent as an MCP tool to delegate across teams; it keeps its own limits and reports failures as errors.

Your host can now plug in any server, including ones you didn't write. That's powerful and risky: in Chapter 14 you'll connect ready-made servers, learn how a server or its data can turn against you and use the `before_call` hook to add a policy layer.
