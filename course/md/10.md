# Chapter 10: Feedback Loops

An agent that says "done" isn't always done. In this chapter you'll build a fixer agent that repairs bugs in a small project by running the tests, reading the failures and editing code until everything passes. You'll protect the tests from tampering, run model-written code safely and stop runs that stall. You'll finish with a diff a human can review.

**What you'll build:** a bug-fixing agent that runs tests in a sandbox, can't touch the tests, and stops when it stops making progress.

## Real-world connection

Coding is one of the strongest uses for agents, because tests make results checkable. Anthropic's *Building effective agents* notes that code solutions "are verifiable through automated tests" and that agents "can iterate on solutions using test results as feedback." GitHub's Copilot cloud agent works this way: it takes an issue, makes changes in its own environment and runs tests and *linters* (tools that flag suspicious or badly styled code), and then a human reviews the pull request.

## 10.1 Why feedback loops work

In Chapters 1 to 9 the agent decided for itself when it was done. That works for questions, but on a task like "fix this bug" the model can believe it's finished when it isn't. A **feedback loop** replaces the model's opinion with an objective signal:

1. Act (edit code).
2. Measure (run tests).
3. Read the result.
4. Repeat until the signal says done or a stop condition fires.

Tests are the classic signal, but any automatic check works: a type checker, a linter, a build, a schema validator, a performance threshold.

## 10.4 Guardrails for code-changing agents

| Guardrail | How the fixer implements it | Why |
| --- | --- | --- |
| Sandbox | `_safe` keeps paths inside `buggy_repo` | Can't touch other projects |
| Protected files | `writable()` is an **allow-list**: only existing source files, never `test*`, `*_test.py`, `conftest.py` or pytest config | Making tests pass by editing the tests (or the files that configure them) is cheating |
| No secrets | `run_tests` runs with `clean_env()`: only `PATH` and `HOME` | Code the model wrote can't read your API key |
| Timeouts | `subprocess.run(..., timeout=60)` | An infinite loop in the code doesn't hang the agent |
| Isolation | The sandbox container: no network, no keys (exercise 10.7) | Model-written code can't leak data or call out |
| Short output | Only the last 3,000 characters of test output | The summary is at the end, and tokens are expensive |
| Review | The script prints a unified diff at the end | A human sees exactly what changed |

:::warn Block lists fail; allow-lists hold
An early version of this fixer refused only files named `test_*.py`. That sounds safe, but a model (or a malicious pull request) can write a `conftest.py` that replaces the function under test, or a `pytest.ini` that skips the failing tests. The suite then reports "passed" with the bug still there. The fix is to list what **may** be written, not what may not. Apply the same rule to every tool that writes.
:::

:::warn Running model-written code
The fixer runs code the model wrote. Even with `clean_env()`, a subprocess in the course container can still read files and reach the network. That's acceptable for a toy repo. For anything else, run tests somewhere with no network and no credentials, such as the kit's sandbox, described next.
:::

The course kit includes a separate **sandbox** container for exactly this. It has no network and none of your API keys, and it sees your workspace **read-only**. Each job runs in a throwaway copy of its folder with memory, CPU, file-size and process limits, and every process the job started is killed when it ends. The copy matters: without it, test code could overwrite a kit file such as `ch04_agent.py`, which the next command in the (networked) course container would import. ## 10.5 Stop conditions: budget and progress

Chapter 4 added an iteration cap. Here `run_agent` gets a `should_stop` function that it checks after every step. The fixer's version stops for two reasons:

- **Token budget.** Over 60,000 tokens, stop. This caps the cost of one task.
- **No progress.** `run_tests` records the number of failing tests. If three runs in a row show no improvement, the agent is stuck, and more attempts are unlikely to help.

A good stop condition ends runs that are going nowhere without cutting off runs that are still improving. The most reliable way to judge progress is to track a number that should move: failing tests, errors, distance to a goal.

## 10.6 Review by diff

The agent's own summary ("I fixed the quantity bug") is a claim. The **diff** is evidence. A *unified diff*, the standard format that marks removed lines with `-` and added lines with `+`, lets a reviewer see every changed line in seconds. Production coding agents deliver their work as a pull request for the same reason.

## Architect's Takeaway

Composable tools need clear execution boundaries: define them before agents scale.

## Common mistakes

- **Letting the agent edit tests** or delete failing assertions.
- **No timeout** on running code.
- **Dumping the entire test output** into the context on every run.
- **Stopping only on an iteration count**, so stuck runs waste the full budget.
- **Trusting the agent's summary** instead of reviewing the diff.

## Summary

- Feedback loops replace "the model thinks it's done" with an objective signal.
- Protect the signal: agents must not be able to edit the tests.
- Run generated code with timeouts, and in isolation for anything real.
- Stop on budget and on lack of progress, not only on an iteration cap.
- Deliver changes as a diff for human review.
