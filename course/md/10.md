# Chapter 10: Feedback Loops

Code has one property that makes it the friendliest place for an agent to work: you can check it. Run the tests and you get a verdict that no amount of confident prose can argue with. But hand a model "make the failing tests pass" as its goal and it has two ways to get there: fix the code, or quietly change what the tests check. From the outside, both look like the same green test run.

**What you'll build:** a bug-fixing agent that runs tests in a sandbox, can't touch the tests, and stops when it stops making progress.

**You are here:** Environment and Agent runtime in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapters 2–4 (tools and the loop), Chapter 9 (approval and review), the testing interlude.

## Learning objectives

By the end of this chapter you can:

- Build an agent that iterates against an objective pass/fail signal.
- Add stop conditions for token budgets and lack of progress.
- Run untrusted code safely with subprocesses and timeouts.
- Present agent changes as a diff for human review.

**In the real world.** Coding suits agents well because tests make results checkable. Anthropic's *Building effective agents* notes that agents "can iterate on solutions using test results as feedback." GitHub's Copilot cloud agent takes an issue, makes changes in its own environment, runs tests and *linters* (tools that flag suspicious or badly styled code) and hands a person a pull request.

## 10.1 Why feedback loops work

On "fix this bug", a model can believe it's finished when it isn't. A **feedback loop** replaces its opinion with an objective signal:

1. Act (edit code).
2. Measure (run tests).
3. Read the result.
4. Repeat until the signal says done or a stop condition fires.

Any automatic check works: tests, a type checker, a linter, a build, a schema validator, a performance threshold.

## 10.4 Guardrails for code-changing agents

Table: Guardrails in the fixer agent
| Guardrail | How the fixer implements it | Why |
| --- | --- | --- |
| Sandbox | `_safe` keeps paths inside `buggy_repo` | Can't touch other projects |
| Protected files | `writable()` is an **allow-list**: only existing source files, never `test*`, `*_test.py`, `conftest.py` or pytest config | Editing the tests or their config is cheating |
| No secrets | `run_tests` runs with `clean_env()`: only `PATH` and `HOME` | Code the model wrote can't read your API key |
| Timeouts | `subprocess.run(..., timeout=60)` | An infinite loop in the code doesn't hang the agent |
| Short output | Only the last 3,000 characters of test output | The summary is at the end; tokens cost money |
| Review | The script prints a unified diff at the end | A human sees exactly what changed |

:::warn Block lists fail; allow-lists hold
A first version of this fixer might refuse only files named `test_*.py`. But a model (or a malicious pull request) can write a `conftest.py` that replaces the function under test, or a `pytest.ini` that skips the failing tests, and the suite reports "passed" with the bug still there. So list what **may** be written instead of what may not, and apply that to every tool that writes.
:::

:::warn Running model-written code
Even with `clean_env()`, model-written code in the course container can still read files and reach the network. Fine for a toy repo; for anything else, use the kit's sandbox.
:::

If a second container feels like a lot of machinery for a toy pricing module, it is, until the first time model-written code does something you didn't expect. The kit's **sandbox** container has no network, no API keys and a **read-only** view of your workspace. Each job runs in a throwaway copy of its folder with memory, CPU, file-size and process limits, and all its processes are killed when it ends. Without the copy, test code could overwrite a kit file such as `ch04_agent.py`, which the networked course container would import next. ## 10.5 Stop conditions: budget and progress

Chapter 4 added an iteration cap. Here `run_agent` also checks a `should_stop` function after every step. The fixer's version stops past 60,000 tokens, which caps the cost of one task. It also stops when three test runs in a row show no fewer failures: every call to `run_tests` appends the failing count to `history`, and `should_stop` compares the last three. The agent is stuck, and more attempts rarely help.

Notice who decides what. The model decides what to read and which line to change. Your code decides whether a file may be written, how long the tests may run and when the run ends; the model can't argue its way past any of those.

A good stop condition ends runs going nowhere without cutting off runs still improving, so track a number that should move: failing tests, errors, distance to a goal.

## 10.6 Review by diff

The agent's summary ("I fixed the quantity bug") is a claim; the **diff** is evidence. A *unified diff* marks removed lines with `-` and added lines with `+`, and shows a reviewer every changed line in seconds. That's why production coding agents deliver pull requests.

## Common mistakes

- Letting the agent edit tests or delete failing assertions.
- No timeout on running code.
- Dumping the entire test output into the context.
- Stopping only on an iteration count, so stuck runs waste the full budget.
- Trusting the agent's summary instead of reviewing the diff.

## Key takeaways

**Architect's takeaway:** A feedback loop is only as honest as its signal: protect the tests, sandbox the code and stop runs that stall.

- Feedback loops replace "the model thinks it's done" with an objective signal.
- Protect the signal with an allow-list: the agent must not edit the tests or their config.
- Run generated code with timeouts, and sandboxed for anything real.
- Stop on budget and on lack of progress as well as on an iteration cap.
- Deliver changes as a diff for human review.
