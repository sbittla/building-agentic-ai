# Chapter 4: The Agent Loop

In Chapter 2 your code made exactly two model calls, so it broke as soon as a question needed one tool's result before calling the next. This chapter fixes that with the agent loop: call the model, run the tools it asks for, send the results back and repeat until it's done. You'll write `run_agent`, the function every later chapter imports, and add the stop conditions, tracing and token measurements that keep it safe and affordable.

**What you'll build:** the agent loop at the heart of every chapter that follows, with step limits, a tracer and a cost profile.

## Real-world connection

Every agent product you've used, including coding agents, research assistants and support bots, runs some version of the loop you write in this chapter. Frameworks add features around it, but the core is the same: call the model, run the tools it asks for, send the results back, repeat. Once you've written the loop by hand, you'll recognize it inside any agent framework you read.

## 4.1 From two calls to a loop

Exercise 2.6 ran into this limit. A question like "How many days until July 4, and what weekday is it?" needs **two** tools in sequence: the agent first calls `get_current_date`, and only once it knows today's date can it call `days_between`. The Chapter 2 code makes exactly two model calls, so it can't handle this.

The fix is to keep going **while** the model keeps asking for tools:

@@code ch04_agent.py::get_client,next_action,run_agent

`run_agent` is about 50 lines, and it's the heart of this book. Every chapter from here on imports it.

## 4.2 Walking through one run

For the July 4 question, a typical run looks like this:

| Step | Model does | Your code does |
| --- | --- | --- |
| 1 | Calls `get_current_date` | Returns "2026-09-23 (Wednesday)" |
| 2 | Calls `days_between("2026-09-23", "2027-07-04")` | Returns "284 days; 2027-07-04 is a Sunday" |
| 3 | Writes the final answer, `stop_reason = end_turn` | Returns the text |

The model decided that July 4 of *this* year had already passed and chose next year. You didn't write that logic. This is what makes it an agent: the path was decided at run time from what the tools returned.

## 4.3 Several tool calls in one turn

A model may request several tools in one response when the calls don't depend on each other. For example, "Convert 10 miles to km and 5 kg to lb" can produce two `tool_use` blocks at once.

`run_agent` handles this by looping over **every** `tool_use` block and returning **all** the results in a single user message. If you return only the first result, the API rejects the next request, because every `tool_use` must have a matching `tool_result`.

:::tip Parallel calls save time
Independent tool calls in one turn mean fewer round-trips to the model. In Chapter 7 you'll run them at the same time with threads, which matters when each tool is a slow network call.
:::

## 4.4 Stop conditions

An agent must always know when to stop, and *why*. `next_action` reads the response's `stop_reason` and decides:

| `stop_reason` | Meaning | What `run_agent` does |
| --- | --- | --- |
| `tool_use` | The model wants tools | Run them and loop |
| `end_turn`, `stop_sequence` | The model finished | Return the answer |
| `pause_turn` | A long server-side step paused | Send the conversation back to continue |
| `max_tokens` | The reply was **cut off** | Stop and say so; don't treat half an answer as an answer |
| `refusal` | The model declined; `stop_details.category` says why (for example `cyber`) | Stop and say so; don't retry the same request |
| `model_context_window_exceeded` | The conversation no longer fits | Stop; trim or compact it (Chapter 16) |

A common bug is `if stop_reason != "tool_use": return answer`. It treats a cut-off or refused reply as success, which is the "ignoring the stop reason" mistake from Chapter 1. Every loop in this book uses `next_action`, so they all handle these cases the same way; `stats["stop_reason"]` records how each run ended.

Besides the model's own stop, `run_agent` has an **iteration cap**: after `max_iterations` model calls, it gives up and says so. Without the cap, a confused model can loop forever, calling the same failing tool again and again, and you pay for every call. `run_agent` also accepts an optional `should_stop` function, checked after every step, which later chapters use to add more stop conditions:

| Condition | Chapter |
| --- | --- |
| Token or cost budget exceeded | 10 |
| No progress in N steps | 10 |
| Human rejects an action | 9 |
| Wall-clock timeout | 15 |

One more safeguard lives in `get_client`: the client is created with a **120-second timeout** and **3 automatic retries** (with backoff, meaning a growing wait between attempts) for overloaded or rate-limited responses. Without an explicit timeout, a stuck request could hang your agent for many minutes.

## 4.5 Tracing: see what your agent does

When an agent gives a wrong answer, the final text rarely tells you why. The **trace** does. `run_agent` prints each tool call, its arguments, a preview of its result and the elapsed time. It also returns `stats` with the step count, tool calls and tokens.

Always look at the trace when something goes wrong. Most agent bugs fall into a few types you can spot there:

- **Wrong tool**: fix the description (Chapter 3).
- **Right tool, wrong arguments**: fix the schema or parameter descriptions.
- **Tool error ignored**: improve the error message.
- **Loop**: the same call repeats. Fix the tool or add a no-progress check.

## 4.6 Why history grows, and what it costs

Every step appends the model's response and the tool results to `messages`, and every model call resends the entire list. Step 5 of a run pays for steps 1–4 again as input tokens. That's why `stats["input_tokens"]` grows much faster than the number of steps.

Three habits keep this under control:

- **Keep tool outputs short.** Return the 10 relevant rows, not 10,000.
- **Cap iterations.** Most good runs finish in two to six steps.
- **Measure.** Print `stats` for every run while you develop.

## 4.7 A multi-turn chat with the agent

`run_agent` accepts an existing `messages` list, so you can build a chat where the agent remembers earlier turns:

```python
from ch03_tools import TOOLS, run_tool
from ch04_agent import run_agent

history = []
while True:
    question = input("You: ")
    if question in ("quit", "exit"):
        break
    answer, history, stats = run_agent(question, TOOLS, run_tool,
                                       messages=history, verbose=False)
    print("Agent:", answer, f"  [{stats['tool_calls']} tool calls]")
```

## 4.8 Thinking and effort {api}

Current models reason before they answer or pick a tool, and two request settings control that:

- **Thinking.** On Claude Sonnet 5 and newer models, **adaptive thinking is on by default**: the model decides for itself how much to think on each step. The reasoning arrives as `thinking` blocks at the start of `response.content`. By default their text is hidden (`display` is `"omitted"`); pass `thinking={"type": "adaptive", "display": "summarized"}` to read a summary of it while you debug. On Claude Sonnet 5 you can switch thinking off with `thinking={"type": "disabled"}` for very simple, high-volume calls; on the newest models (Opus 5.5 and the 5.1 models) it can't be turned off. The older setting `{"type": "enabled", "budget_tokens": N}` now returns a 400 error.
- **Effort** (`effort="low"`, `"medium"`, `"high"`, `"xhigh"` or `"max"`) is the main control for how hard the model works, and it's sent as `output_config={"effort": ...}`. The default is `"high"`. Low effort is plenty for simple lookups and costs less; raise it for hard, multi-step problems. Measure the difference with exercise 4.5 before you pay for it everywhere.

```python
answer, messages, stats = run_agent(
    question, TOOLS, run_tool, effort="medium",
    thinking={"type": "adaptive", "display": "summarized"})
```

Three rules matter in a tool loop:

1. **Send thinking blocks back exactly as you received them.** They carry a signature (a code the API uses to confirm they're unchanged), and the API rejects a conversation where they were removed or edited. `run_agent` appends `response.content` whole, which is exactly right. Code that rebuilds the assistant message from only the text and tool calls breaks.
2. **Leave room in `max_tokens`.** Thinking counts toward `max_tokens` and is billed as output. A limit sized for the answer alone can run out while the model is still thinking, and the response ends with `stop_reason` `max_tokens` and no text. This book's code uses 2,000 to 4,096; you pay only for tokens actually used.
3. **Select blocks by type.** Never assume `content[0]` is the answer or the tool call (Chapter 1).

## 4.9 Budgets for a whole task

`max_iterations` and `should_stop` (section 4.4) are budgets *your* code enforces. Two newer API features do the same job closer to the model. A **task budget** (a beta feature on some models at the time of writing) tells the model roughly how many tokens the whole agentic task may use, so it plans its work to fit instead of being cut off. **Claude Managed Agents** (Chapter 24) goes further and puts a hard spending cap on a session: when it's reached, the session stops with a `budget_reached` reason. Keep your own caps anyway; they're the ones you can test.

## Architect's Takeaway

Unbounded loops kill costs: set iteration caps and stopping conditions first.

## Common mistakes

- **No iteration cap.** A confused agent burns money in an infinite loop. The cap isn't defensive programming; it's mandatory.
- **Returning only the first tool result** when the model asked for several.
- **Not appending the assistant's `tool_use` message** before the results. The API needs both, in order.
- **Forgetting to check `stop_reason`.** A response with `stop_reason=max_tokens` looks like an answer but is incomplete. Stop, log it and say so.
- **Silent failures in the loop.** Treat tool errors as data the model can see, not exceptions that vanish. Log every one.
- **Printing only the final answer.** Without a trace you can't debug.
- **Huge tool outputs** that inflate the token count on every later step.
- **Tight retries on transient failures.** Wait before retrying and cap the total tries, or you spend tokens on something that won't work.
- **No budget-aware stopping.** When a task's token budget runs out, stop asking the model; finish with what you have or hand over to a person.
- **Rebuilding the assistant message by hand**, which drops thinking blocks and breaks the next request.

## Summary

- The agent loop repeats: call model → run tools → send results, until the model stops asking.
- Return a result for every `tool_use` block in a response.
- Always cap iterations; add budgets and no-progress checks later.
- Trace every step. The trace, not the final answer, shows you what went wrong. Appendix B has a step-by-step debugging playbook for when an agent misbehaves.
- History is resent on every call, so input tokens grow quickly; keep tool outputs small.
