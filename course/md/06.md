## Real-world connection

Coding agents explore unfamiliar repositories with three moves: list files, search for text, read the relevant part. They don't load the whole codebase into the prompt. The reference MCP **Filesystem** server offers the same moves with access control, and you'll connect it in Chapter 14.

## 6.1 Agentic search

Give the agent the question and a few tools, and let it decide where to look:

1. **List**: what files exist?
2. **Search**: which files and lines mention the topic?
3. **Read**: read the relevant lines, then answer.

This works because the model can refine its search. If "Kafka" finds nothing useful, it can try "consumer lag" or "message queue". A fixed pipeline can't adapt that way.

## 6.3 The sandbox

`_safe()` is the most important function in the file. A *sandbox* is a boundary a tool can't cross, and `_safe` enforces it. The model chooses the `path` argument, and `../../.ssh/id_rsa` or `/etc/passwd` are valid strings. `_safe` resolves the full path and refuses anything that isn't inside `ROOT`.

:::warn Resolve, then check
Checking the string (`if ".." in path`) is not enough. Symbolic links (files that point to another location) and absolute paths get around string checks. Always resolve to an absolute path first, then check that the result is inside the allowed folder.
:::

## 6.4 Protecting the context window

A 5,000-line file would cost thousands of tokens on every later step (section 4.6). Two limits prevent this:

- **`read_file` pages at 80 lines** and tells the model how to get the next page.
- **`search_files` caps hits at 20** and says when results are truncated.

Size tool outputs for a model's attention: enough to act on, never everything.

## 6.5 Citations

The system prompt requires a `(file:line)` citation for every fact. Because `read_file` and `search_files` both return line numbers, the model can cite precisely. Citations do three things:

- Let the user **check** the answer.
- **Discourage invention**, since every claim must point to a line.
- Make **evaluation** simpler: you can check that cited lines really contain the claim.

## 6.6 Agentic search or RAG?

**RAG** (retrieval-augmented generation) splits documents into chunks, converts each chunk to a list of numbers that captures its meaning (an *embedding*) and, before calling the model, retrieves the chunks most similar to the question.

|  | Agentic search | RAG |
| --- | --- | --- |
| Setup | None; works on files as they are | Chunking, embedding and a vector store |
| Freshness | Always current | Needs re-indexing when files change |
| Exact terms (error codes, names) | Excellent (regex) | Can miss them |
| Fuzzy meaning ("notes about burnout") | Needs good search terms | Excellent |
| Scale | Thousands of files | Millions of documents |
| Cost per question | More model steps | One retrieval plus one call |

Many production systems combine the two: RAG becomes one tool (`semantic_search`) alongside exact search and read tools, and the agent chooses between them.

## Architect's Takeaway

Agent file access needs strong isolation: design permissions before building tools.

## Common mistakes

- **No sandbox**, or a string-based one that `..` or a symlink defeats.
- **Returning whole files.** Costs explode and the model loses focus.
- **No citations**, so answers can't be checked.
- **Silent truncation.** Always tell the model when output was cut and how to get more.

## Summary

- Agentic search is list → search → read, with the model choosing each step.
- Resolve paths, then check they're inside the sandbox.
- Page large outputs and cap search hits.
- Require citations; they make answers checkable and evaluable.
- Use agentic search for exact, fresh, modest-size data, and RAG for fuzzy meaning at large scale, or both.
