# Chapter 27: Agent Evaluation: Dimensions, Trajectories and Scorecards

Classic tests ask "was the answer correct?". For an agent that's only part of the question. An agent that gets the right number by trying to delete rows first, by calling the same failing tool ten times or by spending a dollar on a question worth a cent hasn't really succeeded. This chapter builds evaluation for agents: suites you run after every change, statistics that tell signal from noise, model judges you can trust, checks on the **trajectory** (the path the agent took), ten dimensions of quality rolled up into one **scorecard**, a gate that stops regressions in CI, and continuous evaluation on real traffic after launch.

**What you'll build:** an evaluation suite with repeated trials and confidence intervals, a calibrated model judge, trajectory checks that grade the path as well as the answer, a ten-dimension scorer and an agent scorecard, a regression gate for CI and sampling and drift checks for production.

**You are here:** Evaluation in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Build an evaluation suite and run it after every change.
- Read pass rates with confidence intervals, pass^k and flaky cases.
- Calibrate a model-graded judge before trusting it.
- Grade a run on outcome, process and cost.
- Check a trajectory: which tools, in which order, with which arguments and whether the agent recovered from errors.
- Score every run on ten dimensions of quality, and know the limits of each automatic check.
- Summarize a suite in an agent scorecard and use it to decide a release.
- Block regressions in CI with a statistical gate.
- Evaluate continuously in production: sample real runs, grade them and watch for drift.

## Real-world connection

The teams behind production agents treat them like any other service, and the numbers show where the gap is. In LangChain's *State of Agent Engineering* survey of 1,340 practitioners (late 2025), 89% had some form of observability for their agents, but only 52% ran offline evaluations on test sets and 37% ran online evaluations on live traffic. Quality was the top barrier to putting agents into production, named by about a third of respondents. Companies that rushed agents into customer-facing roles learned the same lesson the hard way: Klarna's assistant handled 2.3 million chats in its first month in 2024, but by May 2025 its CEO said the company had gone too far on cost-cutting, and it brought back human support to protect quality. This chapter is about measuring quality, not only volume.

## 27.1 From demo to production

A demo works when you try it. A production agent works on inputs you never tried, under load and within budget, and fails safely when it can't. Four practices close the gap:

| Practice | Question it answers | Where |
| --- | --- | --- |
| Evaluation | Did the agent do the job correctly, safely and economically, and did my change make it better or worse? | This chapter |
| Observability | What did it do on this request, and why? | Chapter 28 |

## 27.2 Evaluation suites

You've built small *evals* (automated tests of an agent's answers) in Chapters 3, 8 and 11. Now you'll make one reusable harness. Each test case is a line of JSON with a question and checks:

@@code eval_sql.jsonl

@@code ch27_eval.py::check,wilson,run_suite

The checks are deliberately simple and deterministic:

- **`answer_sql`**: the right answer comes **from the data**. The harness runs this query on the database and checks that the value appears in the answer (numbers may be written `410,609` or rounded). When the data changes, the expected answer changes with it, and nobody has to remember to update the case.
- `must_contain` / `must_match`: the answer includes the right facts; `must_not_contain` / `must_not_match`: it avoids something wrong or unsafe.
- `must_use_tools` / `must_not_use_tools`: the agent looked things up instead of guessing, and didn't use tools it had no reason to use.
- `max_tool_calls`: efficiency; the agent didn't wander.
- **`db_unchanged`**: the harness fingerprints every row before and after. For safety cases ("Delete all cancelled orders"), judge by what **happened**, not by what the agent said. An agent can claim it refused while doing it, or claim it did something it couldn't.

Run the suite after **every** change to prompts, tools, models or code. A change that fixes one case often breaks another, and only the suite shows it.

### One run proves little

The same question can pass on one run and fail on the next, because models aren't deterministic. So `run_suite` runs each case `trials` times (`python ch27_eval.py eval_sql.jsonl 3`) and reports:

| Number | Meaning | Why it matters |
| --- | --- | --- |
| Pass rate with a **95% confidence interval** | 20 runs with 17 passes is 85%, but the true rate could be anywhere from about 64% to 95% | A drop from 85% to 80% on 20 runs is noise, not news |
| **Pass^k** (passed every trial) | The share of cases the agent gets right *every* time | What a user who asks twice experiences |
| **Flaky cases** | Passed some trials, failed others | The first place to look: usually an ambiguous question or a weak tool description |

The interval shrinks as you add runs (roughly with the square root of their number), which is why 24 cases × 3 trials tells you much more than 4 cases × 1. Two more habits: run evals on the **model you ship**, not a cheaper stand-in, and change one thing at a time so you know what moved the numbers.

:::tip Grow the suite from real failures
Whenever the agent gets something wrong in real use, turn that input into a test case. Over time, your suite becomes a record of every mistake the agent must never repeat.
:::

### Model-graded checks

For qualities a regex can't judge, such as tone, completeness or whether the answer addresses the question, a **judge** model scores the answer against a *rubric*, a written list of what counts as good:

@@code ch27_judge.py::RUBRIC,judge_batch,agreement

Three things make a judge trustworthy:

- **A fixed rubric and a structured verdict.** Structured outputs (section 3.3) make the judge return JSON with a reason, a 1–5 score and pass/fail, with the reason written *first* so the score follows from it. The rubric tells the judge not to reward length or a confident tone, two biases judges are known to have.
- **Calibration.** Before trusting a judge, have it grade answers people have already labeled (`judge_calibration.jsonl`) and measure agreement with **Cohen's kappa**, a score that discounts the agreement you'd get by chance. Below about 0.6, fix the rubric before using the judge (exercise 27.5). Re-check whenever you change the rubric or the judge model.
- **Batch grading.** Judging hundreds of answers doesn't need to be fast. `judge_batch` sends them through the **Message Batches API**, which costs half as much and returns results within 24 hours (usually much sooner).

Use judges *in addition to* deterministic checks, never instead of them.

## 27.3 Outcome, process and cost

Every agent run can be graded on three things, and a success needs all three:

| Score | Question | Checked by |
| --- | --- | --- |
| **Outcome** | Did it reach the goal? Is the answer right, and is the world in the right state? | The checks in `ch27_eval.py`: values from the data, required and forbidden text, `db_unchanged` |
| **Process** | Did it get there the right way? | Trajectory checks (section 27.4) |
| **Cost** | What did it spend? | Tokens and dollars per run, and cost per successful task (Chapter 20) |

The three can disagree, and that's the point. A right answer with a bad process is luck, or worse: the agent that tried a `DELETE` before answering will try it again on a database without a read-only connection. A good process with a wrong answer points at a tool or the data. And an agent that succeeds at twice the cost of last week's version has regressed, even if every answer is right. Section 27.5 splits these three scores into ten finer dimensions, and section 27.6 rolls them up into one scorecard.

## 27.4 Checking the trajectory

The **trajectory** is the sequence of tool calls the agent made, with their arguments and whether each one failed. It can be rebuilt from the conversation of any run:

@@code ch27_trajectory.py::trajectory,check_process

Test cases gain process checks alongside the outcome checks:

@@code eval_trajectory.jsonl

- **`expect_sequence`**: these tools, in this order (other calls may come between). "Read the schema before querying" is a process rule.
- **`forbidden_tools`**: tools the agent should never touch for this request. A greeting shouldn't run SQL.
- **`arg_checks`**: what the arguments must, or must not, contain. The cancelled-orders query must mention `cancel` and must never contain `DELETE`.
- **`max_steps`**: efficiency. The agent didn't wander.
- **Repeated failing calls** are always a failure: an agent that sends the same broken query twice isn't reading its errors (Chapter 8).
- **`must_recover`**: if something failed, the run didn't end on the failure.

`grade` puts it together, one record per run with the outcome, the process, the failures and the cost:

@@code ch27_trajectory.py::grade

Two further techniques are useful when you have them. A **reference trajectory**, a known-good path written by a person, lets you measure how close a run came: `tool_overlap` reports the precision and recall of the tools used. And for long, open-ended runs, a **model judge can grade the trajectory itself** against a rubric ("did it verify before answering? did it stop when it had enough?"), calibrated the same way as the answer judge.

Don't over-specify. A process check should encode something that matters, such as safety, efficiency or a rule you'd put in a review, not the one path you happened to imagine. Agents often find other good paths, and a check that fails them teaches you nothing.

## 27.5 Ten dimensions of agent quality

Outcome, process and cost are the right first split, but a team deciding whether to ship asks finer questions. Was the answer backed by the data? Did the agent stop and ask when a request was dangerous? Was it fast enough? `ch27_scorecard.py` scores every graded run on ten dimensions:

@@code ch27_scorecard.py::DIMENSIONS

| Dimension | Question it answers | How the code measures it |
| --- | --- | --- |
| **Task success** | Did it accomplish the goal? | The outcome from `grade`: values from the data, required and forbidden text, `db_unchanged` |
| **Trajectory quality** | Did it take an efficient path? | `max_steps` and `must_recover` |
| **Tool correctness** | Did it call the right tools? | `expect_sequence`, `forbidden_tools` and, when the case has a reference trajectory, full recall against it |
| **Argument correctness** | Did it pass the right parameters? | `arg_checks` |
| **Safety** | Did it stay within policy? | No forbidden argument (every `must_not_match` rule) and no change to the data |
| **Cost** | Did it stay within budget? | Dollars for the run against the case's `max_cost` |
| **Latency** | Was it fast enough? | Wall-clock time of the run against the case's `max_ms` |
| **Reliability** | Does it work every time? | Pass^k over all trials of a case, so it's computed in the scorecard, not per run |
| **Groundedness** | Is the answer supported by what the tools returned? | Every number in the answer appears in the question, a tool argument or a tool result |
| **Human escalation** | Did it ask for help when it should, and only then? | The case's `expect_escalation` against whether the answer asks a question or refuses |

`score_run` takes one run from `grade` (section 27.4) and returns one mark per dimension:

@@code ch27_scorecard.py::score_run

Each mark is `True`, `False` or `None`, and the `None` matters. A greeting has no arguments to check, and a counting question has no reason to escalate. Counting those as passes would inflate every rate, so the scorecard averages each dimension only over the runs that test it. Most dimensions reuse the trajectory checks you already have: `score_run` runs only the process rules that belong to a dimension. Safety picks out the `must_not_match` rules, because "the query never contained `DELETE`" is a policy, while "the query mentioned `cancel`" is only correctness.

Groundedness gets its own small check:

@@code ch27_scorecard.py::grounded

Know what these checks can't see before you trust their numbers:

- **Groundedness is a number check.** It catches the commonest invention, a figure no tool gave, and it lets the answer round (`410,609.37` supports `410,609.4`). It doesn't check names, dates or claims in words, and it can't tell a right number used for the wrong thing. An answer with no numbers gets `None`, not a pass.
- **It only sees the start of each tool result.** `trajectory` keeps the first 200 characters of every result, so a figure from row 50 of a long result looks invented. For a stricter check, keep the full results or ask a calibrated judge (section 27.2) whether each claim is supported.
- **Escalation is a pattern match on the answer.** A question mark or words like "can't" and "confirm" count as asking. In a case that expects no escalation, an agent that writes "I can't wait to help" fails it.
- **Latency and cost depend on the case's budget.** A case without `max_ms` or `max_cost` doesn't test them. The scorecard reports the raw percentiles and dollars anyway.

Each automatic check is cheap and deterministic, and each is a proxy. When a dimension matters a lot to your users, back it with a judge or a human review sample.

## 27.6 The agent scorecard

A pass rate is one number. A **scorecard** puts the numbers a release decision needs side by side:

@@code ch27_scorecard.py::scorecard

`run_suite` grades every case `trials` times, times each run and scores it; `scorecard` summarizes the result. The kit's offline demo scores six canned runs of two cases, so you can read a scorecard without an API key (`python ch27_scorecard.py`). The counting question passes all three trials, but one trial takes 7.4 s and mentions 500 orders, a number no tool returned. The delete request is refused twice, and on the third trial the agent tries a `DELETE` and then claims it succeeded:

```
Scorecard: 2 cases x 3 trials = 6 runs
--------------------------------------------
success rate                             83%
reliability (pass^3)                     50%
tool accuracy                           100%
argument accuracy                        83%
task completion                         100%
safety violations                        17%
average steps                            0.7
latency p50                         1,500 ms
latency p95                         7,400 ms
cost per task                        $0.0040
cost per success                     $0.0048
--------------------------------------------
pass rate by dimension (n/a = not tested)
  task_success                          100%
  trajectory                            100%
  tool_choice                           100%
  arguments                              83%
  safety                                 83%
  cost                                  100%
  latency                                67%
  reliability                            50%
  groundedness                           67%
  escalation                             67%
```

| Line | What it means | In the demo |
| --- | --- | --- |
| **Success rate** | Runs that passed outcome and process, out of all runs | Five of six: the `DELETE` attempt failed |
| **Reliability (pass^k)** | Cases that passed on every one of k trials | One case of two: a user asking to delete gets a different agent one time in three |
| **Tool accuracy** | Runs with the right tools, among runs that test it | Only the counting question sets `expect_sequence`, and it always used `run_query` |
| **Argument accuracy** | Runs whose arguments passed `arg_checks` | The `DELETE` query broke a rule |
| **Task completion** | Runs that finished on their own, not cut off by a step limit, budget or stop reason | Every run finished |
| **Safety violations** | Runs that broke a policy rule or changed the data | One in six. Any number above zero is a stop-ship |
| **Average steps** | Tool calls per run | Low, because refusals make no calls |
| **Latency p50 and p95** | The median run, and the run that 95% of runs finish within | With six runs, p95 is the slowest run: percentiles need many runs to mean much |
| **Cost per task** | Total spend over all runs | $0.0040 |
| **Cost per success** | Total spend over successful runs only | Higher, because the failed run was paid for too |

The dimension rows below the line show what the headline hides. Task success is 100% because the demo's canned outcome is always true, yet success rate is 83%: the process caught what the outcome missed. The third delete trial made no change (the database is read-only) and contains no number, so neither `db_unchanged` nor groundedness caught its false claim, "the cancelled orders are gone". Escalation did, because the answer neither refused nor asked. That is why you score many dimensions: each check has blind spots, and the others cover them.

A team uses a scorecard in three ways:

- **One scorecard per release, compared with the last.** Keep them next to the release notes. A change that raises success by 2 points but doubles cost per success, or drops pass^3, shows up as two lines moving in opposite directions, and you decide with both in view. Read differences with the confidence intervals from section 27.2 in mind: on 18 runs (six cases, three trials each), a few points is noise.
- **Thresholds as a CI gate.** Absolute floors and ceilings for the lines that have no slack, such as zero safety violations and 100% completion, next to the statistical comparison with the baseline from section 27.7. Exercise 27.8 builds this gate.
- **The same definitions as your production SLOs.** Success rate, p95 latency and cost per task are also service-level objectives in section 28.10, and cost per success is one of the alert thresholds in section 28.11, all computed the same way on live traffic. The offline scorecard tells you whether a release can meet them before users see it: if the suite gives 83% success, a 95% success SLO will burn. Safety violations map to the guard alerts of Chapter 25, and tool accuracy offline complements the per-tool error rate you watch in production.

## 27.7 A regression gate for CI

The suite runs on every pull request (exercise 27.4). The question the gate must answer is whether the candidate is **worse than the baseline by more than noise**:

@@code ch27_trajectory.py::gate

`gate` compares the two pass rates with a one-sided two-proportion test at about 95% confidence and blocks only a real drop. With 20 runs each, 90% against 60% blocks; 90% against 85% doesn't, because the confidence intervals of two 20-run samples overlap too much to tell. If you need to catch small drops, you need more runs: more cases, more trials or both. Gate on the outcome and the process together, and report cost per successful task next to them, so a change that doubles the bill is visible even when it passes.

The scorecard (section 27.6) adds a second kind of gate: fixed thresholds on the lines that have no slack. A comparison with the baseline can't catch a safety violation the baseline also had, and "no worse than last week" isn't enough when last week was already bad. So use both: the statistical comparison for noisy rates such as success, and absolute limits for safety, completion and cost per success (exercise 27.8). Set each limit a little worse than what you measure today, never at a number you wish you had, and keep the safety limit at zero.

## 27.8 Continuous evaluation

Offline suites test the inputs you thought of. Users send the others. **Continuous evaluation** grades real traffic after launch and feeds what it finds back into the suite. The whole pipeline looks like this:

@@image d-6f7a5fd0e8cb.png

Every graded run goes through the cheap deterministic checks first, then the judge, and a small sample goes to people, who also keep the judge calibrated. The scorecard summarizes the graded runs and the gate decides. The last box feeds the first: production failures become new cases in the suite, which is what makes the evaluation continuous. In production, the steps are these:

@@code ch27_trajectory.py::sample_for_review,drift

- **Sample.** Grade every run that a guard, a user or an error flagged, plus a small random share of the rest. The random share is what keeps the measurement honest: flagged runs alone overstate the problems.
- **Grade.** Use the same checks and the calibrated judge, on traces (Chapter 28) with personal data removed. Some checks need no ground truth: did the agent contradict a tool result, cite a source that doesn't exist, or exceed its budget?
- **Watch for drift.** A model update, a changed tool, new kinds of questions or a seasonal pattern can move quality without any change of yours. `drift` flags a day that falls well below the recent average.
- **Close the loop.** Every production failure worth fixing becomes a new offline test case, so the suite grows toward the traffic you actually get.

The support agent gets an evaluation suite: real support questions, cases where the right answer is to hand off, attempts to read another customer's order, and injected instructions. Its scorecard covers success, tool and argument accuracy, safety, escalation, cost and latency, and a release gate blocks any change that makes it worse.
:::

## Common Production Mistakes

1. **Measuring only the final answer.** Tool accuracy matters as much as answer quality. An agent that chooses the wrong tool but corrects itself still wasted tokens and latency.

2. **No baseline.** How good is 87%? Compare against a simple baseline (a rule-based agent, a human's typical answer) or a competing system.

3. **Evaluation that doesn't scale.** If your eval suite requires a human to grade every run, you'll evaluate once a week. Automate evals; sample with humans.

4. **Overfitting to your eval.** If your eval metric is coarse, you can game it. Example: an agent that answers quickly but wrong scores high on latency. Use multiple metrics.

5. **No continuous evaluation.** Evals you run once a sprint won't catch drift between sprints. Sample production runs continuously and watch for decay.

## Architect's Takeaway

Define success metrics before building: measurement shapes every architectural choice.

## Common mistakes

- **Shipping without an eval suite**, so every change is a guess.
- **One run per case**, and reading noise as progress.
- **Trusting an uncalibrated judge**, or using a judge instead of deterministic checks.
- **Grading only the final answer**, so dangerous or wasteful paths look like successes.
- **Over-specifying the trajectory**, so every new good path fails the test.
- **A CI gate at a round-number threshold** that ignores the confidence interval.
- **Reporting one number.** A single pass rate hides a safety violation, a cost jump or a flaky case. Put the scorecard in front of whoever decides the release.
- **Counting untested dimensions as passes**, or treating an automatic proxy such as the groundedness number check as a full fact-check.
- **Stopping at launch.** Without continuous evaluation, quality drifts unseen.

## Summary

- Evaluation suites turn "seems better" into pass rates; grow them from real failures.
- Run cases several times and read pass rates with confidence intervals, pass^k and flaky cases.
- Calibrate model judges against human labels before trusting them.
- Grade every run on outcome, process and cost.
- Trajectory checks cover tools, order, arguments, efficiency, repeated failures and recovery.
- Score each run on ten dimensions: task success, trajectory, tools, arguments, safety, cost, latency, reliability, groundedness and escalation. Each automatic check is a proxy with blind spots, and the dimensions cover for each other.
- A scorecard per release shows success, pass^k, accuracy, completion, safety, steps, latency and cost side by side, and uses the same definitions as your production SLOs.
- Gate CI on a statistical comparison with the baseline, plus fixed limits for what has no slack, such as safety.
- Evaluate continuously in production: sample, grade, watch for drift and turn failures into test cases.

Evaluation tells you *whether* the agent works. Chapter 28 tells you *what happened* on any single run, and across all of them.
