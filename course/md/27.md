# Chapter 27: Agent Evaluation: Dimensions, Trajectories and Scorecards

The analyst agent gave the right count of cancelled orders. It also tried `DELETE FROM orders` on the way, and the rows survived only because the connection happened to be read-only. A test that checks the answer calls that run a pass. Would you ship it?

The measurement interlude taught you to compare two versions without fooling yourself, and Chapter 28 will watch what happens after release. Here you decide, before a version ships, whether it may. You'll grade the **trajectory** (the path the agent took) as well as the answer, roll ten dimensions of quality into one **scorecard**, and gate releases on it.

**What you'll build:** an evaluation suite with repeated trials and confidence intervals, a calibrated model judge, trajectory checks, a ten-dimension scorer and agent scorecard, a regression gate for CI, and sampling and drift checks for production.

**You are here:** Evaluation in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 3 (the routing eval), Chapter 4 (agent loop), Chapter 8 (checking answers), the measurement interlude.

## Learning objectives

By the end of this chapter you can:

- Build an evaluation suite and read pass rates with confidence intervals, pass^k and flaky cases.
- Calibrate a model judge before trusting it.
- Grade a run on outcome, process (its trajectory) and cost.
- Score runs on ten dimensions of quality, knowing each check's limits.
- Decide a release with an agent scorecard and a statistical CI gate.
- Sample, grade and watch for drift in production.

**In the real world.** In LangChain's *State of Agent Engineering* survey of 1,340 practitioners (late 2025), 89% had observability for their agents, but only 52% ran offline evaluations and 37% evaluated live traffic; quality was the top barrier to production. Klarna's assistant handled 2.3 million chats in its first month in 2024, but by May 2025 its CEO said the company had gone too far on cost-cutting and brought back human support to protect quality.

## 27.2 Evaluation suites

You've built small *evals* (automated tests of an agent's answers) in Chapters 3, 8 and 11. Now you'll make one reusable harness. Each test case is a line of JSON with a question and checks:

@@code eval_sql.jsonl

@@code ch27_eval.py::check,wilson~,run_suite~

The checks are simple and deterministic:

- **`answer_sql`**: the right answer comes **from the data**. The harness runs this query and checks that the value appears in the answer (as `410,609` or rounded), so the expected answer follows the data.
- `must_contain` / `must_match`: the answer includes the right facts; `must_not_contain` / `must_not_match`: it avoids something wrong or unsafe.
- `must_use_tools` / `must_not_use_tools`: the agent looked things up instead of guessing, and left alone tools it didn't need.
- `max_tool_calls`: the agent didn't wander.
- **`db_unchanged`**: the harness fingerprints every row before and after. For safety cases ("Delete all cancelled orders"), judge by what **happened**. An agent can claim it refused while doing it, or claim it did something it couldn't.

Run the suite after **every** change to prompts, tools, models or code.

### One run proves little

The same question can pass on one run and fail on the next. Like the interlude's harness, `run_suite` runs each case `trials` times (`python ch27_eval.py eval_sql.jsonl 3`) and adds pass^k:

Table: What `run_suite` reports
| Number | Meaning | Why it matters |
| --- | --- | --- |
| Pass rate with a **95% confidence interval** | The margin from the measurement interlude (section M.1), computed with the same `wilson` | A drop from 85% to 80% on 20 runs is noise, not news |
| **Pass^k** (passed every trial) | The share of cases the agent gets right *every* time | What a user who asks twice experiences |
| **Flaky cases** | Passed some trials, failed others | The first place to look: usually an ambiguous question or a weak tool description |

The interlude's habits still apply (more cases beat more trials; change one thing at a time), plus one more: run evals on the **model you ship**, because a cheaper stand-in fails in different places.

:::tip Grow the suite from real failures
Whenever the agent gets something wrong in real use, turn that input into a test case. The suite becomes a record of mistakes it must never repeat.
:::

### Model-graded checks

For qualities a regex can't judge, such as tone or completeness, a **judge** model scores the answer against a *rubric*, a written list of what counts as good:

@@code ch27_judge.py::RUBRIC,judge_batch~,agreement

A judge earns trust with a fixed rubric and a structured verdict: JSON (section 3.3) with a reason, a 1–5 score and pass/fail, the reason *first* so the score follows from it. The rubric also tells it not to reward length or confidence, two known judge biases. Then calibrate it: have it grade answers people already labeled (`judge_calibration.jsonl`) and measure agreement with **Cohen's kappa**, which discounts chance agreement. Below about 0.6, fix the rubric (exercise 27.5), and re-check whenever the rubric or judge model changes. To keep it cheap, `judge_batch` sends verdicts through the **Message Batches API** at half the price, with results within 24 hours, usually sooner.

Use judges alongside deterministic checks, never instead of them.

## 27.3 Outcome, process and cost

A successful run needs a right outcome, a sound process and a sensible cost:

Table: Grading outcome, process and cost
| Score | Question | Checked by |
| --- | --- | --- |
| **Outcome** | Is the answer right, and is the world in the right state? | The checks in `ch27_eval.py` |
| **Process** | Did it get there the right way? | Trajectory checks (section 27.4) |
| **Cost** | What did it spend? | Tokens and dollars per run, and cost per successful task (Chapter 20) |

Grade **answer correctness** and **action correctness** separately: what the agent *said* and what it *did* must both pass. **A correct final answer after an unsafe or incorrect trajectory is still a process failure.** A support agent that gives Ana the right refund status after reading Ben's order on the way fails the run, and so does the analyst from the opening.

Table: Answer and action are graded separately {#t:answer-vs-action}
| Answer | Actions | Verdict |
| --- | --- | --- |
| Right | Right tools, allowed arguments, nothing unsafe | Pass |
| Right | An unsafe, unauthorized or wasted step | **Fail**: process failure, however good the answer |
| Wrong | Right steps | Fail: look at the tool, the data or the final reasoning |
| Wrong | Wrong steps | Fail |

A right answer with a bad process is luck: the agent that tried a `DELETE` will try it again where the connection isn't read-only. A good process with a wrong answer points at a tool or the data. And an agent that succeeds at twice last week's cost has regressed, even if every answer is right.

## 27.4 Checking the trajectory

The trajectory is the sequence of tool calls, with their arguments and whether each failed. You can rebuild it from any run's conversation:

@@code ch27_trajectory.py::trajectory~,check_process

Test cases gain process checks alongside the outcome checks:

@@code eval_trajectory.jsonl

- **`expect_sequence`**: these tools, in this order (other calls may come between). "Read the schema before querying" is a process rule.
- **`forbidden_tools`**: tools this request should never touch; a greeting shouldn't run SQL.
- **`arg_checks`**: what the arguments must, or must not, contain. The cancelled-orders query must mention `cancel` and must never contain `DELETE`.
- **`max_steps`**: the agent didn't wander.
- **Repeated failing calls** always fail: the agent isn't reading its errors (Chapter 8).
- **`must_recover`**: if something failed, the run didn't end on the failure.

`grade` puts it together: one record per run with outcome, process, failures and cost:

@@code ch27_trajectory.py::grade

A **reference trajectory**, a known-good path written by a person, lets `tool_overlap` report the precision and recall of the tools a run used. For long, open-ended runs, a calibrated **model judge can grade the trajectory itself** ("did it verify before answering? did it stop when it had enough?").

Don't over-specify. A process check should encode something that matters, such as safety, efficiency or a rule you'd enforce in code review, not the one path you happened to imagine.

## 27.5 Ten dimensions of agent quality

A team deciding whether to ship asks finer questions. Was the answer backed by the data? Did the agent stop and ask when it should? `ch27_scorecard.py` scores every graded run on ten dimensions:

@@code ch27_scorecard.py::DIMENSIONS

Table: Ten dimensions of agent quality
| Dimension | Question it answers | How the code measures it |
| --- | --- | --- |
| **Task success** | Did it accomplish the goal? | The outcome from `grade` |
| **Trajectory quality** | Did it take an efficient path? | `max_steps` and `must_recover` |
| **Tool correctness** | Did it call the right tools? | `expect_sequence`, `forbidden_tools` and full recall against a reference trajectory when the case has one |
| **Argument correctness** | Did it pass the right parameters? | `arg_checks` |
| **Safety** | Did it stay within policy? | No forbidden argument (every `must_not_match` rule) and no change to the data |
| **Cost** | Did it stay within budget? | Dollars for the run against the case's `max_cost` |
| **Latency** | Was it fast enough? | Wall-clock time against the case's `max_ms` |
| **Reliability** | Does it work every time? | Pass^k over a case's trials, computed in the scorecard |
| **Groundedness** | Is the answer supported by what the tools returned? | Every number in the answer appears in the question, a tool argument or a tool result |
| **Human escalation** | Did it ask for help when it should, and only then? | The case's `expect_escalation` against whether the answer asks a question or refuses |

`score_run` takes one run from `grade` (section 27.4) and returns one mark per dimension:

@@code ch27_scorecard.py::score_run

Each mark is `True`, `False` or `None`, and the `None` matters. A greeting has no arguments to check, and a counting question has no reason to escalate; counting those as passes would inflate every rate, so each dimension is averaged only over the runs that test it. Most dimensions reuse the trajectory checks. Safety picks out the `must_not_match` rules, because "the query never contained `DELETE`" is a policy, while "the query mentioned `cancel`" is only correctness.

Groundedness gets its own small check:

@@code ch27_scorecard.py::grounded

Know what these checks can't see before you trust their numbers:

- **Groundedness is a number check.** It catches the commonest invention, a figure no tool gave, and allows rounding (`410,609.37` supports `410,609.4`). It can't check names, dates, claims in words, or a right number used for the wrong thing. An answer with no numbers gets `None`.
- **It sees only the start of each tool result.** `trajectory` keeps 200 characters of every result, so a figure from row 50 looks invented.
- **Escalation is a pattern match.** A question mark or words like "can't" and "confirm" count as asking, so "I can't wait to help" fails a case that expects no escalation.
- **Latency and cost need the case's budget.** Without `max_ms` or `max_cost` they aren't tested, though the scorecard still reports raw numbers.

Each check is cheap, deterministic and a proxy. Where a dimension matters a lot to your users, back it with full tool results, a calibrated judge or a human review sample.

## 27.6 The agent scorecard

A **scorecard** puts the numbers a release decision needs side by side. Its lines define every metric the rest of the book uses, and Chapter 28's SLOs and Chapter 29's latency and cost targets reuse these definitions exactly.

`run_suite` grades, times and scores every trial; `scorecard` summarizes. The kit's offline demo scores six canned runs of two cases, no API key needed (`python ch27_scorecard.py`). The counting question passes all three trials, but one takes 7.4 s and mentions 500 orders, a number no tool returned. The delete request is refused twice; on the third trial the agent tries a `DELETE` and then claims it succeeded:

Table: The lines of the agent scorecard
| Line | What it means | In the demo |
| --- | --- | --- |
| **Success rate** | Runs that passed outcome and process, out of all runs | The `DELETE` attempt failed |
| **Reliability (pass^k)** | Cases that passed on every one of k trials | A user asking to delete gets a different agent one time in three |
| **Tool accuracy** | Runs with the right tools, among runs that test it | Only the counting question tests it |
| **Argument accuracy** | Runs whose arguments passed `arg_checks` | The `DELETE` query broke a rule |
| **Task completion** | Runs that finished on their own, not cut off by a step limit, budget or stop reason | Every run finished |
| **Safety violations** | Runs that broke a policy rule or changed the data | One in six; anything above zero is a stop-ship |
| **Average steps** | Tool calls per run | Low, because refusals make no calls |
| **Latency p50 and p95** | The median run, and the run that 95% of runs finish within | With six runs, p95 is just the slowest run |
| **Cost per task** | Total spend divided by the number of runs | $0.0040 |
| **Cost per success** | Total spend divided by the number of successful runs | Higher: failed runs are paid for too |

The dimension rows show what the headline hides. Task success is 100% because the demo's canned outcome is always true, yet success rate is 83%: the process caught what the outcome missed. The third delete trial changed nothing (the database is read-only) and contains no number, so neither `db_unchanged` nor groundedness caught its false claim, "the cancelled orders are gone". Escalation did, because the answer neither refused nor asked.

**The conditions.** No model runs here: `_canned` builds six runs (2 cases × 3 trials) as `grade` would return them, and the real `scorecard` code computes the rates and percentiles from them. Concurrency and caching aren't modelled, no intervals are reported, and each run's latency and $0.004 cost are typed in, so the figures are illustrative. The full conditions are in `benchmarks/README.md` in the course kit.

A live `ch27_eval.py` run is different: it calls the model named by `MODEL` (default `claude-sonnet-5`), one trial at a time, with no prompt caching, and prints each pass rate with its Wilson 95% interval. Those numbers are measured, on your machine and your model.

:::tip Reading an evaluation result
Start with the size. 83% success is 5 of 6 runs. The `wilson` docstring shows how little that says: 17 passes in 20 runs is 85%, yet the true rate could be anywhere from about 64% to 95%. Six runs leave it wider still, so this 83% can't rank two versions; `gate` does that, on more runs.

Next, pass^3 is 50%: of two cases, only the counting question passed every trial. The delete case is flaky, passing two trials of three, and its failure is a safety violation. Flaky plus unsafe means that, in this small sample, one delete request in three met the bad agent.

So read the failing trajectory first: a `DELETE`, then a claim of success. Fix the cause, keep the case in the suite, and rerun with more trials. A safety violation blocks the release whatever the interval says.
:::

Teams put a scorecard to work like this:

- **One per release, compared with the last.** A change that raises success by 2 points but doubles cost per success shows up as two lines moving in opposite directions, and you decide with both in view. On a small suite, a few points is noise (section 27.2).
- **Thresholds as a CI gate.** Absolute limits where there's no slack, such as zero safety violations and 100% completion, beside section 27.7's statistical comparison (exercise 27.8).
- **The same definitions as your production SLOs.** Success rate, p95 latency and cost per task are service-level objectives in section 28.10, and cost per success is an alert threshold in section 28.11, computed the same way on live traffic. If the suite gives 83% success, a 95% success SLO will burn, and you learn that before users do.

**The release scorecard: eleven qualities.** No single run shows whether every run left a debuggable trace, whether known attacks are still stopped, or whether the next person can change the agent safely. The **agent quality scorecard** puts eleven qualities in one view, each with a floor:

@@code ch27_scorecard.py::QUALITY_TARGETS,quality_scorecard~

This is the same scorecard seen from the release meeting, not a second system: eight rows reuse run-scorecard numbers under reviewers' names, and three come from evidence collected once per release. Escalation stays on the run scorecard. Run `./course.sh python ch27_scorecard.py --release`:

Table: Where each release quality comes from
| Release quality | Computed from | Counted over |
| --- | --- | --- |
| Outcome quality, trajectory quality | The `task_success` and `trajectory` dimensions | Runs |
| Safety | 1 − safety violations | Runs |
| Tool correctness | The lower of tool accuracy and argument accuracy | Runs |
| Groundedness | The `groundedness` dimension | Runs |
| Reliability | Pass^k, the `reliability` dimension | Cases |
| Latency | The suite's p95 against the release's p95 budget | The whole suite |
| Cost | Cost per success against the release's cost budget | The whole suite |
| Observability | Runs with a complete trace (section 28.1) | Release evidence |
| Security | Regression scenarios that pass (section 25.10) | Release evidence |
| Maintainability | Hygiene checks: a versioned release bundle (section 30.13), eval suite in CI, decision records, an owner | Release evidence |

Latency reads 67% on the run scorecard and 100% here, and both are right. The `latency` dimension checks each run against its case's budget: the counting question allows 5 seconds (`max_ms`), so its 7.4-second trial fails and two of three tested runs pass (the delete case sets no budget). The release row asks whether the suite's p95, that same 7.4 seconds, fits the release's 8-second budget. It does, so the row reads 100%. Had the p95 been over budget, the row would show how far over (the budget divided by the p95). Cost splits the same way: each run against its case's `max_cost`, and cost per success against a $0.02 release budget. The case budget catches one slow answer; the release budget judges the suite as a whole.

The same six runs block the release five times over, and one block has nothing to do with answers: nobody owns the agent yet. Adapt the floors like the SLO targets in section 28.10, except safety and security, which stay at 100%. Reference card 6 (Appendix I) lists the eleven qualities.

## 27.7 A regression gate for CI

The suite runs on every pull request (exercise 27.4), and the gate asks one question: is the candidate **worse than the baseline by more than noise**?

@@code ch27_trajectory.py::gate

`gate` compares the two pass rates with a one-sided two-proportion test at about 95% confidence and blocks only a real drop. With 20 runs each, 90% against 60% blocks; 90% against 85% doesn't, because two 20-run samples can't tell those apart. Small drops need more runs. Gate on outcome and process together, and report cost per successful task beside them so a doubled bill stays visible.

But a comparison can't catch a safety violation the baseline also had, and "no worse than last week" isn't enough when last week was bad. So add the scorecard's fixed limits for safety, completion and cost per success (exercise 27.8). Set each a little worse than what you measure today, and keep the safety limit at zero.

## 27.8 Continuous evaluation

Offline suites test the inputs you thought of. Users send the others. **Continuous evaluation** grades real traffic and feeds what it finds back into the suite:

@@image d-6f7a5fd0e8cb.png

Figure: The continuous evaluation pipeline
Alt: Eval-suite cases produce runs with k trials per case. Graders (code checks, trajectory checks, a model judge and a human-review sample) feed the scorecard and a CI gate: pass leads to release, fail to fix and rerun. Production traces turn failures into new eval cases.

Cheap deterministic checks run first, then the judge, and a small sample goes to people, who also keep the judge calibrated. In production:

@@code ch27_trajectory.py::sample_for_review,drift

- **Sample.** Grade every run a guard, a user or an error flagged, plus a small random share of the rest; flagged runs alone overstate the problems.
- **Grade.** Use the same checks and judge on traces (Chapter 28) with personal data removed. Some need no ground truth, such as contradicting a tool result or exceeding a budget.
- **Watch for drift.** A model update, a changed tool or new kinds of questions can move quality without any change of yours. `drift` flags a day that falls well below the recent average.
- **Close the loop.** Every production failure worth fixing becomes a suite case, so the suite grows toward your real traffic.

:::note The support agent so far
The support agent gets an evaluation suite: real support questions, cases that should hand off, attempts to read another customer's order, and injected instructions. Its scorecard covers success, accuracy, safety, escalation, cost and latency, and a release gate blocks any change that makes it worse.
:::

:::note In the field
The customer owner judges the agent by the brief's metric, such as minutes saved per claim file. Put that metric and your pass rate into the acceptance criteria before the pilot, so the agent can't pass your gate and still fail their business (section 31.5).
:::

## Common mistakes

- Shipping without an eval suite, or without a baseline to compare it with.
- One run per case, reading noise as progress.
- Trusting an uncalibrated judge, or using a judge instead of deterministic checks.
- Grading only the final answer, so dangerous or wasteful paths look like successes.
- Over-specifying the trajectory, so every new good path fails.
- Reporting one number, or counting untested dimensions as passes.
- Stopping at launch, so quality drifts unseen between releases.

## Before you move on

- **You should understand:** why a right answer after an unsafe trajectory fails the run, and why 83% on six runs can't rank two versions.
- **You should be able to build:** a suite with `answer_sql`, `db_unchanged` and trajectory checks, run over several trials and summarized in a scorecard.
- **Prove it:** exercise 27.8, then `./course.sh python ch27_scorecard.py --release`.
- **Break it on purpose:** feed `gate` 20 baseline runs at 90% and 20 candidate runs at 85%, and watch it let a real drop through. Then find how many runs it needs.
- **Defend this decision:** why the release gate pairs a statistical comparison with fixed limits, and keeps the safety limit at zero.

## Key takeaways

**Architect's takeaway:** Define success before you build. What you measure decides which designs you can defend.

- Run every case several times; read pass rates with confidence intervals, pass^k and flaky cases.
- Calibrate model judges against human labels before trusting them.
- Grade every run on outcome, process and cost; a right answer after a bad path is a failure.
- Score ten dimensions; each automatic check is a proxy, and the others cover its blind spots.
- One scorecard per release, with the same definitions as your production SLOs.
- Keep evaluating in production, and turn failures into test cases.
