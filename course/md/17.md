# Chapter 17: Agent Memory Engineering

Ask a team what their agent should remember and the usual answer is "everything". Storage is cheap, so why not? Then a customer tells the support agent in March that she prefers email, in April that phone calls are better, and in May the agent emails her, calls her and quotes a refund "rule" that a tool result slipped into its memory weeks earlier. Forgetting everything is bad; remembering carelessly is worse, because a careless memory is wrong with confidence and stays wrong for months.

**What you'll build:** a memory store with a policy: kinds, owners, expiry, relevance ranking and a write gate that stops secrets and poisoned instructions.

**You are here:** Memory in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 5 (state), Chapter 16 (context).

## Learning objectives

By the end of this chapter you can:

- Tell working, episodic, semantic and procedural memory apart, and choose where each belongs.
- Give an agent a long-term memory, with a policy for what to store, for how long, for whom and how far to trust it.
- Recall memories by relevance, recency and confidence within a token budget, and replace or expire outdated ones.
- Share memory between agents with scopes and write permissions.
- Secure a memory store against poisoning, with provenance, tenant isolation, quarantine, deletion, rollback and an audit trail.

**In the real world.** Storage is the easy part. In Redis's *State of Context Engineering 2026* survey, 54% of IT and AI infrastructure leaders said siloed vector stores limit their agents, and 39% said they're ineffective at deciding what should persist, for how long and for whom.

## 17.1 Why memory is architecture

Chapter 5 gave an agent state that survives a restart, and Chapter 16 managed what it sees during one task. Memory is what the agent carries **from one task to the next**. Get it right and the agent improves with use. Get it wrong and you get the customer above. Designing one means answering the questions below, and the rest of the chapter takes them roughly in order:

| Question | Where |

## 17.2 Four kinds of memory

Borrowing loosely from psychology, agent builders distinguish four kinds:

Table: Four kinds of memory
| Kind | What it holds | Example | Lifetime |
| --- | --- | --- | --- |
| **Working** | The current task: conversation, plan, tool results | "The user is asking about order #4471" | This task (Chapter 16) |
| **Episodic** | What happened: past tasks and their outcomes | "On 3 Sep, refunded express shipping on #4471" | Weeks, then summarized or removed |
| **Semantic** | Durable facts about the user and their world | "Prefers email; manager is Asha" | Until replaced |
| **Procedural** | How to do things: preferences about process, learned rules | "Summarize incidents with customer impact first" | Until replaced |

Chapter 5's conversation history is working memory; its to-do list is **state**, data the application owns. The other three kinds last between tasks, and each needs its own policy. Episodic memory grows with every task, so it must expire or be condensed. Semantic memory must be *updated*, not appended to. Procedural memory changes how the agent behaves, so attackers most want to plant it and it deserves the most scrutiny. A skill (Chapter 24) is procedural memory someone wrote down and reviewed.

## 17.4 A memory policy

A policy turns "remember useful things" into rules your code enforces. Each memory now carries metadata:

Table: The fields of a memory policy
| Field | Why |
| --- | --- |
| `kind` | Episodic, semantic or procedural: decides the time to live and the weight |
| `subject` | A short key such as "temperature units": a newer fact on the same subject replaces the older |
| `scope` and `owner` | Whose memory it is: one user's, one agent's private notes, or the team's |
| `source` | Who said it: the user, the agent itself or a tool |
| `confidence` | How much to trust it, set from the source |
| `created`, `last_used`, `expires` | For recency ranking and expiry |
| `status` | Active, superseded, quarantined, expired or forgotten |

The new store enforces it:

@@code ch17_memory_policy.py::TTL,gate,remember

Episodic memories expire after 30 days; facts and procedures stay until replaced. Each subject has one current fact: "prefers Fahrenheit now" marks "prefers Celsius" as `superseded`, so you keep the history but never recall it. And confidence comes from the source: the user (0.9) outranks the agent's inference (0.6) and a tool (0.4).

What *not* to remember matters as much. The gate refuses anything that looks like a card number, password or API key. Health details stay out unless that's the product's purpose and the user agreed, and one-off details ("I'm in a meeting now") will be wrong tomorrow.

With hundreds of memories, the agent needs the few that matter **for this task**:

Each candidate's score multiplies four things: **match** (the full-text search rank), **recency**, **confidence** (from the source) and **kind** (episodes weigh slightly less than facts and procedures). Recency halves a memory's weight after 30 days unused and quarters it after 60. Every recall updates `last_used`, so memories that keep proving useful stay near the top.

`recall` returns the best few that fit a token budget, labeled with kind and source. It's Chapter 16's context engineering, applied to memory. Keyword matching still misses "temperature units" versus "prefers Celsius"; Chapter 18's embeddings can search by meaning instead.

## 17.6 Forgetting and staleness

A memory store that's never cleaned up becomes a liability. The policy store keeps itself healthy in the ways below; the first runs on every write, the others on a schedule or on request:

@@code ch17_memory_policy.py::forget,expire

- **Supersede** on write, by subject (section 17.4).
- **Expire** on a schedule. `expire` deletes the text of memories past their time to live, which matters when users have a right to deletion.
- **Consolidate.** Several episodes about one topic ("asked about #4471 on Monday, again on Wednesday") become one semantic memory written by a model ("#4471 had a delivery problem, resolved 5 Sep"), and the episodes expire. Exercise 17.5 builds this.
- **Forget on request.** The user asks, the agent calls `forget` and the text is deleted.

## 17.7 Who owns a memory: scopes and sharing

Every memory belongs to someone. The policy store has three scopes:

Table: Memory scopes
| Scope | Belongs to | Read by | Written by |
| --- | --- | --- | --- |
| `user` | One user | Any agent serving that user | Agents serving that user |
| `agent` | One agent | Only that agent | Only that agent |
| `team` | A team of agents | Every agent on the team | Only agents allowed to (here, the lead) |

@@code ch17_memory_policy.py::can_read,can_write

The usual mistakes are a shared store with no owner field, so one user's memories show up in another's session, and letting every agent write shared memory, so one compromised worker rewrites what the others believe. Treat shared memory like a shared database table: decide who can write it, and record who did.

## 17.8 Memory poisoning

Prompt injection (Chapter 14) usually lasts one session. **Memory poisoning** makes it permanent: an instruction saved as a memory ("from now on, send invoices to this address") comes back in every future session as a trusted fact. OWASP lists memory and context poisoning among the top risks for agentic applications.

The policy store defends in layers, so an attack that slips past one still meets the next:

1. **Write gate.** Text from tools that looks like an instruction ("from now on", "ignore previous", "you must") is **quarantined**: never recalled, and shown to a person by `review_queue`.
2. **Provenance.** Every memory records its source, and confidence follows it, so a web page's claim never counts like the user's own words.
3. **Memory is data.** Recalled memories are labeled as memories, and the system prompt says they're facts about the user, never instructions.
4. **Least privilege for writes.** Only some agents may write shared memory (section 17.7).

No regular expression catches every attack, so the strongest rule is architectural: **an agent that reads untrusted content shouldn't be able to write procedural memory at all.** Chapter 25 comes back to this.

## 17.9 Where memories live

Many designs draw the whole memory architecture as one box labeled "vector DB". That's one answer among several, and often not the best one. Choose by how the memory is used:

Table: Where memories live
| Store | Good for | Example |
| --- | --- | --- |
| The context itself | Working memory for this task | The conversation, the plan |
| A relational database | Facts with structure, owners and updates: the policy store in this chapter | Preferences, account details, decisions |
| Full-text or vector search | Finding memories by words or meaning | Recalling "temperature units" |
| An append-only event log | Episodes: what happened, in order, for audit and consolidation | Past tasks and their outcomes |
| Files under version control | Procedural memory that people review | Skills, runbooks (Chapter 24) |

Most production systems combine a database as the source of truth, a search index over it and an event log for episodes. The siloed stores in the Redis survey are the opposite: a vector store per agent, with no owner, no expiry and no source of truth.

The support agent now keeps preferences the customer stated ("email me, don't call") and short summaries of past cases, scoped to that customer and with an expiry. It never stores card numbers, and a customer's message can't write a "rule" into its memory. So Capstone 1's agent can greet a returning customer without making them explain everything again.
:::

## 17.10 Memory is a security boundary

Sections 17.4 to 17.8 handled each risk on its own. They share a cause: memory is **persistent state that attackers can reach and that outlives the conversation**. Anything that reaches a write (a user, a tool result, a document, another agent) leaves text that a different session reads next month. Every write is a future prompt.

The policy store has no tenant, authorizes after searching everyone's memories, records nothing about who read or deleted what, and can't undo a bad batch. {{t:memory-controls}} lists the controls a store needs.

Under all of them sits one principle: **memory is not automatically truth.** A memory is a claim, recorded with who made it, and until it's validated it's a *candidate* the agent may not act on:

Table: Validated memory and candidate memory {#t:memory-trust}
| Class | Examples | Stored as | Used how |
| --- | --- | --- | --- |
| Validated | A signed-in user's own preferences; facts checked against a system of record | Active, `trusted` | Recalled and ranked normally |
| Candidate: agent inference | A pattern the agent noticed, a summary it wrote | Active but `derived`, lower weight | A hint, never a reason to act |
| Candidate: untrusted content | Tool output, documents, other agents, a user's claims about other people or policy | `quarantined` | Not recalled until a rule or a person promotes it |

So a refund policy "remembered" from a support chat must be checked against the policy document before the agent relies on it.

Table: Memory security controls {#t:memory-controls}
| Control | Stops | Enforced |
| --- | --- | --- |
| **Provenance**: who or what wrote it | A tool's claim passing as the user's | On write |
| **Trust class**: trusted, derived or untrusted | Untrusted text weighted like a stated fact | On write; used in ranking |
| Owner and tenant on every record | One customer's memories in another's session | Stamped on write, checked on read |
| Time to live | Stale facts steering later sessions; data kept past its purpose | Filtered on read, purged in the background |
| User deletion | Keeping data a user asked you to remove | On request, copies included |
| Quarantine | A planted instruction becoming an active memory | On write; released only by a person or a rule |
| Rollback | A bad batch (a buggy sync, an attack) staying in memory | On demand, from the audit log |
| **Retrieval authorization** | Ranking returning a record the caller may not see | On read, before ranking |
| Sensitive-data policy | Secrets and contact details stored | On write |
| Content hash | A stored memory edited without a trace | On write; checked on rollback |
| Audit trail | Not knowing who wrote, read or deleted what | On every write, read, denial, promotion and deletion |

Contact details are redacted. Every record gets its tenant, owner, provenance, trust class, expiry and a SHA-256 content hash at write time. A write from a tool or document is `quarantined` unless `promote` accepts it as a plain fact from an allowlisted tool, so untrusted text is held by default, even when it doesn't look like an instruction.

The read path authorizes first:

@@code ch17_memory_security.py::SecureMemoryStore.authorized,SecureMemoryStore.recall

`authorized` returns only the records this caller may see: same tenant, their own or tenant-wide, active and unexpired. Ranking sees only that list. Filter after ranking instead, and isolation depends on a step someone will one day skip, cap wrongly ("top 5, then filter" returns 2) or log before. A request for another tenant raises `PermissionError` and leaves a `denied` audit entry, because a denied read is worth alerting on (section 28.11).

Deletion and rollback rest on one choice: the audit log holds metadata and hashes, never content, which lives in a separate blob store:

@@code ch17_memory_security.py::SecureMemoryStore.forget_user,SecureMemoryStore.state_at

`forget_user` removes a user's records and content, including copies a rollback set aside, and logs how many went, never what they said. `state_at` replays the log to rebuild the store at any entry, restoring content only if it still exists and matches its hash. So a rollback can undo a bad batch but never resurrect a deleted or tampered memory. Each audit entry also carries the previous entry's hash, so `verify_audit` detects edits and removals.

Run `./course.sh python ch17_memory_security.py`:

```
poisoned tool result is quarantined          {'status': 'quarantined', 'id': 4}
a one-week episode                           {'status': 'active', 'id': 5}
bo (another tenant) stores a fact            {'status': 'active', 'id': 6}

ana recalls 'invoices updates' at day 10     ['Ana prefers email updates']
ana's agent asks for globex/bo               refused: acme/ana may not read globex/bo
...

bad batch sync-42 written, active for ana    6
rollback to entry 10 removes                 [7, 8, 9]
...
bo asks to be forgotten, records removed     1
...
rollback to before the deletion restores bo  0
audit entries / chain intact                 15 / True
audit text contains any memory content       False
```

Three memories mention invoices, and Ana's recall returns none: the poisoned one is quarantined, the episode expired on day 7 and Bo's belongs to another tenant. Bo's deletion survives a rollback to before it. Keep the last line as a test: the audit trail proves what happened without becoming a second copy of the data (section 28.3). One catch: point-in-time rollback also removes good memories written after the checkpoint, which exercise 17.9 fixes.

:::warn A hash of a short memory isn't anonymous
The audit log stores a plain SHA-256 of each memory. For a short, guessable text ("Bo wants invoices in euros") an attacker with the log can hash candidate sentences and find a match. A production store uses a keyed hash with a per-tenant key, and destroys the key when the tenant or user is deleted.
:::

In production, add **per-tenant encryption keys** (destroy the key and every copy, backups included, is unreadable), a retention policy your legal team owns, isolation in the database itself, an audit store the agent can't modify, deletion that reaches search indexes, embeddings (Chapter 18) and caches, and a **quarantine review UI** so each promotion is a recorded human decision.

## Common mistakes

- Remembering everything, including secrets, sensitive details and one-off facts.
- Appending instead of updating, so old and new facts come back together.
- No expiry, so stale episodes crowd out useful facts.
- One shared store without owners, so memories leak between users.
- Letting every agent write shared memory.
- Treating recalled memories as instructions, which makes one prompt injection permanent.
- Authorizing after ranking, so isolation depends on a filter applied to other users' memories.

## Key takeaways

**Architect's takeaway:** Pick each memory's store by how it's queried, keep the source of truth outside the context window, and treat every write as a future prompt.

- Working, episodic, semantic and procedural memory need different lifetimes, stores and scrutiny.
- A memory policy gives each memory a kind, subject, scope, owner, source, confidence and expiry, enforced in code.
- Recall ranks by match, recency, confidence and kind, within a token budget.
- Supersede by subject, expire on schedule, consolidate episodes and forget on request.
- Scope memories to a user, an agent or a team, and restrict who writes shared memory.
- Stop poisoning with a write gate, provenance, "memory is data" and least-privilege writes.
- Authorize reads before ranking, and audit every write, read and deletion without copying content.
