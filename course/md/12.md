**In the real world.** The Model Context Protocol (MCP) is an open standard for connecting AI applications to tools and data. In December 2025, with over 97 million monthly SDK downloads and around 10,000 active servers, it became a founding project of the Linux Foundation's Agentic AI Foundation, co-founded by Anthropic, Block and OpenAI. ChatGPT, Claude, Cursor, Gemini, Microsoft Copilot and Visual Studio Code all support it.

## 12.1 The problem MCP solves

Without a standard, every host you want to support means writing the function's JSON Schema and wrapper again, in that host's format.

MCP separates **tools** from **agents**. You package tools once as an **MCP server**, and any **MCP client** can discover and call them. Think of USB: one plug, many devices.

## 12.2 Hosts, clients and servers

Table: The three MCP roles
| Role | What it is | Examples |
| --- | --- | --- |
| Host | The AI application the user works in; it runs the model | Claude Desktop, VS Code, your Chapter 13 agent |
| Client | A connection inside the host to one server | One per server the host uses |
| Server | A program that offers capabilities over MCP | Your weather server, GitHub's server, the Filesystem server |

A host with three servers has three clients. They exchange **JSON-RPC** messages with the servers: small JSON objects with a method name (like `tools/list` or `tools/call`) and parameters.

## 12.3 What a server offers

Table: What an MCP server offers
| Primitive | What it is | Who decides to use it | Weather example |
| --- | --- | --- | --- |
| Tools | Functions that do something | The model | `geocode`, `get_forecast` |
| Resources | Data the host can read, identified by a URI | The host or user | `weather://favorites` |
| Prompts | Reusable prompt templates with parameters | The user, e.g. from a menu | `packing_advice(city, days)` |

MCP calls these three kinds of offering *primitives*. Resources are like read-only files the host can attach to a conversation, each with a *URI* (an address such as `weather://favorites`). Prompts are shortcuts a user picks, so many hosts show them as slash commands.

The "Who decides" column is the specification's design intent, which the protocol doesn't enforce: it leaves the user interface to the host. Approval works the same way. The specification says a person should be able to deny a tool call, but no approval step crosses the wire; Claude Desktop asks because its developers built that in. In your own host (Chapter 13), nobody asks unless your code does.

## 12.4 Your first server

The kit's image already has the SDK; in your own projects, install it with `pip install "mcp[cli]"`. Then wrap the Chapter 7 functions:

@@code ch12_weather_server.py

Compare it with Chapter 7. There's **no hand-written JSON Schema**: `@mcp.tool()` builds it from the type hints (`latitude: float`), and the docstring becomes the description, so write docstrings as carefully as the Chapter 2 descriptions. **Errors use `ToolError`**: raising `ToolError("…")` sends the client a result with `is_error` set and your message, as `ERROR:` strings did before; an unexpected exception is reported as an error too, with its details hidden. And **logging goes to stderr**, because with the stdio transport stdout carries the JSON-RPC messages.

### What the protocol defines and what the SDK does

The **MCP specification** defines what crosses the wire: the JSON-RPC methods (`tools/list`, `tools/call`, `resources/read`, `prompts/get`), what a tool definition contains (a name, a description and a JSON Schema for its input), the shape of a result and the transports. It also separates two failures. A tool that ran and failed returns a normal result flagged as an error, which the model reads; a broken request, such as an unknown tool name, gets a JSON-RPC error that the host handles.

Everything else in `ch12_weather_server.py` is the **Python SDK** helping: schemas from type hints, docstrings as descriptions, `ToolError`, hidden exception details, `print()` moved to stderr and the DNS-rebinding protection of section 12.7. Another SDK sends the same messages but may do none of that for you. And most of the protocol is optional: a server with two tools and nothing else is complete, and every feature in section 12.8 can be left out.

:::warn Never write to stdout in a stdio server
Use `logging` configured to `sys.stderr`, as the file does. The Python SDK (version 2 and later) quietly moves `print()` output to stderr while a stdio server runs. Most other SDKs don't, including TypeScript's `console.log`, Java's `System.out` and older Python versions: one stray line corrupts the stream, and the host drops the connection. Make stderr logging a habit.
:::

## 12.5 Testing with MCP Inspector

MCP Inspector, installed in the kit's image, tests servers in your browser without a model:

```
./course.sh inspector ch12_weather_server.py
```

The terminal prints a link like `http://localhost:6274?MCP_INSPECTOR_API_TOKEN=…`. Open the whole link, which includes a security token; the Inspector's ports are published only to your own computer. For quick checks and scripts there's a command-line mode: `./course.sh inspector ch12_weather_server.py --cli --method tools/list`.

List the tools, call `geocode` with "Pune", read the `weather://favorites` resource and fill in the `packing_advice` prompt. Test every server this way before connecting a model; if something fails here, the problem is your server.

## 12.6 Connecting to Claude Desktop {api}

Claude Desktop starts the servers listed in its configuration file, and since yours lives in the kit's container, it starts it through Docker. Generate the configuration for your computer:

```
./course.sh desktop-config
```

It prints something like this, with your kit folder's real path filled in:

```
{
  "mcpServers": {
    "weather": {
      "command": "docker",
      "args": ["compose", "-f", "C:\\Users\\you\\building-agentic-ai\\compose.yaml",
               "run", "--rm", "-T", "course", "python", "ch12_weather_server.py"]
    }
  }
}
```

Open Claude Desktop's config from Settings → Developer → Edit Config and add the `weather` entry. The `-T` flag turns off Docker's terminal mode so the JSON-RPC messages pass through stdin and stdout untouched. Docker Desktop must be running.

Restart Claude Desktop and ask "What should I pack for Seattle this weekend?" Claude discovers your tools, asks permission before calling them and uses the results: a capability you wrote, in a commercial AI app, without changing a line of the app.

## 12.7 Transports: stdio and Streamable HTTP

A *transport* is how messages travel between client and server.

Table: The two MCP transports
|  | stdio | Streamable HTTP |
| --- | --- | --- |
| How it runs | The host starts the server as a subprocess | The server runs as a web service |
| Who can connect | Only that host, on that machine | Any client that can reach the URL (so it needs authentication in production) |
| Good for | Local tools, development | Shared team servers, hosted services |

The same server code supports both. Since the 2026-07-28 specification the protocol is **stateless**: every request carries the protocol version and the client's capabilities, so an HTTP server keeps no per-client session, and any copy behind a load balancer can answer. `Mcp-Method` and `Mcp-Name` headers let gateways route and rate-limit calls without reading the body. The older HTTP+SSE transport is deprecated.

`./course.sh serve ch12_weather_server.py` serves MCP at `http://localhost:8000/mcp`.

Inside a container, a server must listen on all interfaces (`0.0.0.0`) to be reachable through a published port; `serve` sets that through `MCP_HOST`, and the default stays `127.0.0.1`. That raises a catch. **DNS-rebinding protection** checks each request's `Host` and `Origin` headers; it's what stops a web page in your browser from talking to servers on your machine. Whether the SDK turns it on for a server listening on all interfaces depends on the SDK version, so check its documentation rather than trusting a default. The kit doesn't rely on one: it passes `transport_security` with the protection on and explicit lists of the host names (`127.0.0.1` and `localhost`, any port) and origins the server will accept. A client connects with `streamable_http_client` instead of `stdio_client` (exercise 12.7).

## 12.8 Other MCP features you'll meet {api}

Real servers and clients use more than tools, resources and prompts. The 2026-07-28 revision changed several of the other features; {{t:mcp-features}} shows what's current:

Table: Other MCP features and their status {#t:mcp-features}
| Feature | Direction | What it's for |
| --- | --- | --- |
| **Structured tool output** | Server → client | A tool declares an `outputSchema` and returns typed data alongside the text; automatic in Python for a Pydantic model or `TypedDict` return type. |
| **Tool annotations** | Server → client | Hints such as `readOnlyHint` or `destructiveHint` for the host's UI. They're the server's claims, never a security control (Chapter 14). |
| **Elicitation** | Server → user | Mid-call, the server asks the user for input through the host ("How many nights?"). Since 2026-07-28 the tool returns an *input required* result and the client calls again with the answers (**multi round-trip requests**). The Python SDK handles both this and the older style for you; exercise 13.7 uses it. |
| **Tasks** (extension) | Client ↔ server | Long-running calls return a task handle the client polls, instead of holding a request open. |
| **MCP Apps** (extension) | Server → user | A tool points to a `ui://` resource (HTML and JavaScript) that the host shows in a sandboxed frame in the chat, such as a chart or a form. Claude, ChatGPT, VS Code and Goose support it. |
| **Cacheable lists** | Server → client | Since 2026-07-28, lists and resource reads carry cache hints (`ttlMs`, `cacheScope`), so hosts don't re-ask every turn. |
| **Sampling** | Server → model | The server asks the *host's* model to generate text. **Deprecated** as of 2026-07-28; new servers should call a model API directly. |
| **Roots** | Client → server | The client tells the server which folders it may work in. **Deprecated** as of 2026-07-28; pass folders as tool parameters or resource URIs. |
| **Logging** | Server → client | Log messages sent over the protocol. **Deprecated** as of 2026-07-28; log to stderr or with OpenTelemetry, the open standard for traces and logs (Chapter 28). |
| **Authorization** | Client ↔ server | OAuth 2.1, the web's standard protocol for granting access, for remote servers: Chapter 30. |

Deprecated features are still part of the protocol, the Python SDK still supports them, and they'll keep working for at least twelve months. You'll meet them in older servers; don't build new ones on them.

**Where MCP is heading.** The August 2026 roadmap focuses on long-running agent work, one HTTP-based transport, standard agent identity, progressive discovery and better SDKs. Chapter 15 covers the protocol side and sections 30.8 to 30.11 what's built on it; none of it changes the rule that the host stays in control.

:::tip Which version does a server speak?
MCP specifications are named by date, and client and server agree on one per request. The Python SDK speaks 2026-07-28 and older revisions, so you rarely need to care; when a feature seems missing, check which version the server supports.
:::

## Common mistakes

- Writing to stdout in a stdio server. Python's SDK redirects it; most others corrupt the stream.
- Missing type hints or docstrings, so the model gets a vague schema and description.
- Relative paths in the Claude Desktop config. The host starts servers from its own working directory (`desktop-config` writes absolute paths for you).
- Forgetting `-T` with `docker compose run`, which garbles the stdio stream.
- Skipping the Inspector and debugging through the model, so you can't tell a server bug from a model choice.
- Exposing an HTTP server without authentication beyond your machine.

## Before you move on

- **You should understand:** which parts of your server the MCP specification defines (methods, tool definitions, result shapes, transports) and which the Python SDK adds (schemas from type hints, `ToolError`, stdout redirection).
- **You should be able to build:** an MCP server with at least one tool, one resource and one prompt, served over stdio and Streamable HTTP.
- **Prove it:** exercise 12.3 (`./course.sh ex 12.3`), then exercise 12.7.
- **Break it on purpose:** delete the type hints and docstring from `geocode`, run `./course.sh inspector ch12_weather_server.py --cli --method tools/list`, and read the schema the model would now get.
- **Defend this decision:** why a given tool should be an MCP server rather than a function inside your agent, and whether it should run over stdio or HTTP.

## Key takeaways

**Architect's takeaway:** Write a tool once as an MCP server and every host can use it. The price is one more process to run, test and secure.

- MCP packages tools once for any compatible host. A host runs the model and has one client per server; servers offer tools, resources and prompts.
- Log to stderr in stdio servers, and test with Inspector before involving a model.
- Use stdio for local servers and Streamable HTTP for shared or remote ones.
