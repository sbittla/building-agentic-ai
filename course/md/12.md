## Real-world connection

Model Context Protocol (MCP) is an open standard for connecting AI applications to tools and data. In December 2025 it became a founding project of the Linux Foundation's Agentic AI Foundation, co-founded by Anthropic, Block and OpenAI. By then it had over 97 million monthly SDK downloads and around 10,000 active servers, with support in ChatGPT, Claude, Cursor, Gemini, Microsoft Copilot and Visual Studio Code. The official MCP quickstart builds a weather server, which is exactly what this chapter does with your Chapter 7 code.

## 12.1 The problem MCP solves

Look back at Chapters 2 to 11. Every agent re-declared its tools: a Python function, a JSON Schema and a `run_tool` wrapper. Now imagine you want the weather tools in Claude Desktop, in your IDE and in a colleague's agent written in TypeScript. Without a standard, you'd rewrite the integration for each one.

MCP separates **tools** from **agents**. You package tools once as an **MCP server**, and any **MCP client** can discover and call them. It's the same idea as USB: one plug shape, many devices.

## 12.2 Hosts, clients and servers

| Role | What it is | Examples |
| --- | --- | --- |
| Host | The AI application the user interacts with; it runs the model | Claude Desktop, VS Code, your Chapter 13 agent |
| Client | A connection inside the host to one server | One per server the host uses |
| Server | A program that offers capabilities over MCP | Your weather server, GitHub's server, the Filesystem server |

A host with three servers has three clients. Hosts and servers exchange **JSON-RPC** messages: small JSON objects with a method name (like `tools/list` or `tools/call`) and parameters.

## 12.3 What a server offers

| Primitive | What it is | Who decides to use it | Weather example |
| --- | --- | --- | --- |
| Tools | Functions that do something | The model | `geocode`, `get_forecast` |
| Resources | Data the host can read, identified by a URI | The host or user | `weather://favorites` |
| Prompts | Reusable prompt templates with parameters | The user, e.g. from a menu | `packing_advice(city, days)` |

Tools are what you've built throughout this book. Resources are like read-only files the host can attach to a conversation; each has a *URI*, an address such as `weather://favorites`. Prompts are shortcuts a user picks, which is why many hosts show them as slash commands.

## 12.4 Your first server

Install the SDK with `uv add "mcp[cli]"`. Then wrap the Chapter 7 functions:

@@code ch12_weather_server.py

Compare this with Chapter 7:

- **No hand-written JSON Schema.** `@mcp.tool()` builds the schema from the type hints (`latitude: float`), and the docstring becomes the description. Docstrings now matter as much as the descriptions you wrote in Chapter 2.
- **Errors use `ToolError`.** Raising `ToolError("…")` sends the client a result with `is_error` set and your message, as returning `ERROR:` strings did before. An unexpected exception is also reported as an error, but its details are hidden from the client.
- **Logging goes to stderr.** With the stdio transport, stdout carries the JSON-RPC messages, so anything else written there can corrupt them.

:::warn Never write to stdout in a stdio server
Use `logging` configured to `sys.stderr`, as the file does. The Python SDK (version 2 and later) protects you: while a stdio server runs, it quietly sends `print()` output to stderr. Most other SDKs don't, including TypeScript's `console.log`, Java's `System.out` and older Python versions. There, one stray line of output corrupts the stream and the host drops the connection. The official quickstart warns about this for every language, so make logging to stderr a habit.
:::

## 12.5 Testing with MCP Inspector

MCP Inspector is a browser-based tool for testing servers without a model. It's installed in the kit's image. Run it against your server:

```
./course.sh inspector ch12_weather_server.py
```

The terminal prints a link like `http://localhost:6274?MCP_INSPECTOR_API_TOKEN=…`. Open the whole link in your browser; it includes a security token. The Inspector runs inside the container, and its ports are published only to your own computer. A command-line mode is handy for quick checks and scripts: `./course.sh inspector ch12_weather_server.py --cli --method tools/list`.

In the Inspector you can list the tools, call `geocode` with "Pune", read the `weather://favorites` resource and fill in the `packing_advice` prompt. Test every server this way before connecting it to a model. If something fails here, the problem is your server, not the model.

## 12.6 Connecting to Claude Desktop {api}

Claude Desktop reads a configuration file that lists the servers to start. Because your server lives in the kit's container, Claude Desktop starts it through Docker. Generate the exact configuration for your computer with:

```
./course.sh desktop-config
```

It prints something like this, with your kit folder's real path filled in:

```
{
  "mcpServers": {
    "weather": {
      "command": "docker",
      "args": ["compose", "-f", "D:\\Learning\\building-agentic-ai\\compose.yaml",
               "run", "--rm", "-T", "course", "python", "ch12_weather_server.py"]
    }
  }
}
```

Open Claude Desktop's config from Settings → Developer → Edit Config and add the `weather` entry. The `-T` flag matters: it turns off Docker's terminal mode so the JSON-RPC messages pass through stdin and stdout untouched. Docker Desktop must be running.

Restart Claude Desktop and ask "What should I pack for Seattle this weekend?" Claude discovers your tools, asks your permission before calling them and uses the results. You've given a commercial AI app a capability you wrote, without changing a line of the app.

## 12.7 Transports: stdio and Streamable HTTP

A *transport* is how the messages travel between client and server.

|  | stdio | Streamable HTTP |
| --- | --- | --- |
| How it runs | The host starts the server as a subprocess | The server runs as a web service |
| Who can connect | Only that host, on that machine | Any client that can reach the URL |
| Setup | None | A port, and authentication in production |
| Good for | Local tools, personal use, development | Shared team servers, remote and hosted services |

The same server code supports both. Since the 2026-07-28 MCP specification, the protocol is **stateless**: every request carries the protocol version and the client's capabilities, so an HTTP server keeps no per-client session and any copy of it behind a load balancer can answer. HTTP requests also carry `Mcp-Method` and `Mcp-Name` headers, so gateways can route and rate-limit calls without reading the message body. The older HTTP+SSE transport is deprecated; use Streamable HTTP for anything new.

Run `./course.sh serve ch12_weather_server.py` and it serves MCP at `http://localhost:8000/mcp`, reachable from your computer.

Inside a container, a server must listen on all interfaces (`0.0.0.0`) to be reachable through a published port. The server reads that address from the `MCP_HOST` setting, which `serve` sets for you; the default stays `127.0.0.1` for safety. Listening on all interfaces turns off the SDK's automatic **DNS-rebinding protection**, which blocks a trick that lets a web page in your browser talk to servers on your machine. So the server switches it back on with `transport_security` and an explicit list of allowed host names. A client connects with `streamable_http_client` instead of `stdio_client` (exercise 12.7).

## 12.8 Other MCP features you'll meet {api}

This chapter used the three core primitives. The protocol has a few more, and real servers and clients use them. The 2026-07-28 revision of the MCP specification changed several of them, so the table notes what's current:

| Feature | Direction | What it's for |
| --- | --- | --- |
| **Structured tool output** | Server → client | A tool declares an `outputSchema` and returns typed data alongside the text. In the Python SDK, a tool whose return type is a Pydantic model or `TypedDict` gets this automatically. |
| **Tool annotations** | Server → client | Hints such as `readOnlyHint` or `destructiveHint` that a host can show in its UI. They're the server's claims: helpful, never a security control (Chapter 14). |
| **Elicitation** | Server → user | Mid-call, the server asks the user for input through the host ("How many nights?") instead of guessing. Since 2026-07-28 the tool returns an *input required* result and the client calls it again with the answers (**multi round-trip requests**). The SDK handles both the new and the old style for you (exercise 13.7). |
| **Tasks** (extension) | Client ↔ server | Long-running calls that return a task handle the client polls, instead of holding a request open. |
| **MCP Apps** (extension) | Server → user | A tool can come with an interactive user interface: its metadata points to a `ui://` resource (HTML and JavaScript) that the host shows in a sandboxed frame inside the chat, such as a chart, a form or a booking flow. Claude, ChatGPT, VS Code and Goose support it. |
| **Cacheable lists** | Server → client | Since 2026-07-28, tool, prompt and resource lists carry a freshness hint (`ttlMs`), so hosts can cache them instead of asking again on every turn. |
| **Sampling** | Server → model | The server asks the *host's* model to generate text. **Deprecated in 2026-07-28**; new servers should call a model API directly. You'll still meet it in older servers. |
| **Roots** | Client → server | The client tells the server which folders it may work in. **Deprecated in 2026-07-28**; pass folders as tool parameters or resource URIs instead. |
| **Logging** | Server → client | Log messages sent over the protocol. **Deprecated in 2026-07-28**; log to stderr or with OpenTelemetry (Chapter 28). |
| **Authorization** | Client ↔ server | OAuth 2.1 for remote servers: Chapter 30. |

Deprecated features keep working for at least twelve months, and the SDK still supports them, but don't build new servers on them.

**Where MCP is heading.** MCP's roadmap, published in August 2026, focuses on long-running agent work, one HTTP-based transport, standard agent identity, progressive discovery and better SDKs. Chapter 15 covers what this means in practice. None of it changes what you learn in this part: the host stays in control of what the model and the servers may do.

:::tip Which version does a server speak?
MCP specifications are named by date. A client and server agree on one version per request, and the Python SDK speaks both the 2026-07-28 revision and the older ones, so you rarely need to care. When a feature seems missing, check the specification version in the server's documentation first.
:::

## Architect's Takeaway

Standard protocols reduce integration friction but increase orchestration complexity.

## Common mistakes

- **Writing to stdout in a stdio server.** Python's SDK redirects it, but in most other languages it corrupts the protocol stream.
- **Missing type hints or docstrings**, so the model gets a vague schema and description.
- **Relative paths in the Claude Desktop config.** The host starts servers from its own working directory, so use absolute paths (`desktop-config` does this for you).
- **Forgetting `-T`** when a host starts a server through `docker compose run`, which garbles the stdio stream.
- **Skipping the Inspector** and debugging through the model.
- **Exposing an HTTP server without authentication** beyond your machine.

## Summary

- MCP packages tools once so any compatible host can use them.
- Hosts run models; each host has one client per server; servers offer tools, resources and prompts.
- The Python SDK builds tool schemas from type hints and docstrings.
- Log to stderr in stdio servers, and test with Inspector before involving a model.
- Use stdio for local servers and Streamable HTTP for shared or remote ones.

So far, someone else's host has run the model and called your server. In Chapter 13 you'll build that side yourself: an MCP client inside your own agent loop, connected to several servers at once.
