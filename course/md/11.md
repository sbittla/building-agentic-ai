# Chapter 11: Multi-Agent Systems

Some jobs are too broad, too varied or too important for one agent. In this chapter you'll build a research team: a lead agent splits a question into parts, several subagents investigate them in parallel, each with its own clean context, and the lead combines their findings into one cited answer. Then you'll build the other patterns production teams use (a router, a handoff pipeline, a writer-and-critic pair and a vote) and learn how to keep a group of agents safe, affordable and debuggable.

**What you'll build:** a research team of a lead and parallel subagents, and the four other patterns for combining agents.

**You are here:** Agent runtime (teams of agents) in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 3 (forced tool calls), Chapter 4 (agent loop), Chapter 6 (citations), the asynchronous Python interlude.

## Learning objectives

By the end of this chapter you can:

- Build an orchestrator–worker system with a lead agent and parallel subagents.
- Give each subagent its own clean context.
- Get a structured plan from the lead (a forced tool call here; structured outputs on models that reject forced tools).
- Measure when multiple agents are worth their extra cost.
- Choose between five multi-agent patterns: orchestrator–worker, router, handoff, evaluator–optimizer and voting.
- Pass structured messages between agents, and contain failures so one agent can't bring down the rest.

**In the real world.** Anthropic's Research feature uses a lead agent that plans the research and spawns subagents to explore different parts of the question in parallel. On Anthropic's internal research evaluation, this multi-agent system outperformed a single agent by 90.2%. It also used about 15 times as many tokens as a normal chat. That is one measurement, by one team, on one kind of task: broad research questions. Multi-agent systems can pay off for broad, parallel tasks like research; they're usually a poor fit for tightly connected tasks like most coding. Measure on your own cases before you assume a team will help.

## 11.1 Why more than one agent?

A single agent working on a broad question has two problems:

- **Context crowding.** Every search result from every angle piles into one history, and the model loses focus.
- **Serial work.** It explores one angle at a time.

The **orchestrator–worker** pattern can fix both, at a price. A lead agent (the orchestrator) splits the question, each worker (subagent) investigates one part with its own clean context, and the lead combines the results.

Table: One agent compared with orchestrator–worker
|  | Single agent | Orchestrator–worker |
| --- | --- | --- |
| Context | One history for everything | One clean history per subtask |
| Speed | Serial | Parallel |
| Token cost | Lower | Much higher (≈15× chat, in Anthropic's measurement) |
| Best for | Connected, step-by-step tasks | Broad questions with independent parts |
| Failure mode | Loses focus on big tasks | Duplicated work, inconsistent findings |

**A team of agents is not inherently better than one agent.** It's justified when a measured improvement on your own cases, read with confidence intervals (the measurement interlude), exceeds the added cost, latency and failure surface. Section 11.5 starts that comparison; sections 21.10 and 29.8 finish it with numbers.

## 11.3 How it works

The system has three stages:

@@image d-90bf94203d43.png

Figure: The research team: plan, investigate in parallel, synthesize
Alt: A question goes to the lead's make_plan, which fans out to three subagents, each with its own context. Their findings, with sources, return to the lead, which synthesizes the answer.

1. **Plan.** `tool_choice` forces the lead to call `make_plan`, whose schema is a list of 2–4 sub-questions. This is the structured-output trick from Chapter 3: you get a clean Python list with no text parsing.
2. **Delegate.** `asyncio.gather` starts one `run_subagent` per sub-question at the same time. Each is the Chapter 4 loop, made async, with its own `messages` list. Blocking tools run in threads (`asyncio.to_thread`) so subagents don't wait for each other.
3. **Synthesize.** The lead gets all the findings in one prompt and writes the answer, keeping citations and pointing out disagreements.

:::tip Subagents return summaries, not transcripts
Each subagent returns 3–6 bullet findings, not its whole conversation. The lead's context stays small no matter how much searching the workers did. This compression is the main reason the pattern scales.
:::

## 11.4 Writing good subtasks

Subagents know only what the lead tells them, so vague subtasks cause duplicated or missing work. A good subtask states:

- **The objective**: what exactly to find out.
- **The boundaries**: what's out of scope, to avoid overlap with siblings.
- **The output format**: bullets with sources.
- **The effort level**: a quick check or a deep dive.

One of the most effective changes you can make is to improve the `make_plan` description so it asks for these (exercise 11.4).

## 11.5 Cost and when not to use it

`usage` totals tokens across all calls. Compare it with a single Chapter 6 agent answering the same question (exercise 11.6), on several questions and several trials, not one run. Use multiple agents only when the measurements show the team pays for itself:

- The task splits into **independent** parts. Research topics often do; changes to one codebase often don't.
- The better answers you measured are worth several times the cost.
- Speed matters and parallelism helps.

Table: Five multi-agent patterns
| Pattern | How it works | Use it when | Watch out for |
| --- | --- | --- | --- |
| **Orchestrator–worker** (11.2) | A lead splits the task; workers run in parallel; the lead combines | Broad tasks with independent parts | Cost, duplicated work |
| **Router** | One cheap classification picks the one specialist that handles the request | Requests fall into clear categories with different tools | A "none of these" route, or the router forces a bad fit |
| **Handoff** (pipeline) | Each agent does one stage and hands a structured result to the next | Stages need different tools or permissions | Facts lost between stages: pass data, not prose |
| **Evaluator–optimizer** | A writer drafts, a critic checks against the task, the writer revises | Quality criteria you can state clearly | Endless loops: cap the rounds |
| **Voting** | Several independent runs answer; the majority wins | A judgment call where one run is unreliable | Cost times n; only works with a fixed set of answers |

A note on words: this book uses *routing* for four different choices. Chapter 3's model routes a request to a **tool**; this chapter's router sends it to an **agent**; Chapter 16 routes a task to the **sources** its context needs; Chapter 20 routes a step to a **model**. The idea is the same each time, a cheap decision before an expensive one, but what's being chosen differs.

Notice two design choices in the code. Every message between agents is **structured output** with a schema, so the next agent receives fields, not a paragraph to interpret. And in `handoff`, the writer has **no tools and no database access**: it can use only the facts it was handed, which is the simplest defense against a writer that invents numbers. You'll also meet agents *published as MCP servers* in Chapter 13 (section 13.6), which is how these patterns work across teams.

## 11.7 Keeping a team of agents safe and debuggable

More agents means more places for things to go wrong, and failures multiply rather than add. Four rules keep a multi-agent system under control:

- **Contracts between agents.** Define what each agent receives and returns with a schema, and validate it. An agent that gets malformed input should return an error, not guess.
- **Contain failures.** Every agent gets its own iteration cap, budget and timeout, and a failed subagent returns an error the lead can see. One stuck worker must not stall or bankrupt the whole team (the OWASP "cascading failures" risk, section 25.9; Chapter 21 builds these controls).
- **Least privilege per agent.** Give each agent only the tools its job needs. In the handoff above, the writer can't query anything; in the research team, workers can read the library but not write to it.
- **Trace the whole team.** Give every request one trace id that every agent's log lines share (Chapter 28). Without it, you can't tell which agent caused a bad answer.

These rules are enough for the small teams in this chapter. Chapter 21 returns to multi-agent systems at production scale: choosing a topology, checking every result against its contract, a shared task board with hard limits on depth and spend, and the common ways teams of agents fail.

**Across organizations.** When the agents belong to different companies, they can't share code or a process. **A2A (Agent2Agent)**, an open protocol with a stable 1.0 specification since early 2026, covers that case: each agent publishes an *agent card* (a JSON description of what it can do and how to reach it, which can be signed to prove its identity), and agents exchange *tasks* with status and results. MCP connects an agent to tools; A2A connects agents to each other. The four rules above apply unchanged, plus one more: authenticate every agent you talk to. Chapter 21 publishes an agent with A2A and calls it from a coordinator.

## Common mistakes

- **Splitting tightly connected tasks**, so subagents make conflicting decisions.
- **Vague subtasks** that overlap or leave gaps.
- **Passing whole transcripts back to the lead** instead of short findings.
- **Losing citations** during synthesis.
- **No cost tracking.** Multi-agent runs are the most expensive thing in this book.
- **Passing prose between agents.** Use structured outputs so each agent gets fields it can check.
- **Unbounded critic loops.** An evaluator–optimizer pair needs a round limit.

## Key takeaways

**Architect's takeaway:** Multi-agent systems add latency and failure modes: design handoff explicitly.

- Orchestrator–worker: a lead plans, subagents work in parallel with clean contexts and the lead synthesizes.
- Use a forced tool call to get a structured plan.
- Run subagents concurrently with `asyncio`, and run blocking tools in threads.
- Subagents should return short, cited findings.
- Multi-agent systems are more powerful for broad tasks and much more expensive; measure before choosing.
- Beyond orchestrator–worker: routers, handoffs, evaluator–optimizer loops and voting each fit a different job.
- Contracts, contained failures, least privilege and one trace id keep a team of agents under control; A2A connects agents across organizations.
