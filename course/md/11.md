# Chapter 11: Multi-Agent Systems

I spent years tuning parallel systems before I touched an agent, and the first lesson carries straight over: splitting work speeds things up only when the pieces don't need each other. Hand one agent five vendors' pricing pages to compare, and by the third vendor its context is stuffed with the first two, so it starts mixing up whose discount was whose. Give each vendor its own subagent with a clean context and the mix-ups go away. Now, though, you're paying for six agents instead of one, and the hard part of this chapter is knowing when that trade is worth it.

Everything here runs inside one program; Chapter 21 takes teams of agents to production.

**What you'll build:** a research team of a lead and parallel subagents, and the four other patterns for combining agents.

**You are here:** Agent runtime (teams of agents) in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 3 (forced tool calls), Chapter 4 (agent loop), Chapter 6 (citations), the asynchronous Python interlude.

## Learning objectives

By the end of this chapter you can:

- Choose between five patterns: orchestrator–worker, router, handoff, evaluator–optimizer and voting.
- Pass structured messages between agents, and contain failures so one agent can't bring down the rest.

**In the real world.** Anthropic's Research feature has a lead agent spawn subagents that explore parts of a question in parallel. On Anthropic's internal evaluation it beat a single agent by 90.2%, using about 15 times the tokens of a normal chat. That's one measurement, on broad research questions; tightly connected work like most coding usually gains little.

## 11.1 Why more than one agent?

A single agent on a broad question has two problems. Every search result from every angle piles into one history, so the model loses focus. And it explores one angle at a time.

The **orchestrator–worker** pattern fixes both, at a price. A lead agent (the orchestrator) splits the question, each worker (subagent) investigates one part with its own clean context, and the lead combines the results.

Table: One agent compared with orchestrator–worker
|  | Single agent | Orchestrator–worker |
| --- | --- | --- |
| Token cost | Lower | Much higher (≈15× chat, in Anthropic's measurement) |
| Best for | Connected, step-by-step tasks | Broad questions with independent parts |
| Failure mode | Loses focus on big tasks | Duplicated work, inconsistent findings |

**A team isn't automatically better than one agent.** It earns its place when the improvement you measure on your own cases, read with confidence intervals (the measurement interlude), outweighs the extra cost, latency and ways to fail. Section 11.5 starts that comparison; section 21.10 finishes it with numbers.

2. **Delegate.** `asyncio.gather` starts one `run_subagent` per sub-question at once. Each is the Chapter 4 loop, made async, with its own `messages` list; blocking tools run in threads (`asyncio.to_thread`).
3. **Synthesize.** The lead gets all the findings in one prompt and writes the answer, keeping citations and pointing out disagreements.

:::

## 11.4 Writing good subtasks

Subagents know only what the lead tells them, so vague subtasks cause duplicated or missing work. A good subtask says what to find out, what's out of scope (so siblings don't overlap), what to return (bullets with sources) and how much effort to spend: a quick check or a deep dive. Asking for those four things in the `make_plan` description is one of the most effective changes you can make (exercise 11.4).

## 11.5 Cost and when not to use it

`usage` totals tokens across all calls. Compare it with a single Chapter 6 agent on the same questions, over several trials (exercise 11.6). Reach for a team only when the measurements say it pays: the task splits into **independent** parts (research topics often do; changes to one codebase often don't), the better answers are worth several times the cost, and parallel work saves time you care about.

Table: Five multi-agent patterns
| Pattern | How it works | Use it when | Watch out for |
| --- | --- | --- | --- |
| **Orchestrator–worker** (11.2) | A lead splits the task; workers run in parallel; the lead combines | Broad tasks with independent parts | Cost, duplicated work |
| **Router** | One cheap classification picks the specialist for the request | Requests fall into clear categories with different tools | Forcing a bad fit: add a "none of these" route |
| **Handoff** (pipeline) | Each agent does one stage and hands a structured result to the next | Stages need different tools or permissions | Facts lost between stages: pass data, not prose |
| **Evaluator–optimizer** | A writer drafts, a critic checks against the task, the writer revises | Quality criteria you can state clearly | Endless loops: cap the rounds |
| **Voting** | Several independent runs answer; the majority wins | A judgment call where one run is unreliable | Cost times n; only works with a fixed set of answers |

A note on words: *routing* means four things in this book. Chapter 3's model routes a request to a **tool**, this chapter's router picks an **agent**, Chapter 16 picks **sources** and Chapter 20 picks a **model**. Each is a cheap decision before an expensive one.

Look at how the agents talk to each other in the code. Every message between agents is **structured output** with a schema, so the next agent receives fields to check. And in `handoff`, the writer has **no tools and no database access**: it can use only the facts it was handed, the simplest defense against a writer that invents numbers. Section 13.6 publishes agents as MCP servers so these patterns can work across teams.

## 11.7 Keeping a team of agents safe and debuggable

Every agent you add is another place for things to go wrong, and in a team a failure rarely stays where it started. These controls keep it contained:

- **Contracts between agents.** Validate what each agent receives and returns against a schema. Malformed input gets an error back.
- **Contain failures.** Every agent gets its own iteration cap, budget and timeout, and a failed subagent returns an error the lead can see. One stuck worker must not stall or bankrupt the team, the risk security checklists call *cascading failures* (section 25.9).
- **Least privilege per agent.** The handoff writer can't query anything; the research workers can read the library but not write to it.
- **Trace the whole team.** Every agent's log lines share one trace id per request (Chapter 28), or you can't tell which agent caused a bad answer.

Chapter 21 covers what production adds: choosing a topology, checking every result against its contract, a shared task board with hard limits on depth and spend, and the common ways teams fail. When the agents belong to different companies and can't share code or a process, the Agent2Agent (A2A) protocol connects them (section 21.7). The same controls apply, plus one more: authenticate every agent you talk to.

## Common mistakes

- Splitting tightly connected tasks, so subagents make conflicting decisions.
- Vague subtasks that overlap or leave gaps.
- Passing whole transcripts back to the lead instead of short findings.
- No cost tracking on the most expensive runs in this book.
- Passing prose between agents instead of structured fields each agent can check.
- Unbounded critic loops. An evaluator–optimizer pair needs a round limit.

## Key takeaways

**Architect's takeaway:** A team multiplies cost, latency and ways to fail. Adopt one only when measurements on your own cases show it pays.

- Orchestrator–worker: a lead plans with a forced tool call, subagents work in parallel (`asyncio.gather`) with clean contexts, and the lead synthesizes.
- Subagents return short, cited findings.
- Teams help on broad tasks and cost far more; measure before choosing.
- Routers, handoffs, evaluator–optimizer loops and voting each fit a different job.
- Contracts, contained failures, least privilege and one trace id keep a team under control.
