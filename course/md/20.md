# Chapter 20: Planning and Model Routing

The agent loop from Chapter 4 decides one step at a time: look at the history, pick the next tool, repeat. That works well for short tasks, and it's how most agents in this book have run. For longer goals it has two weaknesses. It can wander, because nothing written down says what "finished" means. And it spends the same expensive model on every step, including the ones a much cheaper model would get right. This chapter adds a plan the agent writes before it acts, which your code checks before anything runs, and a router that sends each step to the cheapest model that can do it well.

**What you'll build:** a planner that writes plans as data, a checker that rejects bad plans before they run, an executor that runs each step with its own brief and tools and replans when a step fails, and three model routers you can compare by cost per successful task.

**You are here:** Planning and Model in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Choose between deciding step by step and planning first.
- Get a plan from the model as structured data, with dependencies and a done condition for every step.
- Check a plan in code before running it: known tools, valid dependencies, no cycles, a size limit.
- Execute a plan with a small brief per step, and replan when a step fails.
- Route work between models with rules, a classifier model or a cascade.
- Compare routing strategies by cost per successful task.

## Real-world connection

Planning shows up everywhere agents do real work. Coding agents write a to-do list before touching files, and deep-research systems have a lead agent write a research plan before handing out subtasks (Chapter 11). Model choice has become as deliberate. Providers sell families of models at very different prices: in 2026, Claude Haiku 4.5 costs half as much per token as Claude Sonnet 5 (Appendix E), and open models on your own hardware cost nothing per call. Teams that send every request to their biggest model overspend; teams that send everything to their smallest lose quality. Research on *routing* and *cascades* (see Learn more) shows that choosing per request can keep most of the quality of the larger model at a fraction of its cost, if you measure the result.

## 20.1 Step by step, or plan first?

There are two broad ways for an agent to work:

|  | Decide step by step | Plan first, then execute |
| --- | --- | --- |
| How | After each tool result, decide the next action (the Chapter 4 loop; the research pattern known as ReAct) | Write the list of steps up front, then run them |
| Good at | Short tasks, surprises, exploring | Longer goals, work that can run in parallel, work you want to review or resume |
| Weak at | Staying on track over many steps; knowing when it's done | Adapting when a step reveals something unexpected |
| Cost | Every step sees the whole growing history | Each step sees only its own brief |

In practice you combine them: **plan first, execute each step with a small loop and replan when reality disagrees with the plan.** That's what this chapter builds. The plan also gives you something the step-by-step loop never does: a readable statement of what the agent intends to do, which a person or a check can review before anything happens.

Follow the two loops back to the planner: a plan that fails the check is rewritten before anything runs, and a step that fails sends only the remaining work back to be planned again.

## 20.3 Check the plan before running it

Before a single tool runs, code checks everything about the plan that code can check:

@@code ch20_planning.py::check_plan,order

- **Size.** A 40-step plan for a simple question is a sign of confusion, and a cost you'd rather not pay. The limit sends it back.
- **Known tools only.** A step that names a tool the agent doesn't have would fail later, after money was spent on earlier steps.
- **Valid dependencies.** Every `needs` must point to a real step, and the steps mustn't depend on each other in a circle. Python's `graphlib` finds an order that respects the dependencies, or raises `CycleError`.
- **A done condition for every step.**

A rejected plan goes back to the model with the reasons, and the model tries again. This is the chapter's small example of an idea Chapter 22 builds on: **the model proposes, code checks.** A check like this costs microseconds and catches mistakes before they cost anything.

## 20.5 Replanning

Plans meet reality. A query fails, a table doesn't have the column the plan assumed, a step returns something that changes what's worth doing next. `execute` handles the first case: when a step fails, it asks for a **new plan for the remaining work**, telling the model which steps already succeeded and what their results were. The finished steps are kept; only the rest is planned again, with a limit on how many times.

Replanning on failure is the minimum. Two other triggers are worth adding when your tasks need them:

- **New information.** A step's result shows the plan was based on a wrong assumption ("there's no `region` column; cities are in `customers`"). A check after each step, or a question to the model ("does the plan still make sense?"), can trigger a replan.
- **A person's feedback.** Show the plan before running it. For expensive or risky work, an approval of the plan (Chapter 9) is cheaper than an approval of every step.

Watch for the opposite failure: an agent that replans after every step never makes progress. Keep a limit, and keep finished work.

## 20.6 Plans and long-running jobs

A checked plan is exactly what Chapter 19's job runner needs: a list of steps in order. Turn each plan step into an `agent` action with its brief, and the plan gains checkpoints, retries, leases and escalation for free. Exercise 20.6 does this. The combination is how long agent work is usually built: **the model plans, the durable runner executes**, and a failed step leads to a replan rather than a restart.

## 20.7 Model routing

Different steps need different amounts of intelligence. Reading a schema or counting rows is easy; explaining why revenue fell is not. Paying the largest model's price for every step wastes money, and on the local model, time. **Routing** chooses a model per task, or per step:

| Option | Cost | Good for |
| --- | --- | --- |
| A small model (Claude Haiku 4.5) | $1 in, $5 out per million tokens | Lookups, classification, formatting, simple tool calls |
| A larger model (Claude Sonnet 5) | $2 in, $10 out | Multi-step reasoning, synthesis, judgment |
| A larger model with more `effort` | More output tokens | The hardest steps: tricky analysis, careful plans |
| The local model (Appendix H) | Free, slower | Learning, private data, high volume where quality allows |

There's a second dial inside one model: **effort** (Chapter 4). A router can choose `effort: "low"` for a routine step and `"high"` for planning, without changing models at all.

Routing needs `run_agent` to accept a model, so Chapter 4's loop takes a `model` argument, and its stats record which model ran.

## 20.8 Three routers

@@code ch20_router.py::cost,by_rules,by_model,cascade

- **Rules** cost nothing and are predictable: long tasks, many tools or words like "why" and "compare" go to the large model. They're also blunt, and they miss hard tasks phrased simply.
- **A classifier model** asks the small model to rate the task. It costs one small call and catches what rules miss, but it can be wrong in both directions.
- **A cascade** tries the small model first and accepts its answer only if a **check in code** passes; otherwise it escalates to the large model. Easy tasks cost small-model prices; hard ones cost both. Everything depends on the check: with a weak check, the cascade accepts wrong cheap answers.

Routers can also go the other way: **fallback** routing sends a request to a second model or provider when the first is overloaded or down. That's a reliability feature rather than a cost one, and it needs the same care: make sure the fallback model is evaluated on your tasks too.

## Architect's Takeaway

Planning delays execution: only justify its cost if revisions save more tokens.

## Common mistakes

- **Planning everything**, including one-step questions where the loop alone is faster and cheaper.
- **Plans as prose**, which can't be checked or executed reliably.
- **Running a plan without checking it**, so an unknown tool or a cycle is found only after spending money.
- **Giving every step the whole history** instead of a brief with the results it needs.
- **Replanning from scratch**, throwing away finished steps, or replanning without a limit.
- **Routing by price alone**, without measuring success.
- **A cascade with a weak check**, which accepts wrong answers from the cheap model.

## Summary

- Decide step by step for short tasks; plan first for long ones, and replan when reality disagrees.
- Get plans as structured data: steps, tools, dependencies and a done condition.
- Check plans in code before running them: size, known tools, valid dependencies, no cycles.
- Execute each step with its own brief, tools and done condition; keep finished results when replanning.
- A checked plan can become a durable job (Chapter 19).
- Route between models and effort levels with rules, a classifier or a cascade.
- Compare routers by cost per successful task, measured on real checks.

A plan coordinates the steps of one agent. Chapter 21 coordinates many agents: who delegates to whom, what they're allowed to pass each other, and how agents built by different teams work together.

## Exercises

:::ex Concept | 20.1 | Plan or not?
For each task, choose "step by step", "plan first" or "plan first with approval", and say why: (a) "What's the weather in Oslo?"; (b) "Migrate our 40 cron jobs to the new scheduler"; (c) "Find out why checkout latency doubled yesterday"; (d) "Write a market overview of vector databases"; (e) "Refund these 300 orders".
**Done when:** Each choice is tied to the length of the task, how predictable it is, and what a mistake would cost.
:::

:::ex Concept | 20.2 | Route the steps
A plan has five steps: read the schema; write and run three SQL queries; check the results against a definitions file; write a 300-word explanation of the trends; format the final table. For each step, choose a model and an effort level, and estimate the cost of the whole plan with your routing and with the large model for everything. Use the prices in section 20.7 and assume 3,000 input and 500 output tokens per step.
**Done when:** You have both totals and a sentence on which step you'd least like to get wrong, and why it gets the most capable model.
:::

:::ex Simple | 20.3 | Break the plan
Write five plans by hand (as Python dictionaries) that `check_plan` should reject: too many steps, an unknown tool, a missing dependency, a cycle, and an empty `done_when`. Then write one it should accept.
**Done when:** A test shows each bad plan rejected with the right reason and the good one accepted, without calling a model.
:::

:::ex Medium | 20.4 | Run independent steps in parallel
Change the executor so steps whose `needs` are all finished run at the same time. Use `TopologicalSorter`'s `get_ready()` and `done()` methods, and threads or `asyncio.to_thread` for the steps.
**Hint:** The async interlude shows how to run blocking functions concurrently.
**Done when:** A plan with two independent steps and a final step that needs both runs the first two together, and you've measured the wall time both ways.
:::

:::ex Medium | 20.5 | Evaluate the routers
Write 12 tasks for the SQL tools and label each "easy" or "hard" yourself. Run `by_rules` and `by_model` on them and report each router's accuracy against your labels, and how many hard tasks each sent to the small model.
**Done when:** You have a table of both routers' decisions, their accuracy, and one change to `HARD_WORDS` or the length limit that improves the rules.
:::

:::ex Complex | 20.6 | A plan that survives a crash
Make a plan with `make_plan`, check it, and turn it into a Chapter 19 durable job: one `agent` step per plan step, in dependency order, with each brief built from the results of the steps it needs. Route each step with `by_rules`. Crash the job halfway and resume it.
**Hint:** A durable step's arguments can refer to earlier results with `"$n"`, so a brief can include them when it runs.
**Done when:** The resumed job finishes without repeating any finished step or model call, and the report shows which model ran each step.
:::
