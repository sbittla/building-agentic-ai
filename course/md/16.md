# Chapter 16: Context Engineering

A support agent tells a customer their parcel is still at the warehouse. It left two hours ago: the agent fetched the order status at the start of the chat and never looked again. The model answered correctly from what it was shown; what it was shown was stale. For agents, the question has moved from "How do I write a better prompt?" to "What should the model see on this step, from where, and how old may it be?" Answering that question in code, on every call, is called **context engineering**.

**What you'll build:** a context assembler that routes each task to the sources it needs, fits them into a budget, refreshes stale items and labels every fact with where it came from.

**You are here:** Context in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapter 5 (state), Chapter 6 (keeping large results out of the context), the measurement interlude.

## Learning objectives

By the end of this chapter you can:

- Measure how many tokens a conversation uses and where they go.
- Keep long runs within budget by trimming, compacting and caching.
- Isolate subagents' context, and design system prompts and tool sets deliberately.
- Decide when to let the API, or a program the model writes, manage context for you.

**In the real world.** In Redis's *State of Context Engineering 2026* survey of IT and AI infrastructure leaders, 73% agreed that agents fail more often because of broken context than because of broken models, and 97% said context matters, yet only 4% had built systems that deliver it reliably.

## 16.1 From prompt engineering to context engineering

A prompt is something you write once. Context is something your code **assembles on every step**, from many sources, under a budget:

Table: Where an agent's context comes from
| Source | Example | Changes |
| --- | --- | --- |
| Instructions | System prompt, rules, output format | Rarely |
| Tool definitions | Names, descriptions and schemas | Rarely |
| User and task state | Who's asking, what they're trying to do, what's been decided | Per task |
| Working memory | This conversation, plans, notes | Every step |
| Long-term memory | Preferences, earlier requests (Chapter 17) | Across sessions |
| Retrieved knowledge | Documents, records, search results (Chapter 18) | Per question |
| Tool results | What the last tool call returned | Every step |

More isn't better. Models have a limited **attention budget**: as the context grows, their ability to use any one fact in it drops, an effect called *context rot*. So don't fill the window. Find the smallest set of high-signal information that lets the model take the next step well. Building that set means deciding:

1. **What** goes in: routing a task to the sources it needs (section 16.3).
2. **How much**: budgets and priorities (sections 16.3, 16.5 and 16.6).
3. **How fresh and how trustworthy**: freshness and provenance (section 16.4).
4. **For whom**: a subagent gets its own small context (section 16.9).

Behind all of these sits one habit: prefer **references to content**. An agent holding a file path, an order id or a URL can fetch the details *just in time* instead of carrying them through every call, as Chapter 6's notes tools do by returning paths and line numbers first.

## 16.4 Freshness and provenance

Context goes stale, as the parcel showed. Give every item a **time to live** that suits its source (minutes for live order data, days for a profile, none for a policy document), and decide what happens when it expires: refresh it, or drop it.

In the demo, the order status is 15 minutes old with a 5-minute time to live, so `assemble` calls `refresh` and the agent sees "out for delivery today" instead of this morning's status.

Just as important is **provenance**, saying where each item came from:

@@code ch16_assemble.py::render

Every item arrives in a `<context>` tag with its source, origin (a file and line, a record id, a URL) and age. The model can cite where a fact came from, and you can check it (section 6.5). When two items disagree, the model and your code can prefer the newer or more authoritative one. And when an answer is wrong, the trace shows which item the model relied on and how old it was (Chapter 28).

Provenance is also a security boundary. Retrieved documents, tool results and memories are *data*, and the tags make that visible; Chapter 14 showed what happens when data is mistaken for instructions.

## 16.5 Trimming old tool results

Once the model has read a tool result and acted on it, it rarely needs the full text again:

@@code ch16_context.py::trim_old_tool_results

`trim_old_tool_results` keeps the newest results intact and cuts older ones to their first 300 characters, noting that the model can call the tool again. It returns a **new** list and never touches `tool_use_id`s, so the conversation stays valid.

:::tip Trim the tool result, never the tool call
Every `tool_use` block needs its matching `tool_result`. You can shorten a result's *content*, but remove either half of the pair and the API rejects the request (Chapter 4).
:::

## 16.6 Compacting with a summary

When trimming isn't enough, **compaction** replaces the older part of the conversation with a summary written by the model. `compact` cuts only at the start of a user turn (`_safe_cut`), so no tool call is separated from its result. It asks for a summary that keeps goals, decisions, facts with numbers and ids, and open questions. And it replaces the old turns with two messages, the summary as a user message and a short assistant acknowledgment, so the roles still alternate.

`run_managed_agent` applies both steps before each model call, with `budget_tokens` as the limit. But client-side compaction can only cut **between** user turns. Inside one long turn (a single question that triggers 20 tool calls) trimming does the work; section 16.8 shows how the API can clear old tool results mid-turn.

### Notes outside the context

Compaction throws detail away, and a task that runs for hours across hundreds of steps can't keep everything even as a summary. So let the agent write **structured notes** outside the context: a progress file with what's done, what's next and the decisions so far, which it reads back when needed. Anthropic calls this *structured note-taking*; it keeps long-running agents coherent across many context resets. You'll build it, with checkpoints, in Chapter 19.

## 16.7 Prompt caching {api}

Prompt caching lets the API reuse the processed form of an unchanged prompt prefix (the opening part of the request, up to a marked point). The first call writes the cache at a small premium; later calls within the cache lifetime (5 minutes, or 1 hour with `"ttl": "1h"`) read it for much less. `cache_kwargs` supports two ways to say what to cache:

@@code ch16_context.py::cache_kwargs

Table: Prompt-caching modes in `ch16_context.py`
| Mode | How | What gets cached |
| --- | --- | --- |
| `prefix` | `with_cache` puts `cache_control` on the last tool and the system prompt | Only tools + system prompt |
| `auto` | A **top-level** `cache_control` on the request | Everything up to the end of the request, so the **growing conversation** is cached too |

The history is what grows every step, so `run_managed_agent` uses `auto` by default: on step 6, steps 1–5 come from the cache instead of being paid for again in full.

Table: Claude Sonnet 5 prices with prompt caching
| Claude Sonnet 5 (2026) | Price per million tokens |
| --- | --- |
| Input | $2.00 |
| Cache write (5-minute) | $2.50 |
| Cache read | $0.20 |
| Output | $10.00 |

Take a 6,000-token system prompt plus tools over a 10-step run. Caching turns 60,000 input tokens at $2.00 into one write of 6,000 at $2.50 and nine reads of 6,000 at $0.20. The prefix drops from about $0.12 to $0.026, nearly 80% less. The response's `usage` shows `cache_creation_input_tokens` and `cache_read_input_tokens`, and `run_managed_agent` adds both to its stats.

:::warn Caching has a minimum size, and needs an identical prefix
The API only caches a prefix of at least **1,024 to 4,096 tokens**, depending on the model (check the documentation for yours). Below that, nothing is cached and nothing warns you: `cache_read_input_tokens` stays `0`. This chapter's notes tools plus system prompt fall well short, which is why `auto` mode matters: the conversation soon makes the request long enough.
Any change inside the cached part causes a miss: a timestamp in the system prompt, reordered tools, or **trimming and compaction**, which rewrite old messages. Every trim saves tokens but forces a new cache write, so `run_managed_agent` trims only when the context goes over budget.
:::

The design rule follows: **order the context from stable to volatile.** Instructions and tool definitions first, then slowly changing context (the customer profile, the policy), then the conversation, then this step's fresh results. Everything above the first change is cheap; everything below it is paid for in full.

## 16.8 Letting the API manage context {api}

Everything so far runs in your code, which is the best way to learn it. The API can now do most of it for you:

- **Context editing** (`create_with_server_editing` in the listing): the `clear_tool_uses_20250919` edit clears the oldest tool results once the request passes a token threshold, keeping the most recent few. It's `trim_old_tool_results` on the server.
- **Server-side compaction.** With the `compact_20260112` edit and a token threshold, the API summarizes older turns itself and returns a `compaction` block; you keep appending `response.content` as usual. A newer on-demand variant summarizes when you ask, such as between tasks.
- **Cache diagnostics.** When an expected cache hit doesn't happen, the API tells you why.
- **Changing instructions or tools mid-conversation.** A later `system` message in `messages`, or tools added and removed between turns, used to invalidate the whole cache. Current models keep the part of the prefix before the change; reordering or editing what's already cached still causes a miss, as the warning above says.
- **The memory tool**: the model reads and writes files in a memory directory that *your* code stores, like Chapter 17's memory store behind a standard interface.

Several of these are still in beta, so check the current documentation for names and limits.

## 16.9 Isolating context between agents

When a lead agent hands work to subagents (Chapter 11), the worst thing it can do is pass along its whole context. Each subagent then pays for tokens it doesn't need, gets distracted by other subtasks and sees tool results never meant for it. Give each one a **brief** instead:

@@code ch16_assemble.py::isolated_brief

The brief holds the subtask and only the items tagged for it, and asks for a short answer with origins. Isolation needs a rule for each direction information flows:

- **Down: only what the job needs.** The subagent gets its task and its evidence, not the lead's history or other workers' results.
- **Up: condensed results.** Subagents return a few hundred words with citations.
- **Across: no shared raw tool output.** One worker's untrusted web page must not land unfiltered in another's context. Shared information passes through the lead, or through a shared memory with rules about who may write it (Chapter 17).

Isolation saves money and improves answers. It's also a security control: an injection that reaches one subagent stays in that subagent's small context.

## 16.10 System prompts and tool sets as design

Section 4.10 gave you five questions for a system prompt. Context engineering adds one rule to them: the system prompt is the most stable part of every request, so it sits at the top of the cache (section 16.7) and should change least. Put what varies, such as the customer's name, today's date or the current policy version, lower down, in messages or tool results, and keep the prompt itself to the role, how to use the tools, the rules, the output format and what to do when stuck.

A good tool set has few, distinct tools with names that say what they do and descriptions that say *when* to use them (Chapter 3). It returns small, structured outputs with reusable ids (Chapters 5 and 6) and errors that say how to fix the call, and it keeps dangerous actions behind gates enforced in code (Chapters 9 and 14).

Treat prompts as code: keep them in version control, change one thing at a time and run your evaluation suite after every change (the measurement interlude; Chapter 27 builds the full version).

## 16.11 Keeping big results out of context: programmatic tool calling {api}

"Revenue share of each of eight categories" means eight queries, and the model needs just the eight totals, yet in a normal loop every row of every result ends up in the context. With **programmatic tool calling**, the model writes a short Python program instead. It runs in Anthropic's code-execution sandbox, calls your tool as many times as it needs, adds things up and prints only the answer.

*Needs Claude:* programmatic tool calling runs on Anthropic's servers, so on the local model this section's exercise stops with a clear message (Appendix H).

@@code ch16_programmatic.py::ask

Compared with Chapter 4's loop, you send two tool definitions: the code-execution tool, and your tool with `allowed_callers` set to the code-execution tool, so only the program can call it. Your code still runs the tool: each call arrives as an ordinary `tool_use` block (with a `caller` field naming the program) and gets a normal `tool_result`, so your validation, read-only database and logging still apply. And you pass back the previous response's `container` id, because the program waits in that container while your code works.

Use it when a task fans out over many items or produces large results worth filtering before the model reads them. Skip it when each call depends on the model thinking about the previous result, or when there are only one or two small calls.

:::note The support agent so far
The support agent's context is assembled on every step: the customer's profile and open orders (fresh for five minutes), the policy passages the question needs and the last few turns, within a budget and labeled by source. A shipping question no longer drags in the whole refund policy, and the parcel status is never two hours old.
:::

## Common mistakes

- Treating context as a dump, with no budget and no report, until the model misses the one fact that matters.
- Forgetting that what you leave out doesn't exist for the model: a cost, a privacy flag, a contract term.
- Fetching live data once at the start of a long session and never refreshing it.
- Context without provenance or version labels, so answers can't be cited and behavior changes can't be traced.
- Cutting history between a `tool_use` and its `tool_result`, or writing summaries that drop ids and numbers.
- Changing the cached prefix on every call (timestamps, reordered tools, volatile data above stable data).
- Passing the lead agent's whole context to every subagent.

## Key takeaways

**Architect's takeaway:** Every token you send costs money and attention, so design what the model sees on each step as carefully as the code that runs it.

- Assemble context per call from routed sources, by priority, within a budget; label each item with its origin and a time to live.
- Trim old tool results, compact older turns, keep notes outside the context, and cut only at safe points.
- Order context from stable to volatile and cache the stable prefix; cache reads cost a tenth of normal input.
- Give subagents a small brief and take back a condensed answer; never share raw tool output between agents.
- Programmatic tool calling keeps bulky intermediate results out of the context entirely.
