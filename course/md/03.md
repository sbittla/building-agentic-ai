# Chapter 3: Tool Selection, Routing and Tool Search

Real agents rarely have a single tool. Once the model has several to pick from, the hard part shifts from calling a tool to choosing the right one. In this chapter you'll organize tools in a registry, steer the model's choice with `tool_choice` and get reliable structured data back. You'll also build a small routing eval that turns "it seems better" into a number you can track.

**What you'll build:** a toolbox of date, unit and time tools, an evaluation that checks the model picks the right one, and structured output you can trust.

**You are here:** Tools in the agent architecture reference model  — Intermediate(section 1.7).

## Learning objectives

By the end of this chapter you can:

- Give a model several tools and let it choose.
- Organize tools with a registry that maps names to functions.
- Measure routing accuracy with a small test set.
- Fix misrouting by improving descriptions, merging tools or constraining inputs.

## Real-world connection

Support agents such as Intercom's Fin decide, message by message, whether to answer from the help center, run a configured procedure (like checking an order) or hand off to a human. That decision is tool selection. When it goes wrong, customers get the wrong kind of help, so production teams track routing accuracy as closely as answer quality.

## 3.1 A tool registry

With one tool, an `if` statement is enough. With many, keep two structures side by side:

- **REGISTRY**: a dictionary from tool name to Python function. Your code uses it.
- **TOOLS**: the list of descriptions sent to the model. The model uses it.

## 3.2 How the model chooses

On every call, the model reads the conversation and all the tool descriptions, then decides to call zero, one or several tools. This isn't keyword matching: the model reasons about which description best fits what it needs. That means:

- **Overlapping descriptions cause confusion.** If `calculate` and `days_between` both say "compute", date questions may go to the calculator.
- **Missing guidance causes skipped calls.** If `get_current_date` doesn't say "call this for relative dates", the model may guess what day it is.
- **More tools mean more chances to confuse.** Accuracy usually drops as the tool count grows, especially with near-duplicates.

## 3.3 Controlling the choice with tool_choice {api}

You can steer tool use with the `tool_choice` parameter:

| Setting | Behavior | Use when |
| --- | --- | --- |
| `{"type": "auto"}` (default) | The model decides whether to use a tool | Normal agent operation |
| `{"type": "any"}` | The model must call some tool | You know a tool is needed but not which one |
| `{"type": "tool", "name": "calculate"}` | The model must call this tool | Forcing structured output, or testing a tool |
| `{"type": "none"}` | The model may not call tools | A final "summarize everything" step |

For a long time, forcing a specific tool was the standard trick for getting **structured output**: define a tool whose schema is the JSON you want, force it and read `block.input`. It still works, and you'll see it in older code and in later chapters of this book. Two newer API features make it more reliable:

@@code ch03_structured.py

- **Structured outputs** constrain the model's **reply** to a schema. With `messages.parse(output_format=Contact)` you describe the shape as a Pydantic class (a Python class that declares fields and their types) and get a validated `Contact` back, with no JSON parsing and no "the model forgot a field". Use it whenever you want data, not prose.
- **Strict tools** (`"strict": True`) constrain the model's **tool input** to the tool's schema: every required field is present, types are right and `enum` values are respected. Strict schemas must set `"additionalProperties": false`. This makes the input's shape correct always rather than usually; you still check its *meaning* in your tool code (section 3.5).

:::warn Forced tools are on their way out
The newest models (Claude Opus 5.5 and the Fable and Mythos 5.1 models) reject `tool_choice` of `any` or a named tool with a 400 error, and so does any model running with *manual* extended thinking. Claude Sonnet 5, this book's default, still accepts forced tools. For new code, get structured data with structured outputs, or with a strict tool and `tool_choice` left at `auto`: both work on every current model. Two other old tricks are gone on current models too: setting `temperature` and **prefilling** the start of the model's reply both return 400 errors. Use instructions and structured outputs instead.
:::

Always include questions that need no tool, like "What is a prime number?" A description so eager that the model calls tools for everything is as broken as one the model ignores.

## 3.5 Validating arguments

The model usually sends valid arguments, but not always. It might send `"26.2"` as a string, or a unit you don't support. Defend in layers:

1. **Schema**: types and `enum` values in `input_schema` guide the model.
2. **Tool code**: check inputs and return a clear `ERROR:` message, as `convert_units` does.
3. **Error message quality**: say what was wrong **and** what is allowed ("cannot convert kg to km; units must both be distances or both weights"). A good error message lets the model fix its own call on the next step.

## 3.6 When you have dozens of tools: tool search {api}

Every tool description is sent on every call. With five tools that's fine. With fifty, from several MCP servers, the descriptions can cost tens of thousands of tokens per call, and routing accuracy drops because more tools look alike. **Tool search** fixes both: you mark most tools `defer_loading`, and the model sees only a search tool plus the few tools you keep loaded. When it needs something else, it searches, and the matching tools load for that request.

Tool search runs on Anthropic's servers, so this section and its exercise need Claude (`PROVIDER=claude` in `.env`). On the local model the kit stops with a clear message instead. Appendix H lists every exercise that needs Claude.
:::

Three things to notice:

- **The search runs on Anthropic's servers.** It's a *server tool*: the response contains `server_tool_use` and `tool_search_tool_result` blocks, but you don't run anything for them. Chapter 4's loop already handles this, because it runs only `tool_use` blocks and sends the whole response back.

- **Keep the everyday tools loaded.** Anything needed on most turns (here, the date) shouldn't wait for a search.

Use tool search from about ten tools, or when tool definitions pass roughly 10,000 tokens. Below that, it adds a step for nothing.

## Architect's Takeaway

More tools mean longer reasoning and higher injection risk; evaluate trade-offs.

## Common mistakes

- **Two tools that do almost the same thing.** Merge them or make the difference explicit in both descriptions.
- **Descriptions that say what, but not when.** "Returns the date" versus "Call this whenever the question depends on today".
- **Testing only the questions you expect.** Include tricky, ambiguous and no-tool questions.
- **Error messages that don't say how to fix the call.**

## Summary

- A registry maps names to functions; `TOOLS` describes them to the model.
- The model picks tools by reasoning over descriptions, so overlap and vagueness cause misroutes.
- `tool_choice` can require a tool, forbid tools or force a specific one.
- A routing eval turns "it seems better" into a number.
- Validate arguments in the schema and in code, and write error messages that explain the fix.
- With many tools, defer most of them and let the model find what it needs with tool search.

So far, `ask` handles only one round of tool calls. Chapter 4 replaces it with the agent loop, which keeps calling the model and running tools until the job is done, so your agent can answer multi-step questions.
