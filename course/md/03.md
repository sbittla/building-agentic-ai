# Chapter 3: Tool Selection, Routing and Tool Search

With one tool, a model makes one decision: call it or not. Give it a calculator and a `days_between` tool, then ask "How many days until December 25?", and the decision gets harder. Usually it picks `days_between`. Sometimes it reaches for the calculator, guesses today's date and answers wrong with a straight face, and you'll only notice if you count how often that happens.

**What you'll build:** a toolbox of date, unit and time tools, an evaluation that checks the model picks the right one, and structured output you can trust.

**You are here:** Tools in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 2 (tool calling).

## Learning objectives

By the end of this chapter you can:

- Give a model several tools and let it choose.
- Organize tools with a registry that maps names to functions.
- Measure routing accuracy with a small test set.
- Fix misrouting by improving descriptions, merging tools or constraining inputs.

**In the real world.** Support agents such as Intercom's Fin decide, message by message, whether to answer from the help center, run a configured procedure (like checking an order) or hand off to a human. That decision is tool selection, and production teams track its accuracy as closely as answer quality.

## 3.1 A tool registry

With many tools, keep two structures side by side:

- **REGISTRY**: a dictionary from tool name to Python function. Your code uses it.
- **TOOLS**: the list of descriptions sent to the model. The model uses it.

One `run_tool(name, args)` function looks up the name, calls the function and turns any exception into an error string:

A few design choices are worth a look. `get_current_date` takes no arguments, so its schema is `{"type": "object", "properties": {}}`. `convert_units` uses `enum`, so the model can send only units the tool supports. And `run_tool` never raises: unknown tools and bad arguments come back as text starting with `ERROR`.

## 3.2 How the model chooses

On every call, the model reads the conversation and all the tool descriptions, then decides to call zero, one or several tools. It reasons about which description best fits what it needs, so the descriptions are where routing goes wrong. When two of them overlap, the model has to guess: if `calculate` and `days_between` both say "compute", date questions may go to the calculator. When guidance is missing, it skips the call: if `get_current_date` doesn't say "call this for relative dates", the model may simply guess what day it is. And every tool you add is one more way to choose wrong, especially near-duplicates.

## 3.3 Controlling the choice with tool_choice {api}

The `tool_choice` parameter steers tool use:

Table: `tool_choice` settings
| Setting | Behavior | Use when |
| --- | --- | --- |
| `{"type": "auto"}` (default) | The model decides | Normal operation |
| `{"type": "any"}` | Must call some tool | A tool is needed, but you don't know which |
| `{"type": "tool", "name": "calculate"}` | Must call this tool | Forcing structured output, or testing a tool |
| `{"type": "none"}` | May not call tools | A final "summarize everything" step |

For a long time, forcing a specific tool was the standard trick for **structured output**: define a tool whose schema is the JSON you want, force it and read `block.input`. You'll still see it in older code and later chapters. Two newer API features do it more reliably:

@@code ch03_structured.py::Contact,extract_contact,STRICT_CONVERT

- **Structured outputs** constrain the model's **reply** to a schema. With `messages.parse(output_format=Contact)` you describe the structure as a Pydantic class (a Python class that declares fields and their types) and get a validated `Contact` back, with no JSON parsing and no forgotten fields. Use it whenever you want data rather than prose.
- **Strict tools** (`"strict": True`) constrain the model's **tool input** to the tool's schema: required fields present, types right, `enum` values respected. Strict schemas must set `"additionalProperties": false`. That makes the input's shape right every time instead of usually, but you still check the input's *meaning* in your tool code (section 3.5).

:::warn Forced tools are on their way out
The newest models (Claude Opus 5.5 and the Fable and Mythos 5.1 models) reject `tool_choice` of `any` or a named tool with a 400 error, and so does any model running with *manual* extended thinking. Claude Sonnet 5, this book's default, still accepts them. For new code, use structured outputs, or a strict tool with `tool_choice` left at `auto`; both work on every current model. Two other old tricks are gone too: setting `temperature` and **prefilling** the start of the model's reply both return 400 errors.
:::

## 3.5 Validating arguments

The model usually sends valid arguments, but not always: `"26.2"` as a string, or a unit you don't support. Defend in layers:

1. **Schema**: types and `enum` values in `input_schema` guide the model.
2. **Tool code**: check inputs and return a clear `ERROR:` message, as `convert_units` does.
3. **Error messages**: say what was wrong **and** what is allowed ("cannot convert kg to km; units must both be distances or both weights"), so the model can fix its own call on the next step.

## 3.6 When you have dozens of tools: tool search {api}

Every tool description is sent on every call. With five tools that's fine. A company agent can easily reach forty or fifty (orders, billing, HR, IT, whole MCP servers), and then the descriptions cost thousands of tokens per call and routing accuracy drops. **Tool search** fixes both: you mark most tools `defer_loading`, and the model sees only a search tool plus the few you keep loaded. When it needs something else, it searches, and the matching tools load for that request.

As you read it, notice how little changes for your code:

- **The search runs on Anthropic's servers.** It's a *server tool*: the response contains `server_tool_use` and `tool_search_tool_result` blocks, but you don't run anything for them. So `choose` needs only one call, and Chapter 4's loop will handle it unchanged, because the loop runs only `tool_use` blocks and sends the whole response back.
- **The catalog tools are stand-ins** with real names, descriptions and schemas but fixed replies, because search needs only the descriptions.
- **Names and descriptions still matter most.** Search finds tools by their words, so namespaced names (`orders_get_status`, `hr_request_leave`) and descriptions in the user's language make it work.
- **Keep the everyday tools loaded.** Anything needed on most turns (here, the date) shouldn't wait for a search.

Use tool search from about ten tools, or when tool definitions pass roughly 10,000 tokens. Below that, it adds a step for nothing.

## Common mistakes

- Two tools that do almost the same thing. Merge them, or spell out the difference in both descriptions.
- Descriptions that say what but not when. Compare "Returns the date" with "Call this whenever the question depends on today".
- Testing only the questions you expect. Include tricky, ambiguous and no-tool questions.
- Error messages that don't say how to fix the call.

## Before you move on

- **You should understand:** why misroutes start in overlapping or vague descriptions, and what each `tool_choice` setting does to the model's choice.
- **You should be able to build:** a `REGISTRY` and `TOOLS` pair behind a `run_tool` that never raises, and a routing eval with no-tool questions.
- **Prove it:** `./course.sh check 3.3` passes, and exercise 3.4 reports accuracy over three runs of 20 questions, failures listed.
- **Break it on purpose:** delete the second sentence of `get_current_date`'s description, add "How many days until December 25?" to `CASES` expecting `get_current_date`, and rerun `ch03_routing_eval.py`.
- **Defend this decision:** when you'd switch on tool search, using exercise 3.7's accuracy and token table.

## Key takeaways

**Architect's takeaway:** Every tool you add costs tokens on every call and gives the model one more way to choose wrong, so measure routing before and after.

- A registry maps names to functions; `TOOLS` describes them to the model.
- The model picks tools by reasoning over descriptions, so overlap and vagueness cause misroutes.
- `tool_choice` can require, forbid or force tools; for structured data, prefer structured outputs.
- Validate arguments in the schema and in code, and write error messages that explain the fix.
- With many tools, defer most of them and let the model find what it needs with tool search.
