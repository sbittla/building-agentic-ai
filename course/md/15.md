# Chapter 15: MCP in 2026: From Tool Calling to Agent Infrastructure

Chapters 12 to 14 connected one agent to a few servers on your own machine. Companies now run dozens of MCP servers for hundreds of agents and people, behind load balancers, with security teams asking who called what. The protocol grew up to match: the 2026-07-28 specification made every request stand on its own, let clients cache what servers tell them and moved optional and enterprise features into extensions. This chapter shows what those changes look like on the wire and what they mean for the servers you write. The pieces companies build on top of them (a job pattern for slow tools, a gateway in front of every server, registries and company-wide sign-on) need agent identity and production tracing first, so they wait for Chapter 30.

**What you'll build:** a server that tells clients how long to cache its lists, a client that inspects any server, and raw HTTP requests that show the stateless protocol.

**You are here:** MCP and Policies in the agent architecture reference model (section 1.7).

## Real-world connection

In December 2025, Anthropic donated MCP to the Agentic AI Foundation, a new Linux Foundation project, alongside OpenAI's AGENTS.md and Block's goose. MCP is now run by an open community. The 2026-07-28 specification is its largest revision so far, and most of its changes came from companies running MCP at scale: cloud providers who wanted servers behind ordinary load balancers, security teams who wanted gateways and central sign-on, and hosts that were asking for the same tool list before every model call. This chapter covers the protocol changes; sections 30.8 to 30.11 build the patterns (long-running jobs, gateways, registries, central authorization) that those companies run on top of them.

## 15.1 From tool calling to infrastructure

With one agent and three servers, the Chapter 13 host is all you need. With fifty servers, new problems appear:

| Problem at scale | Answer | Section |
| --- | --- | --- |
| A server must run on many machines behind a load balancer | Stateless requests: no session to keep | 15.2 |
| Every model call asks every server for its tools again | Cache hints on lists | 15.3 |
| Optional features bloat every client and server | Extensions, used only when both sides support them | 15.4 |
| Some tools take minutes, and connections time out | Start-and-poll jobs; the Tasks extension | 30.8 |
| Hundreds of tools don't fit in a prompt | Progressive discovery through search | 30.9 |
| Nobody can say which agent may call which tool | A gateway with allow-lists, tokens and one audit trail | 30.9 |
| Anyone can publish a server | Registries with verified publishers, and your own allow-list | 30.10 |
| Every employee approves every server by hand | Enterprise-managed authorization | 30.11 |

None of this changes the three primitives you learned in Chapter 12. Tools, resources and prompts stay the same; what changes is everything around them.

## 15.2 The protocol on the wire {api}

Before 2026-07-28, a client opened a *session*: an `initialize` handshake, then a session id on every later request, so the same server process had to answer all of them. Now **every request is complete on its own**. It carries the protocol version and the client's capabilities in its `_meta` field, and any copy of the server can answer it.

You can see this with nothing but HTTP. Start the chapter's catalogue server with `./course.sh serve ch15_modern.py`, then send it requests:

@@code ch15_modern.py::ENVELOPE,post

A call to `get_price` is one POST. This is the whole request:

```
POST /mcp
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_price

{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "get_price", "arguments": {"product_id": "P-2"},
            "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
```

And the answer:

```
{"jsonrpc": "2.0", "id": 1, "result": {"content": [{"type": "text", "text": "120.0"}],
 "structuredContent": {"result": 120.0}, "isError": false, "resultType": "complete"}}
```

Three details matter:

- **No handshake, no session.** The first request can be a tool call. A request without the `_meta` envelope is rejected with a clear error.
- **The headers repeat the method and the tool name.** A gateway or load balancer can route, rate-limit or block `tools/call` for `delete_repo` from the headers alone, without parsing JSON. The server checks that headers and body agree; if they don't, it refuses the request, so nobody can slip a different tool past a gateway that trusted the header.
- **`resultType`** says whether this is the final answer (`complete`) or a request for more input (`input_required`, the multi round-trip requests from Chapter 13's elicitation exercise).

A client that wants to know what a server offers before calling it sends **`server/discover`**. The answer lists the protocol versions it speaks, its capabilities, its extensions and its instructions. It's optional: a client that already knows the server can skip it.

:::tip Sessions still exist where you need them
Stateless doesn't mean a server forgets everything. A shopping cart or a database transaction still needs state; keep it in your own storage, keyed by an id you return from a tool, the way Chapter 5 keeps the to-do list in a file. What went away is the protocol forcing every server to hold a session.
:::

## 15.3 Discovery and caching

A host asks for the tool list before every model call, because the list might have changed. Usually it hasn't. Since 2026-07-28, list results carry two hints: **`ttlMs`**, how many milliseconds the answer stays fresh, and **`cacheScope`**, whether one user's cached copy may be served to another (`public`) or not (`private`). A tool list that only changes when you deploy can be `public` for minutes. A list of resources that depends on who's asking must be `private`, or one user's cached list could leak another user's file names.

Run `./course.sh python ch15_modern.py`:

```
     protocol: 2026-07-28
       server: catalog 1.2.0
        tools: ['find_products', 'get_price']
       ttl_ms: 300000
  cache_scope: public
 list_changed: True
  same_answer: True
list requests that reached the server: 1
```

Two list calls, one request to the server. When the list does change, a server that declares `listChanged` notifies clients that are listening, and they drop their cached copy early. A client can also ask for a fresh copy with `cache_mode="refresh"`. Exercise 15.4 measures the saving over a conversation.

## 15.4 Extensions and the road ahead {api}

The 2026-07-28 revision introduced an **extensions framework**. The core protocol stays small; optional features live in extensions with names like `io.modelcontextprotocol/tasks`. A client lists the extensions it supports in each request's capabilities, a server lists its own in `server/discover`, and a feature is used only when both sides have it. Tasks (section 30.8), MCP Apps (interactive user interfaces inside the chat, Chapter 12) and Enterprise-Managed Authorization (section 30.11) are the first official extensions.

Three older features are deprecated, and so is a transport. Each will keep working for at least twelve months, so plan the move rather than rushing it:

| Deprecated | Use instead |
| --- | --- |
| Sampling (the server borrows the host's model) | The server calls a model API itself, with its own key and budget |
| Roots (the client lists allowed folders) | Folders as tool parameters or resource URIs, checked by the server |
| Logging over the protocol | stderr, or OpenTelemetry traces (Chapter 28) |
| The HTTP+SSE transport | Streamable HTTP |

MCP's roadmap, published in August 2026, sets five priorities:

1. **Messaging for long-running agent work:** tasks, subscriptions and progress for agents that run for hours.
2. **One HTTP-native transport** for local and remote servers alike.
3. **Agent identity**, which section 30.11 returns to once Chapter 26 has given agents identities of their own.
4. **Better primitives**, including progressive discovery (section 30.9) in the protocol itself.
5. **Better SDKs** and developer experience.

The direction is clear: MCP is becoming the way agents reach everything a company runs, with the same expectations as any other production API: scale, security, identity and audit. Chapter 30 builds each of those in a small form you can read end to end, once the chapters in between have given you durable jobs (Chapter 19), agent identity (Chapter 26) and tracing (Chapter 28).

## Architect's Takeaway

Stateless protocols and progressive discovery scale better than monolithic tool sets.

## Common mistakes

- **Keeping state in memory between requests** and expecting the same server process to answer next time. Store it, keyed by an id.
- **Caching private lists as public**, so one user's resource names reach another.
- **Trusting the `Mcp-Name` header without checking the body**, on either side of a load balancer.
- **Building new servers on deprecated features** such as sampling or roots.

## Summary

- The 2026-07-28 specification made MCP stateless: each request carries its version and capabilities, so any server copy can answer; `server/discover` is optional.
- HTTP requests repeat the method and tool name in headers for gateways; servers reject requests whose headers and body disagree.
- Lists carry `ttlMs` and `cacheScope`; clients cache them, which saves a request on nearly every model call.
- Optional features now live in extensions; sampling, roots, protocol logging and HTTP+SSE are deprecated with at least a year's notice.
- Jobs, gateways, registries and company sign-on are built on these changes in sections 30.8 to 30.11.

You now know what the protocol looks like on the wire and how its servers scale. Part 6 turns to what an agent knows at each step: Chapter 16 engineers the context of every call, Chapter 17 gives agents memory with rules, and Chapter 18 builds knowledge systems the agent can search and check.
