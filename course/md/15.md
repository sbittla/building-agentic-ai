# Chapter 15: MCP in 2026: From Tool Calling to Agent Infrastructure

Chapters 12 to 14 connected one agent to a few servers on your own machine. Companies now run dozens of MCP servers for hundreds of agents and people, behind load balancers, with security teams asking who called what. The protocol grew up to match: the 2026-07-28 specification made every request stand on its own, let clients cache what servers tell them, standardized long-running work and moved enterprise features into extensions. This chapter shows what those changes look like on the wire, and builds the two pieces most teams add next: a job pattern for slow tools and a gateway in front of all their servers.

**What you'll build:** a server that tells clients how long to cache its lists; a client that inspects any server; raw HTTP requests that show the stateless protocol; a report server whose tools start work and return at once, on Chapter 19's durable runner; and a gateway that hides, authorizes, rate-limits and audits every call to the servers behind it, with tools found by search instead of listed all at once.

**You are here:** MCP and Policies in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Explain what the 2026-07-28 specification changed and which problem each change solves.
- Read and send MCP requests over HTTP without an SDK, and say what each header and `_meta` field is for.
- Set cache hints on a server and measure what caching saves.
- Serve long-running work as start-and-poll tools that survive restarts, and relate them to the Tasks extension.
- Put a gateway in front of several servers that allow-lists, authorizes, rate-limits and audits every call.
- Offer tools through search (progressive discovery) instead of listing them all.
- Choose servers from registries with care, and plan authorization for a company.

## Real-world connection

In December 2025, Anthropic donated MCP to the Agentic AI Foundation, a new Linux Foundation project, alongside OpenAI's AGENTS.md and Block's goose. MCP is now run by an open community. The 2026-07-28 specification is its largest revision so far, and most of its changes came from companies running MCP at scale: cloud providers who wanted servers behind ordinary load balancers, security teams who wanted gateways and central sign-on, and hosts that were asking for the same tool list before every model call. The patterns in this chapter (gateways, registries, central authorization) are how those companies run MCP in production.

## 15.1 From tool calling to infrastructure

With one agent and three servers, the Chapter 13 host is all you need. With fifty servers, new problems appear:

| Problem at scale | Answer | Section |
| --- | --- | --- |
| A server must run on many machines behind a load balancer | Stateless requests: no session to keep | 15.2 |
| Every model call asks every server for its tools again | Cache hints on lists | 15.3 |
| Some tools take minutes, and connections time out | Start-and-poll jobs; the Tasks extension | 15.4 |
| Hundreds of tools don't fit in a prompt | Progressive discovery through search | 15.5 |
| Nobody can say which agent may call which tool | A gateway with allow-lists, tokens and one audit trail | 15.5 |
| Anyone can publish a server | Registries with verified publishers, and your own allow-list | 15.6 |
| Every employee approves every server by hand | Enterprise-managed authorization | 15.7 |

None of this changes the three primitives you learned in Chapter 12. Tools, resources and prompts stay the same; what changes is everything around them.

## 15.2 The protocol on the wire {api}

Before 2026-07-28, a client opened a *session*: an `initialize` handshake, then a session id on every later request, so the same server process had to answer all of them. Now **every request is complete on its own**. It carries the protocol version and the client's capabilities in its `_meta` field, and any copy of the server can answer it.

You can see this with nothing but HTTP. Start the chapter's catalogue server with `./course.sh serve ch15_modern.py`, then send it requests:

@@code ch15_modern.py::ENVELOPE,post

A call to `get_price` is one POST. This is the whole request:

```
POST /mcp
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_price

{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "get_price", "arguments": {"product_id": "P-2"},
            "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
```

And the answer:

```
{"jsonrpc": "2.0", "id": 1, "result": {"content": [{"type": "text", "text": "120.0"}],
 "structuredContent": {"result": 120.0}, "isError": false, "resultType": "complete"}}
```

Three details matter:

- **No handshake, no session.** The first request can be a tool call. A request without the `_meta` envelope is rejected with a clear error.
- **The headers repeat the method and the tool name.** A gateway or load balancer can route, rate-limit or block `tools/call` for `delete_repo` from the headers alone, without parsing JSON. The server checks that headers and body agree; if they don't, it refuses the request, so nobody can slip a different tool past a gateway that trusted the header.
- **`resultType`** says whether this is the final answer (`complete`) or a request for more input (`input_required`, the multi round-trip requests from Chapter 13's elicitation exercise).

A client that wants to know what a server offers before calling it sends **`server/discover`**. The answer lists the protocol versions it speaks, its capabilities, its extensions and its instructions. It's optional: a client that already knows the server can skip it.

:::tip Sessions still exist where you need them
Stateless doesn't mean a server forgets everything. A shopping cart or a database transaction still needs state; keep it in your own storage, keyed by an id you return from a tool, exactly as Chapter 19 keeps a job's state in SQLite. What went away is the protocol forcing every server to hold a session.
:::

## 15.3 Discovery and caching

A host asks for the tool list before every model call, because the list might have changed. Usually it hasn't. Since 2026-07-28, list results carry two hints: **`ttlMs`**, how many milliseconds the answer stays fresh, and **`cacheScope`**, whether one user's cached copy may be served to another (`public`) or not (`private`). The Python SDK sets them from `cache_hints`:

@@code ch15_modern.py::catalog

A tool list that only changes when you deploy can be `public` for minutes. A list of resources that depends on who's asking must be `private`, or one user's cached list could leak another user's file names.

The SDK's client caches automatically and respects the hints:

@@code ch15_modern.py::describe

Run `./course.sh python ch15_modern.py`:

```
     protocol: 2026-07-28
       server: catalog 1.2.0
        tools: ['find_products', 'get_price']
       ttl_ms: 300000
  cache_scope: public
 list_changed: True
  same_answer: True
list requests that reached the server: 1
```

Two list calls, one request to the server. When the list does change, a server that declares `listChanged` notifies clients that are listening, and they drop their cached copy early. A client can also ask for a fresh copy with `cache_mode="refresh"`. Exercise 15.4 measures the saving over a conversation.

## 15.4 Long-running work

A tool call should answer in seconds. Clients, proxies and load balancers close connections that stay silent for too long, and a model waiting on a five-minute call holds everything up. Work that takes minutes (building a report, exporting data, running a deployment) needs a different shape: **start the work, return a handle at once, let the caller check on it**.

@@code ch15_jobs_server.py::start_report,job_status

The pattern has four parts:

1. **`start_report` returns immediately** with a job id and a suggested polling interval. The work runs in the background on Chapter 19's durable runner, so each step is checkpointed in SQLite.
2. **`job_status` reports progress**, and the result once the job has finished.
3. **A `request_id` makes starting safe to retry.** If the call times out and the agent tries again, it gets the same job instead of a second report. This is Chapter 19's idempotency key, applied to a tool.
4. **Nothing is lost in a restart.** When the server starts (`python ch15_jobs_server.py stdio`), `resume_unfinished` claims jobs a previous process left behind; finished steps aren't repeated.

Run `./course.sh python ch15_jobs_server.py` to start a report for March 2026 and poll it to completion.

The status names aren't arbitrary. They're the ones MCP's **Tasks extension** (`io.modelcontextprotocol/tasks`) uses to make this pattern part of the protocol:

|  | This chapter's tools | Tasks extension |
| --- | --- | --- |
| Starting | A `start_…` tool returns a job id | Any `tools/call` may return a task (`resultType: "task"`) with a `taskId` |
| Checking | A `job_status` tool | `tasks/get` |
| Asking for input | `input_required` with a note for a person | `input_required` with requests the client answers through `tasks/update` |
| Stopping | Your own tool | `tasks/cancel` (cooperative: the server may still finish) |
| Statuses | `working`, `completed`, `input_required`, `cancelled` | the same, plus `failed` |

With the extension, the *server* decides per call whether to answer directly or return a task, and the client handles whichever arrives, so a host can show progress for any slow tool without the model polling. Clients and SDKs are adding support through 2026. Until yours has it, the tools above work with every client, and moving to the extension later changes the wrapper, not your durable runner.

:::tip Who polls?
If the model polls, every check costs a model call. Let the host or the harness poll where you can, and give the model a tool that waits (exercise 15.6) or tell it roughly when to check back.
:::

## 15.5 Gateways: one front door

Once a company has many servers, it stops letting every agent connect to each of them. It puts a **gateway** in front: agents connect to the gateway only, and the gateway connects to the servers.

@@image d-ef89b841b81e.png

Chapter 14's policy layer did this inside one host. A gateway does it once, for every host in the company:

@@code ch15_gateway.py::POLICY,Gateway.call_tool,Gateway._check

- **Deny by default.** Only the tools in `POLICY` exist behind the gateway. When a server adds a `delete_everything` tool, no agent sees it until someone adds it to the list.
- **Every call is authorized with Chapter 26's tokens.** A token names the agent, the user it acts for, the gateway as its audience and its scopes. The planner can add tasks but can't query sales; the analyst can query sales but can't add tasks.
- **Rate limits per agent** stop one runaway loop from overloading a server that others depend on.
- **One audit trail** records every call, allowed or refused, with the agent and the user. That's where Chapter 28's traces start.

Run `./course.sh python ch15_gateway.py`:

```
agents see: ['search_tools', 'todo__add_task', 'todo__list_tasks', ...]
Added #1: Book flights
ERROR Not allowed: token lacks todo:write
n
400
ERROR Not allowed: token lacks shop:read
ERROR Not allowed: no tool called 'todo__delete_everything'
```

The gateway also caches each server's tool list for as long as that server's `ttlMs` allows (`Gateway._refresh`), so a busy gateway doesn't ask every server for its tools on every call.

### Progressive discovery

Fifty servers can offer a thousand tools. Listing them all fills the prompt, costs tokens on every call and makes the model worse at choosing (section 3.6). With `progressive=True`, the gateway lists only two tools:

@@code ch15_gateway.py::Gateway.search_tools

The model searches for what it needs ("task", "sales query"), gets back a few names with their descriptions and input schemas, and calls one through `use_tool`. The gateway checks and audits that call exactly like a direct one. This is the idea behind tool search in Claude's API and the "progressive discovery" priority on MCP's roadmap; the gateway gives it to any agent, whatever model it uses. Exercise 15.5 makes the search show only tools the caller is allowed to use, and exercise 15.7 puts the Chapter 13 agent behind the gateway.

:::warn A gateway is a high-value target
Everything passes through it: every token, every argument and every result. Run it with the same care as your identity provider. Keep it small, log to a place agents can't write to, and never let it pass an agent's token to the servers behind it; the gateway calls them with its own credentials, scoped to what that server needs.
:::

## 15.6 Registries and the supply chain

How do you find servers, and how do you know a server is what it claims to be? The **MCP Registry** (`registry.modelcontextprotocol.io`) is the official catalogue of public servers. It stores metadata, not code: a server's name, where to get its package (npm, PyPI, a Docker image) or its URL, and how to run it. Names follow a reverse-DNS pattern, such as `io.github.someone/weather`, and only the owner of that GitHub account or domain can publish under that name. That proves who published a server. It doesn't prove the code is safe; scanning is left to the package registries and to the marketplaces built on top of the registry. The registry is still in preview, so expect changes.

Companies usually run their own **private registry** too, with the same API, listing only the servers they've reviewed. Hosts point to it instead of the public one.

A sensible supply-chain policy, building on Chapter 14's server review:

- **Pin versions.** Install `server@1.4.2`, not "latest", and review the changes before you upgrade.
- **Watch the tool definitions.** A server can change a tool's description after you approved it, and a description is text the model reads, which makes it a way to inject instructions. A gateway can store a hash of each approved definition and refuse tools whose definition changed until someone reviews them.
- **Run third-party servers with the fewest rights** they need: their own container, a read-only token, no access to other secrets (Chapter 13's minimal environment).
- **Keep the gateway's allow-list** as the final word, whatever a registry says.

## 15.7 Authorization for companies {api}

Chapter 30 secures a remote server with OAuth. The 2026-07-28 revision tightened that flow and added a company-wide option:

- **Issuer validation.** A client must now check that the authorization response came from the server it expected (the `iss` parameter from RFC 9207) before redeeming the code. This closes the "mix-up" attack, in which a malicious authorization server tricks a client into sending it a code meant for a different one.
- **Client ID Metadata Documents.** A client identifies itself with a URL pointing to a small JSON document that describes it. The old approach, Dynamic Client Registration, is deprecated: every client used to register itself with every server, which left servers with thousands of unverified registrations.
- **Enterprise-Managed Authorization**, an extension. Instead of every employee approving every server, the company's identity provider (Okta, Microsoft Entra ID and similar) decides. The client, signed in with the employee's company account, asks the identity provider for a signed grant for a particular server; the identity provider checks company policy (group, role, device); the server's authorization server exchanges that grant for an access token. Access is granted, and revoked, in one place.

Notice that all of this identifies the *user and the client application*. Which *agent* is acting, the question at the heart of Chapter 26, is still open. MCP's August 2026 roadmap makes **agent identity** one of its priorities, based on workload identity federation (the way cloud workloads prove who they are without stored secrets) and proof-of-possession tokens (DPoP), which are useless to anyone who steals them without the matching private key. Until that lands, use the pattern from Chapter 26 and this chapter's gateway: the gateway verifies an agent token and records agent and user on every call.

## 15.8 Extensions and the road ahead {api}

The 2026-07-28 revision introduced an **extensions framework**. The core protocol stays small; optional features live in extensions with names like `io.modelcontextprotocol/tasks`. A client lists the extensions it supports in each request's capabilities, a server lists its own in `server/discover`, and a feature is used only when both sides have it. Tasks, MCP Apps (interactive user interfaces inside the chat, Chapter 12) and Enterprise-Managed Authorization are the first official extensions.

Three older features are deprecated, and so is a transport. Each will keep working for at least twelve months, so plan the move rather than rushing it:

| Deprecated | Use instead |
| --- | --- |
| Sampling (the server borrows the host's model) | The server calls a model API itself, with its own key and budget |
| Roots (the client lists allowed folders) | Folders as tool parameters or resource URIs, checked by the server |
| Logging over the protocol | stderr, or OpenTelemetry traces (Chapter 28) |
| The HTTP+SSE transport | Streamable HTTP |

MCP's roadmap, published in August 2026, sets five priorities:

1. **Messaging for long-running agent work:** tasks, subscriptions and progress for agents that run for hours.
2. **One HTTP-native transport** for local and remote servers alike.
3. **Agent identity**, as section 15.7 described.
4. **Better primitives**, including progressive discovery (section 15.5) in the protocol itself.
5. **Better SDKs** and developer experience.

The direction is clear: MCP is becoming the way agents reach everything a company runs, with the same expectations as any other production API: scale, security, identity and audit. The code in this part gives you each of those in a small form you can read end to end.

## Architect's Takeaway

Stateless protocols and progressive discovery scale better than monolithic tool sets.

## Common mistakes

- **Keeping state in memory between requests** and expecting the same server process to answer next time. Store it, keyed by an id.
- **Caching private lists as public**, so one user's resource names reach another.
- **Tools that block for minutes** instead of starting a job and returning.
- **Starting jobs without an idempotency key**, so a retried call does the work twice.
- **Letting the model poll in a tight loop**, paying for every check.
- **Trusting a gateway header without checking the body**, or passing an agent's token straight through to the servers behind the gateway.
- **Showing every tool to every agent** when search and a scoped allow-list would do.
- **Treating a registry listing as a security review.** It proves who published a server, not that it's safe.
- **Building new servers on deprecated features** such as sampling or roots.

## Summary

- The 2026-07-28 specification made MCP stateless: each request carries its version and capabilities, so any server copy can answer; `server/discover` is optional.
- HTTP requests repeat the method and tool name in headers for gateways; servers reject requests whose headers and body disagree.
- Lists carry `ttlMs` and `cacheScope`; clients cache them, which saves a request on nearly every model call.
- Long-running work returns a job handle at once, runs durably and is safe to retry; the Tasks extension standardizes the same shape.
- A gateway gives one place to allow-list tools, check agent tokens, rate-limit, cache and audit, and can offer tools through search.
- Registries verify publishers, not code: pin versions, watch tool definitions and keep your own allow-list.
- Company authorization is moving to issuer validation, client metadata documents and enterprise-managed authorization; agent identity is next on the roadmap.
- Optional features now live in extensions; sampling, roots, protocol logging and HTTP+SSE are deprecated with at least a year's notice.

You now know how agents reach tools at company scale. Part 6 turns to what an agent knows at each step: Chapter 16 engineers the context of every call, Chapter 17 gives agents memory with rules, and Chapter 18 builds knowledge systems the agent can search and check.

:::ex Concept | 15.2 | Plan a migration
An internal server written in 2025 uses sampling to summarize documents with the host's model, roots to learn which folders it may read, protocol logging for its logs, and the HTTP+SSE transport. It also keeps each user's search results in memory between calls. Write the migration plan to the 2026-07-28 specification: what changes, in what order, and how you'll test that nothing broke.
**Done when:** Every deprecated feature has a replacement, the in-memory state has a new home, and the plan says what to ship first.
:::

:::ex Simple | 15.3 | MCP by hand
Start `./course.sh serve ch15_modern.py`. Using `post` from `ch15_modern.py`, send `server/discover`, `tools/list` and a `tools/call` for `get_price`. Then send a request whose `Mcp-Name` header names a different tool from the body.
**Done when:** You can point to the protocol version, the cache hints and the structured result in the answers, and you can explain why the mismatched request is refused.
:::

:::ex Medium | 15.4 | What does caching save?
A host lists tools before every model call. Using `CountingServer`, count how many list requests reach the server over ten turns: with the five-minute hint and caching on, with the cache bypassed, and with the hint set to zero.
**Done when:** You have three counts, and one sentence on when a server should choose a short hint or `private` scope.
:::

:::ex Medium | 15.5 | Search what you may use
Change the gateway's `search_tools` so it returns only the tools the caller's token allows, and nothing for a caller without a valid token.
**Hint:** A tool function can accept a `Context` argument; `_token(ctx)` finds the caller's token.
**Done when:** A planner with `todo:read` finds only the two read tools, an analyst searching for "task" finds nothing, and a caller with no token finds nothing.
:::

:::ex Medium | 15.6 | Fewer polls, safe retries
Give `job_status` a `wait_s` parameter (at most 20 seconds) that holds the call until the job finishes or the time runs out. Then show that calling `start_report` twice with the same `request_id` returns the same job.
**Done when:** Waiting takes one status call where short polling took several, and both starts share one job id.
:::

:::ex Complex | 15.7 | An agent behind the gateway
Run the Chapter 13 agent with the gateway as its only server: the host starts `ch15_gateway.py stdio` for the planner agent and passes its token in the environment. Ask it to add a task and to count cancelled orders.
**Done when:** The agent finds tools through `search_tools`, the task is added, the order query is refused and reported honestly, and the audit trail shows both calls with the agent and the user.
:::
