# Chapter 29: Agent Performance Engineering: Latency, Throughput and Cost

An agent that answers in 3 seconds and costs a cent in testing can take 30 seconds and cost a dollar in production: longer conversations, more steps, bigger contexts, more users at once and a provider rate limit nobody planned for. Performance engineering for agents uses the same discipline as for any service: a model of where the time and money go, experiments that measure it under load and limits set from the measurements. This chapter gives you all three, in code you can run against a simulator for free and then against a real model.

**What you'll build:** a latency model and a cost model you compute from a trace, per-request and per-user budgets enforced in code, a concurrency sweep that finds the knee where an agent stops scaling, an open-loop load test and a capacity plan from latency and rate limits.

**You are here:** Model and Agent runtime (performance and cost) in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapter 16 (prompt caching), Chapter 27 (evaluation), Chapter 28 (traces).

## Learning objectives

By the end of this chapter you can:

- Write an agent's latency and cost per task as sums of terms you can measure, and say how to measure each one.
- Break an agent run's cost and latency down by step, and explain why history dominates.
- Choose among the levers: caching, context trimming, routing, parallel tools, fewer steps, batching and effort.
- Enforce budgets per request and per user in code.
- Run a concurrency sweep, read throughput, goodput and latency percentiles and name the knee and the resource that limits it.
- Choose between a closed-loop sweep and an open-loop load test, and read percentiles correctly.
- Plan capacity with Little's law and the provider's rate limits.
- Judge every optimization by cost per successful task, not cost per call.
- Build a business case for an agent against the human baseline: cost per task and per success, automation, escalation and failure rates, failure cost, break-even, payback and its sensitivity to each assumption.
- Run a reproducible benchmark that compares designs, tool execution, models and context under load, and use its results, with their confidence intervals, to choose an architecture.

**In the real world.** In LangChain's survey of 1,340 practitioners (late 2025), latency was the second most common barrier to putting agents into production, named by about 20%, after quality. Providers have responded with tools aimed squarely at agents: prompt caching that makes a repeated prefix cost a tenth as much (Chapter 16), cheaper small models for routine steps (Chapter 20), batch APIs at half price for work that can wait (Chapter 27's judge) and effort settings that trade thinking for speed (Chapter 4). None of them helps until you've measured where your agent actually spends.

## 29.1 The agent performance model

Every agent task, however clever, spends its time and money in a few places. Write them down as two sums:

```
Total latency = model + tool + retrieval + orchestration + queueing + serialization
Cost per task = model + tools + retrieval + infrastructure + retries + human review
```

Each term is something you can measure, and each has its own levers. When a task is slow or expensive, the sums tell you which term to attack first, instead of guessing.

@@image d-0abd471f49e3.png

Figure: Where the time goes in one agent task
Alt: A task arrives and pays orchestration and serialization. Each step, repeated, waits for a slot, makes a model call (first token, then output), runs a tool or retrieval and pays orchestration and serialization again. The last step waits for a slot and makes the final model call that produces the answer.

The terms of the latency sum, and where each one comes from in Chapter 28's traces:

- **Model:** time inside model calls, from the request leaving your process to the last token arriving. Each call pays the time to the first token plus the time to generate its output. Measure it with the `chat` spans. Timed at the client, it already includes the network.
- **Tool:** time in tools that compute or act (a calculator, sending an email). Measure it with the `execute_tool` spans.
- **Retrieval:** time in tools that fetch data: a search, a SQL query, a vector lookup. They're `execute_tool` spans too, but they scale with the size of the data, not with the model, so they get their own term. `is_retrieval` sorts tools by name.
- **Orchestration:** your own code between the calls: the agent loop, guards, prompt assembly and logging. Nobody traces all of it, so the model computes it as the remainder: total minus every other term.
- **Queueing:** time waiting for a turn: a free slot in your gateway, a connection or a provider's rate limit. Measure it with a `queue` span around the wait. If you don't record it, it hides inside the model term and you blame the model.
- **Serialization:** encoding each request, decoding each reply and copying the history. Record `serialize` spans if you have them; otherwise `measure_serialization` times it on a real conversation, and the model multiplies that by the number of steps.

Network overhead has no term of its own. Timed at the client, the trip to the model is inside the model term and the trip to a remote tool inside the tool or retrieval term; an untraced hop, such as a proxy in front of your service, lands in orchestration.

@@code ch29_perf.py::latency_model

`latency_model` accepts a trace's spans or a dictionary of components, and returns the six terms and the total they add up to. The terms add up only if the steps run one after another. If orchestration comes out negative, spans overlapped (parallel tool calls, section 29.3): read the trace itself instead of the sum.

The cost sum works the same way:

- **Model:** tokens times price. Input read from the prompt cache costs 10% of the input price and input written to it 125% (Chapter 16). Take the token counts from the `chat` spans.
- **Tools:** the per-call price of paid APIs your tools call. Many tools are free.
- **Retrieval:** the per-query price of a search API or a hosted vector database.
- **Infrastructure:** your servers' cost per hour divided by the tasks they finish in that hour. It falls as throughput rises, so an idle server makes every task more expensive.
- **Retries:** model calls you paid for and threw away (a timeout, a malformed reply). The model counts each as an average call of the task.
- **Human review:** the share of tasks a person checks, times their minutes, times their hourly rate. It's the term teams forget, and often one of the largest.

These two sums describe one task. Once many tasks run at once, you'll read a few more numbers from the same traces: latency percentiles (p50, p95 and p99), throughput (tasks finished per second), goodput (tasks that succeeded per second), cost per successful task, and the capacity limits that cap them all: model slots and the provider's rate limits. Sections 29.5 to 29.7 measure each one.

## 29.2 Where the time and money go

The model term dominates most agents, and it grows faster than you'd expect. An agent run is a series of model calls, and each call sends the **whole** conversation so far: the system prompt and tool definitions (the prefix), the question, and every earlier reply and tool result.

@@code ch29_costs.py::estimate

For a 6-step run with a 6,000-token prefix, the model receives about 53,000 input tokens, of which 36,000 are the same prefix sent six times. With Claude Sonnet 5's prices that run costs about $0.12; with prompt caching (the prefix written once and read five times) about $0.07; and on Claude Haiku 4.5 with caching about $0.04. Run `./course.sh python ch29_costs.py` to see the breakdown, then change the numbers to match your own agent's traces (Chapter 28).

Latency has the same structure. Each step pays the time to the first token plus the time to generate its output, and the steps run one after another. Output tokens are the slow part: a step that writes 1,000 tokens takes far longer than one that writes 50. A longer history also raises the time to the first token, which is why caching helps latency as well as cost.

## 29.3 The levers

Table: Performance levers
| Lever | Saves | Cost to you | Chapter |
| --- | --- | --- | --- |
| Prompt caching | Up to about 90% of the repeated prefix's input cost, and time to first token | Almost nothing: keep the prefix stable | 16 |
| Trimming and compaction | Input tokens from old tool results and turns | Some risk of losing detail | 16 |
| Routing to a smaller model | Half or more of the price per token on easy steps | A router, and evaluation to prove quality holds | 20 |
| Lower `effort` or less thinking | Output tokens and time on routine steps | Quality on hard steps, if overused | 4 |
| Fewer steps: better tools and prompts | Whole model calls | Design work | 2, 3 |
| Parallel tool calls | Wall time within a step | Care with shared state | 7 |
| Caching tool results | Slow external calls | Staleness to manage | 7, 16 |
| Batch API | Half the price of work that can wait | Results in minutes to hours | 27 |
| Streaming | Perceived latency | None | 30 |

Each lever shrinks one term of the model in section 29.1, so measure first and pull the lever for the biggest term. Then change one thing and measure again **on your evaluation suite**. A lever that saves 40% of the cost but loses 10% of the successes may raise the cost per successful task. That's the only number to compare (Chapter 20).

## 29.4 Budgets in code

A budget in a prompt ("be concise") is a wish. A budget in code is a limit:

@@code ch29_costs.py::request_budget,DailyBudget

- **Per request:** `request_budget` is a `should_stop` hook for the Chapter 4 loop. The loop checks it after every step and stops before a runaway run overspends, returning a clear reason instead of an answer.
- **Per user per day:** `DailyBudget` refuses new runs once a user has spent their allowance, and charges each run's actual cost when it ends. One user with a script can't spend the whole team's budget.
- **Per job:** long-running jobs carry their own budget (exercise 19.5).
- **Alerts:** cost per successful run has an alert threshold (section 28.11), so a change that doubles it pages someone before the invoice does.

## 29.5 Performance experiments: finding the knee

The model in section 29.1 describes one task. Under load, the question changes: how many tasks can the agent run at once before it stops getting faster and starts getting slower? Every system has a **knee**, the point where adding requests in flight stops buying throughput and starts buying queueing. You find it with an experiment: run the agent at 1, 2, 4, 8 and 16 tasks in flight and measure each level.

At each level, measure:

- **Throughput and goodput:** tasks finished per second, and tasks that *succeeded* per second. They differ once tasks start failing.
- **Latency percentiles:** p50 (the median), p95 and p99. The tail is what users complain about.
- **Tokens per task and steps per task:** if they change with load, the agent is behaving differently, not only waiting longer.
- **Model, tool, retrieval and queueing time per task:** the terms of the latency model, so you can see which one grows.
- **Cache hit rate:** the share of input tokens read from the prompt cache.
- **Cost per successful task and success rate under load:** a system that stays fast by failing half its tasks hasn't scaled.

`experiment` runs the sweep. Each level gets a fresh `Backend`: the model's concurrency slots (a provider limit, or your gateway's) and a fresh prompt cache.

@@code ch29_perf.py::experiment

This is a *closed-loop* test: a fixed number of workers, each starting its next task as soon as the last one ends. That's the right design here because concurrency is the knob you're turning. Little's law (section 29.7) links the three numbers: tasks in flight = throughput × average latency. So the sweep traces the throughput curve directly, and the knee is where it bends. Queueing isn't hidden: the wait for a model slot happens inside each task and is measured. When you want to know what users feel at a given *arrival rate*, for example your forecast peak, use the open-loop test in section 29.6 instead.

The waiting happens in `Backend.slot`, which every model call goes through. It yields the time spent waiting, and gives up with `QueueTimeout` (what a gateway turns into HTTP 429) when a deadline passes:

@@code ch29_perf.py::Backend.slot,_model_call

`simulated_agent` makes 2–4 model calls with a tool call between each, using `_model_call` for each call. A call's time is the time to the first token plus output tokens times decode speed, and a cached prompt halves the time to the first token. Of all calls, 3% time out after 4 seconds, holding their slot, and are retried. A task that has waited 10 seconds in total for slots gives up. Two details matter when you read the numbers:

- **Common random numbers.** Task *i* draws the same random numbers at every level: the same questions, steps, output lengths and timeouts. Differences between rows come from concurrency, not luck.
- **A scaled clock.** The demo runs 100 times faster than real time (`scale=0.01`) so the whole sweep takes seconds, and reports every time as if it had run at full length. Timer overshoot is scaled up too, so orchestration reads a little high, and rows at high concurrency vary a little from run to run.


Read it from the top:

- **Up to 4 in flight, the agent scales perfectly.** Throughput doubles with each level (0.16, 0.32, 0.64 tasks a second) while p50 stays at 5.7 seconds and queueing is a few milliseconds. Little's law checks out: one task in flight at 0.16 tasks a second means about 6 seconds per task on average, a little above the median because of the slow tail. Tokens, steps and model time are the same in every row: that's the common random numbers at work.
- **At 8 the knee has passed.** Throughput barely moves (0.64 to 0.68) but p50 doubles to 11.3 seconds. Model time per task hasn't changed; the task now waits about 5 seconds for slots. Little's law again: 8 in flight at 0.68 a second is about 12 seconds per task. Four slots can serve only four calls at once, so the extra four tasks can only queue. The median task's breakdown shows it: 3.6 of its 11.3 seconds are queueing.
- **The knee is at the number of model slots.** `knee` picks the lowest concurrency that reaches 90% of the best goodput: 4. The limiting resource is the model's concurrency, not your code, your tools or your retrieval, whose times stay flat.
- **The cache hit rate falls with concurrency** (86% to 74%). More tasks start before anyone has written the shared prefix to the cache, and tasks that give up early never reach the later calls that reuse their whole history. In production a third effect joins them: a cache entry can expire while a task waits in a queue. Lower hit rates mean more input cost and a slower first token, so load makes each task more expensive as well as slower.
- **At 16, throughput lies and goodput tells the truth.** Throughput rises to 1.03 tasks a second, the best in the table. But only 40% of tasks succeed: the rest waited 10 seconds for slots and gave up, which is fast. Goodput falls to 0.41, below its value at 4 in flight. Tokens and steps per task drop because failed tasks stopped early, and cost per successful task more than doubles, to $0.0655, because the failed tasks' spend is spread over fewer successes.
- **Cost per success is lowest at the knee.** It falls from $0.0309 to $0.0288 between 1 and 4 in flight because the $2-an-hour infrastructure is spread over more tasks, then rises again as the cache hit rate drops and tasks fail.

:::tip Goodput, not throughput
Judge a level by the tasks that succeeded. Failures that come back fast make raw throughput look better exactly when the system is overloaded. That's why `knee` uses goodput.
:::

@@code ch29_perf.py::_TimedMessages.create

Tool calls are timed the same way and split into tool and retrieval by name, so a real run fills in the same table and the same latency breakdown. Exercise 29.6 runs it at 1, 2 and 4 in flight. With no `model_slots`, the knee comes from wherever the real limit is: the provider's rate limits (429 errors become failed tasks), your network or your machine. Pass `model_slots=2` to see the knee a client-side limit creates. A real sweep costs money: start with a few tasks per level, and use 10 times the concurrency or more once the harness works, because the last tasks of a level run with fewer workers busy.

Then act on the results:

- **Set a concurrency cap at the knee.** Let your gateway run that many tasks at once, queue a few more with a deadline and refuse the rest quickly (section 29.7). Running past the knee buys latency and failures, not throughput.
- **Plan capacity from goodput at the knee.** It's what one deployment can deliver. Divide your forecast peak by it to size the deployment (section 29.7).
- **Name the limiting resource and raise it deliberately.** If it's the provider's rate limit, ask for more or cut tokens per task with the levers in section 29.3. If it's your own slots, add workers and sweep again.
- **Set SLOs from the knee.** p95 latency and cost per successful task at the knee are realistic targets for the SLOs in Chapter 28. Rerun the sweep after every model, prompt or tool change: a knee that moves left is a regression.

## 29.6 Load testing at an arrival rate

The sweep tells you how many tasks the agent can run at once. A load test tells you what users feel at a given arrival rate. Agents are unusually sensitive to load: each request makes several sequential model calls, and model providers enforce rate limits.

@@code ch29_loadtest.py::fake_agent~,open_loop,load_test~

`fake_agent` simulates a run of 2–4 model calls so you can test the harness itself for free. Replace it with a real agent call once the harness works.

Two decisions in `open_loop` make the numbers honest:

- **Requests arrive on a schedule, not when the previous one finishes.** Real users don't wait for each other. A closed-loop test (`load_test`: 50 users, each sending the next question after the last answer) quietly sends **less** traffic as the agent slows down, so it measures a lighter load than the one you asked for. That's fine in the sweep of section 29.5, which reports the throughput it achieved; it's wrong when you want to know what happens at a forecast rate. `open_loop` sends requests at random times averaging `rate` per second, whatever happens.
- **Latency is measured from when the request was supposed to be sent**, including any wait for a free slot. If the clock starts only when work begins, a slow system hides its own queue from the measurement. Load testers call this *coordinated omission*.

With the fake agent and 20 slots, capacity is about 9 requests per second. At 4 and 8 per second, p50 stays around 2.5 seconds. At 12 per second the queue grows and p50 jumps to about 6 seconds, while a clock started after the slot still reports about 2.5: the queue is invisible to it (exercise 29.1).

When you read results, focus on:

- **p95 and max, not the mean.** The slowest 5% of users are the ones who complain.
- **Errors under load**: rate limits (429) and timeouts appear only when you push.
- **Throughput versus offered load**: while throughput keeps up with the offered rate, you're under capacity. When throughput flattens and latency climbs, you've found the limit, usually the provider's rate limit or your own `max_in_flight`.

## 29.7 Capacity planning

Two formulas answer most capacity questions:

@@code ch29_costs.py::concurrency_needed,rate_limited_capacity

- **Little's law.** The number of requests in flight equals the arrival rate times the time each request takes. At 10 requests a second and 8 seconds each, you need room for 80 at once: worker slots, connections and memory. Compare that with the knee from section 29.5: if one deployment's knee is at 20 in flight, you need at least four.
- **Rate limits.** Providers limit requests and tokens per minute. An agent run makes several calls and sends tens of thousands of tokens, so the token limit usually binds first. With limits of 4,000 requests and 2 million tokens a minute, 6-call runs of 60,000 tokens each fit about 33 times a minute, however many requests the limit on calls would allow.

When demand exceeds capacity, fail gracefully: queue with a limit, answer "busy, try again shortly" (HTTP 429 or 503) rather than timing out, and give interactive users priority over background jobs. Then raise capacity with the levers in section 29.3, which cut tokens per run, or by asking the provider for higher limits.

## 29.8 A reproducible benchmark for architecture decisions

The sweep in section 29.5 asks how one agent behaves as load rises. Before that comes a bigger decision: which design, which model, how much context. `ch29_benchmark.py` answers those questions the same way every time, so you can rerun it when a model or a prompt changes and compare like with like. It runs four experiments on the Chapter 27 questions that have known answers:

- **E1. Architecture:** a fixed workflow (write the SQL, run it, phrase the answer), one agent (the Chapter 8 analyst) and a lead with parallel workers (Chapter 11).
- **E2. Tool execution:** the agent's tool calls in one turn run one after another, or at the same time.
- **E3. Model and context:** a small and a large model, each with a short system prompt and with 8,000 more tokens of it.
- **E4. Load:** 1 to 16 tasks in flight sharing four model slots, a mix of one-part and multi-part questions, without and with 10% transient tool failures.

@@code ch29_benchmark.py::task

Four choices make the numbers worth trusting:

- **Success means a right answer.** `task` checks every answer against the database with Chapter 27's `contains_value`. An agent that stops politely with the wrong number has failed.
- **The same dice for every configuration.** Each task draws its random numbers from a key made of the experiment, the question and the repetition, never the configuration (common random numbers, as in section 29.5). When two rows differ, the configuration made the difference, not luck.
- **Everything to rerun it is written down.** Each run writes `config.json` (the commit, model ids, a hash of the prompts and tools, a fingerprint of the data, the seed, repetitions, warm-up, tool latency, hardware and Python version), `raw.jsonl` with one line per task and `summary.md` with the tables.
- **Warm-up and repetitions.** The first task of each configuration is run and thrown away, and every question runs several times (five on the simulator, three on a real model). Success comes with a 95% confidence interval (the measurement interlude).

There are three backends. `--backend claude` and `--backend local` measure a real model: its accuracy, its latency and, for Claude, its price. The default is a **simulator**: a stand-in model whose latency and error rates are the assumptions written at the top of the file (`SIM_MODELS`), driven by a virtual clock. Sleeping advances the clock instead of waiting, calls made at the same time start together, and the load experiment replays each task's recorded timeline through an exact event simulation of the shared model slots. A full run takes about two seconds and gives the same numbers on every machine. It shows the mechanics of each design exactly, and nothing about how good a real model is. Run both, and trust each for what it measures.

**Reading a benchmark to make a decision.** Go through the results in this order:

1. Drop every configuration whose success is below what you need, judging by the confidence interval, not the point estimate.
2. Of the rest, prefer the simplest design, then the lowest cost per successful task.
3. Check its p95 at your expected concurrency against your SLO (section 28.10).
4. Set your concurrency limit at the knee.

A difference smaller than the overlap of two intervals isn't a difference: add tasks before you decide.

**Then run it on your model.** The simulator's error rates and latencies are assumptions; a real model replaces them with measurements. Start small: `--backend claude --quick` runs one repetition of eight questions per configuration for about a dollar, most of it the long-context rows of E3. A full run costs about ten dollars and gives intervals narrow enough to decide with; `--budget` stops it at the amount you set. `--backend local` costs nothing but time. Keep each run's folder: the next time a model, a prompt or a price changes, run the same command and compare.

## 29.9 Agent economics: from cost per task to payback

Everything so far measures the agent against itself: this design against that one, this model against a cheaper one. The person who pays for it asks a different question: is it worth building? To answer it, you turn the costs you measured into a **business case**: what the agent costs a month, what it saves against the way the work is done today, and how long it takes to earn back what it cost to build.

Two rules keep a business case honest. First, compare the agent with the **human baseline**, the people who do the work now, not with zero. Against zero, the support agent looks either like a $4,600 monthly bill or like a $72,000 saving, depending on which half you forget; both are wrong. Second, every input is an assumption until you've measured it. A business case is a hypothesis with numbers in it, and the launch is the experiment that tests it.

These are the metrics, and where this book's code and telemetry give you each number:

Table: Agent economics metrics {#t:econ-metrics}
| Metric | Formula | Where the number comes from |
| --- | --- | --- |
| Token cost | Input tokens × input price + output tokens × output price | Token counts on the `chat` spans (Chapter 28); `PRICES` in `ch20_router.py`; `token_cost`, or `cost_per_task` in section 29.1 for caching |
| Tool cost | Paid tool and retrieval calls × their price | `execute_tool` spans; your API invoices |
| Infrastructure cost | Servers, gateway, tracing and stores, per month | Your cloud bill |
| Cost per task | (Tokens + tools + infrastructure + upkeep) per month ÷ tasks | The rows above, plus the people who keep the agent working |
| Cost per successful task | The same total ÷ tasks the agent completed correctly | Success from your evaluation suite and continuous evaluation (Chapter 27); `$ per success` in section 29.8 |
| Cost per user per month | The same total ÷ distinct users a month | User ids on traces; compare it with a per-seat price |
| Automation rate | Tasks the agent closed with no person ÷ all tasks | Handoff spans and the handoff queue |
| Escalation rate | Tasks handed to a person ÷ all tasks | The handoff queue; here, 1 − automation rate |
| Failure rate | Tasks the agent closed wrongly ÷ all tasks | Continuous evaluation's graded sample (section 27.8), complaints, reversed refunds |
| Failure cost | Failures × the average cost of one | Finance: write-offs, credits, rework |
| Human minutes saved | Baseline minutes − takeover minutes − review minutes | A time study of today's process; handling times in the handoff queue |
| Payback period | Build cost ÷ net monthly saving | The business case |

Cost per successful task is the one to watch among the per-unit costs: the escalated and the failed tasks were paid for too, and bought nothing. Automation, escalation and failure rates are the ones to watch among the rates, because they decide how much of the people's work actually goes away.

What to notice:

- **Tokens are 0.4% of the cost.** The model bill, $167 a month, is the smallest line but one. The people who take over escalated conversations cost 138 times as much, and upkeep 24 times as much. A team that spends a month halving the token bill saves $84 a month. The same month spent raising automation by one point saves about $700 a month.
- **Cost per task is dominated by fixed costs.** $0.255 per conversation, of which about $0.01 is tokens and $0.22 is upkeep. Double the volume and it nearly halves; this is why a small pilot always looks expensive per task.
- **Cost per successful task is half again as much** ($0.392): only 65% of conversations are closed correctly by the agent, and the rest were paid for too.
- **The baseline isn't zero, and isn't perfect.** People alone cost $72,000 in time plus $9,000 in their own 2% of mistakes.
- **Payback is 3.8 months**: $150,000 to build, $39,059 a month net.

**Break-even** is where the monthly net reaches zero, and `break_even` finds it by bisection on one assumption. With failures held at 3%, the agent must close at least 13% of conversations to cost less than people alone; below that it's a cost, however good the demo. With automation held at 68%, the failure rate can rise to 11.7% before the agent stops paying. That second number is the one to put on a dashboard.

The assumption that moves payback most is about people, not the agent: how long a person takes per conversation today. Most teams guess it. Time a sample of real conversations before you present the case. Automation rate comes next, and it's the one the agent can change: measure it in a pilot before you promise it. The model's price per turn moves payback by less than a hundredth of a month.

Read the failure row with care. Twenty percent of a 3% failure rate is only 0.6 points, but failure rates don't move by 20%: one prompt change can multiply them, as release 1.3 did with missed handoffs in the case study. That's why the break-even failure rate belongs next to the sensitivity table.

**The failure-cost term.** A model call costs a third of a cent. A wrong $60 refund costs $60 plus the time to reverse it; a missed handoff can cost a customer. In this case, one failure costs more than 2,000 times the tokens of one conversation, and failures as a whole cost 80 times the token bill. So a cheaper model that fails even slightly more often makes the business case worse: exercise 29.8 finds that Claude Haiku 4.5's $81-a-month token saving is wiped out by 0.02 more percentage points of failures. Spend your effort where the failure cost is: rules in code for refunds (Chapter 22), handoffs that can't be talked out of (the case study), and the release gate (section 27.7).

Every number in `Assumptions` except the model cost is a guess until production replaces it. Present the case with its break-even points and its sensitivity, not a single payback figure, and say which assumptions you'll measure first. After launch, rebuild the case every month from actuals: volume, automation, escalation and failure rates from the handoff queue and continuous evaluation, token and tool cost from traces. A case that no longer pays shows up in a month, not at the annual review.
:::

This is educational code. A production business case adds a ramp-up (automation starts lower and rises over months), volume growth, confidence intervals on every measured rate (the measurement interlude), the cost of re-evaluating after each model upgrade, and discounting for anything that pays back over more than a year. Your finance team has a template; bring them these numbers.

## Common mistakes

- **Guessing where the time goes** instead of breaking it into model, tool, retrieval, orchestration, queueing and serialization from traces.
- **Leaving human review, retries and infrastructure out of the cost model**, so the model bill looks like the whole bill.
- **Estimating cost from the system prompt** instead of the whole growing history.
- **Optimizing cost per call** instead of cost per successful task.
- **A business case against zero, with one payback figure**, instead of against the human baseline with its break-even points and sensitivity; and leaving out failure cost, which can dwarf the token bill.
- **Budgets in the prompt** instead of in code.
- **Reading throughput instead of goodput**, so fast failures look like extra capacity.
- **Running past the knee** and calling the result capacity: more in flight buys only queueing.
- **Comparing load levels with different random draws or too few tasks**, so noise looks like a trend.
- **Measuring latency after queueing**, which hides what users feel.
- **Only testing one user at a time.**
- **Ignoring token rate limits**, so capacity runs out long before the request limit.
- **No per-request cost tracking**, so a prompt change silently doubles the bill.

## Key takeaways

**Architect's takeaway:** Know your cost drivers: token cost and latency often pull in opposite directions.

- Latency is model + tool + retrieval + orchestration + queueing + serialization; cost per task is model + tools + retrieval + infrastructure + retries + human review. Measure every term from traces, and attack the biggest.
- Each step resends the whole conversation, so cost and latency grow faster than the number of steps; output tokens dominate latency.
- Pull the levers in order of payoff: caching, trimming, routing, effort, fewer steps, parallel tools, batching, streaming.
- Judge every change by cost per successful task on your evaluation suite.
- Make the business case against the human baseline, not zero: tokens are often a small line next to takeovers, upkeep and failures. State every assumption, find the break-even automation and failure rates, rank assumptions by their effect on payback, and rebuild the case monthly from actuals.
- Choose a design with a reproducible benchmark: answers checked against the data, the same random numbers for every configuration, everything needed to rerun it recorded, and success read with its confidence interval.
- Enforce budgets in code (per request, per user and per job) and alert on cost per success.
- Sweep concurrency to find the knee: throughput stops rising, queueing takes over latency, the cache hit rate falls and goodput drops as tasks time out. Cap concurrency at the knee and name the limiting resource.
- Load-test open-loop at your forecast rate, measure from arrival and watch p95 and errors.
- Plan capacity with Little's law, the knee and token rate limits, and fail gracefully at the limit.

The agent is now measured, observed and economical, and you know its limits. Chapter 30 ships it as a service other people and programs can call, where the concurrency cap, rate limits and budgets from this chapter become the service's own limits.
