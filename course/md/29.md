# Chapter 29: Agent Performance Engineering: Latency, Throughput and Cost

In testing, your agent answers in 3 seconds for a cent. In production the same agent takes 30 seconds and costs a dollar: conversations run longer, runs take more steps, contexts grow, a hundred users arrive at once, and a provider rate limit nobody planned for starts returning errors. The code is the same in both places; what changed is the load, and testing never put the agent under it.

Chapter 28 showed you where each run's time and money go. Now you measure before you deploy, with the discipline you'd use for any service: a model of the costs, experiments under load, and limits set from the measurements. The numbers become Chapter 30's deployment settings (section 30.5) and the targets for Chapter 28's SLOs. Everything runs against a free simulator first, then a real model.

**What you'll build:** a latency model and a cost model you compute from a trace, per-request and per-user budgets enforced in code, a concurrency sweep that finds the knee where an agent stops scaling, an open-loop load test and a capacity plan from latency and rate limits.

**You are here:** Model and Agent runtime (performance and cost) in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (agent loop), Chapter 16 (prompt caching), Chapter 27 (evaluation), Chapter 28 (traces).

## Learning objectives

By the end of this chapter you can:

- Write an agent's latency and cost per task as sums of measurable terms, and choose levers by cost per successful task.
- Enforce budgets per request and per user in code.
- Find the knee with a concurrency sweep, load-test open-loop and plan capacity with Little's law and rate limits.
- Choose a design with a reproducible benchmark and its confidence intervals.
- Build a business case against the human baseline, with break-even points, payback and sensitivity.

**In the real world.** In LangChain's survey of 1,340 practitioners (late 2025), latency was the second most common barrier to putting agents into production, named by about 20%, after quality. Providers have responded with prompt caching, cheap small models, half-price batch APIs and effort settings. None of them helps until you've measured where your agent actually spends.

## 29.1 The agent performance model

Every agent task, however clever, spends its time and money in a few places. Write them down as two sums:

```
Total latency = model + tool + retrieval + orchestration + queueing + serialization
Cost per task = model + tools + retrieval + infrastructure + retries + human review
```

Each term is measurable and has its own levers. When a task is slow or expensive, the sums tell you which term to attack first.

@@image d-0abd471f49e3.png

Figure: Where the time goes in one agent task
Alt: A task arrives and pays orchestration and serialization. Each step, repeated, waits for a slot, makes a model call (first token, then output), runs a tool or retrieval and pays orchestration and serialization again. The last step waits for a slot and makes the final model call that produces the answer.

Each latency term comes from Chapter 28's traces. **Model** time is the `chat` spans (time to first token plus output time, network included). **Tool** and **retrieval** are both `execute_tool` spans, split by `is_retrieval` because fetching data scales with the size of the data. **Orchestration** (your loop, guards, prompt assembly, any untraced proxy) is whatever's left of the total. **Queueing** is the wait for a slot or a rate limit; wrap it in a `queue` span, or it hides inside the model term and you blame the model. **Serialization** comes from `serialize` spans, or `measure_serialization` times one conversation and multiplies by the steps.

@@code ch29_perf.py::latency_model

`latency_model` takes a trace's spans or a dictionary of components and returns the six terms and their total. The terms add up only when steps run one after another; if orchestration comes out negative, spans overlapped (parallel tool calls, section 29.3), so read the trace instead.

Cost works the same way. Model cost is tokens times price, with cache reads at 10% of the input price and writes at 125% (Chapter 16). Infrastructure is servers' hourly cost divided by tasks finished per hour, so an idle server makes every task dearer. Retries are calls you paid for and threw away. Human review (share reviewed × minutes × rate) is the term teams forget, and often one of the largest.

@@code ch29_perf.py::cost_per_task

Take a 6-step run (section 29.2 shows where its tokens come from): 53,100 input tokens on Claude Sonnet 5, 30,000 read from the cache and 6,000 written to it, and 1,800 output tokens. Add two free tool calls, three $0.002 retrieval calls, one retry, a $2-an-hour server finishing 600 tasks an hour, and a person spending 3 minutes at $60 an hour on 2% of tasks:

```

              cache_write_tokens=6_000, model="claude-sonnet-5", model_calls=6,

The task costs about $0.155. The model is 47% of it, but reviewing one task in 50 is 39%, almost as much as all the tokens. Infrastructure is 2% because the server is busy; at 60 tasks an hour it would be ten times as much.

Under load you'll also read **throughput** (tasks finished per second), **goodput** (tasks that *succeeded* per second) and the capacity limits that cap them. Sections 29.5 to 29.7 measure each.

## 29.2 Where the time and money go

The model term dominates most agents, and it grows faster than you'd expect. Each model call sends the **whole** conversation so far: the system prompt and tool definitions (the prefix), the question, and every earlier reply and tool result.

@@code ch29_costs.py::estimate

For a 6-step run with a 6,000-token prefix, the model receives about 53,000 input tokens, 36,000 of them the same prefix sent six times. At Claude Sonnet 5's prices that run costs about $0.12; with prompt caching (prefix written once, read five times) about $0.07; on Claude Haiku 4.5 with caching about $0.04. Run `./course.sh python ch29_costs.py` for the breakdown, then plug in your own numbers.

Latency has the same structure, and output tokens are the slow part: a step that writes 1,000 tokens takes far longer than one that writes 50. A longer history also raises time to first token, so caching helps latency as well as cost.

## 29.3 The levers

Table: Performance levers
| Lever | Saves | Cost to you | Chapter |
| --- | --- | --- | --- |
| Prompt caching | Up to about 90% of the prefix's input cost, and time to first token | Keep the prefix stable | 16 |
| Trimming and compaction | Input tokens from old tool results and turns | Some risk of losing detail | 16 |
| Routing to a smaller model | Half or more of the price on easy steps | A router, and evals to prove quality holds | 20 |
| Lower `effort` or less thinking | Output tokens and time on routine steps | Quality on hard steps, if overused | 4 |
| Fewer steps: better tools and prompts | Whole model calls | Design work | 2, 3 |
| Parallel tool calls | Wall time within a step | Care with shared state | 7 |
| Caching tool results | Slow external calls | Staleness to manage | 7, 16 |
| Batch API | Half the price of work that can wait | Results in minutes to hours | 27 |
| Streaming | Perceived latency | None | 30 |

Each lever shrinks one term of section 29.1's model, so pull the lever for the biggest term, one change at a time, and measure again **on your evaluation suite**. A lever that saves 40% of the cost but loses 10% of the successes may raise the cost per successful task, the only number to compare (Chapter 20).

## 29.5 Performance experiments: finding the knee

Under load the question becomes: how many tasks can the agent run at once? If you come from web services, you'll look for the usual suspects first (CPU, connection pools, the database), and for an agent they rarely matter; the model's concurrency limit usually is the whole story. Every system has a **knee**, the point where adding requests in flight stops buying throughput and starts buying queueing. To find it, run the agent at 1, 2, 4, 8 and 16 tasks in flight and measure each level.

At each level, measure throughput and goodput, p50/p95/p99 latency (section 27.6), tokens and steps per task, the latency terms, the cache hit rate, and cost per successful task with the success rate. A system that stays fast by failing half its tasks hasn't scaled.

`experiment` runs the sweep. Each level gets a fresh `Backend`: the model's concurrency slots (a provider limit, or your gateway's) and a fresh prompt cache.

This is a *closed-loop* test: a fixed number of workers, each starting its next task when the last ends, which suits a sweep because concurrency is the knob. **Little's law** (section 29.7) links the numbers: tasks in flight = throughput × average latency. For what users feel at a given *arrival rate*, use section 29.6's open-loop test.

Every model call waits in `Backend.slot`, which records the wait and raises `QueueTimeout` (a gateway's HTTP 429) past a deadline:

`simulated_agent` makes 2–4 model calls with a tool call between each; a cached prompt halves time to first token, 3% of calls time out after 4 seconds and are retried, and a task that has waited 10 seconds in total for slots gives up. Task *i* draws the same random numbers at every level (**common random numbers**), so differences between rows come from concurrency alone. Median task at concurrency 8, in ms:
  model 7,539 + tool 35 + retr 0 + orch 163 + queue 3,576 + serial 4 = 11,317 ms
Knee at 4 in flight: 0.64 good tasks/s, p95 10.5 s; at 16: 0.41/s, p95 17.7 s, 40% ok.
```

Read it from the top:

- **Up to 4 in flight, the agent scales perfectly.** Throughput doubles with each level while p50 stays at 5.7 seconds. Little's law checks out: one in flight at 0.16 tasks a second is about 6 seconds per task.
- **At 8 the knee has passed.** Throughput barely moves (0.64 to 0.68) but p50 doubles to 11.3 seconds. Four slots serve four calls at once, so the extra tasks can only queue: 3.6 of the median task's 11.3 seconds are queueing. Little's law agrees: 8 in flight at 0.68 a second is about 12 seconds per task.
- **The knee is at the number of model slots.** `knee` picks the lowest concurrency reaching 90% of the best goodput: 4. The model's concurrency is the limit: tool and retrieval times stay flat.
- **The cache hit rate falls with load** (86% to 74%): more tasks start before the shared prefix is cached, and tasks that give up never reuse their history. In production, a cache entry can also expire while a task waits in the queue. Load makes each task dearer as well as slower.
- **At 16, throughput lies and goodput tells the truth.** Throughput hits its best, 1.03 tasks a second, but only 40% succeed: the rest gave up after 10 seconds of waiting, which is fast. Goodput falls to 0.41, below its value at 4. Tokens and steps per task drop only because failed tasks stopped early, and cost per success more than doubles to $0.0655.
- **Cost per success is lowest at the knee** ($0.0288), where the $2-an-hour infrastructure is spread over the most successful tasks.

:::tip Goodput, not throughput
Judge a level by the tasks that succeeded. Failures that come back fast make raw throughput look better exactly when the system is overloaded. That's why `knee` uses goodput.
:::

To sweep a real model, pass `real_agent` instead of `simulated_agent`. It runs the Chapter 8 SQL analyst through the Chapter 4 loop, with the model client wrapped so every call waits for a slot and records its time and cache tokens:

@@code ch29_perf.py::_TimedMessages.create

A real run fills in the same table (exercise 29.6). With no `model_slots`, the knee comes from the real limit: provider rate limits (429s become failed tasks), your network or your machine. A real sweep costs money, so start with a few tasks per level, then use 10 times the concurrency or more, because a level's last tasks run with fewer workers busy.

Then act on the results.

- **Cap concurrency at the knee.** Run that many tasks at once, queue a few more with a deadline and refuse the rest quickly. Past the knee you buy only latency and failures.
- **Plan capacity from goodput at the knee:** divide your forecast peak by it (section 29.7).
- **Raise the limiting resource deliberately:** ask the provider for more, cut tokens per task (section 29.3) or add workers, then sweep again.
- **Set SLOs from the knee.** Its p95 latency and cost per success are realistic targets for Chapter 28's SLOs. Rerun the sweep after every change: a knee that moves left is a regression.

## 29.6 Load testing at an arrival rate

The sweep tells you how many tasks the agent can run at once. A load test tells you what users feel at a given arrival rate. Agents are unusually sensitive to load, because each request makes several sequential model calls against a rate-limited provider.

@@code ch29_loadtest.py::fake_agent~,open_loop,load_test~

`fake_agent` simulates 2–4 model calls so you can test the harness for free. What keeps `open_loop`'s numbers honest is how it sends requests and where it starts the clock:

- **Requests arrive on a schedule, not when the previous one finishes.** Real users don't wait for each other. A closed-loop test (`load_test`: 50 users, each asking again after an answer) quietly sends **less** traffic as the agent slows, which is fine for a sweep and wrong for a forecast rate. `open_loop` sends requests at random times averaging `rate` per second, whatever happens.
- **Latency is measured from when the request was due**, including any wait for a slot. Start the clock when work begins and a slow system hides its own queue. Load testers call this *coordinated omission*.

**The conditions here.** `fake_agent` stands in for the model with 2–4 random waits on a real `asyncio` clock, and requests arrive open-loop at random times for 20 seconds per rate, each rate run once. No model, tokens, cache or cost is modelled, and the report has no intervals. The figures below are illustrative: they show how the harness behaves, not how any agent performs. The full conditions are in `benchmarks/README.md` in the course kit.

With the fake agent and 20 slots, capacity is about 9 requests per second. At 4 and 8 per second, p50 stays around 2.5 seconds. At 12 the queue grows and p50 jumps to about 6 seconds, while a clock started after the slot still reports about 2.5 (exercise 29.1).

Read p95 and max, because the mean hides the tail. Watch for errors that appear only under load, such as 429s and timeouts. While throughput keeps up with the offered rate, you're under capacity; when it flattens and latency climbs, you've hit the limit, usually the provider's rate limit or your `max_in_flight`. The p99 at your forecast rate, plus a margin, is a sound request timeout.

## 29.7 Capacity planning

Most capacity questions come down to Little's law and the provider's rate limits:

@@code ch29_costs.py::concurrency_needed,rate_limited_capacity

- **Little's law.** Requests in flight equal the arrival rate times the time each takes. At 10 requests a second and 8 seconds each, you need room for 80 at once: worker slots, connections and memory. If one deployment's knee (section 29.5) is at 20 in flight, you need at least four.
- **Rate limits.** Providers limit requests and tokens per minute. An agent run makes several calls with tens of thousands of tokens, so the token limit usually binds first. With 4,000 requests and 2 million tokens a minute, 6-call runs of 60,000 tokens fit about 33 times a minute, however many the request limit would allow.

When demand exceeds capacity, fail gracefully: queue with a limit, answer "busy, try again shortly" (HTTP 429 or 503) rather than timing out, and put interactive users ahead of background jobs. Then cut tokens per run (section 29.3) or ask for higher limits.

Before load comes a bigger decision: which design, which model, how much context. `ch29_benchmark.py` answers those the same way every time, so you can rerun it after any change and compare like with like. It runs four experiments on Chapter 27's known-answer questions:

How the benchmark is built is what makes its numbers worth trusting. **Success means a right answer**, checked against the database with Chapter 27's `contains_value`. **Every configuration gets the same dice** (common random numbers, keyed on experiment, question and repetition). **Everything to rerun it is written down**: `config.json` (commit, model ids, hashes of prompts, tools and data, seed, hardware), `raw.jsonl` with one line per task and `summary.md`. **Reading a benchmark to make a decision.** Go through the results in this order:

1. Drop every configuration whose success is below what you need, judging by the confidence interval, not the point estimate.
2. Of the rest, prefer the simplest design, then the lowest cost per successful task.
3. Check its p95 at your expected concurrency against your SLO (section 28.10).
4. Set your concurrency limit at the knee.

If two intervals overlap by more than the difference between them, you can't tell the configurations apart yet, so add tasks before you decide.

:::warn Illustrative numbers, not production targets
Thresholds in these chapters and the case study, such as an 8-second p95, $0.05 per task or 85% success, were chosen to make the demos readable. None is a target for your agent. Set yours from measurements on your model, data and traffic, using the table in section 30.5.
:::

**Then run it on your model.** `--backend claude --quick` runs one repetition of eight one-part and three multi-part questions per configuration for about a dollar, most of it E3's long-context rows; a full run about ten, with intervals narrow enough to decide with, and `--budget` caps it. `--backend local` costs nothing but time. Keep each run's folder to compare against after the next change.

## 29.9 Agent economics: from cost per task to payback

The person paying for the agent asks a different question: is it worth building? A **business case** answers it: what the agent costs a month, what it saves against how the work is done today, and how long it takes to earn back its build cost.

To keep it honest, compare the agent with the **human baseline**, the people who do the work now, not with zero: against zero, the support agent looks like either a $4,600 monthly bill or a $72,000 saving, and both are wrong. And treat every input as an assumption until measured; the launch is the experiment that tests it.

Here are the metrics, and where this book's code and telemetry give you each number:

Table: Agent economics metrics {#t:econ-metrics}
| Metric | Formula | Where the number comes from |
| --- | --- | --- |
| Token, tool and infrastructure cost | Tokens × price; paid calls × price; servers and stores per month | `chat` and `execute_tool` spans (Chapter 28), `PRICES` in `ch20_router.py`, your invoices and cloud bill |
| Cost per task | (Tokens + tools + infrastructure + upkeep) per month ÷ tasks | The rows above, plus the people who keep the agent working |
| Cost per successful task | The same total ÷ tasks the agent completed correctly | Success rate from evaluation (Chapter 27); `$ per success` in section 29.8 |
| Cost per user per month | The same total ÷ distinct users a month | User ids on traces |
| Automation rate | Tasks the agent closed with no person ÷ all tasks | Handoff spans and the handoff queue |
| Escalation rate | Tasks handed to a person ÷ all tasks | Here, 1 − automation rate |
| Failure rate | Tasks the agent closed wrongly ÷ all tasks | Continuous evaluation (section 27.8), complaints, reversed refunds |
| Failure cost | Failures × the average cost of one | Finance: write-offs, credits, rework |
| Human minutes saved | Baseline minutes − takeover minutes − review minutes | A time study of today's process |
| Payback period | Build cost ÷ net monthly saving | The business case |

Watch cost per successful task (the scorecard's cost per success, section 27.6), because escalated and failed tasks were paid for too, and the automation, escalation and failure rates, because they decide how much of people's work actually goes away.

What to notice:

- **Tokens are 0.4% of the cost.** Takeovers cost 138 times as much as the $167 model bill, and upkeep 24 times. Halving the token bill saves $84 a month; raising automation by one point saves about $700.
- **Fixed costs dominate cost per task**: of $0.255, about $0.01 is tokens and $0.22 upkeep, which is why a small pilot always looks expensive per task.
- **Cost per successful task is half again as much** ($0.392): the agent closes only 65% of conversations correctly.
- **The baseline isn't zero, and isn't perfect.** People alone cost $72,000 in time plus $9,000 in their own 2% of mistakes.

**Break-even** is where the monthly net reaches zero; `break_even` finds it by bisection on one assumption. With failures at 3%, the agent must close at least 13% of conversations to beat people alone. With automation at 68%, failures can rise to 11.7% before it stops paying. Put that second number on a dashboard, because it's the one a bad release moves.

**Sensitivity.** A single payback figure hides which assumption it rests on. `sensitivity` lowers and raises each assumption by 20%, holding the others, and ranks them by how far payback moves:

The biggest swing is about people: how long a person takes per conversation today. Most teams guess it, so time real conversations first. Automation rate comes next, and it's the one the agent can change, so measure it in a pilot before you promise it. The model's price per turn moves payback by less than a hundredth of a month. Read the failure row with care: failure rates don't move by 20%, they multiply after one bad prompt change (as release 1.3's missed handoffs did in the case study), which is why the break-even failure rate matters.

**The failure-cost term.** A model call costs a third of a cent; one failure, a wrong refund or a missed handoff, costs $25 in these assumptions once you count the credit and the rework. So one failure costs more than 2,000 times one conversation's tokens, and failures cost 80 times the token bill. That's why a cheaper model that fails slightly more often makes the case worse: in exercise 29.8, switching to the simulator's small model saves $81 a month in tokens, and 0.02 more percentage points of failures wipe it out. Spend your effort where the failure cost is: rules in code for refunds (Chapter 22), handoffs that can't be talked out of (the case study) and the release gate (section 27.7).

Present break-even points and sensitivity instead of a single payback figure, and say which assumptions you'll measure first. After launch, rebuild the case monthly from the handoff queue, continuous evaluation and traces, so a case that stops paying shows up within a month.

This is teaching code. A production business case also adds ramp-up, volume growth, confidence intervals on measured rates, re-evaluation after model upgrades and discounting. Your finance team has a template; bring them these numbers.

## Common mistakes

- Guessing where the time goes instead of breaking it down from traces.
- Leaving human review, retries and infrastructure out of the cost model, or estimating from the system prompt instead of the whole growing history.
- Optimizing cost per call instead of cost per successful task.
- A business case against zero, with one payback figure and no failure cost.
- Budgets in the prompt instead of in code.
- Reading throughput instead of goodput, or running past the knee and calling it capacity.
- Measuring latency after queueing, which hides what users feel, or ignoring token rate limits.
- Comparing load levels with different random draws or too few tasks, so noise looks like a trend.

## Before you move on

- **You should understand:** why each step's resent history makes cost grow faster than the step count, and why the knee is read from goodput, not throughput.
- **You should be able to build:** a concurrency sweep whose latency breakdown adds up to its total, and a business case with break-even points and a sensitivity ranking.
- **Prove it:** exercise 29.6 on a real model, then exercise 29.8.
- **Break it on purpose:** start `open_loop`'s clock inside `async with sem` (exercise 29.1) and watch p50 stay near 2.5 seconds at 12 requests a second while the queue grows.
- **Defend this decision:** the concurrency cap per instance, naming the limiting resource and giving p95 and cost per success at the knee, with the conditions they were measured under.

## Key takeaways

**Architect's takeaway:** Measure before you optimize. The biggest cost is rarely the tokens, and the limit is usually the model's concurrency, so find both from data before you change anything.

- Latency and cost are sums of measurable terms; measure each from traces and attack the biggest.
- Judge every lever by cost per successful task on your evaluation suite, and enforce budgets in code.
- Load-test open-loop at your forecast rate, measuring from arrival; plan capacity with Little's law and token rate limits.
- Choose designs with a reproducible benchmark, reading success with its confidence interval.
- Make the business case against the human baseline, with break-even points and sensitivity, and rebuild it monthly from actuals.
