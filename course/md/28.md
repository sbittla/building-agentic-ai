# Chapter 28: AgentOps: Observability, Telemetry and SLOs for Agents

Your dashboards are green. CPU sits at 30%, there hasn't been a server error all week and p95 latency hasn't moved. Meanwhile the agent has been quoting a refund policy that was replaced on Monday, retrying a broken query four times per run and spending ten times what it did last week. The server is fine; the agent is failing its users, and nothing you're watching can tell.

Agent observability follows the chain that matters: the user's goal, the context the agent was given, each model call and its decision, each tool call and its result, and the outcome. Chapter 27's scorecard decides whether a release may ship. Now you watch the released agent with real users, measuring it with the scorecard's definitions (section 27.6). You'll build traces, logs, a failure taxonomy, a dashboard, SLOs and alerts, so you can answer "what happened?" for one run and "how are we doing?" for all of them.

**What you'll build:** OpenTelemetry traces and structured logs for every model call and tool call, run summaries with tokens, cost and latency, a text timeline of one run, a classifier for 12 kinds of agent failure, a one-page production dashboard, agent SLOs with error budgets and alerts, and a join of spans with resource metrics and profiles that explains why a span was slow.

**You are here:** Observability in the agent architecture reference model (section 1.7).

**Prerequisites:** Chapter 4 (tracing), Chapter 27 (evaluation).

## Learning objectives

By the end of this chapter you can:

- Trace model and tool calls with OpenTelemetry, join structured logs to them and keep secrets and personal data out.
- Turn spans into run records with tokens, cost, latency and per-tool error rates.
- Classify failures with a 12-class taxonomy and say which classes traces alone can't see.
- Build a dashboard, and set SLOs with error budgets and alerts on what users feel.
- Go from an alert to a root cause with a repeatable playbook.
- Join spans with resource metrics and profiles to explain why a span was slow.

**In the real world.** Observability is the most widely adopted agent practice. In LangChain's survey of 1,340 practitioners (late 2025), 89% had some form of it and 62% traced individual steps and tool calls; among teams with agents in production, those figures rose to 94% and about 72%. The gap is in using the data: traces nobody summarizes, failures nobody classifies, alerts on server health instead of user outcomes.

A failure can start at any link of the run:

Table: The links in an agent run, and what to record for each
| Link | What to record | Example question it answers |
| --- | --- | --- |
| The request | Id, user or tenant, time, the goal in a few words | Which customers were affected? |

| The outcome | Final status, eval or judge score if graded, user feedback | Are we getting worse? |

A **trace** is one request; a **span** is one named, timed step inside it, with attributes and a parent. Spans answer "why was this slow?" (one tool took 9 seconds) and "why did costs double?" (a prompt change added two steps).

`traces.jsonl` is fine for one developer. In production, use **OpenTelemetry**, the standard almost every observability tool reads. You don't change the agent; you wrap the two things the loop calls:

@@code ch28_otel.py::JsonLinesExporter~,TracedClient,traced_tool,run_traced

Each question becomes an `invoke_agent` span with one `chat` span per model call (tokens, stop reason) and one `execute_tool` span per tool call. The attribute names (`gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.tool.name`...) follow OpenTelemetry's **GenAI semantic conventions**, so dashboards chart them for free. The conventions are still marked *Development* (`gen_ai.system`, for example, became `gen_ai.provider.name`), so pin your version. Arguments and message text aren't recorded, because they can hold personal data. For a real collector, swap `JsonLinesExporter` for the OTLP exporter.

## 28.2 Structured agent logs

Logs carry the events between spans: a run started, a retry happened, a guard decided. **Structured logs**, one JSON object per line with fixed fields, can be counted and joined; "calling tool..." can't.

@@code ch28_ops.py::EVENTS,log_event

Every line has a timestamp, the `trace_id`, a `run_id` and an event from a fixed list. The `trace_id` turns "show me the logs for this trace" into a filter. In the agent, take it from the current span: `f"{trace.get_current_span().get_span_context().trace_id:032x}"`.

Text fields pass through `redact` (section 28.3) first. Here's the demo's line for a question containing an email address:

```
{"ts": "2026-09-26T20:47:46.480+00:00", "trace_id": "run-ok-1",
 "run_id": "r1", "event": "run_start", "question": "Email [email] sales"}
```

`log_event` redacts top-level strings only; redact nested values yourself.

## 28.3 What never goes into telemetry

Traces and logs are copied, retained and read by many people. Decide what they may hold before you turn them on:

@@code ch28_agentops.py::redact

- **Never:** secrets, tokens (Chapter 26 keeps them out of the model; keep them out of telemetry too), full card numbers.
- **Only redacted:** personal data in questions, answers and tool arguments. `redact` replaces email addresses, card numbers and keys; extend it for your domain.
- **References over copies:** a document id and version, a hash of a prompt.
- **Retain on purpose:** detailed traces for days or weeks, summaries longer, deleted on schedule, as with memories (Chapter 17).

`ch28_otel.py` records no arguments or message text at all. Start there, and add redacted text only where you need it to debug.

## 28.5 Tool-call telemetry

Most incidents start at a tool: an API slows down, a database rejects a query, a permission was never granted. `report` gives each tool its call count, p95 latency and error rate. The p95 is the time 19 of 20 calls beat; the average hides the slow minority your users notice.

An error flag says *that* a tool failed. To route it to the right owner you need *why*:

@@code ch28_ops.py::error_type

- **`tool_error`**: the tool or its dependency failed; that's for the tool's owner (Chapters 7 and 19).
- **`not_authorized`**: Chapter 26's identity checks refused the call. A spike means a misconfigured token or an agent trying things it shouldn't.
- **`guard_blocked`**: a Chapter 25 guard stopped an action. One canary alert is an incident on its own.

`traced_tool` doesn't yet record `error.type` (an OpenTelemetry attribute name) or a hash of the arguments, which section 28.8 uses to spot a repeated call. Add both after the line that sets `error`:

```
# two more attributes: what kind of error, and "same arguments as before?"
kind = error_type(str(out))
if kind:
    span.set_attribute("error.type", kind)
span.set_attribute("tool.args_hash", hashlib.sha256(
    json.dumps(args, sort_keys=True).encode()).hexdigest()[:8])
```

This needs `import hashlib` and `from ch28_ops import error_type`. A hash doesn't truly hide a guessable value such as an email address, so treat it as internal, like the rest of the trace.

## 28.6 Latency breakdown

"The agent is slow" has three possible answers: the model, the tools or everything in between.

@@code ch28_ops.py::latency_breakdown

For the demo's first run it prints:

```
LATENCY 4,140 ms: model 80%, tools 14% {'get_schema': 120.0, 'run_query': 480.0}, other 6%
```

When model time dominates, as it usually does, cut steps, use a smaller model or cache the prompt; Chapter 29 measures each. When tool time dominates, the breakdown names the tool to cache, parallelize or fix. A large "other" is the loop itself, and often hides a retry with backoff. (It goes negative only when parallel tool calls overlap.) Break down the runs above the p95, because the slow tail is where causes differ.

:::tip Reading a trace
These runs come from `sample()` in `ch28_ops.py`, whose span times are typed in, but you read a real trace the same way.

Find the first failing span, or the longest bar. In the looping run it's the first `run_query !`. All four failing calls carry the same `tool.args_hash` (`a1f3`), so the model sent identical arguments each time and never acted on the error. Then let `error.type` decide whose problem it is. A `tool_error` goes to the tool's owner. A `not_authorized`, like the `refund` in `run-denied`, goes to whoever configures the agent's tokens (Chapter 26). A `guard_blocked` is a security incident. The repetition itself is the agent team's: an error the model can't act on (Chapter 8), and no loop detector to stop the retries.

When nothing failed, read the latency breakdown. For the first run, the model takes 80% of 4,140 ms, so the levers are fewer steps, a smaller model or prompt caching (Chapter 29), not the tools.
:::

Without start times, `timeline` lays children one after another, which is wrong for parallel calls. To record them, add `"start_ms": round(s.start_time / 1e6, 1)` to the dictionary `JsonLinesExporter` writes.

## 28.8 The agent failure taxonomy

"The agent failed" gives you nothing to act on. "12% of runs this week ended in a tool loop, all on `run_query`" does. Classified failures are countable, and a growing count tells you where to look before you open a trace.

There are two levels. The first is one headline class per run, checked in a fixed order so counts compare over time. `report` uses it for the success rate:

@@code ch28_agentops.py::FAILURES,classify

Each class points somewhere: `refusal` to the prompt, `cut_off` to context size (Chapter 16), `step_limit` and `tool_loop` to tool design and errors the model can't act on (Chapter 8), `wrong_answer` to Chapter 27, `tool_errors` to a dependency and `too_slow` to the slowest span.

The second level is a 12-class taxonomy, each class with its detection, fix and the evaluation that keeps it fixed. A run can show several. Detection that starts with "Eval" or "Audit" needs more than a trace:

Table: The agent failure taxonomy
| Failure | Detection | Mitigation | Evaluation | Chapters |
| --- | --- | --- | --- | --- |
| `wrong_tool` | Eval: expected tool not called | Better tool names and descriptions | Routing eval | 3, 27 |
| `wrong_args` | Eval: tool called with wrong arguments | Schemas, enums, examples | Argument checks | 3, 27 |
| `tool_failure` | Trace: tool span error flag | Retries, fallbacks, clear errors | Fault injection | 7, 19 |
| `misread_result` | Eval: right tools, no errors, wrong answer | Structured results | Answer against the data | 8, 27 |
| `hallucination` | Eval: answer numbers in no tool result | Cite sources, verify | Groundedness check | 6, 18, 27 |
| `context_overflow` | Trace: stop reason or input tokens near the limit | Trim, summarize, retrieve | Long-input cases | 16 |
| `injection` | Trace: a guard blocked a tool result | Quarantine untrusted text | Red-team suite | 14, 25 |
| `planning_failure` | Eval: trajectory eval failed the plan | Plan, then check the plan | Trajectory eval | 20 |
| `infinite_loop` | Trace: same call repeated, or step limit | Loop detector, step cap | Step-limit test | 4, 28 |
| `memory_poisoning` | Audit of the memory store | Provenance, write policy | Poisoning tests | 17, 25 |
| `auth_failure` | Trace: `error.type` is `not_authorized` | Scoped tokens, checks at the tool | Permission tests | 26 |
| `runaway` | Trace: cost, time or steps over budget | Budgets, cheaper models | Budget assertions | 29 |

The same table is `TAXONOMY` in `ch28_ops.py`, and `classify_detailed` checks a run against it:

@@code ch28_ops.py::ungrounded_numbers~,classify_detailed

For the demo's five runs it finds:

```
  run-ok-1       ok
  run-ok-2       ok
  run-loop       tool_failure, infinite_loop
  run-denied     auth_failure
  run-made-up    hallucination
```

`run-made-up` looks perfect in its trace: one query, no errors, a quick answer. Only the eval shows that its $48,210 appears in no tool result. `misread_result` is found by elimination: the eval failed, tools ran, and no other class explains it.

So know what each detection needs. Five classes need an eval that knows what *should* have happened (Chapter 27), and `memory_poisoning` needs an audit of the memory store; a trace-only dashboard calls all of those runs healthy. `auth_failure` needs `error.type`, and the reliable `infinite_loop` check needs `tool.args_hash` (section 28.5); without it, `repeated_calls` falls back to the same tool failing three times in a row. An `injection` that no guard, eval or red-team case caught looks like any other run.

## 28.10 SLOs for agents

A **service-level objective** (SLO) is a target you promise yourself, measured continuously. Behind it is a **service-level indicator** (SLI): a number users would recognize, such as the share of tasks that succeeded. Agent SLIs come from traces, the eval suite and human review.

@@image d-81ba61470da9.png

Figure: Where agent SLOs come from, and what they drive
Alt: Traces give latency and cost per task; the eval suite and judge give task success, tool selection and retrieval recall; human review gives unsafe actions, escalation and accuracy. All feed SLO targets and an error budget, which drives burn-rate alerts and release gates.

`AGENT_SLOS` holds seven objectives. Treat the targets as starting points and set yours from your first weeks of data.

Table: Example SLOs for an agent
| SLO | Example target | How it's measured | Source |
| --- | --- | --- | --- |
| Task success | >= 95% | Success rate, as in the scorecard (27.6) | Evals and judge (Chapter 27) |
| p95 latency | < 8 s | Latency p95, as in the scorecard | Traces |
| Cost per task | < $0.05 | Cost per task, as in the scorecard | Traces |
| Tool selection accuracy | >= 98% | Tool accuracy, as in the scorecard | Eval suite (Chapters 3 and 27) |
| Unsafe action rate | < 0.01% | Share of actions a reviewer judged unsafe | Human review, guard logs (Chapter 25) |
| Human escalation accuracy | >= 95% | Share of escalation decisions a reviewer agreed with | Human review (Chapters 9 and 19) |
| Retrieval recall | >= 90% | Share of the needed documents that retrieval found | Eval suite (Chapter 18) |

`measure_slos` never guesses: an SLO with no data says so. On the demo's five runs, `slo_table` prints:

```
SLO                         target    value  status   budget  measured from
Task success                >= 95%      40%  MISSED   -1100%  evals + judge (Ch 27)
p95 latency (ms)           < 8,000    5,500  met              traces
Cost per task ($)          < 0.050    0.020  met              traces
Tool selection accuracy     >= 98%     100%  met        100%  eval suite (Ch 27)
Unsafe action rate         < 0.01%    0.00%  met        100%  human review (Ch 25)

```

The **error budget** is the failure the objective allows: 95% over 1,000 runs allows 50 failures. Five graded runs allow 0.25; three happened, 12 times the budget, so -1100% is left. Latency, cost and recall aren't pass-or-fail per run, so they have no budget.

Two cautions. A handful of runs can't show an SLO is met: a one-in-10,000 target needs many thousands of reviewed actions, so until then treat every unsafe action as an incident. And use the budget to decide: while there's budget left, ship changes; when it's spent, fix reliability first. Chapter 27's regression gate makes that automatic.

## 28.11 Alerting

An alert wakes a person, so it must mean "users are affected and someone must act now". Alert on **symptoms users feel**: failed tasks, slow answers, unsafe actions. Causes such as CPU or token counts belong on the dashboard, where they explain an alert.

`ch28_agentops.py` checks four objectives and names the tool when one is failing:

@@code ch28_agentops.py::SLO,alerts

These thresholds are looser than section 28.10's objectives: 90% success and a 20-second p95 say "act now"; 95% and 8 seconds say "where we aim".

A single-window threshold fires on a noisy five minutes and misses a slow leak. **Burn-rate alerts** fix both: the burn rate is how fast you're spending the error budget relative to the allowed pace. With a 95% objective, 5% may fail; if 20% fail in the last hour, the burn rate is 4, and a 30-day budget is gone in under eight days. Page on a high burn rate over a short window confirmed by a longer one; open a ticket for a low rate sustained over days. Exercise 28.5 builds one.

## 28.12 Debugging production agents

When an alert fires, work from the aggregate down to one step:

1. **What's hurting?** Which SLO, since when, how fast the budget is burning.
2. **Which class and which tool?** Compare failure-class counts and the tools table with yesterday's; what grew names the suspect.
3. **Which runs?** Filter run records by class, tool and time. Pick one typical, one worst and one from the incident's first minutes.
4. **Where in the run?** Print `timeline` and `latency_breakdown`. The first failing span or the longest bar is usually the cause.
5. **Why?** Filter the logs by that `trace_id`: the step's redacted arguments and result, the context (Chapter 16), the stop reason. If the step was slow rather than wrong, join it with the machine and the profiler (section 28.13).
6. **What changed?** Most incidents follow a change to a prompt, model, tool, dependency or traffic. Line the start up against deploy history.
7. **Mitigate, then fix.** Roll back first; find the root cause after users are safe.
8. **Never again.** Add the failing input as a test case (Chapter 27), and add a class to the taxonomy if none fit.

## 28.13 Correlating traces with resources: continuous profiling

:::note Advanced: skip on a first reading
This section is for when traces aren't enough: a slow span with no obvious cause. Nothing later in the book depends on it, so read it when you meet that problem.
:::

A trace tells you *where* a run's time went: `run_sql` took 1.9 seconds. It doesn't tell you *why*, and one slow span can have half a dozen causes with different owners: another job holding database locks, 40,000 rows your code spent a second serializing, a noisy neighbor, a garbage-collection pause, a slow TLS handshake, a cold cache. None of them is in the span. To find it, join the span with what the machine was doing while it ran, and with what your code was doing inside it.

Table: The signals that explain a span, and how each one joins {#t:profile-signals}
| Signal | Where it comes from | Joins on | What it explains |
| --- | --- | --- | --- |
| Span duration, tokens, rows | Traces (section 28.1) | Trace and span id | Where the time went; how much work the span did |
| Queue wait | A `queue` span around the wait for a slot (section 29.1) | Span id | Time spent waiting for a turn |
| Process CPU and memory, CPU throttling | Host and container metrics | Time window and host | Whether your code could run when it wanted to |
| GPU utilization and memory | DCGM or `nvidia-smi`, for a self-hosted model | Time window and GPU node | Whether the model server is full |
| Database query time and rows | Client spans, the database's own statistics | Span id (client), time (server) | Whether the database was slow or the query big |
| Network time | Client spans: DNS, connect, TLS | Span id, or time and destination | Whether the wire was the problem |
| Stack samples | A continuous profiler | Span id if samples are labeled, else time and thread | Which function the thread was in |

Anything recorded *inside* a request (child spans, log lines, labeled profiler samples) carries its span id, so that join is exact. Metrics describe the machine, so they join on a **time window** and a place: the host's CPU between the span's start and end. That needs metrics sampled at least as often as spans are short (a 15-second scrape averages a 2-second spike into nothing) and a shared clock (200 ms of skew changes the answer for a 300 ms span).

`ch28_profile.py` does the time join. It reads spans in `ch28_otel.py`'s format (with `start_ms`, section 28.7) and resource samples with a timestamp, CPU %, memory %, GPU %, database query time and network round trip:

@@code ch28_profile.py::normalize~,resources_during,attribute~

Each span gets the mean of every metric over its window, plus the milliseconds spent while each resource was **saturated**, past the point where requests queue for it (`SATURATION`: 85% CPU, 250 ms per database query and so on). A span saturated for at least half its time is marked `saturated_by` that resource.

### Which resource explains the latency?

Now compare. For each group (one tool, or all model calls), ask two questions of each signal: does latency rise with it, and are spans slower while it's saturated?

@@code ch28_profile.py::rank_corr,correlate,diagnose~

`rank_corr` is **Spearman's rank correlation**: it correlates the order of values, so one 30-second outlier can't manufacture a correlation. The **lift** is the p50 latency while saturated divided by the p50 while not. `diagnose` blames a resource only when both agree: a lift of at least 1.5 and a correlation of at least 0.3. Either alone misleads: a lift can come from five unlucky spans, and a correlation from load, since CPU, database time and latency all rise together when traffic doubles. The correlation bar is low because saturation is a threshold effect: a tool three times slower above 85% CPU gives a modest r when only 15% of its spans ran there. Span signals (output tokens, rows) measure the span's own work, so a correlation of 0.5 or more explains latency on its own.

### The profile: what the code was doing

A **continuous profiler** says what *your code* was doing. It samples every thread's stack many times a second (100 by default in py-spy), always, in production, for around 1% CPU. Joined with the slowest spans, the samples show where the time went:

@@code ch28_profile.py::top_frames,slowest~

`top_frames` counts each sample's **leaf frame** with its caller ("`socket.recv` called from `cursor.execute`"). It joins on span id when samples carry one, and on time otherwise, mixing in every concurrent request (exercise 28.8 shows how much). `slowest(..., unexplained=True)` drops spans a saturated resource already explains.

Two traps. A CPU profile records only running threads, so a thread waiting for the database is invisible; for latency questions, profile wall-clock time (py-spy's `--idle` flag). And starvation looks normal: a thread denied a CPU is sampled in the same function as always, so the profile keeps its shape and only gets longer. Record the thread's CPU time on the span:

```python
cpu0 = time.thread_time()                      # in traced_tool, around run_tool
out = run_tool(name, args)
span.set_attribute("agent.tool.cpu_ms", round((time.thread_time() - cpu0) * 1000, 1))
```

Wall time close to CPU time means the code is the work. Much larger with host CPU low means waiting on I/O or a lock; much larger with the CPU saturated means starved.

Read it one group at a time:

1. **Model calls are 90% of the time and follow output tokens** (r = 0.99). The GPU never went above 88%, so it isn't the cause. The levers are Chapter 29's: fewer output tokens and fewer steps.
2. **`run_sql` is slow when the database is busy** (lift 12.5), and 91% of its slowest samples wait in `socket.recv`. The batch job should move to a replica: a ticket for the database's owner, with this evidence attached.
3. **`render_chart` is slow when the CPU is saturated** (x3.3), yet its profile has the same shape as on a calm day: 80% `draw_path`. Alone, the profile would send someone to optimize `draw_path`. The resource join says the code got less CPU; the fix is a CPU reservation or moving the neighbor.
4. **The rest of `run_sql`'s tail is the work itself**: a median of 41,655 rows, 87% of the time in `json.dumps`. Make the tool aggregate in SQL and cap its results (section 8.5), which also saves the model's tokens.

The -0.25 between `render_chart` and the database is pure timing (the database was calm during the CPU incident), which is why `diagnose` never blames on correlation alone. The final proof is an experiment: reproduce the load and change one thing (Chapter 29).

### Collecting the signals in production

The agent needs nothing beyond its spans; the rest comes from standard tools:

- **Spans:** `ch28_otel.py` with start times, plus OpenTelemetry's database and HTTP client instrumentation. Record `db.rows` yourself and redact query text (section 28.3).
- **Host and container metrics:** OpenTelemetry's host metrics, plus CPU throttling (cAdvisor's `container_cpu_cfs_throttled_periods_total`), which is starvation even when the host looks idle. **Exemplars** attach a trace id to a metric point, so a spike on a chart links to a trace.
- **GPU:** NVIDIA's DCGM exporter (`DCGM_FI_DEV_GPU_UTIL`), or `nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv -lms 500`. GPU "utilization" only means some kernel ran, so the inference server's queue and KV-cache metrics are the better saturation signal.
- **Database:** `pg_stat_statements` in PostgreSQL, lock waits, CPU and I/O.
- **Profiles:** `py-spy record --idle --pid <pid>` for a one-off look; Grafana Pyroscope or Parca (eBPF) for always-on profiles. Pyroscope can label samples with the span id for some languages.

A production version runs over streams in your observability backend, joins on host and pod, checks a metric's maximum as well as its mean (a 200 ms stall vanishes in a 1-second mean) and compares spans at similar load.

Its SLOs (task success, p95 latency, cost per resolved conversation, unsafe-action rate) have dashboards and alerts, and each failure is classified with the taxonomy in section 28.8.

## Common mistakes

- Monitoring only the server, so an agent that's up but wrong looks healthy.
- Logging secrets or personal data, or logs without a trace id.
- Leaving failures unclassified, so every incident starts from zero.
- Trusting traces for eval-only failures such as wrong tools, hallucinations and bad plans.
- Averages instead of percentiles, which hide the slow minority.
- Alerting on causes such as CPU instead of what users feel.
- Explaining a slow span from the span alone, or from a CPU profile that can't see waiting.

## Before you move on

- **You should understand:** which failure classes a trace can't see, and why a slow span needs resource metrics and profiles before you can blame anything.
- **You should be able to build:** OpenTelemetry spans for every model and tool call, run records, failure classes and an SLO table with error budgets.
- **Prove it:** exercise 28.6, starting from `./course.sh python ch28_ops.py`.
- **Break it on purpose:** delete `error.type` from `run-denied`'s tool step in `sample()`, rerun `classify_detailed`, and see which class it lands in instead of `auth_failure`.
- **Defend this decision:** why alerts page on what users feel, such as failed tasks and p95 latency, and leave CPU and token counts on the dashboard.

## Key takeaways

**Architect's takeaway:** Trace every decision and tool call, and alert on what users feel. An agent can be up, fast and cheap while failing every user.

- Trace the chain from goal to outcome; join logs through the `trace_id`.
- Keep secrets out, redact personal data, retain on purpose.
- Run records give tokens, cost, latency and per-tool errors; `error.type` routes each failure to its owner.
- SLOs measure what users feel; error budgets drive burn-rate alerts and release gates.
- To explain a slow span, join it with resources and profiles, and blame a resource only when lift and correlation agree.
