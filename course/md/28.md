# Chapter 28: AgentOps: Observability, Telemetry and SLOs for Agents

Traditional monitoring watches CPU, memory, latency and errors. An agent can look healthy on every one of those while quietly failing its users: answering from a stale document, calling the wrong tool, looping on a broken query or spending ten times what it did last week. Agent observability follows the chain that matters: the user's goal, the context the agent was given, each model call and the decision it made, each tool call and its result, and the final outcome. This chapter builds that chain in code, from traces and logs to a failure taxonomy, a dashboard, service-level objectives and alerts, so you can answer "what happened?" for one run and "how are we doing?" for all of them.

**What you'll build:** OpenTelemetry traces and structured logs for every model call and tool call, run summaries with tokens, cost and latency, a text timeline of one run, a classifier for 12 kinds of agent failure, a one-page production dashboard and agent SLOs with error budgets and alerts.

**You are here:** Observability in the agent architecture reference model  — Intermediate(section 1.7).

## Learning objectives

By the end of this chapter you can:

- Describe what agent observability records that traditional monitoring doesn't.
- Trace every model call and tool call with OpenTelemetry and the GenAI conventions, and join structured logs to those traces.
- Keep secrets and personal data out of traces and logs.
- Turn spans into run records with tokens, cost, latency and per-tool error rates.
- Break a run's latency into model, tool and orchestration time, and read its trajectory as a timeline.
- Classify failures with a 12-class taxonomy, and say which classes traces alone can't see.
- Map public agent incidents to failure classes and to the controls that prevent them.
- Build a production dashboard, and set agent SLOs with error budgets and alerts on the symptoms users feel.
- Go from an alert to a root cause with a repeatable playbook.

## Real-world connection

Observability is the most widely adopted agent practice. In LangChain's survey of 1,340 practitioners (late 2025), 89% had implemented some form of observability, 62% had detailed tracing of individual steps and tool calls, and among teams with agents in production those figures rose to 94% and about 72%. Many observability tools now read OpenTelemetry's conventions for generative AI, and agent platforms ship tracing built in. The gap is in using the data: traces that nobody summarizes, failures nobody classifies and alerts on server health rather than on whether users got what they asked for.

## 28.1 Tracing with OpenTelemetry

The whole chapter fits in one picture. The agent and its tools emit spans and log lines; a collector redacts and forwards them; stores keep traces, logs and metrics; and dashboards, SLOs and alerts turn them into decisions for the person on call. Eval results from Chapter 27 feed in beside the traces, because some failures only an eval can see.

@@image d-64e5e0e37503.png

An agent run is a chain, and a failure can start at any link:

| Link | What to record | Example question it answers |
| --- | --- | --- |
| The request | Id, user or tenant, time, the goal in a few words | Which customers were affected? |
| The context | Sources assembled, their ages, tokens per source (Chapter 16) | Did the agent see the updated policy? |
| Each model call | Model, tokens in and out, latency, stop reason | Why did this run cost $0.40? |
| Each decision | Which tool it chose, with which (redacted) arguments | Why did it query the wrong table? |
| Each tool call | Tool, latency, error flag, policy and guard decisions (Chapters 14 and 25) | Which tool is slow today? |
| The outcome | Final status, eval or judge score if graded, user feedback | Are we getting worse? |

Tracing tools represent the request as a **trace** and each step as a **span** inside it: a named, timed piece of work with attributes and a parent. With that structure you can answer "why was this request slow?" (one tool took 9 seconds) or "why did costs double this week?" (a prompt change added two steps to every run).

`traces.jsonl` is fine for one developer. In production, use **OpenTelemetry**, the standard that almost every observability tool reads. You don't have to change the agent to add it: wrap the two things the loop calls.

@@code ch28_otel.py::JsonLinesExporter,TracedClient,traced_tool,run_traced

Each question becomes a trace with an `invoke_agent` span, one `chat` span per model call (with token counts and stop reason) and one `execute_tool` span per tool call. The attribute names (`gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.tool.name`...) follow OpenTelemetry's **GenAI semantic conventions**, so dashboards that know them can chart tokens, cost and latency per step without extra work. The conventions are still marked *Development* and names have changed before (`gen_ai.system` became `gen_ai.provider.name` in 2025), so pin the version you follow and check what your tools actually emit. Note what's *not* recorded: tool arguments and message text, which can contain personal data. To send spans to a real collector, swap `JsonLinesExporter` for the OTLP exporter.

## 28.2 Structured agent logs

Traces show structure and time: what called what, and for how long. Logs carry the events in between: a run started, a retry happened, a guard decided, a run ended with this status. Plain text logs ("calling tool...") can't be counted or joined. **Structured logs** can: one JSON object per line, with the same fields every time.

@@code ch28_ops.py::EVENTS,log_event

Every line has a timestamp, the `trace_id`, a `run_id` and an event name from a fixed list, plus the fields you pass. The `trace_id` is what makes logs and traces one system. When a span looks wrong, "show me the logs for this trace" becomes a filter, not a search. In the agent, take it from the current span, in the same format `JsonLinesExporter` writes: `f"{trace.get_current_span().get_span_context().trace_id:032x}"`.

Text fields pass through `redact` (section 28.3) before they're written. Here's the line the demo writes for a question that contains an email address:

```
{"ts": "2026-09-26T20:47:46.480+00:00", "trace_id": "run-ok-1",
 "run_id": "r1", "event": "run_start", "question": "Email [email] sales"}
```

`log_event` redacts top-level string fields only. If you log a nested dictionary or a list, redact its strings yourself first.

## 28.3 What never goes into telemetry

Traces and logs are copied, retained and read by many people. Decide what they may hold before you turn them on:

@@code ch28_agentops.py::redact

- **Never:** secrets, tokens (Chapter 26 keeps them out of the model; keep them out of telemetry too), full card numbers.
- **Only redacted:** personal data in questions, answers and tool arguments. `redact` replaces email addresses, card numbers and keys; extend it for your domain.
- **Prefer references to copies:** a document id and version rather than the document, a hash of a prompt rather than the prompt.
- **Retain on purpose:** keep detailed traces for days or weeks, summaries for longer and delete on schedule, as with memories (Chapter 17).

`ch28_otel.py` records no arguments or message text at all. That's the safe default; add redacted text only where it's needed to debug.

Cost comes from tokens, and tokens come from the spans, so the bill is visible per run, per step and per day, not at the end of the month. Across runs, `report` turns run records into the fleet's headline numbers:

## 28.5 Tool-call telemetry

Tools are where agents touch the world, and where most production incidents start: an API that slows down, a database that rejects a query, a permission that was never granted. `report` groups every tool call by name and gives each tool its number of calls, p95 latency and error rate. The p95, the 95th percentile, is the time that 19 of 20 calls beat. Use it rather than the average, which hides the slow minority your users notice.

An error flag alone says *that* a tool failed, not *why*. Three kinds of failure need three different owners:

@@code ch28_ops.py::error_type

- **`tool_error`**: the tool or its dependency failed. That's a reliability problem for whoever owns the tool (Chapters 7 and 19).
- **`not_authorized`**: the identity checks from Chapter 26 refused the call. A few are normal; a spike means a misconfigured token or an agent trying things it shouldn't.
- **`guard_blocked`**: a Chapter 25 guard stopped an action. That's a security signal, and one canary alert is an incident on its own.

`error.type` is an OpenTelemetry attribute name, but `ch28_otel.py`'s `traced_tool` doesn't record it yet. Neither does it record a hash of the arguments, which section 28.8 uses to spot the same call repeated. Add both to `traced_tool`, after the line that sets `error`:

```
# two more attributes: what kind of error, and "same arguments as before?"
kind = error_type(str(out))
if kind:
    span.set_attribute("error.type", kind)
span.set_attribute("tool.args_hash", hashlib.sha256(
    json.dumps(args, sort_keys=True).encode()).hexdigest()[:8])
```

This needs `import hashlib` and `from ch28_ops import error_type` at the top. The hash says "the same arguments as last time" without recording them. It isn't a way to hide data, though: anyone can hash a guessable value, such as an email address, and compare. Treat hashes as internal, like the rest of the trace.

## 28.6 Latency breakdown

"The agent is slow" has three possible answers: the model, the tools or everything in between. Split one run's time into those three parts:

@@code ch28_ops.py::latency_breakdown

For the demo's first run it prints:

```
LATENCY 4,140 ms: model 80%, tools 14% {'get_schema': 120.0, 'run_query': 480.0}, other 6%
```

Read it like this:

- **Model time dominates** (the usual case): fewer steps, a smaller model for simple steps, a shorter prompt or prompt caching. Chapter 29's performance model shows how much each lever saves.
- **Tool time dominates**: the breakdown names the tool. Look at its p95 in the tools table (section 28.5), then cache, parallelize or fix it.
- **"Other" is large**: the time between spans, where the loop builds prompts, parses results, retries and waits on the network. A large share is orchestration overhead, and it often hides a retry with backoff.

"Other" goes negative only when tools run in parallel, because their times overlap. Break down the slow runs, those above the p95, rather than the average run: the slow tail is where the causes differ.

## 28.7 Visualizing a trajectory

A run record says a run took 5.5 seconds and made nine calls. A **timeline** shows the order, the gaps and where the time went, at a glance. `timeline` draws one row per span on a shared time axis, as text, so it works in a terminal, a log or an incident ticket:

@@code ch28_ops.py::timeline

Here's the demo's output for its first run. `#` is a model call, `=` a tool call and `-` the whole agent run:

```
span                  ms |0                                                   4,140 ms|
agent               4140 |------------------------------------------------------------|
  chat               900 | #############                                              |
  get_schema         120 |              ==                                            |
  chat              1100 |                 ###############                            |
  run_query          480 |                                 =======                    |
  chat              1300 |                                         ################## |
```

And here's the demo's looping run, where `x` and `!` mark a failed tool call:

```
span                  ms |0                                                   5,500 ms|
agent               5500 |------------------------------------------------------------|
  chat               700 |########                                                    |
  run_query !        300 |         xxx                                                |
  chat               800 |            #########                                       |
  run_query !        300 |                     xxxx                                   |
  chat               800 |                         #########                          |
  run_query !        300 |                                  xxxx                      |
  chat               800 |                                      #########             |
  run_query !        300 |                                               xxx          |
  chat               800 |                                                   #########|
```

You don't need to read a single attribute to see the problem: the same tool failing four times, with the model trying again each time.

`ch28_otel.py` records each span's duration but not its start time. Without start times, `timeline` lays each span's children end to end in the order they finished, which is right for an agent loop that runs one step at a time but wrong for parallel tool calls. The demo's spans carry a `start_ms` field; to get true start times from your own traces, add `"start_ms": round(s.start_time / 1e6, 1)` to the dictionary `JsonLinesExporter` writes.

## 28.8 The agent failure taxonomy

"The agent failed" isn't actionable. "12% of runs this week ended in a tool loop, all on `run_query`" is. Classifying failures makes them countable, and a count that grows tells you which part of the system to look at before you open a single trace.

There are two levels. The first is one headline class per run, checked in a fixed order so counts compare over time. `report` uses it for the success rate:

@@code ch28_agentops.py::FAILURES,classify

A `refusal` points to the request or the system prompt; `cut_off` to context size (Chapter 16) or `max_tokens`; `step_limit` to tool design or a loop; `tool_loop` to tool errors the model can't act on (Chapter 8); `wrong_answer` to Chapter 27's failures; `tool_errors` to a tool or its dependency being down; and `too_slow` to the slowest span in the trace.

The second level is a finer taxonomy of 12 classes, each with how you detect it, how you fix it and which evaluation keeps it fixed. A run can show several at once. Detection that starts with "Eval" or "Audit" needs more than a trace:

| Failure | Detection | Mitigation | Evaluation | Chapters |
| --- | --- | --- | --- | --- |
| `wrong_tool` | Eval: expected tool not called | Better tool names and descriptions | Routing eval | 3, 27 |
| `wrong_args` | Eval: tool called with wrong arguments | Schemas, enums, examples | Argument checks | 3, 27 |
| `tool_failure` | Trace: tool span error flag | Retries, fallbacks, clear errors | Fault injection | 7, 19 |
| `misread_result` | Eval: right tools, no errors, wrong answer | Structured results | Answer against the data | 8, 27 |
| `hallucination` | Eval: answer numbers in no tool result | Cite sources, verify | Groundedness check | 6, 18, 27 |
| `context_overflow` | Trace: stop reason or input tokens near the limit | Trim, summarize, retrieve | Long-input cases | 16 |
| `injection` | Trace: a guard blocked a tool result | Quarantine untrusted text | Red-team suite | 14, 25 |
| `planning_failure` | Eval: trajectory eval failed the plan | Plan, then check the plan | Trajectory eval | 20 |
| `infinite_loop` | Trace: same call repeated, or step limit | Loop detector, step cap | Step-limit test | 4, 28 |
| `memory_poisoning` | Audit of the memory store | Provenance, write policy | Poisoning tests | 17, 25 |
| `auth_failure` | Trace: `error.type` is `not_authorized` | Scoped tokens, checks at the tool | Permission tests | 26 |
| `runaway` | Trace: cost, time or steps over budget | Budgets, cheaper models | Budget assertions | 29 |

The same table is `TAXONOMY` in `ch28_ops.py`, and `classify_detailed` checks a run against it:

@@code ch28_ops.py::ungrounded_numbers,classify_detailed

For the demo's five runs it finds:

```
  run-ok-1       ok
  run-ok-2       ok
  run-loop       tool_failure, infinite_loop
  run-denied     auth_failure
  run-made-up    hallucination
```

`run-made-up` looks perfect in its trace: one query, no errors, a quick answer. Only the eval result shows that the answer's $48,210 appears in no tool result.

Be clear about what each detection needs:

- **Traces alone can't see five classes:** `wrong_tool`, `wrong_args`, `misread_result`, `hallucination` and `planning_failure` need an eval that knows what *should* have happened (Chapter 27). `memory_poisoning` needs an audit of the memory store (Chapter 17). A dashboard built only on traces will report these runs as healthy.
- **`misread_result` is found by elimination:** the eval failed, tools ran and nothing else explains it.
- **`auth_failure` needs `error.type`**, and the most reliable `infinite_loop` check needs `tool.args_hash`: the two attributes section 28.5 adds to `traced_tool`. Without the hash, `repeated_calls` falls back to the same tool failing three times in a row.
- **`injection` is detected only when a guard caught it,** or an eval or red-team case flags it. An injection that no guard noticed looks like any other run.

### Failures in the wild

Failures like these happen in public. The incidents below were widely reported, and each maps to a class and to a control from this book:

| Incident | What happened | Class | Control that prevents it |
| --- | --- | --- | --- |
| Moffatt v. Air Canada, 2024 | A support chatbot invented a refund policy; the tribunal held the airline responsible for what it said | `hallucination` (ungrounded answer) | Answer policy questions only from retrieved sources and verify the answer (Chapter 18); groundedness checks (Chapter 27) |
| Chevrolet of Watsonville dealer chatbot, December 2023 | Users talked the chatbot into "agreeing" to absurd deals | `injection` (direct), with no business-rule guard | Model outputs are proposals; rules and prices come from records, and code guards what the model says (Chapter 22) |
| Cursor's AI support agent, April 2025 | The agent invented a login policy and told users it was real | `hallucination` (ungrounded answer) | Grounded answers (Chapter 18), escalation to a human when the evidence isn't there (Chapter 9) |
| Replit's coding agent, July 2025 | The agent deleted a production database during a code freeze | Unsafe action without approval | Risk-rated actions with an approval gate in code (Chapter 9), step-up for risky actions (Chapter 26) |
| EchoLeak in Microsoft 365 Copilot, June 2025 (CVE-2025-32711) | A zero-click prompt injection in an email could make the assistant leak data | `injection` (context contamination) | Keep untrusted text away from the agent that acts, and egress checks (Chapter 25) |
| GitHub MCP "toxic agent flow", May 2025 | A malicious issue in a public repository led an agent with a broad token to leak private-repository data | `injection` plus an authorization failure | A policy layer for servers you didn't write (Chapter 14), narrow tokens per task (Chapter 26) |

The Replit case doesn't fit a trace-visible class: the agent had permission to do what it did. That's why section 28.10 has an unsafe-action SLO measured by human review, and why the fix is an approval gate, not better monitoring. The last two are also examples of the lethal trifecta from Chapter 25: private data, untrusted content and a way to send data out, in one agent.

## 28.10 SLOs for agents

A **service-level objective** (SLO) is a target you promise yourself, measured continuously. The measurement behind it is a **service-level indicator** (SLI): a number users would recognize, such as the share of tasks that succeeded. For agents, the useful SLIs come from three sources: traces, the eval suite and human review.

@@image d-81ba61470da9.png

`AGENT_SLOS` holds seven objectives. The targets are examples to start from, not universal truths: a coding assistant, a refund agent and a research agent need different ones. Set yours from what you measure in the first weeks and from what your users need, then tighten them.

| SLO | Example target | How it's measured | Source |
| --- | --- | --- | --- |
| Task success | >= 95% | Share of graded runs that passed | Evals and judge (Chapter 27) |
| p95 latency | < 8 s | 95th percentile of run time | Traces |
| Cost per task | < $0.05 | Mean cost of a run, from tokens and prices | Traces |
| Tool selection accuracy | >= 98% | Share of runs that called the expected tool | Eval suite (Chapters 3 and 27) |
| Unsafe action rate | < 0.01% | Share of actions a reviewer judged unsafe | Human review, guard logs (Chapter 25) |
| Human escalation accuracy | >= 95% | Share of escalations (and non-escalations) a reviewer agreed with | Human review (Chapters 9 and 19) |
| Retrieval recall | >= 90% | Share of the needed documents that retrieval found | Eval suite (Chapter 18) |

@@code ch28_ops.py::_error_budget,measure_slos

`measure_slos` never guesses: an SLO with no data says so. On the demo's five runs, `slo_table` prints:

```
SLO                         target    value  status   budget  measured from
Task success                >= 95%      40%  MISSED   -1100%  evals + judge (Ch 27)
p95 latency (ms)           < 8,000    5,500  met              traces
Cost per task ($)          < 0.050    0.020  met              traces
Tool selection accuracy     >= 98%     100%  met        100%  eval suite (Ch 27)
Unsafe action rate         < 0.01%    0.00%  met        100%  human review (Ch 25)
Escalation accuracy         >= 95%     100%  met        100%  human review (Ch 19)
Retrieval recall            >= 90%      75%  MISSED           eval suite (Ch 18)
```

The **error budget** is the failure the objective allows. A 95% success target over 1,000 runs allows 50 failures. In the demo, five graded runs allow 0.25 failures. Three happened, 12 times the budget, so -1100% is left. The budget column is empty for latency, cost and recall, because they aren't pass-or-fail per run.

Two cautions. A handful of runs can't show an SLO is met: the demo's "met" on unsafe actions comes from three reviewed runs, and a target of one in 10,000 needs many thousands of reviewed actions before the number means anything. Until you have that volume, treat every unsafe action as an incident. And the budget is a decision tool, not a report card: while there's budget left, ship prompt and model changes; when it's spent, stop and fix reliability first. Chapter 27's regression gate is where that decision becomes automatic.

## 28.11 Alerting

An alert wakes a person, so it must mean "users are affected, and someone needs to act now". Alert on **symptoms users feel**: failed tasks, slow answers, unsafe actions. Put causes, like CPU, a single tool's latency or token counts, on the dashboard, where they explain an alert rather than raise one.

`ch28_agentops.py` checks four objectives and names the tool when one is failing:

@@code ch28_agentops.py::SLO,alerts

These thresholds are looser than the objectives in section 28.10: 90% success and a 20-second p95 say "act now", while 95% and 8 seconds say "where we aim". Use both, for different jobs.

A threshold on a single window has two failure modes: it fires on a noisy five minutes and it stays quiet while a slow leak eats the month's budget. **Burn-rate alerts** fix both. The burn rate is how fast you're spending the error budget compared with the pace the objective allows. With a 95% objective, 5% of runs may fail. If 20% fail in the last hour, the burn rate is 4, and at that pace a 30-day budget is gone in under eight days. Page a person on a high burn rate over a short window, confirmed by a longer one so a brief spike doesn't page anyone; open a ticket for a low burn rate sustained over days. Exercise 28.5 builds one.

## 28.12 Debugging production agents

When an alert fires, work from the aggregate to one step, with the tools from this chapter:

1. **What's hurting?** Read the alert and the dashboard: which SLO, since when and how fast the budget is burning.
2. **Which class and which tool?** Compare the failure-class counts and the tools table with yesterday's. The class that grew, and the tool whose error rate or p95 grew, name the suspect.
3. **Which runs?** Filter run records by class, tool and time. Pick three: one typical, one worst, one from the first minutes of the incident.
4. **Where in the run?** Print each run's `timeline` and `latency_breakdown`. The first failing span, or the longest bar, is usually the cause.
5. **Why?** Filter the logs by that `trace_id`. Read the redacted arguments and result of that step, the context the agent had (Chapter 16) and the model's stop reason.
6. **What changed?** Most incidents follow a change: a prompt, a model, a tool, a dependency or the traffic. Line the start of the incident up against your deploy and config history.
7. **Mitigate, then fix.** Roll back or switch off the change first; find the root cause after users are safe.
8. **Never again.** Add the failing input as a test case (Chapter 27), and if the failure had no class, add one to the taxonomy so the next one is counted.

## Common Production Mistakes

1. **Logging without observability.** If you write 10 million logs a day and can't search them in 5 seconds, they might as well not exist. Use structured logging and a fast query tool.

2. **No failure classification.** If an agent fails, you need to know if it's a model hallucination, a tool error, a network timeout or a data problem. Classify failures consistently.

3. **SLOs that can't be measured.** If your SLO is "reliable," it's not an SLO. "success rate ≥95%, p95 latency <8 seconds" is an SLO; measure both with every request.

4. **Alerts that cry wolf.** If 50% of your alerts are false positives, people ignore them. Set thresholds you'll actually act on.

5. **No cost attribution.** If you don't know which agent or user burned the budget, you can't fix it. Tag every request with agent, user and team.

## Architect's Takeaway

Trace every decision and tool call: observability is foundational, not optional.

## Common mistakes

- **Monitoring only the server**, so an agent that's up but wrong looks healthy.
- **Logging secrets or personal data** in traces and logs.
- **Logs without a trace id**, so an incident means searching text instead of filtering one trace.
- **Traces nobody summarizes.** Thousands of spans answer no question until they become run records.
- **Unclassified failures**, so every incident starts from zero.
- **Trusting traces for eval-only failures.** Wrong tools, hallucinations and bad plans look healthy in a trace; without evals, the dashboard reports them as successes.
- **Averages instead of percentiles**, which hide the slow and failing minority.
- **Copying SLO targets** from a book, this one included, instead of setting them from your own measurements and users.
- **Alerting on causes** such as CPU or token counts instead of on what users feel, so people get paged for nothing and miss what matters.
- **No cost in the trace**, so a doubled bill is discovered at the end of the month.

## Summary

- Agent observability follows the chain from goal to context, decision, tool, result and outcome.
- OpenTelemetry spans with the GenAI conventions record model and tool calls without changing the agent; structured logs join them through the `trace_id`.
- Keep secrets out and redact personal data; prefer references to copies; retain on purpose.
- Summarize runs into tokens, cost, latency and per-tool error rates; record `error.type` so a tool error, a denied authorization and a blocked action reach different owners.
- Break latency into model, tool and "other", and read a run's trajectory as a timeline.
- Classify failures with a fixed taxonomy; five of the 12 classes need evals and one needs a memory audit, because traces can't see them.
- Public incidents map to the same classes and to controls from earlier chapters: grounding, business rules in code, approval gates, isolation of untrusted text and narrow tokens.
- One page shows the headline numbers, SLOs, failure classes and tools. SLOs measure what users feel, from traces, evals and human review; their error budgets drive burn-rate alerts and release gates.
- Debug from the alert down: SLO, class, runs, span, logs, change, mitigation and a new test case.

You can now see where every run's time and money go. Chapter 29 uses these measurements to make agents faster and cheaper: it models the cost and latency of a run, load-tests the agent and plans capacity, with the SLOs from this chapter as its targets.

## Exercises

:::ex Medium | 28.1 | A trace viewer
Write a script that reads `traces.jsonl` and prints, for the last 50 runs: pass rate, p50/p95 latency, mean tokens, the most-used tools and the five slowest questions.
**Done when:** The report runs on real traces and points to at least one improvement.
:::

:::ex Concept | 28.2 | What would you trace?
For the Chapter 22 refund workflow, list the spans and attributes you'd record for one request, what you'd redact, and three SLOs with targets. Say which of your SLOs would catch a model update that makes the reply guard fall back twice as often.
**Done when:** Every state transition has a span, nothing sensitive is recorded in plain text, and one SLO catches the fallback increase.
:::

:::ex Simple | 28.3 | Read the report
Run `ch28_otel.py` five times with different questions, then `ch28_agentops.py spans.jsonl`. Then make one tool fail on purpose (for example, point it at a missing file) and run both again.
**Done when:** You can explain every number in the report, and the second report classifies the failing runs and raises an alert that names the tool.
:::

:::ex Medium | 28.4 | A new failure class
Add a class `ignored_error`: the run finished, but a tool error was never followed by a successful call of the same tool, so the answer was probably built without data. Put it in the right place in `classify`'s order and test it.
**Hint:** Order matters: a run that's both a `step_limit` and an `ignored_error` should be counted once, as the more fundamental cause.
**Done when:** Tests show the new class for a crafted run, and the existing classes unchanged for the others.
:::

:::ex Complex | 28.5 | An SLO dashboard with burn alerts
Compute the report for every hour of a simulated day of runs, and alert when the success rate's error budget is burning too fast: for a 90% objective, more than 10% failures sustained over two consecutive hours. Print an hourly table and the alerts.
**Hint:** Generate runs with a scripted model and inject an incident in the afternoon (a tool that starts failing), so you can check that the alert fires then and not in the morning.
**Done when:** The alert fires within two hours of the incident, not before it, and clears after it ends.
:::

:::ex Medium | 28.6 | A production dashboard
Write a script that goes from spans to one HTML page. Summarize each run with `summarize`, give each a headline class with `classify` (using the eval result's `passed` where there is one) and build the fleet report with `report`. Add the 12-class taxonomy counts from `classify_detailed` to the report, measure the agent SLOs with `measure_slos`, print `slo_table` and write the page with `dashboard`. Run it on `ch28_ops.py`'s built-in sample, then on your own `spans.jsonl`, which has no eval results.
**Hint:** `ch28_ops.sample()` returns the spans by trace id and the eval results by trace id, the same shapes `load_spans` and your evals give you.
**Done when:** The page opens in a browser and shows the tiles, the SLO table, the taxonomy counts and the tools; on the sample, task success shows as missed with a negative budget; and on your own traces, the eval-based SLOs say "no data" instead of a number.
:::

:::ex Medium | 28.7 | Classify real failures
Script 10 small incidents from earlier chapters as spans with `build_spans`, each with the eval result you'd have: a question about revenue answered from the customer table, the right query with last year's dates, a weather API that was down, a query result in cents read as dollars, a figure no tool returned, a whole log file pasted into the context, a web page that told the agent to email the customer list (blocked by a guard), the same failing query repeated until `max_iterations`, a refund above the agent's limit and a research task that made 20 model calls. Run `classify_detailed` on each, then print, for every class found, its detection, mitigation and evaluation from `TAXONOMY`, in the taxonomy's order.
**Hint:** Some incidents need span attributes that `traced_tool` doesn't record yet: `error.type` (`guard_blocked`, `not_authorized`) and `tool.args_hash`. Pass them in the attributes of the tool steps.
**Done when:** Every incident gets the class you expected, the research task shows both `planning_failure` and `runaway`, and you can say which incidents would look healthy without their eval result.
:::
