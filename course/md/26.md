# Chapter 26: Agent Identity and Authorization

When an agent refunds an order, who did it? The customer who asked? The support team that deployed the agent? The agent itself? For most of this book the answer was vague: the agent used whatever key or password the program had. That's how incidents happen: an agent acting with a person's full permissions, a token that works everywhere and never expires, a sub-agent that inherits everything its lead could do and an audit log that says only "the bot". This chapter gives every agent its own identity, lets it act on behalf of a user with exactly the rights a task needs and checks those rights where the action happens.

**What you'll build:** signed, short-lived tokens that name the agent, the user it acts for, the API they're good for, their scopes and limits; a tool server that checks them on every call; narrower tokens for sub-agents; a single-use token issued after a person approves a risky action; and an audit log that answers who did what for whom.

**You are here:** Policies (identity) in the agent architecture reference model (section 1.7).

## Learning objectives

By the end of this chapter you can:

- Distinguish the user, the agent and the service in every action, and record all three.
- Give an agent its own identity instead of a person's credentials.
- Issue short-lived tokens with scopes, an audience and limits, and verify them at the tool.
- Check ownership and limits in the tool, not in the prompt.
- Narrow a token for a sub-agent, and never widen one.
- Require a person's approval for risky actions through a single-use, step-up token.
- Audit every decision, and revoke a token or disable an agent at once.

## Real-world connection

Identity for agents is one of the fastest-moving areas of 2026. MCP's authorization specification is built on OAuth, so remote MCP servers receive a user's token rather than a shared key (Chapter 30 uses it). A2A agent cards declare how callers must authenticate (Chapter 21). Identity providers now offer agent identities alongside human and workload ones, and the OWASP agentic list names identity and privilege abuse as one of the top ten risks. The ideas underneath are older and well tested: least privilege, delegation, short-lived credentials and audit trails. What's new is applying them to software that decides for itself what to do next.

## 26.1 Who is acting?

Every action an agent takes involves three identities:

| Identity | Example | What it answers |
| --- | --- | --- |
| The **user** | Ana, a customer | On whose behalf? Whose data may be touched? |
| The **agent** | `support-agent` | Which software decided to act? What is it ever allowed to do? |
| The **service** | The orders API | Where does the action happen, and who checks it? |

Keep all three, in every token and every log line. "The agent refunded $49 on Ana's order A-1001, approved by Sam" is an audit record. "The API key refunded $49" isn't.

## 26.2 Never lend an agent your password

The first rule is simple: **an agent never uses a person's credentials.** A person's password or personal token grants everything that person can do, everywhere, until it's changed. An agent with it can do all of that too, and when something goes wrong, the logs blame the person.

Give each agent its own identity instead: a service account, a workload identity or an agent identity from your identity provider. Chapter 23's browser agent already signed in as `agent-bot`, with a password the harness held and the model never saw. This chapter goes further: the agent doesn't hold long-lived secrets at all, only short-lived tokens issued for a task.

## 26.3 Tokens that say what's allowed

A token here is a **JWT** (JSON Web Token): a small signed document of *claims* that any service can verify with the right key. Ours say:

@@code ch26_identity.py::AGENTS,mint,verify

| Claim | Meaning |
| --- | --- |
| `sub` | The agent: `agent:support-agent` |
| `act_for` | The user it acts for: `user:ana` |
| `aud` | The one API this token works on: a token for `orders-api` is useless at `billing-api` |
| `scope` | What it may do there: `orders:read returns:create` |
| `limits` | Extra conditions, such as a maximum amount or single use |
| `exp` | When it stops working: minutes, not months |
| `jti` | The token's own id, so it can be revoked |
| `chain` | The ids of the tokens it was derived from |

The **registry** (`AGENTS`) is the ceiling: an agent can never be given a scope that isn't listed for it, whoever asks. The analyst agent can read orders; no mistake anywhere can hand it refunds.

The kit signs tokens with a shared key (HS256) to stay self-contained. In production, an identity provider signs them with a private key, and services verify them with the public key, so no service can forge a token.

## 26.4 Checking at the tool

The token means nothing unless the tool checks it, on every call, before doing anything:

@@code ch26_identity.py::authorize,refund

`authorize` is the **policy enforcement point**. In order, it checks:

1. **The token itself:** signature, issuer, audience, expiry and whether it or any token it came from was revoked.
2. **Ownership:** the order belongs to the user the token acts for. This is Capstone 1's rule, "identity is never a tool argument", enforced by the service: the model can type any order id, and Ana's token still can't touch Ben's order.
3. **Scope:** the token allows this action.
4. **Limits:** the amount is within the token's maximum, and a single-use token hasn't been used.

Whatever the outcome, `authorize` writes an audit record. Notice that the tool doesn't trust anything the model said about who the user is; it trusts only the signed token, which the harness holds.

## 26.5 Narrower tokens for sub-agents

When a lead agent hands work to a specialist (Chapter 21), the specialist shouldn't inherit everything the lead can do. **Attenuation** derives a narrower token:

A derived token can have fewer scopes, an earlier expiry and tighter limits, never more. It records the chain of tokens it came from, so revoking the lead's token also revokes every token derived from it. That's how delegation should work across any boundary: from lead to specialist, from your agent to a tool server and across organizations over A2A, where the remote agent should receive a token for its task, not your credentials.

## 26.6 Step-up for risky actions

The support agent's everyday token can read orders and start returns, but not refund. When it tries, the tool refuses with `NeedsApproval`, and the harness asks a person:

If the person approves, the harness mints a **step-up token**: one scope, one maximum amount (the one approved), a two-minute life, single use. The refund goes through with that token, and the token is worthless afterwards. Compare this with Chapter 9's approval gate: the approval is no longer only a check in the harness, it's a credential the tool itself verifies. Even a bug in the harness can't turn one approved refund into two, or into a bigger one.

Run `./course.sh python ch26_identity.py`: Ana asks for a refund on her order and on Ben's. You're asked to approve her refund; Ben's is refused by ownership before anyone is asked, because no approval should be able to override who owns the order.

## 26.7 Audit, revocation and the kill switch

Every call to `authorize` leaves a record: time, decision, reason, scope, audience, agent, user and token id. That's enough to answer the questions that follow an incident: what did this agent do yesterday, on whose behalf and was it allowed? Chapter 28 sends the same facts into traces.

Things go wrong, so you need three switches:

- **Revoke a token.** Its id goes on a list every service checks; tokens derived from it stop working too.
- **Disable an agent.** Every token it holds stops working at once, and no new ones can be issued. This is the kill switch for an agent that misbehaves.
- **Rotate keys.** Signing keys change on a schedule, and immediately if one might have leaked.

Short lifetimes are the quiet hero here. A token that lives for 15 minutes limits the damage of a leak even if nobody notices it.

## 26.8 In production

The code in this chapter shows the ideas; in production you use standard systems for them:

- **OAuth 2.x and your identity provider** issue and sign tokens. MCP's authorization specification builds on OAuth, so a remote MCP server receives a token meant for it (Chapter 30).
- **Token exchange** (OAuth token exchange, RFC 8693) turns a user's token into one that says "this agent, acting for this user", with narrower scopes. That's the standard form of this chapter's `mint` and `attenuate`.
- **Audience-bound tokens** (resource indicators) stop a token for one server being replayed at another.
- **A policy engine** can hold authorization rules as data, the way Chapter 22 held business rules.
- **Secrets managers** hold the few long-lived secrets that remain, and give them to the harness, never to the model.

Never write your own cryptography. Use a maintained library for tokens (this chapter uses PyJWT) and your identity provider for keys.

A refund needs a single-use step-up token issued after a person approves, and every decision lands in the audit log.
:::

## Architect's Takeaway

Least privilege applies harder for agents: privilege must match autonomy exactly.

## Common mistakes

- **Letting the agent use a person's credentials**, so it can do everything the person can, and the logs blame them.
- **One long-lived key for everything**, with no audience, no expiry and no scopes.
- **Passing the user's identity as a tool argument** that the model fills in.
- **Checking permissions in the harness only**, so the tool itself trusts any caller.
- **Sub-agents inheriting the lead's full token.**
- **Approvals that don't bind the amount**, so an approved $49 refund can become $490.
- **No way to revoke** a token or stop an agent quickly.
- **Audit logs without the user or the agent**, so nobody can say who did what.

## Summary

- Every action has a user, an agent and a service; record all three.
- Agents get their own identities and short-lived tokens, never a person's credentials.
- Tokens carry the agent, the user, an audience, scopes, limits, an expiry and an id; a registry caps what each agent may ever hold.
- The tool verifies the token, the resource's owner, the scope and the limits on every call, and logs the decision.
- Derived tokens can only narrow; revoking a token revokes everything derived from it.
- Risky actions need a step-up token: minted after a person approves, for one action, one amount, once.
- Keep revocation, an agent kill switch and key rotation ready; use OAuth, token exchange and your identity provider in production.

## Exercises

:::ex Concept | 26.1 | Whose permission?
For each action, name the user, the agent and the service, the scopes the token needs, and whether it needs a step-up: (a) a calendar agent books a meeting room for Priya; (b) a finance agent pays a supplier invoice of $12,000; (c) a coding agent opens a pull request in the team's repository; (d) a research sub-agent reads three internal wiki pages for its lead; (e) an HR agent reads an employee's salary history to answer the employee's own question.
**Done when:** Every action has all three identities, minimal scopes, and a step-up decision with a reason.
:::

:::ex Concept | 26.2 | Design the token
Design the token a travel agent should hold while booking one trip for one employee: every claim, its value, the audience, the scopes, the limits (think about amounts, dates and destinations), and the lifetime. Then write down what an attacker could do with a stolen copy.
**Done when:** Your token lets the agent book this trip and nothing else, and the damage from a stolen copy is limited to something you'd accept.
:::

:::ex Simple | 26.3 | Break the token
Mint a token for the support agent, then try to use it five wrong ways: change one character of it, wait for it to expire (use `ttl=1`), use it at `billing-api`, revoke it, and disable the agent. Then try to mint `refunds:create` for the analyst agent.
**Done when:** Each attempt fails with a different, clear reason, and you can find each failure in `AUDIT` or in the exception.
:::

:::ex Medium | 26.4 | Tokens for a team
Give the Chapter 21 team tokens: the lead gets `orders:read` and `refunds:create` for one user; the analyst gets an attenuated `orders:read` token with a 5-minute life; the checker gets `orders:read` too. Make `delegate` pass the attenuated token to the specialist's tools, and show that a specialist asking for more is refused.
**Done when:** A test shows each specialist's token has only its scopes and expires no later than the lead's, and revoking the lead's token stops the specialists' tokens too.
:::

:::ex Medium | 26.5 | An audit circuit breaker
Write a monitor that reads `AUDIT` and disables an agent automatically when it gets more than three denials within one minute, or any denial for acting on another user's resource. Report what it did and why.
**Hint:** Denials are cheap to cause, so decide what should trip the breaker and what should only raise an alert.
**Done when:** A test shows an agent disabled after a burst of denials, its next call refused, and a normal agent untouched.
:::

:::ex Complex | 26.6 | A token-checked API
Serve the order tools as a small HTTP API with Starlette that accepts `Authorization: Bearer <token>` and checks it with `authorize`, audience `orders-api`. Point the agent's `run_tool` at the API, with the token held by the harness. Show that a token minted for `billing-api` is refused, that an expired token is replaced by the harness without the model noticing, and that the model never sees a token.
**Hint:** Starlette's `TestClient` lets you call the API in-process, without opening a port.
**Done when:** A test covers all three, and the audit log shows every request with the agent and the user.
:::
